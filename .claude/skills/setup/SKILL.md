# /setup — 내 프로젝트로 시작하기

이 템플릿을 받은 후 **처음 한 번** 실행한다. 하는 일은 둘이다: 환경이 제대로 깔렸는지 확인하고, 이 환경이 어떻게 동작하는지 알려준다. **무엇을 만들지는 여기서 정하지 않는다.** 그 일은 소개가 끝난 뒤의 대화에서 한다.

## 전제
- Node·pnpm 버전, 루트·`web`·`mobile` 세 곳의 설치 순서, `git init`(ZIP 이면 설치 전에)과 커밋 게이트 설치가 실패했을 때의 처리는
  `docs/boilerplate/setup.md` 의 "준비물"·"1. 설치" 절이 정본이다. 설치가 안 돼 있으면 그 절을 읽고 그대로 안내한다.
  한 플랫폼만 남긴 프로젝트에서는 없는 폴더의 설치를 건너뛴다.
- 이 스킬은 파일을 지우거나 고치지 않는다. 이미 한 번 돌렸던 프로젝트라면 소개를 되풀이할 뿐이니,
  두 번째 이후에는 "이미 돌려 보셨으면 `/help` 가 더 짧습니다." 라고 한 줄 덧붙인다.

## 새 프로젝트 폴더로 시작하기 (선택)

원본을 그대로 쓰지 않고 복사하려는 사용자에게만 `pnpm bootstrap` 을 안내한다. `/setup` 이 대신 실행하지 않는다.
이 명령은 템플릿 원본에만 있다. bootstrap 으로 만든 프로젝트(루트에 `template.json` 이 있다)에는 없으니 안내하지 않는다.

명령·플래그·복사 범위·성공 뒤의 순서는 `docs/boilerplate/setup.md` 의 "새 프로젝트로 복사하기" 절이 정본이다. 그 절을 읽고 그대로 안내한다.

## 절차

### 1단계: 환영 & 환경 확인

다음을 출력한다:

```
👋 안녕하세요! 이 환경은 AI와 함께 웹 서비스를 만들기 위한 작업 공간입니다.

지금부터 두 가지를 할 거예요:
  1. 환경이 제대로 깔렸는지 확인 (30초)
  2. 이 환경이 뭔지 간단히 소개 (2분)
```

환경 확인:
```bash
pnpm run doctor          # 이 저장소의 읽기 전용 환경 점검
pnpm --silent run doctor --json # pnpm 실행 배너 없이 기계가 읽는 JSON
```

둘 중 필요한 출력 형식 하나로 실행한다. `pnpm doctor` 는 pnpm 자체 명령이므로 `run` 을 붙인다.
doctor 가 보는 것과 종료 코드는 `docs/boilerplate/setup.md` 의 "1. 설치" 절이 정본이다. 여기서는 결과를 이렇게 다룬다.

- 실패(`✗`, 종료 1)가 있으면 결과의 해결 명령(`→`)을 안내하고 멈춘다.
- 경고(`!`)는 멈추지 않고 한 줄로 알린다. 예: Node 24 는 범위 안이라 통과지만 `.nvmrc`(22)와 다르다.
- `HUSKY=0` 이면 훅 검사를 건너뛴다. 이 상태를 게이트가 켜진 것으로 소개하지 않는다.
- doctor 는 Supabase 설정·env 파일·실제 DB 를 보지 않는다. DB 없이도 웹·앱 시작 화면은 열린다.
  저장·로그인이 필요할 때 `.env.example` 과 `database` 스킬로 안내한다. doctor 통과는 `/verify` 통과를 대신하지 않는다.

선택 항목 — 로컬 DB(`pnpm db:start`)를 쓸 때만 필요하다:
```bash
supabase --version     # Supabase CLI 설치 확인
docker info >/dev/null # Docker Desktop 이 켜져 있는지 확인
```

이 둘은 실패해도 멈추지 않는다. "로컬 DB 는 선택입니다. 쓰려면 Docker Desktop 과 Supabase CLI 가 필요합니다." 라고만 알리고 넘어간다.

### 2단계: 이 환경 소개

사용자에게 다음을 **대화체로 자연스럽게** 설명한다 (목록을 덤프하지 않는다):

#### 핵심 개념 (1분)

> **이 환경은 "가드레일"입니다.**
>
> 당신이 "이런 거 만들고 싶어"라고 말하면, 저는 그냥 코드를 짜는 게 아니라:
> - **작게 나눠서** 구현하고
> - 매 단계마다 **자동으로 검증**하고
> - 배포 전에 **전문가 관점으로 점검**합니다.
>
> 이렇게 하면 "돌아가긴 하는데 엉망인 코드"가 아니라, **나중에도 고치고 키울 수 있는 코드**가 만들어집니다.

#### 기억할 커맨드 (1분)

> **이것만 기억하시면 됩니다:**
>
> - **`/verify`**: 서식·타입·린트·테스트·구조·토큰·색·빌드를 한 번에 검사합니다
> - **`/predeploy-review`**: 배포 전에 전문가 관점으로 점검합니다
> - **`pnpm run doctor`**: 설치 환경을 읽기만 하고 문제의 해결 명령을 알려줍니다
>
> 만들 것의 크기에 따라 두 갈래로 갑니다. 화면 하나·표 하나 같은 **작은 일**은 바로 만들고(요구가 모호하면
> **`/interview-quick`** 으로 짧게 정리), 여러 단계에 걸친 **큰 일**은
> `/interview` → `/spec` → 계획 → 단계별 구현 → 검증 순서로 진행합니다.
>
> 나머지는 전부 뒤에서 자동으로 돌아갑니다. 모르겠으면 언제든 **`/help`** 라고 하세요.

#### 자동으로 되는 것 (30초)

> **이런 건 신경 안 써도 됩니다:**
> - 코드 서식(들여쓰기·따옴표·줄 바꿈) → Prettier 가 정함. `pnpm format` 한 번이면 맞춰지고, 어긋나면 검증·커밋 게이트가 알려줌
> - 코드 규칙(재할당 없는 `let`·딥임포트·상대경로) → ESLint가 자동으로 잡아줌
> - 색·DB 타입 → 정본(`design/tokens.json`·마이그레이션)에서 생성되고, 어긋나면 커밋 게이트가 막아줌
> - 커밋 전 검증 → Husky가 자동으로 막아줌

#### DB (30초)

> **DB 는 나중에 붙여도 됩니다.** 지금은 없어도 화면이 뜹니다. 붙일 때는 둘 중 하나예요:
> - **로컬** — 계정 없이 내 컴퓨터에서. Docker Desktop 을 켜고 Supabase CLI 를 설치한 뒤 `pnpm db:start` 를 돌리면 웹·앱 환경변수까지 채워집니다.
> - **클라우드** — supabase.com 무료 프로젝트. 실제로 배포할 때 씁니다.

`pnpm db:start` 는 여기서 실행하지 않는다(환경변수 파일을 쓰는 명령이다). 사용자가 직접 돌리도록 알려만 준다.

배포는 아직 자동이 아니다. Vercel·EAS 연결은 `/setup` 다음에 사람이 `docs/boilerplate/first-deployment.md`(첫 배포 안내)를 따라 한다.
그러니 여기서 "push만 하면 올라간다"고 말하지 않는다. 템플릿 스모크(`pnpm smoke:template`)를 돌려 봤다고 추정하지 않는다.
실제 로그인 검증은 별도이며, 모바일 JS 번들 생성이 네이티브 컴파일·실기기·스토어 검증을 뜻하지 않는다.

### 3단계: 다음 걸음 안내

확인과 소개가 끝나면 **여기서 멈춘다.** 방향을 잡는 인터뷰를 직접 진행하지 않는다.

doctor 가 통과하면 있는 플랫폼의 `pnpm -C web dev`·`pnpm -C mobile start` 를 안내하고,
그다음 `/verify` 또는 `pnpm verify` 로 전체 검증하도록 연결한다.

마지막으로 만들 것을 묻는 말로 넘긴다:

> 이제 만들고 싶은 것을 그냥 말씀해 주세요. "독서 기록을 남기는 웹 페이지가 필요해요"
> 처럼 한 문장이면 충분합니다. 거기서부터 같이 좁혀 나가겠습니다.
> 여러 단계에 걸친 큰 일이면 인터뷰로 정리한 스펙을 `polaris/specs/planned/` 에 남기고, 그것을 기준으로 만듭니다.

미션·스펙의 자리는 AGENTS.md 의 "미션 & 스펙" 절이 정본이다. Polaris 플러그인은 같은 자리를 쓰는 선택 도구라서
설치를 권하거나 설치 여부를 확인하지 않는다.

## 주의사항

- `/setup` 은 **처음 한 번**을 위한 것이다. 다시 돌려도 지우거나 고치는 것이 없으니 해는 없지만,
  두 번째 이후에는 `/help` 를 권한다.
- 환경 확인에서 문제가 있으면 소개로 넘어가지 않고, 문제 해결부터 안내한다. 선택 항목(Supabase CLI·Docker)은 예외다.
- 소개는 **짧고 자연스럽게**. 매뉴얼을 읽어주는 느낌이 아니라 "같이 만들어봐요" 느낌으로.
- 코드 견본(로그인·조직·작업·활동)은 `architecture` 스킬의 "서버 코드라면" 절에 있다. 에이전트는 가장 가까운 코드를 따라 하므로
  새 기능은 이것을 기준으로 짓는다. 견본을 지우면 그 파일 이름 규약을 다른 첫 기능이 대신 보여 줘야 한다.

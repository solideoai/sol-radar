# 스펙: 추천 분석 팝업·상세화

- 최종 갱신: 2026-11-03
- 앞선 스펙: [[2026-10-29-recommendation-insight|추천 분석 1단계]](운영 반영 완료)
- 출처: [사용자 결정] 사용자가 정함, [제안 후 승인] 제안을 사용자가 고름. 모두 2026-11-03 문답.

## 1. 목표

공고 상세의 추천 분석을 팝업으로 옮기고, 설명을 지금의 약 3배 길이로 늘린다 [사용자 결정]. 사용자는 추천 분석을 이 서비스에서 가장 중요한 화면으로 본다 [사용자 결정]. 길이는 모델 출력 칸을 늘려서 얻는다(판단 이유 확대, 새 칸 3개) [제안 후 승인].

## 2. 비목표

- 이 기능 밖의 화면은 바꾸지 않는다. 화면 동결(ADR-073)에서 이 기능만 빼서 촬영 전(늦어도 2026-11-04)에 운영에 올린다(ADR-078) [사용자 결정].
- 판정(점수·권고)은 바꾸지 않는다. 금지어·판정 이름·참여 권유 표현을 막는 규칙도 바꾸지 않는다. 예외는 진행 표시의 `%` 하나다(4.6) [제안 후 승인].
- 진행률을 계산하려고 서버·DB에 진행 단계를 기록하지 않는다 [제안 후 승인].
- 상세 화면에 이미 있는 자격 체크리스트·점수 요소·Bosun 구역을 팝업에 표로 다시 넣지 않는다. 늘어나는 분량은 모델 해설에서 나온다 [제안 후 승인].

## 4. 인터페이스 계약

### 4.1 팝업 섹션 [제안 후 승인]

| 순서 | 섹션 | 쓰는 쪽 | 분량 |
|---|---|---|---|
| 1 | 판정·점수·고지 문장(머리) | 규칙 값 | — |
| 2 | 판단 이유 | 모델 | 4~6문장, 800자 이내 |
| 3 | 점수 요소별 해설: 요소마다 점수, 해설 1~2문장, 근거 번호 | 모델 | 요소마다 |
| 4 | 자격 요건 해설: 미충족·확인 필요 항목마다 걸린 것과 확인할 것 | 모델 | 해당 항목마다 |
| 5 | 강점·보완할 점 | 모델 | 각 6개까지 |
| 6 | 참여 전 확인할 것(서류·질의·인력 배치) | 모델 | 3~5개 |
| 7 | 사업 기간 인력 가용 | 규칙 값 | — |
| 8 | 근거 원문 전체 목록(공고 인용 B, 회사 자료 C) | 규칙 값 | — |

- 6번은 "참여하려면 …를 확인해야 합니다" 형태로 쓴다.
- 근거 칩을 누르면 인용이 펼쳐지는 지금 동작을 유지한다.
- 팝업은 `web/components/ui/dialog.tsx`로 만든다.

### 4.2 출력 계약: gateway → worker → `recommendation_insights.payload` [제안 후 승인]

- 프롬프트를 `insight/v0.2`로 올린다(새 프롬프트·스키마 파일). promptHash가 바뀐다.
- 기존 칸: 판단 이유 상한은 400자에서 800자로, 강점·보완할 점은 각 4개에서 6개로 늘린다.
- 새 칸 3개(요소별 해설, 자격 해설, 확인할 것)는 없어도 되는 항목이다. 새 칸이 없는 옛 결과도 같은 스키마로 읽힌다.
- 모델 출력 상한 `INSIGHT_MAX_TOKENS`를 1024에서 약 3000으로 올린다. 구현 값은 4096이다(추출과 같은 값, 사전 리뷰로 3072에서 올림).
- 상한을 함께 바꾸는 곳: `services/ai/src/sol_ai/contracts.py`(`InsightBody`), `web/server/analysis/gateway.model.ts`(`insightResponseSchema`), `web/server/insight/insight.model.ts`(`insightPayloadSchema`), `services/ai/src/sol_ai/adapters/qwen.py`(`INSIGHT_MAX_TOKENS`), mock 어댑터.

### 4.3 검사와 대체 [제안 후 승인]

- 검사 항목(JSON 모양, 근거 번호, 금지어, 판정 표현, 입력에 없는 숫자)은 지금과 같다.
- 세부 칸(요소 해설, 자격 해설, 강점, 보완할 점, 확인할 것)이 금지어·숫자·판정 표현에 걸리면 걸린 항목만 뺀다.
- 판단 이유가 걸리거나 JSON 모양이 틀리면 전체를 템플릿으로 대체한다. 템플릿은 새 칸을 규칙 값으로 채운다(3절 7번).
- 세부 항목에 없는 근거 번호가 나오면 그 항목만 뺀다. 숨은 문자는 어디서 나오든 전체를 템플릿으로 대체한다 [제안 후 승인].
- 이 대체 정책 변경은 구현 때 새 ADR로 기록한다.

### 4.4 재요청과 DB [제안 후 승인]

- 새 마이그레이션 1개로 제약 `recommendation_insights_pending_or_model_once`(`20261029000200`)를 "같은 run·같은 프롬프트 버전에서 PENDING과 DONE·MODEL을 합쳐 하나"로 바꾼다. 모델 호출 반복을 막는 보안 의도는 유지한다. (이전에 승인한 "마이그레이션 없음"은 이 제약 때문에 철회했다.)
- 서버 중복 판정(`web/server/insight/insight.service.ts`)도 같은 기준을 쓴다. 같은 버전의 DONE·MODEL이면 있던 행을 돌려주고, 옛 버전이면 새 행을 만든다.

### 4.5 배포 순서 [제안 후 승인]

- worker·web을 먼저 올리고 gateway를 나중에 올린다. 반대 순서면 worker가 400자를 넘는 판단 이유를 `GATEWAY_INVALID`로 거절한다.

### 4.6 진행 표시

- 추천 분석이 걸리는 동안 로딩 스피너와 진행률을 퍼센트로 100%까지 보인다 [사용자 결정].
- [추천 분석]을 누른 직후부터 0%로 보인다 [제안 후 승인].
- 진행률은 경과 시간으로 어림한 값이다. 지금 상태가 PENDING과 완료뿐이라 실제 진행을 알 수 없어서다. 서버·DB는 바꾸지 않는다 [제안 후 승인]. 예상 시간 10초에 90%까지 고르게 오르고 3분 대기 상한(`INSIGHT_POLL_LIMIT_MS`)까지 99%를 향해 천천히 오르며, 완료되면 그 값에서 100%까지 이어 채운다 [사용자 결정 2026-11-03 "균일한 속도로 가게", 운영 회사 Qwen 생성 6.4초·8.9초(2026-11-03 v0.2 2건)].
- 경과는 요청 시각(`createdAt`)부터 센다. POST 응답 전에는 누른 시각이다. 새로고침하거나 다른 사람이 요청한 PENDING을 열어도 숫자가 뒤로 가지 않는다 [제안 후 승인]. 이 화면에서 누른 새 요청은 끝까지 누른 시각을 쓴다(기기·서버 시계 차 방지, 구현 보완).
- 완료 전에는 99%에서 멈추고, DONE이 오면 100%를 600ms 보인 뒤 내용으로 바꾼다. FAILED는 100%를 거치지 않는다 [제안 후 승인].
- 3분(`INSIGHT_POLL_LIMIT_MS`)을 넘기면 지금처럼 늦음 안내와 [다시 확인]을 보인다 [제안 후 승인].
- `%`는 이 진행 표시에만 쓴다. 결과 글·점수·모델 출력의 `%` 금지는 그대로다. 구현 때 새 ADR로 ADR-061 금지어 조항에 이 예외를 적는다. 브라우저 시험은 진행 상태에서만 `%`를 허용하고, 결과 상태 검사는 그대로 둔다 [제안 후 승인].

### 4.7 화면 세부 [제안 후 승인]

- 배치·상태·문구는 [[2026-11-03-recommendation-insight-detail-design|디자인 스펙]]을 따른다.
- 구역 버튼은 결과가 없으면 [추천 분석], 있으면 [추천 분석 보기]다.
- 767px 이하 전체 화면 팝업의 머리에 공고명 한 줄(말줄임)을 둔다.
- 움직임 줄이기에서는 회전 아이콘도 멈춘다. `docs/06-UI-UX.md`의 움직임 문구를 이에 맞춘다.
- 공용 `web/components/ui/dialog.tsx`의 닫기 이름과 뒷막 흐림은 이번에 바꾸지 않는다.
- 옛 형식은 저장된 프롬프트 버전으로 판별한다. 서버 중복 판단과 같은 기준이다.

## 5. 엣지 케이스와 실패 시나리오

| 상황 | 처리 |
|---|---|
| 옛 형식 결과 | 있는 칸(판단 이유, 강점, 보완할 점)과 규칙 값 섹션(1·8)을 그린다. 섹션 7의 인력 가용 값은 새 형식 payload에만 있어 그리지 않는다. 요청 가능 역할에게는 "새 형식으로 다시 분석" 버튼을 보인다 [제안 후 승인] |
| 새 형식 재요청이 실패 | 옛 결과를 계속 보이고, 그 위에 실패 안내와 [다시 요청]을 띄운다 [제안 후 승인] |
| 판단 이유 검사 실패, JSON 모양 오류(출력이 토큰 상한에서 잘린 경우 포함) | 전체 템플릿. 새 칸은 규칙 값으로 채운다 [제안 후 승인] |
| 세부 칸 항목 검사 실패 | 그 항목만 뺀다 [제안 후 승인] |
| 인젝션 의심 입력 | 지금처럼 모델을 부르지 않고 템플릿으로 답한다. 새 칸은 규칙 값으로 채운다 [제안 후 승인] |
| 같은 run에 두 사람이 동시에 다시 요청 | 같은 버전 PENDING은 하나만 생기고, 나중 요청은 있던 행을 받는다 [제안 후 승인] |
| 생성이 3분을 넘음 | 진행률은 99%에서 멈춰 있고, 지금처럼 늦음 안내와 [다시 확인]을 보인다. 상한을 늘릴지는 미결정 |

## 미결정 사항

필드 이름·상한, 버전 열, 마이그레이션 위치는 구현 계획(`docs/plans/2026-11-03-recommendation-insight-detail.md`)에서, 팝업 배치 세부는 디자인 스펙에서 정했다. 근거 번호·숨은 문자 처리, 재요청 실패 때 옛 결과, 진행률 기준은 2026-11-03 사용자가 정했다(4.3·4.6·4.7·5절).

1. 대기 상한(`INSIGHT_POLL_LIMIT_MS`, 3분)을 줄일지. 진행률 기준은 2026-11-03 정했다(운영 회사 Qwen 생성 6.4초·8.9초(2026-11-03 v0.2 2건), 위 4.6). 상한은 그대로 둔다.
2. 한 run 안에서 자격 이름(`label`)이 겹칠 수 있는지: 구현 첫 단계에서 확인한다. 겹치면 자격 해설 짝짓기를 다시 정한다.

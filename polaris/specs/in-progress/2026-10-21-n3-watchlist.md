# 스펙: N3 관심 공고(`/watchlist`·★ 토글·마감 알림)

- 최종 갱신: 2026-10-21
- 배정: sol-radar-12 → sol-radar-fa. 브랜치 `feat/n3-watchlist`(base main `ca0e5f7`). 마이그레이션 대역 `20261022000100`~.
- 승인: 설계는 2026-10-16 사용자 승인([사이드바 정보 구조 설계](../../../docs/plans/2026-10-16-sidebar-ia-design.md), ADR-021). 착수는 ADR-042(2026-10-21 사용자 결정, P1 다섯 화면 병행).
- 출처 표기: [설계] = 사이드바 설계 문서(쪽수는 절 번호). [정본] = 04·05·06·11·13 에 이미 적힌 줄. [12 판단] = 마스터 세션이 정함(사용자 위임 "결정이 필요한 것은 추천안대로"). [작업자 몫] = 구현자가 정한다.

## 1. 목표

영업·분석 담당이 눈여겨보는 공고를 ★로 표시해 두고, `/watchlist` 에서 그것만 모아 본다. 표시한 공고의 마감이 다가오면(D-3·D-1) 인앱 알림을 받는다. 남이 무엇을 표시했는지는 보이지 않고, 공고마다 "관심 N명"만 조직에 보인다. [설계 §2.2·§3.2 P1-1, D6·D7]

## 2. 비목표

- 공고 복제·별도 필터·별도 표를 만들지 않는다. `/watchlist` 는 `/bids` 의 `BidTable`·`BidFilters` 를 그대로 쓴다. [설계 §2.2]
- 남의 관심 목록, ADMIN "전체 관리"는 만들지 않는다. ADMIN 도 본인 것만. [설계 D6]
- 개인 알림 수신 설정, 카카오·메일 채널의 마감 알림은 하지 않는다. 마감 알림은 인앱만. [정본 13 표, 설계 §3.3]
- 관심 공고 수를 대시보드 카드로 만들지 않는다(카드 5개는 N9·N6 몫). [설계 §2.3]
- `bid_list_items` 뷰·`ingest_save_revision`·분석 job·기존 목록 응답 항목(`BidListItem`) 계약을 바꾸지 않는다. 덧붙이기만 한다. [ADR-042 조건 ②]
- 모바일·결제·승률 표시는 하지 않는다(ADR-007).

## 3. 저장 [설계 §2.5, 정본 04]

- 새 표 `bid_watches`: `org_id`, `user_id`, `bid_id`, `created_at`. PK(`org_id`,`user_id`,`bid_id`). (`org_id`,`user_id`) → `memberships` 복합 FK(멤버십이 지워지면 함께 지운다), `bid_id` → `bid_notices` FK(on delete cascade). 인덱스 `bid_watches(org_id, bid_id)`(관심 인원 수 집계).
- RLS: 본인 행만 읽기·넣기·지우기(`user_id = auth.uid()` 이고 `org_id in (select public.my_org_ids())`). update 권한은 주지 않는다. 다른 조직 0행.
- 관심 인원 수는 집계 함수로만 연다(D6). `bid_watch_count(p_bid_id uuid) returns integer`, security definer, 호출자의 조직 안에서만 센다. 누가 표시했는지는 돌려주지 않는다. [작업자 몫: 함수 이름·모양]
- 표는 만들자마자 잠그고 정책 시험을 `scripts/database.test.mjs` 에 더한다. `pnpm db:types` 를 같은 커밋에 넣는다. 클라우드 적용(`pnpm db:push`)은 사용자 확인 뒤(ADR-042 조건 ⑤).

## 4. API (Route Handler `/api/v1`) [정본 05 §2·§3]

| 메서드 | 경로 | 권한 | 내용 |
|---|---|---|---|
| PUT | `/bids/:id/watch` | 업무 조직 구성원 전원(본인) | 관심 등록. 멱등: 이미 있으면 그대로 200. 응답 `{ bidId, watched: true, watcherCount }` |
| DELETE | `/bids/:id/watch` | 같다 | 관심 해제. 멱등: 없어도 200. 응답 `{ bidId, watched: false, watcherCount }` |
| GET | `/bids?watched=me` | 정본 그대로 | 기존 목록에 쿼리 하나. 본인 관심 공고만. 다른 필터·정렬·커서와 함께 쓴다 |

- 경로 id 가 UUID 가 아니거나 공고가 없으면 404(`pathNotFound("bid")`). 조직은 서버가 정한다(M17). 본문은 받지 않는다.
- 응답 봉투·오류 형식은 기존 업무 라우트(`businessRoute`)와 같다. CSRF·가입 완료 확인도 같은 입구가 한다.
- `watched` 의 허용 값은 `me` 하나. 다른 값은 400 `VALIDATION_ERROR`. [정본 05 §3]
- 목록 항목에 관심 여부 필드를 더하지 않는다(계약 불변). 화면은 본인 관심 공고 id 목록을 서버에서 따로 읽어 ★ 상태를 그린다. [12 판단 Q2 ①, 아래 §8]

## 5. 화면 [설계 §2.1·§2.2, 정본 06 §4.1·§5]

- 사이드바 "관심 공고"(`/watchlist`, `star`)를 "준비 중"에서 링크로 바꾼다. 전원에게 보인다.
- `/watchlist`: 제목 "관심 공고". `/bids` 와 같은 필터 막대·표·더 보기. 조건은 `watched=me` 가 고정으로 붙는다(필터 막대에 보이지 않는다). 기본 조건(진행 중 공고·출처)은 `/bids` 와 같다. 빈 상태: 관심 공고가 하나도 없으면 "아직 관심 공고가 없습니다" + [입찰 공고 보기](`/bids`). 조건 때문에 0건이면 `/bids` 와 같은 "조건에 맞는 공고 없음".
- `/bids` 표: 행마다 ★ 토글(누르면 등록·해제, 행 열기와 겹치지 않는다). `/watchlist` 표에서도 같은 토글이고, 해제해도 그 자리에서 행을 바로 지우지 않는다(되돌릴 수 있게). [작업자 몫: 다음 새로 고침 때 빠진다]
- `/bids/[id]` 머리: ★ 토글과 "관심 N명"(0명이면 숨김 또는 "관심 0명", web-designer 스펙에서 정한다).
- 토글은 낙관적으로 바꾸고 실패하면 되돌린 뒤 토스트로 알린다. 읽기 전용 역할(VIEWER)도 쓸 수 있다. [설계 §2.4 "관심 공고 본인"]
- 접근성: ★ 는 `aria-pressed` 가 있는 버튼, 이름은 상태와 상관없이 "관심 공고"로 고정한다(§8 fa 판단). 아이콘 16px(`lucide-react` `StarIcon`).
- 화면 명세는 구현 전에 web-designer 스펙으로 받는다. 확인은 1440·1280 두 폭.

## 6. 마감 알림 [설계 D7·§2.5, 정본 13]

- 종류 `DEADLINE_APPROACHING`, 채널 인앱. 마감 D-3·D-1 의 09:00 KST 부터 그날 안에 한 번.
- 수신자: 그 공고의 담당자(조직마다 최신 `bid_reviews` 행의 `assignee_id`)와 관심 등록자의 합집합. 사용자 ID 로 중복을 없앤다. 활동 계정(`profiles.status = 'active'`)이고 그 조직 구성원인 사람만.
- 멱등 키 `bidId:userId:DEADLINE_APPROACHING:D-n`(`notifications.idempotency_key` unique). 담당자이면서 관심 등록자인 사람도 1건. 다시 돌거나 동시에 돌아도 1건.
- 대상 공고: `deadline_at` 이 있고 아직 지나지 않았고, 상태가 `OPEN`·`AMENDED`. 취소·마감 공고는 보내지 않는다. 그날(KST)이 D-n 이 아니면 보내지 않는다(놓친 D-3 을 D-2 에 늦게 보내지 않는다).
- 만드는 곳: worker 주기 작업이 DB 함수를 부른다(service role). 함수가 대상·수신자·키를 계산하고 `notifications` 에 바로 넣는다(`on conflict do nothing`). outbox 를 거치지 않는다. [12 판단 Q1 ①, 아래 §8]
- 문구: 제목은 공고명, 내용 "마감 3일 전입니다."·"마감 하루 전입니다.", 링크 `/bids/<id>`. [작업자 몫]
- 정본 13:22·:48 대로 담당자 + 관심 등록자 합집합이다. 담당자는 지금 데이터의 검토 배정 담당자(`bid_reviews.assignee_id`)로 넣는다. [12 확인 2026-10-21]
- 시험에 넣는다: 5분 주기에서 09:00 KST 이후 첫 회차에만 1건, 같은 날 다시 돌아도 키로 막힘, 09:00 전 회차는 0건. [12 지시 2026-10-21]
- 순수 규칙(어느 날이 D-n 인지, KST 09:00 경계)은 `web/server/notifications/deadline.*` 에 두고 시험한다(정본 11 FX-14 행의 `deadline.test.ts`).

## 7. 완료의 정의 [설계 §3.2 P1-1, 정본 11 NAV-P1-01]

1. DB 정책 시험: 본인 행만 읽기·쓰기, 다른 조직 0행, 남의 행 넣기·지우기 거부, 비로그인 거부, 관심 인원 수 함수가 조직 안 수만 내고 다른 조직 공고·사람을 드러내지 않음, 마감 알림 함수의 수신자 합집합·중복 0·D-n 경계·취소 공고 제외·두 번 돌려도 1건.
2. 단위 시험: 쿼리 `watched` 파싱, PUT·DELETE 멱등(두 번 불러도 같은 결과), 404·400 계약, 마감 규칙(KST 경계·D-3·D-1·그날만).
3. 브라우저 시험: ★ 토글(낙관적 반영·실패 되돌림·`aria-pressed`), `/watchlist` 빈 상태, 1440·1280 넘침 없음.
4. 실앱(격리 Supabase): ★ 등록 → `/watchlist` 에 보임 → 해제, 상세 "관심 N명", 1440·1280 스크린샷 `docs/evidence/`.
5. `pnpm verify` 통과(verify-slot.sh). 3e 게이트 병합. freeze(10-24 22:00) 전 green 이 아니면 데모에서 빼고 사이드바 "준비 중" 유지.
6. 정본 반영은 병합 뒤 45 와 절 목록을 합의해서(04 §3.8·05 §2·§3·06 §5.12·11 NAV-P1-01·13 마감 행·PROGRESS).

## 8. 12 판단(2026-10-21, 사용자 위임)

- **Q1 마감 알림 생산자 → ①**: worker 주기 작업(기본 5분)이 DB 함수 하나를 불러 `notifications` 에 바로 넣는다. 키가 unique 라 멱등이다. notify-outbox 와 같은 안전 규칙을 지킨다: 함수가 `org_id`·`user_id` 를 직접 넣고, 수신자가 그 조직 구성원인지와 `profiles.status = 'active'` 인지 확인한다. 채널은 `IN_APP` 만이다. 카카오·메일 마감 알림은 범위 밖이다(ADR-041 비목표). 13 의 "outbox 두 단계"와 다른 길이라, 45 에 보낼 절 목록에 "마감 알림은 직접 삽입 + 키 멱등"을 넣는다. - **Q2 목록의 ★ 상태 → ①**: 목록 응답(`BidListItem`)은 그대로 두고 화면이 본인 관심 id 목록을 서버에서 따로 읽는다. 05 계약은 그대로다. [12 판단]
- **Q3 `/watchlist` 기본 조건 → ①**: `/bids` 와 같다(진행 중만). 마감·취소된 관심 공고는 상태 필터로 본다. [12 판단]

## 9. 엣지 케이스

- 같은 공고를 두 창에서 동시에 ★: PK 충돌은 `on conflict do nothing` 으로 200.
- 공고가 취소·마감돼도 관심 행은 남는다. 알림만 멈춘다.
- 구성원이 조직에서 빠지면 그 사람의 관심 행은 복합 FK 로 함께 지워진다.
- 담당자가 없는 공고: 관심 등록자에게만 보낸다. 둘 다 없으면 보내지 않는다.
- 시각 없는 마감(07: KST 18:00 으로 저장)도 같은 규칙. D-n 은 KST 날짜로 센다.
- worker 가 09:00 전후로 멈춰 있다가 그날 안에 다시 뜨면 그때 보낸다. 다음 날까지 못 뜨면 그 D-n 은 보내지 않는다.

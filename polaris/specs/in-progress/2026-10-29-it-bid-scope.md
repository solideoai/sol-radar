# IT 공고만 보이기 — 공식 분류 기준 숨김·분야 키워드 필터·추천순 정렬·IT 공고 1회 일괄 분석

사용자 요청(2026-10-29): "지금 공고 가져온 거 보니까 우리 회사랑 맞지 않아. 우리 회사는 정부24, 소상공인24, 식약처, 국방부, 세움터 등 공공SI 프로젝트 위주와 이제는 AI와 AX에 관한 프로젝트에 관심이 많아져서 그런 공고 위주로 가져오고 싶어."

이어진 답(brainstorming 문답, 원문):

- "AI와 AX 관련된 공고야. 왜냐하면 올해 AI 예산이 9.9조라고 하던데"
- "맞아. IT 공고 아닌 것들은 다 제외시켜. 아예 안 보이지 않길 바라." → "아예 안 보이길 바란다"로 읽었다(앞 문장 "다 제외시켜"와 맞춤). 사용자가 정정하지 않았다.
- "1. IT 분류만 남겨. 2. IT 공고만 남겨. 3. 행사랑 교육 전시는 빼고 연구만 남겨"
- "가장 먼저는 일단 키워드로 분류할 수 있게 해서 필터링해서 보게 했으면 좋겠어. 지금 그 기능도 없으니까 새로 추가하고 가장 먼저는 추천 공고순으로 위에서부터 나오는 거지. SOL SCORE가 높은 순으로"
- "공고가 들어올 때마다 자동 분석은 하지말고, 지금 있는 공고들만 아까 IT 관련 공고들만 추려서 분석하자. 그리고 키워드 필터는 그렇게 맞으니까 구현 계획 세워봐"

## 1. 왜 하는가

- 솔리데오는 공공 SI(정부24·소상공인24·식약처·국방부·세움터 같은 중앙부처 대국민 시스템)가 본업이고, 정부 AI 예산이 커지면서 AI·AX 사업을 다음 먹거리로 본다.
- 지금 운영 D1 목록은 IT가 아닌 공고로 덮여 있다. 2026-10-29 운영 DB 실측(마감 전 실공고 2,016건): 나라장터 1,766 · 한전 202 · LH 48 · K-water 0. 관련성 규칙 결과는 RELEVANT 76 · CANDIDATE 245 · 나머지 1,695 는 UNCLASSIFIED. 무작위 표본의 대부분이 건설폐기물 처리·제설장비 임차·측량·철탑 공사였다.
- 반대로 IT 공고는 이미 들어와 있다. 나라장터 공식 분류 기준 IT 376건, 그 안의 AI·AX 37건, 분류 밖 AI 연구용역 11건. 수집이 아니라 **보여 주는 방식**이 문제다.
- 분석된 실공고는 마감 전 3건뿐이라 "추천순"이 의미가 없다. 분석은 지금 사람이 [분석]을 누를 때만 돈다.

성공한 모습: 영업 담당이 `/bids` 를 열면 IT 공고만 보이고, 맨 위에 SOL Score 가 높은 공고가 온다. 상단 키워드 칩(AI·AX, SI·SW 등)으로 바로 걸러 볼 수 있다. 대시보드·달력·시장 화면의 숫자도 IT 공고만 센다.

## 3. 목표 · 안 할 것 · 실패로 볼 것

목표

1. IT 범위 판정(아래 §4)을 한 곳에서 정하고, 공고 목록·대시보드 집계·달력·시장·공백(gaps) 화면이 모두 같은 판정을 쓴다.
2. `/bids` 상단에 분야 키워드 칩을 항상 보이게 둔다(지금은 "분야" 다중 선택이 상세 조건 안에 숨어 있다, `web/components/work/opportunities-filters.tsx`).
3. `/bids` 기본 정렬을 추천순으로 바꾼다. 다른 정렬(최신·마감 임박·예산)은 그대로 고를 수 있다.
4. 일괄 분석 CLI 를 한 번 돌려 IT 범위의 마감 전 실공고를 분석한다.

안 할 것

- 수집 단계에서 공고를 버리지 않는다. 지금처럼 모든 공고를 저장하고 화면에서만 숨긴다(ADR-047 의 보존 원칙 유지, 기준이 틀리면 되살릴 수 있어야 한다).
- 새 공고 자동 분석, 정기 일괄 분석을 만들지 않는다.
- 사용자가 직접 키워드를 추가·편집하는 기능은 만들지 않는다(칩은 고정 8개).
- SOL Score 계산식·가중치·임계값(`sol-v0.1.0`)을 바꾸지 않는다. 관련성 점수를 SOL Score 에 섞지 않는다.
- 데모 공고(FX, `is_demo`)를 재분석하지 않는다. FX-01 은 어떤 경우에도, FX-02 는 촬영 전에 재분석하지 않는다(ADR-059).

실패로 볼 것

- 숨김 기준이 화면마다 달라서 목록에는 없는데 대시보드 숫자나 달력에는 IT가 아닌 공고가 남는 것. 예외는 사람이 직접 담은 관심 공고와 진행 중 프로젝트뿐이다(§5.2).
- 데모 경로(`?origin=demo`)에서 FX 공고가 사라져 발표 촬영이 깨지는 것.
- 일괄 분석이 회사 ingest Worker·예약 작업(아래 §7)을 멈추거나 나라장터 보조 조회 한도를 넘기는 것.
- 금지 문구(승률·확률·가능성·수주 금액·점유율·경쟁사·%)가 칩·정렬 이름·빈 상태 문구에 들어가는 것.

## 4. IT 범위 판정 규칙

판정은 공고의 최신 revision 하나로 한다. 결과는 "IT 범위 안 / 밖" 두 값이고, 밖이면 모든 목록·집계에서 뺀다.

| 출처 | IT 범위 안 |
|---|---|
| 나라장터(`g2b-bid-notice`) | (가) 공공조달분류명이 IT 분류다: `정보시스템`, `소프트웨어`, `데이터`, `정보인프라`, `클라우드`, `공간정보DB`, `정보통신`, `네트워크`, `전산`, `정보화` 중 하나를 포함. **또는** (나) 제목에 AI·AX 단어가 있고 공공조달분류명에 `연구조사` 가 들어 있다 |
| 한전·LH·K-water 등 공식 IT 분류가 없는 출처 | 관련성 규칙(`relevance-v0.1`) 결과가 RELEVANT 또는 CANDIDATE |
| 데모(`fixture`, `is_demo = true`) | 항상 안. 데모 경로의 촬영 화면을 그대로 둔다 |
| 지원사업(`program_notices`, 기업마당·부처 공고) | 제목(본문이 있으면 본문도)에 관련성 규칙 `relevance-v0.1` 의 분야 단어(AI_AX·SI_SW·CLOUD·DATA·SECURITY·DIGITAL_TWIN)가 하나라도 있다. 2026-10-29 실측 104건 중 약 22건. 단어 규칙만 쓰므로 잘못 빠지거나 남는 공고가 있을 수 있다(사용자에게 알림) |

- (가) 목록은 2026-10-29 실측 분류명에서 왔다: 정보시스템유지관리서비스 227, 정보시스템개발서비스 44, 소프트웨어유지및지원서비스 25, 패키지소프트웨어개발및도입서비스 21, 데이터서비스, 정보인프라구축서비스, 클라우드서비스, 공간정보DB구축서비스 등. 클라우드·공간정보 DB 를 넣은 것은 설계자(Claude) 판단이다.
- (나)의 AI·AX 단어는 관련성 규칙 `AI_AX` 와 같은 단어 경계 규칙을 쓴다(`AI`·`AX`·`LLM`·`RAG`·인공지능·머신러닝·딥러닝, 생성형·챗봇·초거대 추가). "지능형"만으로는 AI로 보지 않는다(실측 오탐: 지능형교통시스템 유지관리).
- 행사·교육·전시 분류(`행사기획`, `교육서비스`, `전시`, `여행`, `동영상제작` 등)는 (나)에 해당하지 않으므로 자연히 빠진다.
- 공공조달분류명이 비어 있는 나라장터 공고(예: 사전규격·발주계획 단계)는 공식 분류가 없는 출처처럼 관련성 규칙으로 판정한다. 설계자 판단.
- 알려진 손실(사용자에게 알림, 2026-10-29): 기관이 분류를 잘못 붙인 IT 공고 일부가 빠진다. 실측 예: "2027년도 정보시스템 통합 유지보수 용역"(기타기술용역), "부동산거래 전자계약시스템 공인서비스"(기타사업지원서비스). 공고는 저장되어 있으므로 규칙 버전을 올려 되살릴 수 있다.
- 기대 수치(2026-10-29 실측, 마감 전): 나라장터 376 + 11, 한전 6, LH 0 → 약 393건.
- 규칙에는 버전 이름을 붙인다(예 `it-scope-v1`). 판정 근거(어느 분류명·어느 단어)를 남겨 나중에 "왜 숨겨졌나"를 확인할 수 있게 한다.

## 5. 화면

### 5.1 `/bids` 공고 목록

- 맨 위 줄에 분야 키워드 칩 8개를 항상 보인다: **AI·AX · SI·SW · 클라우드 · 데이터 · 보안 · 디지털트윈·BIM · 유지관리 · ISP·ISMP**.
  - 여러 개를 고르면 "하나라도 해당"(OR)이다. 아무것도 고르지 않으면 IT 공고 전체다. 설계자 판단.
  - 칩 → 데이터: AI·AX=`AI_AX`, SI·SW=`SI_SW`, 클라우드=`CLOUD`, 데이터=`DATA`, 보안=`SECURITY`, 디지털트윈·BIM=`DIGITAL_TWIN`(태그 `BIM`·`smartcity` 포함), 유지관리=태그 `maintenance`, ISP·ISMP=태그 `ISP`·`ISMP`.
  - 공식 분류로 IT 범위에 들어왔지만 관련성 규칙 분류가 없는 공고(실측 115건)는 SI·SW 칩에 잡힌다. 공식 분류명이 `유지관리`를 포함하면 유지관리 칩에도 잡힌다. 설계자 판단.
  - 칩 선택은 주소 쿼리(`category`, 태그용 새 파라미터)에 남는다. 지금 목록이 쓰는 "필터 값은 주소 쿼리가 정본" 원칙을 따른다.
- 기존 "공공 SI·AI 우선" 스위치는 **"AI·SI 우선"으로 바꿔 남기고 기본 ON** 이다(사용자 2026-10-29: "IT 공고만 보이는데 그 중에서도 AI를 가장 최우선, 그 다음 SI 공고 순으로 잡자"). 켜져 있으면 IT 공고를 세 묶음으로 나눠 이 순서로 보인다.
  1. AI·AX 공고(분야 `AI_AX`). AI·AX 와 SI·SW 를 함께 가진 공고도 여기다.
  2. SI 공고(분야 `SI_SW`, 공식 분류로만 IT 범위에 들어온 공고 포함 — 아래 칩 규칙과 같다).
  3. 나머지 IT 공고(클라우드·데이터·보안·디지털트윈만 있는 공고 등).
  - 묶음 안의 순서는 아래 "추천순"이다. 즉 묶음이 먼저, 점수가 다음이다(사용자 문장의 "최우선"을 이렇게 읽었다).
  - 끄면 IT 공고 전체를 묶음 없이 추천순으로 보인다.
  - 켜진 채 다른 정렬(최신순 등)을 고르면 묶음이 먼저이고, 묶음 안에서 고른 정렬을 쓴다(사용자 2026-10-29 통합 리뷰 뒤 결정: "켜져 있으면 늘 묶음 먼저").
- 기본 정렬은 **추천순**이다.
  - 분석된 공고가 위, 분석 안 된 공고가 아래다. "분석된"은 목록이 지금 점수를 붙이는 기준(`opportunity_list_items`: 조직의 최신 회사 프로필 revision 으로 돈 run)을 그대로 쓴다.
  - 분석된 공고 안에서는 SOL Score 높은 순. 점수가 같으면 마감 임박 순, 그다음 안정 ID.
  - 필수 자격 미충족으로 비추천(NO-BID)인 공고는 점수가 높아도 분석된 공고 중 맨 아래에 둔다. 설계자 판단(점수가 높은 비추천 공고가 맨 위에 오는 것을 막는다).
  - 분석 안 된 공고는 지금 기본 순서(최근 공고 순)를 따른다.
  - 정렬 이름은 "추천순". 다른 선택지는 최신순·마감 임박순·예산 큰 순.
- 결과 개수 문구, 빈 상태 문구는 "IT 공고 n건"처럼 범위를 밝힌다. 금지 문구는 쓰지 않는다.
- 데스크톱 1440·1280 두 폭에서 칩 줄이 넘치지 않아야 한다.

### 5.2 다른 화면

- 대시보드(`/dashboard`)의 공고 수·마감 임박·권고 분포·기관 순위, `/calendar`, `/market`, `/gaps`, 사이드바 배지 숫자는 IT 범위만 센다.
- `/calendar` 의 "내 관심"·진행 중 프로젝트 일정(`bid_watches`·`bid_projects` 를 따로 읽는다)은 사람이 직접 고른 것이므로 IT 범위 밖이어도 남긴다. 설계자 판단.
- 지원사업 탭(`/bids/programs`)과 그 집계는 §4 의 지원사업 규칙으로 IT 관련만 보인다. 키워드 칩·추천순은 넣지 않는다(지원사업은 SOL Score 분석 대상이 아니다). 설계자 판단.
- 공고 상세(`/bids/[id]`)는 주소로 직접 열면 그대로 열린다(숨김은 목록·집계에서만). 설계자 판단.
- `/workforce`·`/analysis`의 공고 고르기 목록과 `GET /api/v1/bids`(관심 `watched=me` 제외)도 IT 공고만 보인다. 처음 스펙에서 빠졌고 통합 리뷰에서 찾았다.
- `/projects` "검토 대기" 칸은 IT 일괄 분석 run(멱등 키 `it-batch-`)만 있는 공고를 넣지 않는다. 일괄 분석 결과는 `/bids` 추천순에서 본다. DEMO 사전 분석과 사람이 누른 분석은 그대로다(사용자 2026-10-29 통합 리뷰 뒤 결정: "일괄 분석 결과는 빼기").
- 관심 공고(`/watchlist`)는 사람이 직접 담은 것이므로 IT 범위 밖이어도 보인다. 설계자 판단.
- 알림(새 공고 알림 후보)은 IT 범위만 대상으로 한다. 알림 전용 Worker 는 아직 기동하지 않았으므로 코드 기준만 맞춘다.

## 6. IT 공고 1회 일괄 분석

- 대상: 실행 시점에 IT 범위 안이고, 마감 전이고, 실공고(`is_demo = false`)이며, 솔리데오 조직에 최신 회사 프로필 revision 으로 돈 분석이 아직 없는 공고. 실측 기준 약 390건.
- 분석할 원문이 있어야 한다. 화면 [분석]과 같은 준비 확인(`web/server/bids/analysis-readiness.model.ts`, 정규화 본문 또는 파싱된 첨부)을 통과한 공고만 넣는다. `demo-preanalyze.ts` 는 이 확인을 하지 않으므로 그대로 베끼지 않는다. 원문이 없는 공고는 건너뛰고 건수만 보고한다. 설계자 판단. 2026-10-29 실측: 나라장터 IT 387건 중 370건이 파싱된 첨부가 있다. 14건은 첨부가 없고 3건은 아직 파싱 전이다.
- 회사 프로필: 일괄 분석 뒤 회사 프로필을 고치면 목록 점수가 모두 "분석 안 됨"으로 돌아간다(위 "분석된" 기준). 발표 전 프로필 수정 계획은 없다고 보고 한 번 돌린다. 고치게 되면 같은 CLI 를 사용자 승인 뒤 다시 돌린다. 그래서 멱등 키에 프로필 revision 을 넣는다. 설계자 판단.
- 방식: `web/worker/demo-preanalyze.ts` 와 같은 모양의 CLI 를 새로 만든다. 화면의 [분석]과 같은 enqueue 계약으로 analysis 큐에 넣고, 회사 Analysis Worker 가 처리한다. 대상은 DB 에서 고르고 목록을 코드에 박지 않는다. 같은 공고를 두 번 넣지 않는다(멱등 키).
- 속도: 실공고 분석 1건은 운영 실측 10~21초였다. 동시에 너무 많이 넣지 않도록 한 번에 넣는 수와 간격을 제한하고, 회사 gateway health 를 먼저 확인한다.
- 나라장터 보조 조회(기초금액·면허제한·참가가능지역)는 하루 한도가 있다(밀린 1,005건을 하루 100~200건씩 채우는 중, 기록 [[PROGRESS]] 10-29). 일괄 분석 대상의 보조 조회를 먼저 채울지, 보조 조회 없이 분석할지는 빌더가 정한다. 단 한도를 넘기지 않는다.
- 로그에는 bid id·상태·건수만 싣는다. 제목·원문·점수·오류 message 는 싣지 않는다(demo-preanalyze 와 같은 원칙).
- 한 번 실행하고 끝이다. 정기 실행·자동 재시도 예약을 만들지 않는다. 실행 결과(대상 수·완료·부분·실패)는 `docs/evidence/` 에 남긴다.
- 실행 뒤 새로 들어오는 IT 공고는 지금처럼 사람이 [분석]을 누를 때만 분석한다. 그 공고는 추천순에서 "분석 안 된 공고" 쪽에 놓인다.
- 추천 분석(ADR-066, Qwen 설명)은 일괄로 돌리지 않는다. 버튼을 누를 때만이다.

## 7. 제약

- 일정: 화면 동결 2026-11-01, 제출 11-03, 발표 11-04(ADR-054·061). 목록·대시보드 화면이 바뀌므로 동결 전에 운영 반영과 촬영 화면 확인이 끝나야 한다.
- 운영 변경은 각각 사용자 승인 뒤: 운영 DB 마이그레이션(`pnpm db:push`), Vercel 배포, 회사 컨테이너 변경·재생성, 일괄 분석 실행.
- 회사 서버: 나라장터 ingest Worker 는 운영 중이며 함부로 재시작하지 않는다. 22:15 예약 보조 조회 작업(`sol-refill-20261029`)은 `sol-radar-app` checkout 의 HEAD 가 `cbb3831e86da` 인지 확인한다. 회사 쪽 반영이 필요하면 HEAD 를 옮기지 않는 방식(빌드 context 덮어쓰기)을 쓴다(기록 [[PROGRESS]], 메모 rec-insight·g2b-aux).
- 스택·구조: Next.js `web/`, 서버 도메인 `web/server/<도메인>`, 마이그레이션은 새 파일로만, RLS 유지. service role 은 worker·seed·`scripts/ops` CLI 에서만.
- 검증: 개발 중 `pnpm verify:changed`, 통합 전 `pnpm verify`(ADR-046). 무거운 검증은 슬롯 스크립트로 감싼다. 화면은 1440·1280 두 폭에서 직접 본다.
- 새 시험은 핵심 동작만: IT 범위 판정 규칙(분류명·AI 연구·행사 제외·지능형 오탐·분류명 없음), 목록·집계가 같은 판정을 쓰는지, 추천순 정렬(분석된 공고 위, 점수 순), 일괄 분석 대상 선택(데모·이미 분석·마감 지난 공고 제외).
- 문서: ADR-069 로 ADR-047 의 "숨김 아님" 해석을 개정한다. [[PROGRESS]] 갱신. 발표 대본·덱 명세에서 목록 화면이 나오는 장면은 반영 뒤 다시 본다.

## 8. 빌더에게 맡기는 것

- IT 범위 판정을 어디에 둘지(DB 뷰·함수, 저장 열, 관련성 projection 확장 중 무엇) — 단 §3 목표 1(한 곳, 모든 화면 공유)과 §7 회사 서버 제약을 지킨다.
- 칩에 태그(`maintenance`·`ISP`·`ISMP`·`BIM`)를 걸기 위한 목록 뷰·쿼리 파라미터 모양.
- 일괄 분석 CLI 의 동시성·간격·보조 조회 처리.
- 화면 세부(칩 모양, 선택 상태, 개수 표시)는 기존 디자인 시스템과 `opportunities-filters.tsx` 관례를 따른다.

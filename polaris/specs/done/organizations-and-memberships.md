# 스펙: 조직·멤버십·역할 견본 (멀티테넌시)

- 최종 갱신: 2026-10-14 (구현 뒤 차이 반영)

## 1. 목표

SaaS 를 바로 만들 수 있도록 멀티테넌시의 기준 코드를 더한다. 모든 데이터는 조직에 속한다. 가입하면 개인 조직이 자동으로 생기고,
협업은 팀 조직을 따로 만들어 초대한다(Vercel·GitHub 방식). 메모 견본을 조직 단위로 옮겨 "조직의 행 여러 개"의 기준으로 삼는다. [제안 후 승인]

## 2. 비목표

- 조직 이름 바꾸기·조직 삭제. [제안 후 승인]
- 초대 메일 발송. 초대한 사람이 직접 알린다. [제안 후 승인]
- 로그인 상태 E2E·seed 사용자. 별도 작업으로 한다. [제안 후 승인]
- `admin` 조직 역할. [제안 후 승인]
- 운영자(관리자) 화면, 결제. [제안 후 승인]
- 앱의 조직 전환·멤버 관리·초대 화면. 앱은 개인 조직의 메모만 다룬다. [제안 후 승인]

## 3. 완료의 정의

1. **DB 정책** — `pnpm test:db` 에 아래 시험이 있고 통과한다. [제안 후 승인]
   - 조직 밖의 사람은 그 조직의 조직·멤버십·초대·메모를 읽지도 쓰지도 못한다. 단, 초대받은 사람은 수락 전에 그 조직의 이름·주소만 읽는다(4.2).
   - 멤버는 자기 조직의 메모를 읽고 추가한다. 메모 삭제는 작성자나 owner 만 한다.
   - 역할 변경·내보내기·초대는 owner 만 한다.
   - 마지막 owner 는 나가거나 강등되지 않는다. 한 문장으로 owner 둘을 함께 내려도 0명이 되지 않는다.
     두 연결이 동시에 서로 강등하는 경우는 PGlite(연결 하나)로 시험할 수 없어 실제 Postgres(로컬 Supabase)에서 손으로 확인한다.
   - 개인 조직에는 초대할 수 없다.
   - 초대는 초대받은 이메일로 로그인한 사람만, 만료 전에만 수락한다.
   - 가입하면 개인 조직과 owner 멤버십이 생긴다. 이미 가입한 계정도 마이그레이션이 채운다.
   - 이미 있던 메모는 작성자의 개인 조직으로 옮겨진다.
   - 운영자(`is_admin`)도 남의 조직을 읽지 못한다.
2. **도메인 단위 시험** — 웹 조직 도메인의 model·service 시험(`pnpm -C web test`), 앱 메모의 조직 필터 시험(`pnpm -C mobile test`)이 통과한다. [제안 후 승인]
3. **전체 검증** — `pnpm verify` 가 통과한다. DB 타입 생성물·`db-verify` 허용 목록·lodestar·빌드를 포함한다. [제안 후 승인]
4. **E2E** — 경로가 바뀐 기존 로그아웃 시험을 고쳐 `pnpm -C web test:e2e` 가 통과한다. [제안 후 승인]
5. **브라우저 확인** — 로컬 Supabase 에서 두 계정으로 팀 만들기 → 초대 → 수락 → 전환 → 메모 공유 → 내보낸 뒤 접근 불가를 직접 확인한다. 375·1280px. [제안 후 승인]
6. **문서** — `docs/database.md` 의 조직 견본 절, `database` 스킬, 에이전트의 견본 목록을 고친다. 루트 `pnpm test` 의 문서 경로 시험이 통과한다. [제안 후 승인]

## 4. 인터페이스 계약

### 4.1 표 [제안 후 승인]

| 표 | 열 | 규칙 |
|---|---|---|
| `organizations` | `id`, `slug`(unique), `name`, `personal_owner_id`(unique, null 가능), `created_at` | 개인 조직이면 `personal_owner_id` 에 주인, 팀이면 null |
| `memberships` | `org_id`, `user_id`, `org_role`, `created_at` | 기본 키 `(org_id, user_id)`. `org_role` 은 `owner`·`member`, check 제약. `user_id` 는 `profiles` 를 가리킨다(멤버 목록이 프로필을 한 질의로 붙여 읽는다) |
| `invitations` | `id`, `org_id`, `email`, `org_role`, `invited_by`, `expires_at`, `created_at` | `(org_id, email)` unique. 만료 7일. 이메일은 소문자로 저장한다 |
| `memos` | `org_id` 추가 | 기본값은 작성자의 개인 조직. `user_id` 는 작성자 열로 남기고 `profiles` 를 가리키며 `on delete set null` 이다(팀 메모가 작성자 이름을 붙여 읽는다) |

- 역할 열 이름은 `org_role` 이다. 서비스 운영자(`profiles.is_admin`)와 구분한다. [제안 후 승인]
- 마이그레이션은 새 파일로 쌓는다. 역할은 enum 이 아니라 check 제약이다. [제안 후 승인]
- 마이그레이션은 셋이다: `20261014000001_organizations`(본체), `20261014000002_memos_author_profile`(작성자 외래 키), `20261014000003_invitation_fixes`(독립 검토의 결함 수정). [제안 후 승인]

### 4.2 권한과 정책 [제안 후 승인]

- 메모: 멤버 전원이 읽고 추가한다. 삭제는 작성자나 owner.
- 멤버 관리(역할 변경·내보내기)와 초대는 owner. 멤버는 스스로 나갈 수 있다.
- 개인 조직은 혼자만 쓴다. 초대는 팀 조직에만 한다.
- 초대는 이메일을 지정한다. 그 이메일로 로그인한 사람(JWT 의 email 클레임)만 받은 초대를 보고 수락한다.
  초대받은 역할로만 수락하고, 수락하면 그 초대는 지워진다(로그인 이메일·프로필 이메일 어느 쪽으로 온 초대든).
- 초대받은 사람은 수락 전에 그 조직의 이름·주소만 읽는다(받은 초대 화면). 만료된 초대도 거절·취소하기 전까지는 같다.
- 조직 밖의 사람이 초대를 넣어 보면 이유와 상관없이 같은 정책 오류다(멤버 여부·개인 조직 여부를 알려 주지 않는다).
- 팀원끼리는 서로의 이메일·표시 이름을 읽는다(profiles 정책 추가). 이때 `is_admin` 열도 함께 보이는 것을 감수한다.
- 운영자(`is_admin`)에게 조직을 넘어 읽는 정책을 주지 않는다.
- 정책용 security definer 함수(내 조직 id 목록, 내가 owner 인 조직 id 목록)를 하나나 두 개 두고, 이유와 함께 `db-verify` 허용 목록에 더한다.
- 마지막 owner 보호는 트리거가 하고, 조직 행을 잠가 동시 강등을 막는다. JWT 가 없는 관리 작업과 service_role 은 통과한다(`protect_is_admin` 과 같다).
- 개인 조직·owner 멤버십은 가입 트리거를 새 마이그레이션에서 넓혀 만든다.

### 4.3 웹 경로 [제안 후 승인]

| 경로 | 화면 |
|---|---|
| `/[slug]/dashboard` | 대시보드(조직의 메모 요약) |
| `/[slug]/memos` | 조직의 메모 |
| `/[slug]/settings` | 계정 설정(지금의 설정 화면) |
| `/[slug]/settings/members` | 멤버·초대. 개인 조직이면 팀 만들기 안내 |
| `/teams/new` | 팀 만들기 |
| `/invitations` | 받은 초대 |

- 팀 slug 는 만들 때 받는다. 소문자·숫자·하이픈 3~32자. 최상위 경로 이름(`account`·`auth`·`settings` 등)은 예약어라 쓸 수 없다.
- 개인 조직 slug 는 무작위 8자다.
- 옛 주소 `/dashboard`·`/memos`·`/settings` 는 개인 조직의 같은 화면으로 보낸다.
- 조직 전환기는 사이드바 위 로고 자리에 둔다.
- 로그인 전에는 조직이 있는지 묻지 않고 안내(200)를 그린다. 그래서 조직 틀의 화면에는 `robots: noindex` 를 단다(없는 주소가 검색에 오르지 않게).

### 4.4 앱 [제안 후 승인]

- 앱은 `personal_owner_id` 가 나인 조직의 메모만 읽고 쓴다. 전환·멤버·초대 화면은 없다.

## 5. 엣지 케이스와 실패 시나리오

- 마지막 owner 가 나가기·강등을 시도하면 DB 가 막는다. 두 owner 가 동시에 서로 강등해도 owner 가 0명이 되지 않는다. [제안 후 승인]
- 개인 조직은 owner 가 한 명이라 같은 규칙으로 나갈 수 없다. [제안 후 승인]
- 개인 조직에 초대하면 막는다. [제안 후 승인]
- 만료된 초대·다른 이메일의 초대는 수락할 수 없다. [제안 후 승인]
- 이미 가입한 계정·이미 있던 메모는 마이그레이션이 개인 조직으로 채우고 옮긴다. [제안 후 승인]
- 이미 멤버인 이메일은 초대하지 않고 "이미 멤버입니다"로 알린다. 자기 이메일 초대도 막는다. [제안 후 승인]
- 같은 이메일을 다시 초대하면 만료를 7일로 새로 늘린다. [제안 후 승인]
- 초대 이메일은 대소문자를 무시하고 비교한다. [제안 후 승인]
- 팀 slug 가 이미 쓰이면 `{ status: "invalid", field: "slug", message: "이미 쓰는 주소입니다" }` 를 돌려준다(화면이 주소 칸에 붙인다). [제안 후 승인]
- 메모를 지우지 못했는데 아직 보이면(그새 member 로 바뀜) `forbidden` 을 돌려주고, 이미 없으면 `deleted` 다. [제안 후 승인]
- 계정(`auth.users`)이 지워질 때는 관리 작업(JWT 없음)만 마지막 owner 보호를 통과한다(`protect_is_admin` 과 같은 방식).
  팀의 메모는 남고 작성자는 비워진다(`on delete set null`). [제안 후 승인]
- 이미 배포된 앱 빌드는 `org_id` 없이 메모를 추가한다. `memos.org_id` 의 기본값(작성자의 개인 조직)으로 계속 동작한다. [제안 후 승인]

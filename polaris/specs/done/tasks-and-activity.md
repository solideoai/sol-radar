# 스펙: 작업·활동 기록 견본 (메모 견본 대체)

- 최종 갱신: 2026-10-14 (구현 뒤 미결정 사항 확정·차이 반영)

## 1. 목표

메모 견본은 상태·숫자·관계가 없어 대시보드가 "날짜별 작성 수"밖에 보여 주지 못한다. 메모를 **작업(tasks)** 견본으로 바꿔
SaaS 대시보드가 흔히 쓰는 패턴(상태 집계·기한·담당자·필터와 페이지가 있는 데이터 표·DB 집계)의 기준 코드로 삼는다.
**활동 기록(activities)** 을 더해 조직 안에서 누가 언제 무엇을 했는지 남기고 대시보드에 보여 준다. [사용자 결정]

## 2. 비목표

- 기존 메모 데이터 보존. memos 표와 데이터는 옮기지 않고 지운다. [사용자 결정]
- 활동 기록 전용 화면. 대시보드 피드만 둔다. [사용자 결정]
- 앱(mobile)의 데이터 견본. 앱은 메모 화면을 빼고 계정 견본만 남긴다. 작업·활동 화면을 두지 않는다. [사용자 결정]
- 작업의 우선순위·라벨·검색·하위 작업·댓글·첨부. [제안 후 승인]
- 활동 기록의 보관 기한·정리. [제안 후 승인]
- 로그인 상태 E2E·seed 사용자. 별도 작업으로 한다. [제안 후 승인]
- 운영 DB 적용(`pnpm db:push`). 이 작업은 로컬 DB 까지만 적용하고, 운영 적용은 사용자 확인 뒤 따로 한다. [제안 후 승인]

## 3. 완료의 정의

1. **DB 정책** — `pnpm test:db` 에 아래 시험이 있고 통과한다. [제안 후 승인]
   - 조직 밖의 사람은 그 조직의 작업·활동을 읽지도 쓰지도 못한다. 운영자(`is_admin`)도 마찬가지다.
   - 멤버는 자기 조직의 작업을 읽고, 추가하고, 고친다(제목·설명·상태·마감일·담당자). 삭제는 만든 사람이나 owner 만 한다.
   - 담당자는 같은 조직의 멤버만 된다. 다른 조직 사람을 넣으면 DB 가 거절한다.
   - 멤버가 나가거나 내보내지면 그 사람이 담당하던 작업의 담당자가 비고, 작업은 남는다.
   - 상태가 완료로 바뀌면 완료 시각이 채워지고, 완료에서 다른 상태로 바뀌면 비워진다.
   - 화면 역할(authenticated)은 활동 기록을 직접 넣거나 고치거나 지우지 못한다. 4.3 의 일이 일어나면 트리거가 기록한다.
   - 대시보드 집계 함수는 호출한 사람의 권한으로 돌고, 내 조직이 아니면 아무것도 세지 않는다.
   - memos 표가 없다.
2. **도메인 단위 시험** — `web/server/task`·`web/server/activity` 의 model·service 시험이 `pnpm -C web test` 에서 통과한다. [제안 후 승인]
3. **전체 검증** — `pnpm verify` 가 통과한다(DB 타입 생성물·`db-verify` 허용 목록·lodestar·빌드 포함). [제안 후 승인]
4. **E2E** — 메모 경로를 쓰던 로그아웃 시험(보호 경로·반응형)을 작업 경로로 고쳐 `pnpm -C web test:e2e` 가 통과한다. [제안 후 승인]
5. **브라우저 확인** — 로컬 Supabase 에서 두 계정으로 팀 만들기 → 초대 → 수락 → 작업 추가·담당 지정·완료 → 대시보드 수치와 활동 피드 →
   멤버 내보내기 뒤 담당자 비움을 직접 확인한다. 375·1280px. [제안 후 승인]
6. **문서** — `AGENTS.md`·`docs/`·스킬·에이전트에 적힌 메모 견본 경로(`web/server/memo` 등)를 작업·활동 견본으로 고친다.
   루트 `pnpm test` 의 문서 경로 시험이 통과한다. [제안 후 승인]
7. **스펙 대조** — `/spec-check` 로 이 파일과 구현을 대조해 어긋남이 없다. [제안 후 승인]

## 4. 인터페이스 계약

### 4.1 표 [제안 후 승인]

| 표 | 열 | 규칙 |
|---|---|---|
| `tasks` | `id`, `org_id`, `title`, `description`, `status`, `due_date`, `assignee_id`, `created_by`, `completed_at`, `created_at`, `updated_at` | `title` 앞뒤 공백 없이 1~120자. `description` 은 null 또는 1~2000자. `status` 는 `todo`·`in_progress`·`done`(check 제약, enum 아님). `due_date` 는 날짜(시각 없음), null 가능. `completed_at` 은 DB 가 채운다 |
| `activities` | `id`, `org_id`, `actor_id`, `kind`, 대상 열, `created_at` | 트리거만 쓴다. 대상이 지워져도 기록이 읽히도록 작업 제목 등 표시할 값을 기록 시점에 함께 남긴다 |

- `assignee_id` 는 `(org_id, assignee_id)` 로 `memberships (org_id, user_id)` 를 가리키는 복합 외래 키다. 멤버십이 지워지면 `assignee_id` 만 비운다. [제안 후 승인]
- `created_by`·`actor_id` 는 `profiles` 를 가리키고, 계정이 지워져도 행은 남는다(`on delete set null`). [제안 후 승인]
- 조직이 지워지면 그 조직의 작업·활동도 지워진다. [제안 후 승인]
- memos 표·정책·함수는 새 마이그레이션에서 지운다. 이미 있는 마이그레이션은 고치지 않는다(append-only). [사용자 결정]
- 조직 주소의 예약어(`memos` 등)는 바꾸지 않는다. 전역 `/tasks` 경로를 새로 만들지 않으므로 예약어를 더하지 않는다. [제안 후 승인]

### 4.2 권한 [사용자 결정]

| 표 | 읽기 | 추가 | 수정 | 삭제 |
|---|---|---|---|---|
| `tasks` | 같은 조직 멤버 | 같은 조직 멤버(만든 사람은 본인) | 같은 조직 멤버 — 제목·설명·상태·마감일·담당자 | 만든 사람(아직 멤버일 때)이나 owner |
| `activities` | 같은 조직 멤버 | 트리거만 | 없음 | 없음 |

### 4.3 활동 기록이 남기는 일 [제안 후 승인]

- 작업: 만듦, 완료함, 다시 엶(완료 → 다른 상태), 담당자 바꿈, 지움.
- 멤버: 들어옴(초대 수락), 역할 바뀜, 나감(스스로) · 내보냄(owner 가).
- 초대: 보냄. 역할만 남기고 이메일은 남기지 않는다(초대 목록은 owner 만 읽는다). 같은 이메일을 다시 초대해 기존 초대를 갱신하는 일은 남기지 않는다. [사용자 결정]

남기지 않는 일 [사용자 결정]:
- 멤버가 빠지며 외래 키로 담당자가 비는 일. 멤버 나감·내보냄 기록 하나로 충분하다.
- 가입·팀 만들기로 생기는 조직의 첫 owner 멤버십. 초대 수락만 "들어옴"이다.
- 할 일 ↔ 진행 중 전이, 만들 때 정한 담당자(디자인 스펙 Q3·Q5).

누구로 보이는가 [사용자 결정]:
- 행위자 이름은 사본으로 남기지 않고 지금 멤버 중에서 찾는다. 떠났거나 계정을 지웠거나 JWT 가 없는 관리 작업이면 "떠난 멤버"로 보인다.
- 대상(멤버·담당자)의 이름은 기록 시점의 사본으로 남긴다. 대상이 계정을 지우면 사본도 지워 "떠난 멤버"로 보인다.

### 4.4 웹 화면 [제안 후 승인]

- 사이드바: 대시보드 · 작업 · 설정.
- `/[slug]/tasks` — 작업 표. 상태·담당자로 거르고 마감일·만든 날로 정렬한다. 한 쪽에 20개, 서버에서 나눈다. 거르기·정렬·쪽은 URL 쿼리에 둔다.
  추가·편집은 대화상자로 한다(디자인 스펙이 확정한다).
- `/[slug]/memos` 는 없앤다. 옛 주소 `/memos` 는 개인 조직의 `/[slug]/tasks` 로 보낸다.
- `/[slug]/dashboard`:
  - 카드: 열린 작업(완료가 아닌 것), 기한 지남(오늘보다 마감일이 이른 열린 작업), 이번 주 완료(월요일 0시부터), 내 담당(나에게 맡겨진 열린 작업).
  - 차트: 최근 14일 날짜별 추가 수와 완료 수.
  - 표: 기한이 가까운 열린 작업 5개. [사용자 결정]
  - 피드: 최근 활동 10개.
  - 날짜는 서울 시간으로 가른다. 수치는 DB 집계 함수 하나가 낸다(목록을 읽어 앱에서 세지 않는다).

### 4.5 서버 도메인 [제안 후 승인]

- `web/server/task/`·`web/server/activity/` 에 `model`·`repo`·`service`·`index`(배럴)로 둔다. `web/server/memo/` 는 지운다.

### 4.6 앱 [사용자 결정]

- `mobile/app/memos.tsx`·`mobile/lib/memo.ts` 와 그 시험, 홈의 메모 버튼을 지운다. 앱은 계정 견본만 남는다.

## 5. 엣지 케이스와 실패 시나리오

- 다른 조직 멤버를 담당자로 넣는 요청 → DB 가 거절하고, 화면은 "이 팀의 멤버가 아닙니다"류로 알린다. [제안 후 승인]
- 고치는 사이 작업이 지워졌거나 내가 조직에서 빠졌다 → 서버 함수가 상태로 돌려주고 화면이 알린다(조직 견본과 같은 방식). [제안 후 승인]
  조직에서 빠졌으면 다시 그린 화면이 곧바로 404 라 대화상자 안 문구는 보이지 않는다. 그래서 오류 토스트로 알린다. [사용자 결정]
- 잘못된 URL 쿼리(없는 상태·담당자·쪽 번호) → 기본값으로 보여 준다. [제안 후 승인]
- 담당자 계정이 지워짐 → 멤버십이 함께 지워져 담당자가 빈다. [제안 후 승인]
- 조직이나 계정이 지워지며 연쇄로 지워지는 행(작업·멤버십·초대)은 활동으로 남기지 않는다. 남기려 하면 지워지는 조직을 가리키는 기록이 생겨 삭제가 외래 키 위반으로 실패할 수 있다. [사용자 결정]
- 화면 결정(D1~D7·Q1~Q12)은 디자인 스펙 `tasks-and-activity.design.md` 0절·7절을 따른다. [사용자 결정]

## 미결정 사항

없음. 구현 중 기본안으로 둔 네 가지(담당자 비움 기록 안 함, 첫 owner 기록 안 함, 초대 기록에 이메일 없음, 기한 표 5개·피드 10개)는 2026-10-14 사용자가 확정했다(4.3·4.4).

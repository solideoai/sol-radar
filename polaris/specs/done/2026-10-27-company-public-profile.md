# 회사 역량 — 공개 자료 기반 솔리데오 프로필과 임원 권한

사용자 요청(2026-10-27): "대시보드에서 회사 역량 메뉴에 회사가 수행 실적했던 것들이랑 기술 스택이랑 보유 자격 등 임의의 데이터로 들어가 있는 것 같아. 인터넷에서 찾을 수 있는 정보를 다 수집해서 넣으면 좋을 거 같아. 이제 진짜 데모가 아니라 운영 서버이고 시연을 해야하니까."

## 1. 왜 하는가

운영 서버(`https://www.solideos-radar.com`)에서 관리자 계정으로 시연한다. 지금 `/company`(회사 역량)는 가상 프로필(`is_demo=true`, "가상 회사 프로필" 칩)이다. 실적 3건·기술 8개·자격 9개·재무가 모두 지어낸 값이다(`fixtures/company/solideo-profile.json`, ADR-019·020). 이 값은 SOL Score 다섯 요소 중 네 개(기술 30·실적 25·규모 15·선호 10)와 필수 자격 판정에 그대로 들어간다. 실제 공고를 실제 회사 정보로 판정하는 장면을 보여 주려면 프로필이 실제여야 한다.

성공한 모습: ADMIN(또는 임원) 계정으로 `/company`에 들어가면 실제 솔리데오의 실적·기술·인증·재무가 보이고, 값마다 출처 링크가 있으며 "가상" 칩이 없다. 이후 새로 돌리는 공고 분석은 이 프로필로 점수를 계산한다.

## 3. 목표 · 비목표 · 안티 목표

목표

- A. `EXECUTIVE` 역할을 추가하고 `/company`를 ADMIN·EXECUTIVE 전용으로 바꾼다.
- B. 공개 자료로 솔리데오 프로필을 만들고, 출처와 함께 운영 DB에 새 revision으로 넣는다.

비목표

- 회사 프로필 편집 화면·`PUT /api/v1/company-profile`. 넣는 길은 운영자 CLI 하나다.
- 비공개 자료(실적증명서·내부 문서)로 빈칸 채우기.
- 가상 직원 명부 200명·`team_member_scoring`·인력 가용성 점수 변경.
- `fixtures/company/solideo-profile.json`·골든·08 §6.1 worked example·발표 고정 점수(94/72/68) 변경. 로컬·시험·`demo:reset`은 계속 가상 프로필을 쓴다.
- 지난 분석(`score_runs`) 재계산. 지난 분석은 그때 revision에 고정돼 있다.

안티 목표 (기술적으로 돌아가도 실패로 본다)

- 출처 없는 값, 또는 공개 자료가 말하지 않는 것을 사실처럼 넣는 것. 예: 2014년에 받은 CMMI L3를 지금 보유(`HELD`)로 적는 것. 예외는 D7의 "회사 확인" 자격과 D10의 "회사 확인" 기술뿐이다.
- ADMIN·EXECUTIVE가 아닌 사람이 `/company` 화면이나 회사 프로필 API로 프로필을 보는 것. DB 수준은 §4-5에 따로 정했다.
- ANALYST 등이 공고 분석을 못 돌리게 되는 것.
- 회사 Worker가 새 프로필을 못 읽어서 운영 분석이 실패하는 것.
- 직원 개인 정보 수집. 공개 회사 정보만 모은다.

## 4. 파트 A — `EXECUTIVE` 역할과 `/company` 접근

### 지금

- 메뉴 `web/components/app-nav.ts:80`(`/company`, `roles` 없음). 페이지 가드 `requireWork`(`web/app/(app)/(work)/work.ts`)는 sol_role이 있는 팀원이면 누구나 통과시킨다.
- API `GET /api/v1/company-profile`·`/revisions`는 `requireBusinessUser`만 확인한다.
- RLS `company_profiles` select는 `org_id in (select public.my_org_ids())`다(`supabase/migrations/20261019000003_company_profiles.sql:66-69`). insert는 ADMIN만 가능하고, update·delete는 막혀 있다.
- 공고 분석 요청은 **사용자 세션**으로 `company_profiles`의 `id,revision`을 읽는다(`web/server/bids/bids.supabase.ts` `resolveAnalysisInput`). 분석 job(`web/worker/analysis-job.ts`)은 service role로 전체를 읽는다.
- 분석할 때마다 프로필 전체가 `score_runs.input_snapshot.profile`에 복사된다. `score_runs`는 조직 멤버 누구나 읽는다(`20261019000004_score_runs.sql`). 가정 재계산(`bids.supabase.ts`)과 인력 배치 시뮬레이션(`workforce.repo.ts`)도 사용자 세션으로 이 사본을 읽는다.
- 목록·대시보드·관심 공고 뷰(`opportunity_list_items`·`watched_opportunity_list_items`·`procurement_summary`, security_invoker)는 **조직의 최신 프로필 revision으로 만든 분석만** 붙인다(`20261023000200_procurement_reads.sql`). 공고 상세(`latestAnalysis`)는 프로필과 관계없이 최신 분석을 보인다.
- sol_role 값은 CHECK 제약 세 곳에 있다: `memberships`, `invitations`, `member_join_requests`. 역할 목록을 쓰는 코드·정책 파일은 `grep -rlnE "[\"'](VIEWER|SALES)[\"']"`로 찾는다. 2026-10-27 기준 마이그레이션 13개와 `web/` 파일 11개다.

### 바뀐 뒤

1. `EXECUTIVE`를 sol_role에 더한다. 화면 이름은 "임원"이다. 마이그레이션은 새 파일로만 쌓는다.
2. ADMIN이 초대·가입 승인·역할 변경에서 EXECUTIVE를 고를 수 있다. 부여 권한은 지금 규칙(ADMIN만 역할을 바꾼다, 마지막 ADMIN 보호)을 그대로 따른다.
3. EXECUTIVE의 다른 화면 권한은 VIEWER와 같다(D8). 읽기만 하고, 분석 요청·검토·입찰 결정·프로젝트 쓰기는 하지 않는다. 다른 점은 회사 역량을 읽을 수 있다는 것 하나다. 역할 목록이 들어 있는 정책·코드에서 EXECUTIVE는 VIEWER가 들어 있는 읽기 목록에만 더한다.
4. `/company` 메뉴는 `roles: ["ADMIN", "EXECUTIVE"]`다. 다른 역할이 주소로 들어오면 기존 역할 제한 화면과 같은 방식으로 막는다. API 두 개는 다른 역할에게 403 `FORBIDDEN`을 준다.
5. `company_profiles`의 RLS select는 **그대로 둔다**(조직 멤버 읽기). 열람 제한은 메뉴·페이지·API에서 한다. *(Claude 판단)*
   - 이유 1: 같은 내용이 `score_runs.input_snapshot`에도 들어 있고, 그 사본을 조직 멤버가 읽는다. 표만 잠가도 DB로는 볼 수 있다. 사본까지 잠그려면 가정 재계산·인력 시뮬레이션·목록 뷰 3개를 모두 security definer 경로로 옮겨야 하는데, 막을 대상에 비해 일이 크다.
   - 이유 2: 넣는 값이 전부 공개 자료다.
   - 이 판단과 이유를 새 ADR에 적는다. 나중에 비공개 자료를 넣게 되면 그때 DB 수준 잠금을 다시 정한다.
6. 분석 결과 화면에 인용되는 회사 근거(자격 이름·실적 이름)는 그대로 둔다. 판정 근거로 쓰인 항목 이름만 보이고 프로필 원본은 보이지 않는다. *(Claude 판단)*

- 공개 페이지만 읽는다. 로그인이 필요한 곳, 이용약관이 자동 수집을 막는 곳(나라장터 웹 화면 긁기 포함)은 쓰지 않는다. 나라장터 기록은 공공데이터 API로만 받는다.
- 값마다 출처 URL·확인일·원문 인용 한 줄을 남긴다. 수집 원장과 페이지 근거는 `docs/evidence/company-public-profile/20261027/`에 둔다.
- 실제 프로필 JSON은 `fixtures/`에 두지 않는다. `fixtures/`는 전부 가상 데이터다. 위치는 구현자가 정한다.
- data.go.kr 활용 신청이나 키가 필요하면 멈추고 사용자에게 요청한다. 키 값은 문서·로그·커밋에 넣지 않는다.

### B2. 프로필에 옮기는 규칙

- `isDemo=false`. 회사명은 공개 표기 "㈜솔리데오"다.
- **기술(`technologies`)**: 공개 자료가 회사가 쓴다고 말하는 기술만 넣는다. `level`·`yearsOfExperience`는 비운다. `technologiesComplete=false`로 둔다. 그러면 목록에 없는 기술은 미충족이 아니라 확인 필요가 된다.
- **자격(`licenses`)**: 판정은 `QUALIFICATION_CODES` 사전 코드로 맞춘다(`web/server/scoring/qualification-codes.ts`). 사전에 있는 코드만 점수용 목록에 넣는다.
  - `HELD`는 공개 자료가 **지금 유효함**을 보여 줄 때만 쓴다. 공개 조회 결과나 유효기간 표기가 그 근거다.
  - 공개 조회로 확인하지 못한 자격은 목록을 사용자에게 보여 준다. 사용자가 보유를 확인한 것만 `HELD`로 넣고, 출처 종류는 "회사 확인"(확인자·확인일)으로 적는다(D7). 확인 요청은 사용자에게 한 번에 묶어서 보낸다.
  - 취득 연도만 있는 것은 점수용 목록에 넣지 않는다. 그러면 판정이 `NEEDS_REVIEW`가 된다. 이런 항목은 "공개 이력"으로만 보인다. 예: CMMI L3 2014, 정보통신공사업 2011.
  - `NOT_HELD`는 공개 자료가 미보유를 밝힐 때만 쓴다.
- **업종 코드(`industryCodes`)**: 나라장터 공공데이터로 확인되면 넣고, 아니면 비운다.
- **실적(`pastProjects`)**
  - `name`·`domain`은 필수다. `domain`은 `DOMAINS` 사전 값(민원·데이터 플랫폼·교육·AX·스마트시티·국방·기타)을 사업 이름으로 고른다.
  - `amountKrw`·`completedAt`은 공개 자료에 있을 때만 넣고, 없으면 `null`이다.
  - 지분이 공개되지 않은 컨소시엄 총액은 `amountKrw`에 넣지 않고 비고에 적는다.
  - 운영 중이라 끝나지 않은 사업은 `completedAt`을 비운다.
  - 나라장터 계약 기록은 정보화·SW 용역 계약만 넣는다. 완료일 기준 최근 5년과 진행 중인 계약이 대상이고, 금액 하한은 두지 않는다. 5년보다 오래된 계약은 최근성이 0.2라 점수에 거의 기여하지 않으므로 화면 분량만 늘린다. 공동수급 지분율이 공개돼 있으면 `amountKrw`는 총액 × 지분율로 넣고 총액은 비고에 적는다. *(Claude 판단)*
  - `evidenceRef`는 나라장터 계약 기록(계약번호 등)이 있을 때만 쓴다. 홈페이지 목록은 실적 증빙이 아니므로 `null`이다. 이 경우 유사도가 ×0.5 깎이는데, 이것은 의도한 결과다. *(Claude 판단)*
- **재무(`financials`)**
  - `fiscalYear` 2025, `annualRevenueKrw` 60,240,000,000, `capitalKrw` 3,380,000,000, `employeeCount` 281(2025-12-31).
  - 홈페이지의 290명은 기준일이 없어 비고에만 적는다.
  - `creditRating`·`maxContractKrw`는 비운다.
- **선호(`preferences`)**: 회사의 전략 선택이라 공개 자료가 아니다. D13에 따라 사용자가 고른 선호 분야(민원·데이터 플랫폼·AX·스마트시티)만 넣고 나머지는 빈 배열이다. 사실이 아니라 선택값이므로 화면에 "회사 확인" 선택값으로 표시한다.
- **공개 이력**: 인증·등록·수상 연혁은 점수에 쓰지 않는 별도 목록으로 저장해 화면에 보인다.
- **출처**: 프로필 단위 `sources[]`(id·제목·URL·확인일)와 항목별 `sourceIds[]`.

### B3. 구조·점수·화면 변경

- `companyProfileSchema`(`web/server/scoring/analysis-input.model.ts:206`)
  - `pastProjects[].amountKrw`·`completedAt`을 nullable로 바꾼다.
  - `sourceIds`(항목), `sources`, 공개 이력을 선택 필드로 더한다.
  - 기존 fixture가 그대로 통과해야 한다.
  - 새 필드를 JSONB 열에 끼울지 새 열을 만들지는 구현자가 정한다. 새 열이면 새 마이그레이션이고 `database.types.ts`도 다시 만든다.
- 점수(`web/server/scoring/factors.ts`)
  - `amountKrw`가 `null`이면 금액비는 0.5다. 지금의 "금액 없음" 처리와 같다.
  - `completedAt`이 `null`이면 최근성은 0.2다(가장 낮은 구간, 08 §4 보수 원칙). *(Claude 판단)*
  - 규모 적합성의 "실적 최대 금액"은 `null`을 뺀다.
  - 08 §3.2·§4에 적는다. 기존 입력의 점수는 바뀌지 않아야 한다. 골든·worked example이 그대로 통과하는지로 확인한다.
- 화면(`web/components/company/`)
  - `isDemo=false`면 "가상 회사 프로필" 칩 대신 "공개 자료 기준 · 확인일 2026-10-27"과 출처 목록을 보인다.
  - 비운 칸은 "공개 자료 없음"으로 표시한다.
  - 보유 자격 탭 아래에 "인증·등록 이력(점수 미사용)"을 보인다.
  - 값 옆에 출처 링크를 둔다.
  - 1440·1280px 두 폭에서 확인한다.

### B4. 운영 반영

- `scripts/ops/`에 운영자 CLI를 둔다. 사람이 로컬에서 직접 돌리고 service role을 쓴다(docs/CLAUDE.md 허용 범위).
  - JSON을 `companyProfileSchema`로 검증한 뒤 솔리데오 업무 조직에 새 revision을 넣는다.
  - `note`는 "공개 자료 기준(2026-10-27 수집)", `created_by`는 지정한 ADMIN 사용자다.
  - 기본은 dry-run(넣을 행과 직전 revision과의 차이를 출력)이고, 실제로 넣으려면 `--apply`를 줘야 한다.
- 순서. 운영을 바꾸는 단계는 모두 실행 직전에 사용자 확인을 받는다.
  1. 코드·마이그레이션 병합, 전체 `pnpm verify` 통과.
  2. 운영 DB 마이그레이션(`pnpm db:push`). 사용자 확인 뒤에 한다.
  3. Vercel web 배포.
  4. **회사 Worker와 AI gateway를 새 코드로 갱신.** AI gateway도 결정 모델 입력에서 실적 금액을 필수로 검사한다(`services/ai/src/sol_ai/contracts.py` `ProfileProject`, `kev_state.py`). 그래서 금액 `null`을 받도록 같이 고친다. 분석 job이 프로필을 `companyProfileSchema`로 검사하므로(`web/server/analysis/analysis-store.model.ts:242`), 옛 Worker는 `null` 금액을 못 읽고 분석이 실패한다. 회사 Worker는 실운영 중이라 재시작을 함부로 하지 않는다(2026-10-26 실운영 전환). 재시작 시점은 사용자와 정한다.
  5. (D6 개정으로 하지 않음) DEMO 정리 실행서 03 삭제. ADR-054에 따라 운영 DEMO 공고는 발표 뒤까지 남긴다.
  6. CLI dry-run 결과를 사용자에게 보인다.
  7. 사용자 확인 뒤 `--apply`.
  8. 다시 분석한다. 새 revision이 들어가면 목록·대시보드는 옛 프로필로 낸 분석을 모두 "미분석"으로 보인다(§4 "지금"). 추천 권고 수도 0부터 다시 쌓인다. 회사 AI 호출 예산(live 24시간 창 약 260회)을 넘지 않게, 시연할 공고와 열린 공고 중 우선순위가 높은 것부터 나눠 다시 분석한다. 어떤 방식으로 묶을지는 구현자가 정한다.
- 운영 DB에는 DEMO 공고 19건과 그 분석이 남아 있다(`docs/evidence/demo-cleanup/20261026/`, 2026-10-27 기준 03 삭제 미실행). D6 개정에 따라 지우지 않고, 8단계에서 발표에 쓸 DEMO 공고를 새 프로필로 다시 분석한다.
- 문서: 새 ADR(ADR-052)로 ADR-020의 "모든 모드에서 가상 프로필"을 고친다(운영 DB는 공개 자료 프로필, 로컬·시험은 가상). `EXECUTIVE` 역할도 같은 ADR이나 다음 번호에 적는다. 함께 고칠 문서는 04 §3.2, 05 §4.4, 06 §5.6, 08 §3.2·§4·§6, 09(프로필 열람 역할), PROGRESS다.

## 6. 수용 기준

1. EXECUTIVE 계정
   - 화면: `/company` 메뉴가 보이고 화면이 열린다. 다른 화면은 VIEWER와 같다.
   - 막히는 것: 분석 요청·입찰 결정·프로젝트 쓰기 버튼이 없고, API도 403을 준다.
2. VIEWER·ANALYST·SALES 계정
   - 막히는 것: `/company` 메뉴가 없고, 주소로 들어가도 막힌다. API 두 개는 403이다.
   - 되는 것: 분석 요청·목록 점수·가정 재계산·인력 시뮬레이션이 지금처럼 된다.
3. ADMIN이 초대·가입 승인·역할 변경에서 "임원"을 고를 수 있다.
4. 운영 프로필은 `isDemo=false`다.
   - 출처: 모든 기술·자격·실적·재무 값에 출처가 하나 이상 있다.
   - 비운 값: 공개 자료가 없는 값은 비어 있다.
   - 인증: `HELD`인 항목은 모두 현재 유효함을 보이는 근거가 있다.
5. 기존 가상 fixture로 계산한 점수·골든·worked example이 바뀌지 않는다. `null` 금액·완료일 처리 시험이 있다.
6. 운영 반영 뒤 회사 Worker가 새 revision으로 분석을 하나 이상 끝낸다(`score_runs`가 SCORED 상태).
7. 검증
   - 개발 중: `pnpm verify:changed`.
   - 통합 전: 전체 `pnpm verify`.
   - DB 정책 시험(`scripts/database.test.mjs`): EXECUTIVE 역할 부여·변경 규칙, EXECUTIVE는 쓰기 정책에 막힌다.
   - Route 시험: 회사 프로필 API 두 개가 ADMIN·EXECUTIVE에게 200, 다른 역할에게 403.
   - 화면: 1440·1280px 스크린샷.

## 7. 남은 확인과 구현자에게 맡기는 것

사용자 확인이 남은 것: 없음. 2026-10-27 질문 3개는 D6·D7·D8로, 이어진 질문 4개는 D9·D10·D11·D6 개정으로, 재조사 범위는 D12로, 최종 리뷰의 추천 불가 문제는 D13으로 정했다. 운영을 바꾸는 단계(§5 B4)는 실행 직전마다 확인을 받는다.

구현자 재량

- 프로필 JSON과 수집 원장의 저장 위치·파일 형식(`fixtures/` 밖).
- 출처·공개 이력을 JSONB 안에 둘지, 새 열로 둘지.
- 역할 제한 화면이 403 화면인지 `notFound`인지. 저장소의 기존 ADMIN 전용 화면 방식을 따른다.
- 다시 분석할 공고를 고르고 묶는 방식(§5 B4-7).
- 사업 이름을 `DOMAINS` 값으로 나누는 기준. 나눈 결과를 수집 원장에 적는다.

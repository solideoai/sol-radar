# 사이드바 핵심 메뉴 3개 — 자격 갭 레이더·발주 현황·입찰 일정

사용자 요청(2026-10-28): "해커톤 발표가 다음 주인데 아직도 좀 기능이 많이 약한 것 같아. 해커톤에서 본선 가고 우승할 수 있을만한 아이디어를 떠올려봐. … 특히 대시보드 옆에 사이드바가 좀 비어서 몇개 더 추가하고 싶고, 핵심 기능이면 좋겠어." 아이디어는 메인 세션(45)과 Fable 5.1 이 각자 낸 뒤 교차 검증했다. 두 쪽 모두 자격 갭 레이더를 1순위로 독립적으로 골랐다.

## 1. 왜 하는가

- 운영 실공고(나라장터 입찰공고)는 1,285건이 모였지만 AI 분석은 0건이다(첨부 처리 Worker 보류, [[PROGRESS]]). 실용성 30·완성도 25 의 공통 약점이다.
- 공고마다 이미 저장되는 **API 구조화 필드**(면허제한·참가가능지역, `bid_structured_requirements`)와 기존 규칙 엔진만으로 실공고 전체에 결정론적 1차 선별을 걸 수 있다. 첨부·AI 가 필요 없다.
- 운영 회사 프로필(공개 자료 revision 5)은 보유 자격이 정보통신공사업 1건뿐이라 DEMO 분석이 전부 WATCH 다. 이 약점을 "무엇을 갖추면 어떤 시장이 열리는가"라는 임원용 질문으로 바꾼다.

성공한 모습: 발표에서 `/gaps` 를 열면 "실공고 기준 지금 참가 가능 N건. '소프트웨어사업자'를 보유했다고 가정하면 M건·Y억이 열린다. 저장되지 않고 수주 금액이 아니다"를 30초 안에 보인다. `/market`·`/calendar` 는 사이드바를 채우고 실용성·완성도를 보강한다.

관찰:
- live 공고에 SI·AI 와 무관한 업종(폐기물·여행·건설기계)이 섞여 있다. 화면은 관련성 판정(`bid_relevance_assessments`, 수집 때 계산, `web/server/ingestion/procurement-projection.ts:287`)으로 기본 거르기를 한다.

## 4. 공통 규칙 (세 파트 모두)

- 정직한 AI 원칙: 수주확률·승률·"수주 가능 금액" 표현 금지. 예산 합계는 "참가 자격이 열리는 공고의 배정 예산 합"이다. 정보 부족은 미충족이 아니다.
- 데이터 출처를 화면에 밝힌다: "나라장터 입찰공고 수집분", 기준 시각(최신 수집 시각), 낙찰·계약 데이터 미수집, 발주계획·사전규격 미포함.
- 읽기 전용 기능이다. 새 표·마이그레이션 없이 만든다. 마이그레이션이 꼭 필요해지면 멈추고 메인 세션에 보고한다(운영 적용 `pnpm db:push` 는 사용자 확인 사항).
- 데이터 접근은 anon 키 + RLS(웹 서버 기본 통로). service role 금지. 다른 조직 데이터 0행.
- 서버 코드는 `web/server/<도메인>/`(model·repo·service·index 배럴), 다른 도메인은 배럴로만(`@/server/scoring` 등). lodestar 계층 규칙을 따른다.
- 화면: 데스크톱 1280px 이상, 1440·1280 두 폭 확인. 색·글꼴은 `design/tokens.json` 정본(`design-system` 스킬). 새 차트·날짜 라이브러리를 설치하지 않는다(표·CSS 막대·`Intl`). 가장 가까운 견본 화면은 `/analysis`·`/watchlist`·`/projects` 다. 빈 상태·로딩·오류·권한 없음 상태를 둔다.
- 사이드바(`web/components/app-nav.ts`)와 `web/components/app-shell.tsx` 는 고치지 않는다. 다른 세션이 사이드바 디자인을 고치는 중이다. 메뉴 등록은 통합 때 메인 세션이 한다(§7). 그 전까지 화면은 주소로 연다.
- 정본 문서(`docs/0*.md`·`docs/1*.md`·`docs/PROGRESS.md`)는 고치지 않는다. 증거는 `docs/evidence/<파트>/20261028/` 에 둔다.
- 시험은 MVP 핵심만([[11-TESTING]] "현재 MVP 자동 시험", ADR-046): 순수 계산 함수 단위 시험(변형 확인 포함) + 화면 브라우저 시험 1개(1440·1280 스크린샷). 계층별 중복·무차별 조합 금지.

## 5. 파트 A — 자격 갭 레이더 `/gaps`

메뉴: 분석 묶음 "자격 갭 레이더". 브랜치 `feat/gaps-radar`.

### A1. 대상

live 공고(`is_demo=false`) 중 `status in (OPEN, AMENDED)` 이고 마감이 지금 이후인 것. 기본 거르기는 관련성 `RELEVANT`·`CANDIDATE`(최신 revision 의 최신 정책). "전체 업종 보기" 토글로 거르기를 끈다. 회사 프로필은 이 조직의 최신 revision.

### A2. 공고별 1차 판정

기존 규칙 엔진을 그대로 쓴다. 공고의 최신 revision 정규화 데이터(구조화 요건·`auxLookup`)와 회사 프로필로 구조화 필드 판정(`structuredChecks`+`auxLookupChecks` 와 같은 결과)을 낸다. 같은 공고를 공고 상세에서 분석했을 때의 구조화 필드 판정과 어긋나면 안 된다. 추출(Qwen) 항목은 없다고 본다. `scoring` 도메인에서 함수를 새로 내보내야 하면 내보내되 골든 94/72/68 시험이 그대로 통과해야 한다.

판정 묶음(공고 하나는 한 묶음):

| 묶음 | 조건 | 화면 이름 |
|---|---|---|
| ELIGIBLE | 구조화 판정이 모두 `SATISFIED`(또는 판정 항목 없음)이고 `auxLookup.status=OK` | 참가 가능(API 기준) |
| MISSING_RECORD | 면허제한 1행, 사전 코드로 풀리고, 회사 프로필에 그 코드 기록이 없음(`COMPANY_EVIDENCE_MISSING`). 다른 판정은 통과 | 회사 기록 없음 |
| NOT_HELD | 회사 프로필에 `NOT_HELD` 로 기록된 자격 때문에 `NOT_SATISFIED` | 미보유 |
| NEEDS_REVIEW | 나머지(면허제한 2행 이상, 사전 밖 업종, 지역 확인 필요, `auxLookup` OK 아님·없음 등). 사유 코드를 같이 집계 | 사람 확인 필요 |

고정 문구(화면 상단, 늘 보임): "공고 API 의 구조화 필드(면허제한·참가가능지역)만으로 1차 선별했습니다. 첨부(제안요청서)의 자격 요건은 반영하지 않았습니다." / "예산 합계는 참가 자격이 열리는 공고의 배정 예산 합이며 수주 금액이나 확률이 아닙니다."

### A3. 화면

1. 요약 띠: 대상 공고 수, 묶음별 건수·예산 합, 기준 시각, 회사 프로필 revision·출처 배지("공개 자료 회사 프로필" 등 기존 배지 재사용).
2. 막는 자격 순위: `MISSING_RECORD`·`NOT_HELD` 공고를 API 업종 이름/코드별로 묶어 건수·예산 합. 같은 업종이 들어 있는 2행 이상 공고 수는 따로 "조건 묶음 포함(확인 필요) n건"으로 보인다. 사전 밖 업종은 "자격 코드 사전 밖"으로 표시한다.
3. 보유 가정: 순위 표의 사전 코드 행마다 "보유 가정" 스위치(공고 상세 가정 재계산 ADR-037 과 같은 말). 켜면 같은 판정을 가정 자격으로 다시 계산해 "참가 가능 N → N′건, 예산 X → X′" 와 새로 열리는 공고 목록(제목·기관·마감·예산, `/bids/[id]?origin=live` 링크)을 보인다. 가정은 주소 쿼리(`?assume=SW_BUSINESS_REG,…`)로 들고, 서버에서 계산한다. DB 쓰기·감사 로그·알림 0. 고정 문구 "가정 결과입니다. 저장되지 않고 결정 기록에 쓰이지 않습니다."
4. 사람 확인 필요 내역: 사유 코드별 건수(면허제한 복수 행 AND/OR 미확인, 사전 밖, 보조 조회 미완료 등).

권한: 조직 구성원 전원 조회(읽기). 회사 프로필 읽기가 RLS 로 막히는 역할이 있으면 그 상태를 그대로 안내한다.

### A4. 수용 기준

- 순수 함수(공고 판정 묶음 + 집계 + 가정 재계산)에 단위 시험: 1행 HELD → ELIGIBLE, 1행 기록 없음 → MISSING_RECORD, 2행 → NEEDS_REVIEW, `auxLookup` 없음·FAILED → NEEDS_REVIEW, 가정 켜면 MISSING_RECORD → ELIGIBLE 이동과 예산 합. 변형 확인(분기 하나 뒤집으면 실패).
- 1,051건 규모에서 PostgREST 1,000행 제한에 걸리지 않는다(나눠 읽기 등).
- 화면 브라우저 시험 1개(mock 데이터): 요약·순위·가정 켜기 → 숫자 변화. 1440·1280 스크린샷을 `docs/evidence/gaps/20261028/` 에.
- 승률·확률·"수주" 금액 문구 0. `pnpm verify:changed` 통과.

## 6. 파트 B — 발주 현황 `/market`

메뉴: 분석 묶음 "발주 현황". 브랜치 `feat/market-overview`.

### B1. 1단계(지금)

대상: live 공고(`is_demo=false`), 기간 선택(게시일 기준 최근 30·90일, 기본 90일), 기본 거르기는 관련성 `RELEVANT`·`CANDIDATE`, 토글로 끔. 기존 `opportunities` 도메인 집계(`opportunityLiveMetricsSchema` 의 `topAgencies`·`knownBudgetKrw`, `web/server/opportunities/model.ts:114`)를 먼저 재사용한다.

화면:
1. 요약: 기간 내 공고 수·예산 합·마감 미래 공고 수, 기준 시각.
2. 상위 발주기관 10곳(건수·예산 합, CSS 막대).
3. 관련성 카테고리 분포(`bid_relevance_assessments.categories`).
4. 예산 구간 분포(구간은 구현자가 정하고 화면에 적는다).
5. 주별 게시 추이(최근 13주).
6. 마감 다가오는 큰 사업 10건(예산 순, `/bids/[id]?origin=live` 링크).

고정 배지: "나라장터 입찰공고 수집분 기준 · 낙찰·계약 데이터는 수집하지 않습니다 · 발주계획·사전규격 미포함". "시장 점유율·경쟁사" 같은 말을 쓰지 않는다.

### B2. 2단계(파트 A 병합 뒤, 메인 세션이 알림)

기관·카테고리 행에 파트 A 판정 묶음 분포(참가 가능·회사 기록 없음·확인 필요)를 겹쳐 보인다. 파트 A 배럴(`@/server/gaps` 등)만 부른다.

### B3. 수용 기준

- 집계 순수 함수 단위 시험(기간 경계 KST, 관련성 거르기, 예산 null 처리) + 변형 확인.
- 화면 브라우저 시험 1개(mock), 1440·1280 스크린샷 `docs/evidence/market/20261028/`.
- `pnpm verify:changed` 통과.

## 7. 파트 C — 입찰 일정 `/calendar`

## 8. 메인 세션 판단 (2026-10-28 사용자 채택)

1. 판정은 새 규칙이 아니라 기존 `structuredChecks`·`auxLookupChecks` 결과를 묶는다. "자격 미달"은 `NOT_HELD` 기록이 있을 때만 쓴다(Fable 지적, `qualification.ts:119-149` 확인).
2. 면허제한 행이 없고 `auxLookup=OK` 인 공고는 "참가 가능(API 기준)"으로 센다. 첨부 자격 요건은 미반영이라고 늘 밝힌다.
3. 기본 거르기는 관련성 `RELEVANT`·`CANDIDATE`. 토글로 전체.
4. 가정 단위는 자격 코드 사전 9코드(ADR-037 과 같음). 순위 표는 API 업종 이름/코드로 보인다.

6. 발주 예보(발주계획·사전규격)는 live 수집이 꺼져 있어 이번에 하지 않는다.
7. 새 표·마이그레이션 없음. 새 차트·날짜 라이브러리 없음.

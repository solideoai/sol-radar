# 프로필 사진 등록과 명부 연결(신규 입사자·기존 직원)

> 2026-10-24 사용자 대화(Claude Code 세션 81, brainstorming)로 정한 설계다. 구현은 main에 들어갔고 운영에 배포됐다. "사용자 결정"과 "Claude 판단"을 구분해 적는다. Claude 판단은 사용자가 검토 중이며 바뀔 수 있다.

## 1. 의도와 이유

지금은 회원가입·간편 로그인·로그인 뒤 설정 어디에서도 프로필 사진을 올릴 수 없다. 조직도에는 가상 직원 200명과 미리 만든 정장 사진만 보이고, 가입한 사람은 조직도에 나오지 않는다.

사용자가 원하는 그림은 실제 회사처럼 쓰는 조직도다.
- 새로 가입한 사람(신규 입사자)이 자기 사진을 올린다. 조직도의 자기 부서·직급 자리에 새 사람으로 나타난다.
- 기존 가상 직원도 자기 계정으로 들어와 자기 사진을 바꾼다.
- 관리자는 누구의 사진이든 바꾼다.
- 사진은 연결된 Supabase 클라우드 Storage 에 저장된다.

해커톤 시연에 꼭 들어가야 한다(사용자 결정). 기능 동결은 2026-10-24 22:00 이다(ADR-042).

## 3. 목표·비목표·실패 조건

**목표**
- G1 본인 사진 올리기·바꾸기·지우기: 가입 직후 단계와 설정 화면.
- G2 조직도·사람 상세·사이드바 사용자 칸에 올린 사진이 보인다.
- G3 신규 입사자가 승인 뒤 조직도에 새 사람으로 나온다.
- G4 기존 직원 연결 신청 → 관리자 승인·거절.
- G5 관리자가 조직도에서 누구의 사진이든 바꾼다.
- G6 사진 파일은 Supabase 클라우드 Storage 의 비공개 보관함에 저장된다.

**비목표**: 해커톤 범위 밖이다.
- 연결 해제·다른 사람으로 옮기기.
- 명부의 이름·부서·직급 편집. 이것은 N4b 몫이다.
- 사진 자르기 편집기(확대·이동).
- 얼굴 검사·부적절 이미지 자동 판정.
- 200명 자동 계정 만들기. ADR-019 는 그대로 둔다.
- 모바일 화면(ADR-007).

**실패 조건**: 동작하더라도 아래에 하나라도 걸리면 실패로 본다.
- 남의 이름으로 연결을 가로챈다. 관리자 승인 없이 가상 직원이 되면 안 된다.
- 다른 조직 사람이나 로그인하지 않은 사람이 사진을 본다. 공개 URL·공개 버킷도 안 된다.
- 웹 서버가 service role 키를 쓴다(ADR-017·048, `web/app/_lib/deployment-role.ts`).
- 기존 200명 조직도·정장 사진·인력 시뮬레이션·점수(27명)가 깨진다.
- 가입만으로 조직 멤버십이 생긴다(ADR-019 스펙 §3 "가입만으로 멤버십을 부여한다는 뜻이 아니다").

## 4. 현재 코드 사실 (2026-10-24 main `f20cd1e7` 기준 조사)

**조직도·명부**
- 조직도는 `web/app/(app)/org-chart/page.tsx` → `web/server/people/*` → 표 `team_members`(200명)이다. 사진은 `team_members.portrait_path` 의 정적 파일 `web/public/demo/people/SOL-P0001~0200.png` 이다.
- 사진 표시 화이트리스트가 두 곳에 있다: `people.model.ts:183-188`, `web/lib/demo-portrait.ts` + `web/components/people/person-avatar.tsx:12-14`. `memberSchema` 는 `isDemo: z.literal(true)`(`people.model.ts:72`)라서, `is_demo=false` 행이 하나만 있어도 명부 전체 파싱이 실패한다.
- `team_members` 에는 user_id·email 칼럼이 없다. 제약은 `name ~ '^[가-힣]{3}$'`, `unique(org_id,name)`, `gender`·`portrait_path` NOT NULL 이고, 부서는 TEAM 만 허용한다(`20261016000001`, `20261016000003`).
- `team_members` RLS 는 `org_id in my_org_ids()` 읽기만 열려 있다. 화면 역할의 쓰기 권한은 없다.
- 조직도 배치: TEAM 에만 사람이 붙고, 팀 안에서는 `job_titles.sort_order` 다음 이름순이다(`org-chart-model.ts`, `org-chart.tsx:125-130`). 사람 상세는 `person-drawer.tsx` → `/api/v1/team-members/{id}` 이다.
- `scripts/demo-reset.mjs:159-166` 은 fixture 밖 `person_code` 행을 지우고, 요약은 `people=200` 을 기대한다.
- 인력 시뮬레이션·점수는 `team_member_scoring` 기준이다. 점수 행이 없는 새 사람은 후보가 아니다.

**계정·가입**
- `profiles.avatar_url` 이 이미 있다. 제약은 `^https://` 이고, 간편 로그인 제공자 사진을 트리거가 채운다. 화면 역할의 UPDATE 권한은 없다.
- 설정의 문구는 "사진은 처음 가입한 로그인 수단의 것을 쓰며, 여기서 바꿀 수 없습니다"(`web/app/account/account-settings.tsx:133`)다.
- 이메일 가입은 클라이언트 `auth.signUp` 이다(`sign-up-form.tsx:81`). 메일 확인이 켜져 있어(`supabase/config.toml:61`) 가입 직후 세션이 없다.
- 메일 확인 뒤 흐름은 `/auth/confirm` → `afterEmploymentAuthentication` 이다. 조직이 없으면 `/auth/organization-state` "조직 초대가 필요합니다"로 간다.
- 간편 로그인 첫 진입은 `/auth/complete-profile` 이다. 부서·직급은 `PATCH /api/v1/me/employment` 로 저장한다.
- 조직 소속은 초대 수락으로만 생긴다(`20261019000001:120-171`, `web/app/invitations/*`). 솔리데오는 org-01, UUID `db4c863c-cb6a-593d-93ff-709a17e0157a` 다.
- `admin@admin.com` 은 org-01 `org_role owner` + `sol_role ADMIN` 이고 `is_admin` 이 아니다. ADMIN 화면은 `web/app/(app)/(work)/settings/organization/page.tsx` 이다(구성원·sol_role·초대·감사 기록). 왼쪽 아래 UserMenu '설정'은 `/${slug}/settings` → `AccountSettings` 로 간다.

**Storage·보안**
- 버킷은 `bid-documents`·`bid-parsed` 두 개이고 둘 다 private 이다. 버킷은 SQL 이 아니라 운영 스크립트 `scripts/ops/ensure-storage-buckets.mjs` 가 만든다(service role, `--apply`, public 거부, MIME·크기 제한).
- 웹은 사용자 JWT 로 signed URL 만 만든다(`web/server/documents/documents.repo.ts`). `storage.objects` 정책은 SELECT 하나뿐이고 사용자 업로드 예는 없다.
- CSP `img-src` 는 `'self' blob: data:` + 구글·카카오·네이버 CDN 이다(`web/server/csp/csp.model.ts:18-22,66`). Supabase 출처가 없다. 아바타는 next/image 가 아니라 `<img>` 다.

## 5. 설계 (사용자 결정 + Claude 판단)

### 5.1 흐름

**가입 신청 단계** (Claude 판단 C1·C2)
- 이메일 가입 폼은 지금처럼 이름·부서·직급·이메일 등을 받는다.
- 사진과 "신규 입사자/기존 직원" 선택은 **메일 확인 뒤 첫 로그인 때 나오는 가입 신청 화면**에서 받는다. 가입 폼 단계에는 세션이 없어 본인 권한으로 업로드할 수 없기 때문이다.
- 간편 로그인 첫 진입은 지금의 `/auth/complete-profile` 을 이 화면으로 확장하거나 같은 부품을 쓴다.
- 이 화면은 조직이 없는 계정도 열 수 있어야 한다(`/auth/*` 쪽).

**가입 신청 화면의 내용**
- 신규 입사자: 부서·직급(이메일 가입자는 미리 채워짐) + 사진(선택) → "가입 신청".
- 기존 직원: 부서 선택 → 이름 입력. 그 부서에 이름이 **정확히 일치하고 아직 연결되지 않은** 가상 직원이 있을 때만 그 사람 카드 하나(이름·직급·사진)를 보여 준다 → "본인 맞음, 연결 신청". 부서 명부 전체 목록은 보여 주지 않는다(C3).
- 사진은 선택 사항이다. 건너뛰어도 신청할 수 있다(C4).
- 신청 뒤 화면은 "관리자 승인 대기 중"이다. 지금의 "조직 초대가 필요합니다" 화면 자리를 쓴다. 대기 중에도 설정(`/auth/account`)에서 사진을 바꿀 수 있다.
- 반려되면 반려 상태를 보여 주고 다시 신청할 수 있다(C5).
- 이미 초대를 받은 사람은 지금처럼 초대 수락으로 들어간다. 초대 흐름은 바꾸지 않는다.

**이미 조직에 있는 계정** (U10)
- `admin@admin.com`, seed 계정, 초대로 들어온 사람이 대상이다.
- 설정 프로필 칸에 "조직도에 나를 추가·연결" 신청 진입점을 둔다. 신청 내용은 가입 신청 화면과 같다(신규 입사자 또는 기존 직원 연결).
- 이미 멤버이므로 승인 때 멤버십은 새로 만들지 않고, 조직도 연결만 한다. 업무 역할(sol_role)도 바꾸지 않는다.
- 관리자는 자기 신청을 바로 승인할 수 있다.
- 조직도에 연결되지 않은 기존 계정도 사진은 올릴 수 있다. 사이드바·설정에만 보인다.

**관리자 승인** (U5·U6, Claude 판단 C6·C7)
- 신규 입사자도 관리자 승인을 거친다(C6). 가입만으로 멤버십을 주지 않는다는 기존 원칙(ADR-019 스펙 §3) 때문이다.
- 승인 화면은 sol_role ADMIN 의 `/settings/organization` 안 "가입 신청" 표다. 표는 신청 종류·이름·부서·직급·연결 대상·사진을 보여 주고, 승인·거절 버튼이 있다.
- 승인할 때 업무 역할(sol_role)을 고른다. 기본값은 VIEWER 다(C7).
- 승인은 한 트랜잭션으로 처리한다.
  - org-01 멤버십을 만든다.
  - 기존 직원이면 `team_members` 행에 계정을 연결한다. 부서·직급은 명부 값을 따른다(U6).
  - 신규 입사자면 `team_members` 에 새 행을 만든다(C8).
  - 감사 기록을 남긴다.
- 한 가상 직원에게는 계정 하나만 연결된다. 같은 사람에게 대기 신청이 둘이면 먼저 승인된 것만 성공하고 나머지는 실패한다.

**사진 바꾸기**
- 본인: 설정(`AccountSettings`, `/${slug}/settings` 와 `/auth/account`)의 프로필 칸에서 올리기·바꾸기·지우기. "여기서 바꿀 수 없습니다" 문구를 없앤다.
- 관리자: 조직도 사람 상세(`person-drawer`)에 ADMIN 에게만 "사진 변경·지우기" 버튼을 둔다. 연결 여부와 관계없다(U4·U6).
- 연결된 사람은 계정 사진과 조직도 사진이 늘 같다(C9). 본인이 바꾸든 관리자가 바꾸든 둘 다 바뀐다.

### 5.2 사진 표시 우선순위 (Claude 판단 C10)

| 대상 | 1순위 | 2순위 | 3순위 | 마지막 |
|---|---|---|---|---|
| 가상 직원(연결 여부 무관) | 올린 사진 | 기존 정장 사진 | — | 머리글자 |
| 신규 입사자 | 올린 사진 | 간편 로그인 제공자 사진 | — | 머리글자 |
| 사이드바·설정의 본인 | 올린 사진 | (연결된 가상 직원이면) 정장 사진 | 제공자 사진 | 머리글자 |

"지우기"는 올린 사진만 지운다. 그 뒤에는 다음 순위가 보인다.

### 5.3 저장소 (Claude 판단, 세부는 구현자 몫)

**Storage 버킷**
- 새 private 버킷 `profile-photos` 를 만든다.
  - MIME: `image/jpeg`·`image/png`·`image/webp`.
  - 크기 제한: 2MB.
  - 생성: `scripts/ops/ensure-storage-buckets.mjs` 에 추가한다. 클라우드 실행은 사용자 확인 뒤에 한다.
- 브라우저에서 정사각형 가운데 자르기 + 512px 축소를 한 뒤 올린다(C11).
- 경로 규칙: 본인 업로드는 `users/{auth.uid()}/…`, 관리자 업로드는 `members/{team_member_id}/…`. 이름 대신 UUID 를 쓰고, 덮어쓰기 대신 새 파일 + 포인터 교체로 한다(캐시 무효화).

**`storage.objects` 정책** (사용자 JWT 기준)
- INSERT·DELETE: `users/{uid}` 는 본인만, `members/{id}` 는 그 사람 조직의 sol_role ADMIN 만.
- SELECT: 본인 파일, 그리고 내가 활성 멤버인 조직의 사람에게 연결된 파일만.
- 웹은 서버에서 사용자 JWT 로 signed URL 을 만든다(만료 1시간 안팎, 조직도는 `createSignedUrls` 한 번에 묶어서).
- CSP `img-src` 에 이 Supabase 프로젝트 Storage 출처를 더한다.

**DB** (새 마이그레이션만, append-only)
- 가입 신청 표를 새로 만든다. 칼럼은 신청자, org, 종류(NEW_HIRE/EXISTING), 대상 team_member, 부서, 직급, 상태(PENDING/APPROVED/REJECTED), 결정자, 시각이다. 표는 만들자마자 잠근다.
  - 본인은 자기 신청을 읽는다.
  - ADMIN 은 자기 조직 신청을 읽는다.
  - 쓰기는 security definer RPC 로만 한다. 신청, 승인, 거절, 기존 직원 이름 일치 확인이다.
- `team_members` 에 칼럼을 더한다.
  - `user_id`: nullable, unique, profiles FK.
  - 사진 포인터: Storage 경로, nullable.
- 신규 입사자 행(`is_demo=false`)을 위해 이름 3자·성별·정장 사진 NOT NULL 제약을 가상 직원 행에만 걸도록 고친다. `person_code` 는 가상 직원과 겹치지 않는 별도 대역을 쓴다.
- `profiles` 사진 포인터를 본인이 바꾸는 RPC(경로가 `users/{uid}/` 인지 확인)와, ADMIN 이 사람 사진을 바꾸는 RPC 를 둔다. 연결된 사람은 두 포인터를 함께 바꾼다. 기존 `avatar_url`(제공자 사진, https 제약)은 그대로 둔다.
- `pnpm db:types` 로 타입을 다시 만들고, RLS·RPC 정책 시험을 `scripts/database.test.mjs` 에 더한다.

**화면 코드**
- `memberSchema` 의 `isDemo` 리터럴과 사진 화이트리스트를 "정장 사진 경로 또는 signed URL" 을 받도록 고친다. 정적 정장 사진의 경로 검사는 유지한다.
- 조직도·명부 요약 인원 수는 200 + 승인된 신규 입사자다.

**Claude 판단 C13~C15** (검토자 질문 중 구현자가 정해도 되는 것)
- C13 신규 입사자 이름: `unique(org_id,name)` 와 한글 3자 제약은 가상 직원 행(`is_demo=true`)에만 건다. 신규 입사자 이름은 계정 표시 이름을 쓰고 같은 이름을 허용한다. 화면에서는 부서·직급으로 구분한다.
- C14 승인 대기자의 사진: 관리자가 승인 표에서 볼 수 있도록, Storage SELECT 정책에 "내가 ADMIN 인 조직에 대기 신청을 낸 사람의 `users/{uid}/` 파일"을 더한다.
- C15 ADR: 이 문서의 승인을 ADR-019 개정 ADR 제안의 승인으로 본다(ADR-037 선례). 승인 뒤 `docs/16-DECISIONS.md` 에 새 ADR 을 채택으로 적는다.

### 5.4 구현 순서와 빼는 순서 (U8)

1. 사진 저장 기반: 버킷, Storage 정책, 사진 포인터, 표시 우선순위, CSP.
2. 본인 사진: 설정에서 올리기·바꾸기·지우기, 사이드바.
3. 신규 입사자: 가입 신청 화면(간편 로그인 첫 진입 + 메일 확인 뒤 첫 로그인), 관리자 승인 표, 조직도 새 사람.
4. 관리자 사진 변경: 조직도 사람 상세.
5. 이미 조직에 있는 계정의 신청(설정 진입점, U10).
6. 기존 직원 연결: 이름 일치 확인, 연결 신청, 승인 경쟁 처리. **시간이 모자라면 이것부터 뺀다.**

시연 E2E 는 간편 로그인 신규 입사자 경로 하나다(U9). 테스트 환경에서는 간편 로그인 대신 같은 미완료 프로필 상태를 만들어 쓴다.

### 5.5 시연 초기화 (Claude 판단 C12)

`pnpm demo:reset` 은 처음 상태(가상 직원 200명, 정장 사진, 연결 0, 신청 0)로 되돌린다. 하는 일은 다음과 같다.
- 신규 입사자 행 삭제.
- 연결 해제.
- 신청 삭제.
- 사진 포인터 비우기. Storage 파일 삭제는 같은 스크립트에서 하거나 남겨도 된다(구현자 몫).

리허설 뒤 실제 가입 계정(Auth)을 지울지는 기존 reset 규칙을 따른다. 시연 전에 연결된 계정을 미리 만들어 두지 않는다. 시연은 reset 된 처음 상태에서 현장에서 진행한다.

## 6. 제약

- 기술 스택은 Next.js 16 + Supabase(Postgres·RLS·Auth·Storage)다. 웹 서버·클라이언트에서 service role 을 쓰지 않는다. Storage 쓰기는 사용자 JWT + 정책이나 security definer RPC 로 한다.
- 웹 코드를 쓰기 전에 `web/node_modules/next/dist/docs/` 를 확인한다. 서버 코드는 `web/server/<도메인>/`(model·repo·service·index) 구조를 따른다.
- 마이그레이션은 새 파일로만 쌓는다. 클라우드 적용(`pnpm db:push`)과 버킷 생성(`--apply`)은 사용자 확인 뒤에 한다. 이때 대기 중인 다른 마이그레이션 13개와 메일 마이그레이션도 함께 올라간다(U11). 직전에 목록을 보여 주고 확인받는다.
- 화면은 데스크톱 1280px 이상이다. 1440·1280 두 폭으로 확인한다. 색·글꼴은 `design/tokens.json`, 부품은 `web/components/ui/` 를 쓴다.
- 시험은 MVP 핵심만 한다(ADR-046). 정책 시험(Storage·RPC·RLS), 승인 경쟁 1건, 가입 → 신청 → 승인 → 사진 → 조직도 표시 E2E 1개.
- 시간: 2026-10-24 22:00 기능 동결(ADR-042)까지 green 이어야 한다. 그 전에 클라우드 DB·버킷 적용까지 마쳐야 시연에 쓸 수 있다.
- ADR: ADR-019(명부와 Auth 계정 분리)를 고치는 새 ADR 을 "제안"으로 올린다. 사용자가 채택한다.

## 7. 구현자에게 맡기는 것

- 가입 신청 화면을 `/auth/complete-profile` 확장으로 할지, 새 경로로 할지.
- 표·RPC·칼럼 이름, 신규 입사자 `person_code` 대역 형식.
- signed URL 만료 시간, 조직도 URL 묶음 방식.
- 브라우저 축소 구현(canvas 등). 새 패키지가 필요하면 먼저 알린다.
- Storage 고아 파일 정리 시점.

# 솔리데오 가상 직원 200명·프로필 이미지·가입 정보

## 1. 목적과 현재 상태

솔리데오의 부서 구성을 바탕으로 데모용 가상 직원 200명을 만들고, 가입자가 같은 부서·직급/직책 목록을 선택하도록 한다. 인력 명부와 로그인 계정은 별개다. 사용자 인터뷰와 대화 설계는 2026-10-16 승인되었으며, 이번 작업은 문서 반영이다. JSON 명부·이미지·DB migration·가입 폼은 후속 구현 대상이다.

기존 저장소에는 인증·가입 폼이 있으나 부서·직급 필드는 없다. `team_members`와 SOL RADAR용 seed도 아직 구현 전이다. 이 문서는 구현 완료를 뜻하지 않는다. 제품·보안·스코어 규칙의 정본은 `docs/00-README.md`~`docs/20-GLOSSARY.md`이며, 이번 결정은 `docs/16-DECISIONS.md` ADR-019에 반영한다.

## 3. 범위와 비목표

구현 범위는 부서·직급 카탈로그, 가상 직원 200명의 명부, imagegen 생성 계획과 200개 최종 이미지, DB seed, 가입·추가 정보 입력 및 조회 계약이다. 문서 작업 이후 별도의 구현 계획과 검증을 거친다.

이번 문서 단계에서 이미지 생성·DB 적용·가입 폼 코드를 실행하거나 수정하지 않는다. 다중 회사 선택, 가상 직원 200명 자동 가입, 원본 인물 식별 정보·사진 이식, 인력 자동 배정·추천은 범위 밖이다. 기존 인력 배정 API/화면은 P1이고, 모바일·결제는 계속 제외한다.

솔리데오는 실제 회사명이다. 부서·직급 명칭을 제외한 직원 이름·얼굴·실적·자격·재무·가용 인력 수치는 데모용 가상 설정이며 회사의 실제 현황으로 소개하지 않는다. `org-01`을 솔리데오 업무 조직으로 사용하고 `org-02`는 숨겨진 RLS 격리 시험용 조직으로만 남긴다. 회사 고정은 RLS를 없애거나 가입만으로 멤버십을 부여한다는 뜻이 아니다.

`personId`는 `SOL-P0001`~`SOL-P0200`으로 고정한다. JSON의 ID·DB seed UUID 매핑·이미지 파일명을 같은 인물에 연결한다. 재실행으로 이름이나 부서가 바뀌어도 ID를 무작위로 다시 만들지 않는다. 부서 ID·직급 ID 역시 표시 이름과 분리한 안정적인 코드다. 생성 이후 정본 JSON을 코드·DB·화면이 함께 사용하며 화면에 별도 선택 목록을 하드코딩하지 않는다.

가상 공개 이미지에는 정적 파일 방식이 가장 단순하다. MinIO 방식도 검토했으나 공개 가상 이미지에 사용자별 다운로드 처리를 추가하지 않기로 했다. 이 결정은 공고 첨부·기밀 파일의 MinIO 사설 저장 원칙을 바꾸지 않는다. 실제 로그인 사용자 `profiles.avatar_url`의 HTTPS 제약도 바꾸지 않으며, 가상 사진은 `team_members`의 전용 자산 경로로 연결한다.

## 5. 엑셀 해석과 배분

`people` 시트는 병합 셀과 반복된 팀 구역을 포함한 조직도 형식이다. 행 전체를 일반 표로 읽거나 전화·주소를 이름으로 오인하지 않는다. 확인된 이름/직급 열 쌍은 A/B, E/F, I/J, M/N이다. 추출기는 이름 오른쪽 직급과 팀 제목의 셀 범위를 함께 사용한다.

확인된 직급/직책 표현은 `CFO`, `사장`, `부사장`, `이사`, `본부장`, `그룹장`, `팀장`, `소장`, `수석`, `책임`, `담당`, `인턴`이다. 이 목록의 순서는 업무 권한이나 직급 서열을 뜻하지 않는다. 본부·그룹·팀·근무지 제목은 구분하고, 주소·전화·근무지 설명을 가입 부서로 만들지 않는다. 2026-10-16 추가 인터뷰에서 사용자는 **팀명이 명시된 행만 배분 가중치에 사용**하고, 팀이 없는 임원·본부·그룹·프로젝트 구역은 배분에서 제외하기로 선택했다. 원본 전체 이름은 제외 집합에 계속 포함한다. 근무지 제목은 팀을 바꾸지 않지만, 팀명 없는 새 조직·프로젝트 제목에서 앞선 팀을 임의 상속하지 않는다. 승인된 제외 구역은 익명 셀 범위·건수로 기록하며, 팀 범위/제외 범위 어느 쪽에도 분류되지 않은 인력 행은 추출 오류로 보고한다. 카탈로그 작성 단계에서 원본의 팀명과 범위를 대조한다.

같은 팀명은 앞뒤 공백을 제거한 뒤 정확히 같은 문자열끼리 합산한다. 내부 공백·영문 대소문자·팀명을 임의 변경하거나 비슷한 이름을 자동 병합하지 않는다. 직원 중복 이름만으로 동일 인물이라고 판정하지 않는다. 원본 부서별 인력 행 수는 배분 가중치이며 실제 고유 임직원 수라고 발표하지 않는다.

배분 알고리즘은 다음과 같이 결정적으로 고정한다.

1. 고유 팀 수를 D, 팀별 원본 가중치를 w, 전체 가중치를 W라 둔다. D가 1~200 범위가 아니거나 w가 0 이하인 팀이 있으면 중단한다.
2. 각 팀에 1명을 배치한다. 남은 `200 - D`명을 `q = (200 - D) * w / W`로 나눈다.
3. 각 팀에 `floor(q)`명을 더하고, 남은 자리는 q의 소수 부분이 큰 팀부터 1명씩 배치한다. 동률은 부서 ID 오름차순으로 해소한다.
4. 부서별 직급 구성은 해당 부서 원본의 직급 비율에 최대 나머지 방식으로 맞추며 동률은 직급 ID 오름차순으로 해소한다. 최소 직급별 1명 조건은 추가하지 않는다. 선택 카탈로그는 원본의 12개 표현을 모두 유지한다.
5. 각 팀 남성 수의 기본값은 `floor(targetCount / 2)`다. 남성 합계가 100명이 되도록 나머지가 큰 팀부터 보충하며 동률은 부서 ID 순으로 해소한다. 나머지는 여성으로 두어 총 100명씩 맞춘다. 성별 설정은 직급·업무 권한·점수에 사용하지 않는다.

## 6. 자연스러운 이름과 원본 이름 제외

2026-10-16에 직접 확인한 이름 후보 출처는 [네임차트 남성 이름 통계](https://www.namechart.kr/chart/2008?gender=m)와 [네임차트 여성 이름 통계](https://www.namechart.kr/chart/2008?gender=f)다. 이 자료는 두 글자 이름의 실제 사용 여부를 참고하는 자료이며 직원의 생년·나이 또는 특정 실존 인물의 성명을 가져오는 자료가 아니다.

통계에 있는 자연스러운 두 글자 이름과 일반적인 한 글자 한국 성씨를 조합한 후보에서 고른다. 임의 음절 조합·번호 접미사·직무를 붙인 이름은 사용하지 않는다. 최종 이름은 `^[가-힣]{3}$`, 고유 이름 수 200, 원본 이름과의 교집합 0을 모두 통과해야 한다.

원본 이름 제외 검사는 로컬에서 원본의 모든 이름 셀을 다시 읽어 수행한다. 공백·괄호 메모 등 표기 부가분을 제거한 이름도 제외 집합에 넣는다. 제외 집합·원본 이름·전화번호·주소·원본과 가상 인물의 대응표는 JSON·문서·이미지 프롬프트·로그에 저장하지 않는다. 증거에는 입력 파일 해시와 일치 건수 0만 남긴다. 원본 입력이 없으면 이 검사를 통과한 것으로 처리하지 않는다.

검사를 통과한 후보도 사람이 읽어 어색한 조합을 제외하고, 같은 ID에 이름을 확정해 재생성 때 흔들리지 않게 한다. 일반적인 한국 이름이므로 원본 밖의 모든 실존 인물과 동명이인이 없다고 보장하지 않는다.

## 7. 프로필 이미지 생성

imagegen 스킬의 기본 내장 `image_gen`을 사용한다. `bulk`는 200개의 개별 인물 작업을 뜻하며, 연락처 시트·콜라주 한 장이나 동일 얼굴 복제를 뜻하지 않는다. 남성·여성 100개씩의 인물별 프롬프트와 생성 상태를 manifest로 관리하고 실패한 ID만 다시 생성한다. API/CLI 모드로 자동 전환하지 않는다. CLI/API가 필요하면 해당 경로와 비용을 별도로 설명하고 명시적으로 선택받는다.

공통 프롬프트 기준은 가상의 성인 한국인 직장인, 정장, 실사 프로필 사진, 정사각형, 얼굴과 어깨가 보이는 구도, 일관된 밝은 중립 배경과 부드러운 조명이다. 각 얼굴·헤어스타일·성인 연령대·정장 세부는 다양하게 구성한다. 원본 인물 사진이나 유명인 얼굴을 참조하지 않고, 이름·회사 로고·워터마크는 이미지에 넣지 않는다.

내장 도구의 기본 저장 위치는 `$CODEX_HOME/generated_images/...`다. 생성 뒤 선택된 최종 PNG를 승인된 프로젝트 경로로 복사한다. 도구에 목적지 경로 인자가 있다고 가정하지 않으며, 프로젝트가 Codex 캐시 경로를 직접 참조하지 않게 한다. 정장·구도·인원 1명·서로 다른 얼굴을 검수하고 이미지 해시 중복도 검사한다. 해시가 다르다는 사실만으로 서로 다른 얼굴이라고 판단하지 않는다. 기존 확정 파일은 재시도 중 덮어쓰지 않고 새 후보를 검수한 뒤 교체한다.

완료 전까지 manifest는 `PLANNED / GENERATED / READY / FAILED`로 진행 상태를 구분한다. 최종 완료는 READY 200건·고유 이미지 경로/해시 200개·남녀 각 100건이다. 생성 사진을 실제 임직원 사진으로 소개하지 않고 가상 인물/DEMO 표시를 유지한다.

## 8. 가입·저장·권한 경계

가입 화면의 회사 표시와 선택 카탈로그는 솔리데오 고정이다. 이메일 가입 폼의 이름 가까이에 `부서`, `직급/직책` 필수 선택을 추가한다. 자유 입력·빈 항목·알 수 없는 ID를 허용하지 않는다. 실제 가입자의 이름에는 가상 명부 전용인 세 글자 정규식을 새로 강제하지 않는다.

가입 선택 카탈로그는 승인된 부서·직급 JSON에서 얻으며 공개 응답은 ID·표시명·카탈로그 버전·고정 회사명만 포함한다. 원본 가중치·배정 인원·인물 이름·사진 manifest는 공개 가입 응답에서 제외한다. 정식 계약은 `docs/05-API-SPEC.md`의 `GET /api/v1/signup-options`다.

Supabase Auth 이메일 가입 메타데이터에 이름과 `department_code`, `job_title_code`를 전달한다. 새 migration의 가입 트리거는 허용 카탈로그를 확인해 `profiles.declared_department_id`, `profiles.declared_job_title_id`로 저장한다. 두 값은 **가입자 신고 정보**이며 조직 멤버십의 부서 배치나 업무 권한이 아니다. 값을 바꾸어 `org_role`, `sol_role`, `is_admin`, 조직 접근 권한을 얻을 수 없다. Auth 메타데이터 자체를 권한 근거로 사용하지 않는다.

OAuth는 가입 폼을 건너뛸 수 있으므로 DB의 두 열은 처음에 null을 허용한다. 서버에서 이름·두 선택값을 검증하기 전에는 `/auth/complete-profile`로 보내고 업무 화면 및 업무 API는 차단한다. 기존 사용자 중 정보가 없는 사람도 같은 흐름을 거친다. 추가 정보 조회/저장 계약은 이름도 포함한다. 이름은 기존 표시 이름 규칙(1~40자)으로 검증해 부서·직급과 함께 원자적으로 저장한다. 추가 정보 저장은 세션 + RLS로 본인만 가능하며 실패하면 입력을 유지하고 재시도한다. 로그아웃·추가 정보 입력·초대 안내 등 계정 정리에 필요한 경로는 허용해 반복 이동을 막는다. 입력 완료만으로 솔리데오 조직에 자동 합류하지 않고 기존 초대·RLS 검증을 따른다.

`departments`·`job_titles`는 `org_id`를 갖는 카탈로그 표로 seed가 쓴다. profiles의 두 신고 FK는 `ON DELETE SET NULL`로 하여 데모 카탈로그 삭제가 기존 가입 계정 삭제나 초기화 실패로 이어지지 않게 한다. 해당 값이 비면 다음 업무 진입에서 필수 정보 보완을 요구한다. 부서·직급은 `team_members`에도 연결하되, `team_members.role`(PM/개발 직무), `grade`(기술등급), `memberships.sol_role`(업무 권한)과 구분한다. 가상 명부는 로그인 사용자와 자동 매칭하지 않으며 200명이 Auth 생성으로 이어지는 코드 경로를 두지 않는다. `profiles.avatar_url`에 가상 사진 상대경로를 넣지 않는다.

## 9. 기존 점수·데모 정합성

솔리데오 데모의 전체 인력 명부와 `financials.employeeCount`는 200으로 통일한다. 기존 문서의 인력 seed 6명·전체 임직원 120명 표기는 폐기한다. 기술/자격/실적/매출은 검증된 실기업 정보가 아니라 기존 가상 점수 예시 데이터임을 명시한다.

200명을 모두 투입 가능 인력으로 간주하지 않는다. 기존 점수 예시의 PM 2·PL 4·개발 18·데이터/AI 3, 총 27명은 명부 200명 안의 가상 점수 계산 대상 하위 집합이다. `scoringEligible`로 명시하고 나머지 173명은 계산 대상에서 제외한다. 2026-12~2027-06 구간 가용 20 FTE를 보존한다. 이는 원본 조직도에서 추정한 실제 직무·가용성이 아니다. 기존 FX-01/02/03의 94/72/68과 권고 BID/WATCH/NO-BID를 골든으로 검증한다. 입력 스냅샷 `team.members`에는 계산 대상 ID·직무·기술등급·스킬·가용성, `team.assignments`에는 기간 배정, `team.asOf`에는 고정 기준 시각을 보존한다.

기존 seed 로그인 5계정은 그대로 별도 유지한다. 문서의 `org-01`은 고정 seed slug이고 실제 DB ID는 UUID다. 회사 고정 후에도 `org-02` 격리 시험과 RLS는 유지한다. 사용자에게 회사 선택·조직 생성·조직 전환 UI를 제공하는 범위는 이번 요구에서 제외하며, 템플릿 개인 조직의 물리적 정리는 기존 Phase 1 migration 검토 대상이다.

## 10. 후속 구현 순서와 완료 기준

| 순서 | 후속 산출물 | 기계적으로 검증할 조건 |
|---|---|---|
| 1 | 부서·직급·200명 이름 fixture | 합계 200, 팀마다 1명 이상, 승인 배분 알고리즘 일치, 남녀 100/100, 이름 고유 200·세 글자·원본과 교집합 0, 모든 참조 ID 유효 |
| 2 | 인물별 프롬프트·이미지 | READY 200, 경로·해시 고유 200, 파일 존재·정사각형·PNG, 남녀 100/100. 서로 다른 얼굴·정장·품질은 사람 검수 기록 |
| 3 | DB 카탈로그·신고 정보·인력 seed | append-only migration, RLS·허용 값·본인 쓰기·권한 상승 거부·다른 조직 0행, 2회 seed 후 200명/5계정 동일 |
| 4 | 가입·추가 정보 입력 | 이메일 누락/위조 거절, OAuth·기존 미완료 사용자 보완, 미완료 업무 화면/API 차단, 완료·재로그인 후 값 유지, 회원 가입이 Auth 200계정 생성으로 이어지지 않음 |
| 5 | 통합 | `pnpm verify`, 가입 관련 브라우저/E2E, 점수 골든 94/72/68, 1440·1280 화면·키보드 조작 검증 |

구현 계획은 이 문서 검토 후 별도로 작성한다. 최종 검증 파일·명령 매핑은 `docs/11-TESTING.md`에 둔다. 이 문서 단계의 검증은 요구사항 추적·문서 링크·원본 이름 비포함·기존 문서 정합성 및 저장소 검증 결과다.

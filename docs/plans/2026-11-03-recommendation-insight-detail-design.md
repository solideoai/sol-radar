### 1.2 한계 [사실]

- 운영·로컬 화면을 브라우저로 열어 보지 않았다. 구조는 코드에서 읽었다. 폭별 모양은 구현 뒤 QA 가 360·390·768·1280·1440px에서 확인한다.
- 새 칸 3개의 필드 이름은 스펙 미결정 1이다. 그래서 이 문서는 요소 해설, 자격 해설, 확인할 것이라는 뜻 이름으로 쓴다.
- 문서와 코드가 한 곳에서 다르다. `docs/06-UI-UX.md:134` 는 움직임 줄이기에서도 회전 아이콘을 남기지만, 지금 코드는 회전을 끈다(`recommendation-insight.tsx:98-99`). 이 문서는 코드 쪽을 따른다(7.4).

## 2. 흐름 [제안]

```
상세 화면 구역의 버튼
 ├─ 결과 없음 + 요청 가능 역할 → 팝업 열림과 함께 요청 → 진행 0% … 99% → DONE → 100% 잠깐 → 내용
 │                                                       ├─ 3분 넘음 → 99% 멈춤 + 늦음 안내 + [다시 확인]
 │                                                       └─ FAILED → 실패 안내 + [다시 요청]
 ├─ 진행 중(이미 누가 요청함) → 팝업 열림 → 지금 진행률에서 이어 보임
 └─ 결과 있음 → 팝업 열림 → 바로 내용
```

1. 요청·묻기 상태(`useInsightRequest`)는 지금처럼 상세 화면 구역 컴포넌트가 갖고, 팝업은 그 아래에서 그린다. Base UI 팝업은 닫히면 내용을 내리기 때문에, 상태를 팝업 안에 두면 닫는 순간 묻기가 끊긴다. 이렇게 두면 팝업을 닫아도 요청과 묻기가 이어지고, 다시 열면 같은 숫자에서 이어진다.
2. [추천 분석]은 한 번의 클릭으로 팝업을 열고 요청도 보낸다(스펙 3절 1번). 요청 뒤 구역 버튼은 [추천 분석 보기]로 바뀌고, 누르면 팝업만 연다. 그래서 두 번 눌러도 요청이 두 번 가지 않는다. 훅의 Idempotency-Key 는 그대로 둔다.
3. 진행 중에 팝업을 닫거나 Esc 를 눌러도 분석은 이어진다. 진행 중 닫기를 막지 않는다.
4. 결과를 받은 순간 팝업이 열려 있으면 100%를 보인 뒤 내용으로 바꾼다. 닫혀 있으면 구역만 바뀐다.
5. 팝업을 닫으면 초점이 그것을 연 구역 버튼으로 돌아간다.

## 3. 상세 화면 구역

### 3.1 배치 [제안]

```
추천 분석                                                  h2 type-heading (지금 그대로)
판정은 규칙 엔진이 하고, 최종 참여 결정은 사람이 합니다.        caption muted (지금 그대로)
11월 3일 14:20 작성                                         상태 줄: type-label muted, role="status"
필수 자격을 모두 충족했고 과거 수행 사업이 공고 범위와 겹칩니다.   첫 문장: type-body, line-clamp-3
[추천 분석 보기]                                             Button outline sm, 왼쪽 정렬
```

- 간격은 제목과 고지 사이를 지금 그대로 두고, 고지와 상태 줄 사이 `mt-3`, 상태 줄과 첫 문장 사이 `mt-1`, 첫 문장과 버튼 사이 `mt-3` 이다.
- 칩·목록·근거는 구역에 두지 않는다(스펙 3절 2번).
- 이 화면의 기본(default) 버튼은 [분석 실행]·[재분석]이다(`docs/06-UI-UX.md` §5.5). 그래서 구역 버튼은 outline 이다.
- 버튼은 상태마다 글자만 바뀌는 같은 요소 하나다. 팝업을 닫을 때 이 요소로 초점을 돌리기 때문이다(9절).
- 첫 문장은 판단 이유(summary)에서 처음 나오는 "." 까지다. 단 그 "." 뒤가 공백이거나 글 끝일 때만 문장 끝으로 본다. 그래서 "3.5" 같은 숫자는 자르지 않는다. 그런 "."이 없으면 summary 전체를 쓴다. 긴 문장은 `line-clamp-3` 으로 세 줄에서 자른다.
- 모든 폭에서 한 열이다. 767px 이하에서는 버튼이 44px 높이가 된다(`button.tsx`).

### 3.2 상태표

| 상태 | 언제 | 보이는 것 | 사용자가 할 수 있는 것 |
|---|---|---|---|
| 없음·요청 가능 | 이 run 에 추천 분석 행이 없고, 역할이 ADMIN·SALES·ANALYST | 상태 줄 C3 | [추천 분석]을 누르면 팝업이 열리고 요청이 간다 |
| 없음·읽기 전용 | 행이 없고, 역할이 EXECUTIVE·VIEWER | 상태 줄 C4 | 없음 |
| 진행 중 | `requesting`·`polling`, 또는 서버가 PENDING 을 줌 | 회전 아이콘 + C5. 퍼센트는 구역에 넣지 않는다 | [추천 분석 보기] |
| 늦어짐 | `delayed` | C6 | [추천 분석 보기]. [다시 확인]은 팝업 안에 있다 |
| 완료 | DONE. MODEL·TEMPLATE·Mock·옛 형식 모두 해당 | 작성 줄 C8 + 판단 이유 첫 문장 | [추천 분석 보기] |
| 실패·요청 가능 | FAILED, 요청 가능 역할 | C7 | [다시 요청]을 누르면 팝업이 열리고 요청이 간다 |
| 실패·읽기 전용 | FAILED, 읽기 전용 역할 | C7 | 없음 |

- 상태 줄은 polite 알림 영역이다. 글자는 상태가 바뀔 때만 바뀐다.
- 퍼센트를 구역에 넣지 않으면 매초 바뀌는 숫자가 한 곳에만 있게 되고, `%` 예외도 팝업 진행 표시 한 곳으로 좁아진다.

## 4. 팝업 틀

### 4.1 폭별 형태 [제안]

| 폭 | 형태 | 크기 | 모서리·선 | 안쪽 여백 |
|---|---|---|---|---|
| 768px 이상 | 가운데 팝업 | 너비 `md:max-w-2xl`(672px), 높이 `md:h-[min(48rem,calc(100dvh-2rem))]` 고정 | `rounded-xl`, `ring-1 ring-foreground/10`, 그림자 없음(지금 부품 그대로) | 좌우 24px(`px-6`) |
| 767px 이하 | 전체 화면 | `max-md:inset-0 max-md:h-dvh`, 너비·높이 상한 없음, 이동(translate) 없음 | `max-md:rounded-none max-md:ring-0` | 좌우 16px(`px-4`) |

- 672px 를 고른 이유: 본문 폭이 약 624px 이 되어 14px 한글이 한 줄에 약 44자 들어간다. 480px(`run-ingest-dialog.tsx:159`)는 점수 요소 줄(이름, 점수, 해설)을 담기에 좁다. 768px(`max-w-3xl`)은 한 줄이 55자를 넘어 길다.
- 높이를 고정하는 이유: 가운데 정렬된 팝업은 진행 표시에서 내용으로 바뀌며 키가 커지면 제목이 위로 튄다. 높이를 고정하면 머리가 제자리에 있다. 1440×900·1280×800·768×1024 모두 768px 높이가 된다.
- 팝업 틀은 `flex flex-col gap-0 overflow-hidden p-0` 이다. 부품 기본값인 `grid gap-4 overflow-y-auto p-6` 은 className 으로 덮는다. `sm:max-w-sm` 은 `sm:max-w-none` 으로 덮는다. 640~767px에서도 전체 화면이 되는지 구현 때 700px 폭으로 확인한다.
- 뒷막(overlay)은 공용 부품 그대로 둔다(`bg-foreground/10 backdrop-blur-xs`, `dialog.tsx:26-37`). DialogContent 로는 className 을 넘길 수 없다.
- 열고 닫는 움직임은 768px 이상에서 지금 부품의 fade+zoom 을 쓴다. 767px 이하에서는 확대 없이 fade 만 쓴다. 움직임 줄이기에서는 둘 다 끈다(7.4).
- 공용 `dialog.tsx` 는 고치지 않는다. 모두 className 과 props 로 처리한다.

### 4.2 머리 (늘 고정) [제안]

```
┌──────────────────────────────────────────────────────┐
│ 추천 분석                                         [×] │ DialogTitle(h2) · 닫기 ghost icon-sm
│ [↑ 추천]  SOL Score 82 / 100  [참고]                  │ 권고 배지 · 점수 (flex-wrap)
│ 판정은 규칙 엔진이 하고, 최종 참여 결정은 사람이 합니다. │ DialogDescription (type-body muted)
├──────────────────────────────────────────────────────┤ border-b border-border
```

- 머리는 모든 폭과 모든 상태에서 스크롤되지 않는다. 그래서 고지 문장이 늘 보인다(스펙 4.1 1번).
- 첫 줄은 제목 "추천 분석"과 닫기 버튼이다. 닫기 버튼에는 `aria-label="닫기"` 를 단다. 부품 기본 닫기 버튼은 끄고(`showCloseButton={false}`) 머리 안에 직접 둔다. 기본 버튼은 영어 "Close" 이고 절대 위치라 머리 줄 배치와 맞지 않는다.
- 둘째 줄은 `StatusBadge kind="recommendation"` 과 "SOL Score" 라벨(`type-label text-muted-foreground`), "82 / 100"(`type-label tabular-nums text-foreground`)이다. "참고" 표시는 상세 화면 점수(`score-gauge.tsx`)와 같은 조건, 같은 모양이다. 값은 규칙 run 에서 부르는 쪽이 넘긴다.
- 셋째 줄은 고지 문장이다. `DialogDescription` 으로 두어 팝업의 설명(aria-describedby)이 되므로, 열 때 화면 낭독기가 제목에 이어 고지를 읽는다.
- 여백은 768px 이상에서 `px-6 pt-6 pb-4`, 767px 이하에서 `px-4 pt-4 pb-3` 이고, 줄 사이는 `gap-2` 다.

### 4.3 본문 (스크롤) [제안]

- `min-h-0 flex-1 overflow-y-auto overscroll-contain` 이고, 아래 여백은 `pb-6` 이다. 767px 이하에서는 기기 아래 안전 영역만큼 더 띄운다.

## 7. 진행 표시

### 7.1 모양 [제안]

```
[⟳] 추천 분석을 만들고 있습니다.                                  42%
▕█████████████████░░░░░░░░░░░░░░░░░░░░░░░░▏
공고와 회사 자료를 읽고 정리하고 있습니다. 진행률은 걸린 시간으로 어림한 값이고,
창을 닫아도 분석은 계속됩니다.
```

- 본문 맨 위(`pt-6`)에 둔다. 아래에는 아무것도 두지 않는다. 결과 모양이 상태마다 달라서, 8개 섹션 skeleton 은 길기만 하고 맞지도 않는다. 글자, 숫자, 막대가 함께 있으므로 `docs/06-UI-UX.md:250` 의 "스피너 단독 금지"에 걸리지 않는다.
- 첫 줄: 회전 아이콘 `LoaderCircleIcon size-4 animate-spin text-muted-foreground motion-reduce:animate-none`, 글자 `type-body text-foreground`, 숫자 `ml-auto type-heading tabular-nums text-foreground`.
- 막대(`mt-3`): 바탕은 `h-2 w-full overflow-hidden rounded-full bg-muted` 로 `MeterBar` 와 같은 모양이다. 채움은 `h-full rounded-full bg-foreground` 이고 너비 변화는 150ms ease-out 이다. 너비는 `MeterBar` 처럼 inline style 이다. 채움을 brand 가 아니라 foreground 로 하는 이유: 이 화면에서 brand 막대는 규칙 점수를 뜻한다.
- 설명(`mt-2`): `type-label text-muted-foreground`.

### 7.2 계산 [제안]

- 진행률 p 는 min(99, floor(100 × 경과 / T)) 이다. 1초마다 따로 갱신하고, 묻기 간격(2초·5초)과 묶지 않는다.
- 경과의 시작점은 POST 응답 전에는 클릭 시각이다. 그 뒤는 13절 미결정 9에 따른다. 숫자는 줄지 않는다. 계산 값이 이미 보인 값보다 작으면 보인 값을 유지한다.
- T 는 예상 소요 시간이다(스펙 미결정 6). 디자인 권고는 T = `INSIGHT_POLL_LIMIT_MS`(3분)다. 그러면 99%에 닿는 때와 늦음 안내가 나오는 때가 같아서, 안내 없이 99%에 오래 멈춰 있는 구간이 생기지 않는다. 상수도 하나로 끝난다. 실측한 시간이 상한보다 훨씬 짧으면 숫자가 중간쯤에서 100%로 건너뛰는데, 이는 일찍 끝난 것으로 읽힌다. 실측값 기반 T 를 따로 두면 그 반대로 99%에 머무는 구간이 생긴다.
- DONE 이 오면 곧바로 100%로 하고 600ms 동안 둔 뒤 내용으로 바꾼다. FAILED 는 100%를 거치지 않고 바로 실패 상태로 간다. 100%는 성공처럼 읽히기 때문이다. 팝업이 닫힌 채 DONE 을 받으면 멈춤 없이 구역만 바뀐다.
- 가짜 시계 시험 기준(스펙 3절 12번): 0초에 0%, T의 절반에 50%, DONE 이 없으면 99%를 넘지 않음, DONE 이면 100%, 600ms 뒤에는 내용이 보이고 본문에 `%` 가 없음.

### 7.3 접근성 [제안]

- 막대 바탕에 `role="progressbar"`, `aria-label="추천 분석 진행률"`, `aria-valuemin=0`, `aria-valuemax=100`, `aria-valuenow={p}`, `aria-valuetext="{p}%"` 를 단다. 눈에 보이는 숫자는 `aria-hidden` 으로 두어 두 번 읽히지 않게 한다.
- 알림 영역은 팝업 본문 안에 polite `role="status"` 하나를 둔다. 상태가 바뀔 때만 읽는다. 시작 때는 "추천 분석을 만들고 있습니다.", 늦어지면 "응답이 늦어지고 있습니다. 잠시 뒤 다시 확인하세요.", 끝나면 "추천 분석이 끝났습니다.", 실패하면 "추천 분석을 만들지 못했습니다."다. 매초 바뀌는 숫자는 알림 영역에 넣지 않는다. 화면 낭독기 사용자는 진행 막대 값을 언제든 직접 물을 수 있다.
- 모달이 열리면 바깥은 화면 낭독기에서 가려진다(Base UI 모달 동작, 구현 때 확인). 그래서 구역의 상태 줄과 팝업 알림이 겹쳐 읽히지 않는다.

### 7.4 움직임 줄이기 [제안]

- 회전 아이콘은 멈춘다(지금 코드와 같음). 막대 너비 전환과 팝업 열고 닫는 움직임도 끈다.
- 숫자는 계속 바뀐다. 글자가 바뀌는 것은 움직임이 아니다. 회전이 멈춰도 숫자로 진행이 보인다.
- `docs/06-UI-UX.md:134` 와 코드가 다른 점은 14절 열린 질문 10이다.

| 2. 칩을 누르면 섹션 8로 스크롤 | 칩이 목록 항목으로 가는 링크가 된다 | 읽던 위치에서 떨어지고 "돌아가기"가 필요하다. 고정 머리 아래 스크롤·초점 처리가 늘어난다 |
| 3. 둘 다 | 펼치기에 "목록에서 보기"를 더한다 | 같은 일을 하는 조작이 둘이 된다 |

- 칩 글자 "{공고문|회사 자료} {id}"와 섹션 8 항목 머리의 id 를 같게 써서 눈으로 짝을 맞춘다.
- 펼침은 항목마다 하나씩이고, 같은 칩을 다시 누르면 접힌다(지금 그대로). 칩의 `aria-expanded`·`aria-controls` 도 그대로다.

## 9. 접근성 체크 항목

- [ ] 팝업은 `role="dialog"`·`aria-modal`이고, 이름은 제목 "추천 분석", 설명은 고지 문장이다.
- [ ] 제목 계층은 팝업 제목 h2, 섹션 h3 이다. 건너뛴 단계가 없고 요소·자격 이름은 제목이 아니다.
- [ ] 열면 초점이 본문 영역으로 간다. 본문 영역은 `tabIndex={0}`, `role="region"`, `aria-label="추천 분석 내용"` 이고 `initialFocus` ref 로 지정한다. 본문이 스크롤 틀이라 방향키·PageDown 이 바로 먹는다. 팝업 자체는 스크롤되지 않으므로 부품 기본값에 맡기지 않는다.
- [ ] Tab 순서는 머리 닫기, 본문 영역, 상태 안내 버튼, 읽는 순서의 근거 칩, 생성 정보다. 초점은 팝업 안에서만 돈다.
- [ ] Esc 와 뒷막 클릭은 모든 상태(진행 중 포함)에서 닫는다.
- [ ] 닫으면 `finalFocus` 로 구역 버튼에 초점이 돌아간다. 구역 버튼은 상태가 바뀌어도 같은 요소다.
- [ ] 진행 표시에서 내용으로 바뀌어도 본문 영역 요소는 다시 만들지 않으므로 초점이 사라지지 않는다. [다시 요청]·[새 형식으로 다시 분석]·[다시 확인]은 누르면 사라지므로 초점을 본문 영역으로 옮긴다.
- [ ] 누르는 대상은 칩 28px, sm 32px, 닫기 32px, 생성 정보 32px(`min-h-8`)로 모두 24px 이상이다. 767px 이하에서 버튼은 44px 다.
- [ ] 초점 표시는 부품의 `focus-visible:ring-3 ring-ring/50` 이다. 본문 영역은 같은 링을 안쪽(`ring-inset`)으로 그린다. 흰 바탕에서 링이 보이는지 QA 가 본다.
- [ ] 글자 대비(계산 값): foreground 는 흰 바탕에서 약 16.6:1, muted-foreground 는 약 7.1:1 로 AA 를 넘는다. 진행 막대 채움(foreground)과 바탕(muted)의 대비도 3:1을 넘는다.
- [ ] 권고·자격 상태는 색만이 아니라 아이콘과 글자로도 나타낸다(`StatusBadge`).
- [ ] 움직임 줄이기는 7.4대로다.
- [ ] 진행 숫자는 매초 읽히지 않는다(7.3).

## 13. 미결정 9 디자인 권고 [사용자 결정]

질문: 진행 중에 팝업을 닫았다 열거나 새로고침하면 진행률을 요청 시각(`createdAt`)부터 이어 셀지, 0%부터 다시 셀지.

먼저, 같은 페이지에서 팝업을 닫았다 여는 것은 어느 쪽을 골라도 이어진다. 요청 상태를 구역이 갖기 때문이다(2절 1번). 이 결정이 실제로 갈리는 것은 새로고침, 다른 화면에서 돌아올 때, 그리고 다른 사람이 요청한 PENDING 을 열 때다.

| 안 | 뜻 | 결과 |
|---|---|---|
| 1. `createdAt` 부터 이어 셈 | 경과 = 지금 − 서버의 `createdAt`(음수면 0) | 숫자가 뒤로 가지 않는다. 읽기 전용 사용자와 다른 탭도 같은 진행률을 본다. 대기 상한도 같은 기준으로 재면 "3분"이 요청 뒤 3분이 된다. 대신 훅의 경과 기준(`use-insight-request.ts:156-186`, 지금은 훅이 잰 시작 시각)을 바꿔야 하고 늦어짐 시험도 바뀐다. 손님 컴퓨터와 서버 시계가 다르면 숫자가 조금 틀리지만 0~99로 묶이고 어림값이다 |
| 2. 0%부터 다시 셈 | 다시 열 때마다 그때를 시작점으로 | 지금 훅 그대로다. 대신 2분 지난 요청을 새로고침하면 0%에서 다시 시작하고, 이어서 3분을 더 기다려야 늦음 안내가 나온다. 즉 실제로 최대 5분이다. 다른 사람이 요청한 PENDING 은 늘 0%로 보인다 |

**권고: 안 1.** 진행률이 뒤로 가거나 처음으로 돌아가면 어림값이라는 것이 드러나 신뢰를 잃는다. 대기 상한과 진행률을 같은 시계로 재면 7.2의 "99% = 늦음 안내" 권고와도 맞는다.

# N3·N5·N6·N7 화면 명세

## 기준과 범위

승인된 [[2026-10-22-dashboard-missing-pages-plan|구현 계획]]의 의미를 현재 `c9bc496` UI에 구체화한다. `polaris/mission.md`는 없으며 [[00-README]]·[[01-PRD]]·[[06-UI-UX]]·[[09-SECURITY]]가 목적·범위의 근거다. 기존 화면을 실행하지 않고 코드에서 관찰했다. 아래 카피는 구현용 초안이다. 구현·시험 통과 또는 사용자 화면 검수를 주장하는 문서가 아니다.

견본은 `AppPage`, `components/work/opportunities-{table,filters}.tsx`, `bids/[id]/bid-detail-view.tsx`, `dashboard/dashboard-view.tsx`, `components/bids/{status-badge,format}.tsx`와 `design/tokens.json`이다. N3·N6 옛 설계는 각각 `n3-watchlist`, `n6-bid-projects` 작업 폴더의 2026-10-21 디자인을 재사용하되 이 문서의 최신 UI 적용 사항이 우선한다. 새 화면·표시 부품은 승인된 기능 범위 안에서만 만들며 새 토큰·패키지·shadcn 부품은 필요 없다.

- 업무 틀과 `AppPage contentClassName="max-w-360"`를 쓴다. 화면에 h1 하나, 기본 `type-title`; 본문에 `typeScale="dashboard"`를 적용하지 않는다.
- 사이드바 256px 펼침 + 본문 좌우 32px 기준 가용 폭은 1440에서 1120px, 1280에서 960px다. 1280 미만 레이아웃은 만들지 않는다. 페이지 자체의 가로 넘침은 없어야 한다.
- 흰 바탕·가는 선·`gap-6`, 구역 안 `gap-4`, 조밀한 표·목록을 쓴다. 과한 통계 카드나 장식 차트를 추가하지 않는다. 필터는 URL이 정본이며 다른 조직 ID·사용자 ID는 입력받지 않는다.
- 조회 전 `requireWork`, 조직 전원 ADMIN·SALES·ANALYST·VIEWER가 N5·N7을 읽는다. 페이지를 숨기는 것과 서버 권한을 구분한다. 다른 조직 자원은 404, API 권한 부족은 403이다.

## N5 — 분석 이력과 결과 비교 `/analysis`

### 흐름과 배치

사이드바 → 조직 이력 → 2~4건 체크 → `선택한 분석 비교` → 같은 페이지 아래 비교 영역. 분석 실행은 공고 상세에서만 한다. 제목은 `분석 결과 비교`, 설명은 `조직의 분석 이력을 확인하고 저장된 결과를 비교합니다.`다.

1. 필터: 공고·분석 상태·권고·실행 모드 `Select` 4개와 `필터 초기화` outline. 공고는 UUID 직접 입력이 아닌 제목으로 고르는 선택지다. 기존 조직 공고 조회를 재사용하고 현재 선택된 공고는 목록에 없어도 표시한다. 선택지는 긴 제목이 폭을 밀지 않게 줄인다. 필터 줄은 `flex-wrap`, 각 선택 폭 약 200px, 공고만 280px다. 1280에서는 자연스럽게 두 줄이 되어도 된다.
2. `분석 이력` h2와 `N건 선택 · 최대 4건` 안내. 선택된 공고명·revision을 짧은 줄 목록으로 보여 페이지가 바뀌어도 선택 내용을 알 수 있다. 각 항목 `선택 해제` ghost와 `선택 초기화` ghost. 기본 버튼은 `선택한 분석 비교` 하나, 0~1건이면 비활성 + `2건 이상 선택하세요` 설명.
3. 이력 표: 선택 40px / 공고명 유동 / 분석 revision 88px / 상태 112px / SOL Score 88px / 권고 88px / 분석 시각 144px. 960px 안에 맞추고 표 내부 고정 최소 폭을 추가하지 않는다. 공고 제목 두 줄·DEMO, revision 아래 회사 프로필 revision, 점수·날짜는 `tabular-nums`. 시각은 완료 시각 우선, 없으면 접수 시각과 `접수` 표시. 실행 모드·알고리즘 버전·실패 사유·reviewFlags는 공고명 아래 `details`로 열어 볼 수 있다.
4. 기존 더 보기 패턴으로 다음 20건을 붙인다. 기본 정렬 `created_at desc, id desc`; 표시 완료 시각을 정렬 기준으로 오해하게 하지 않는다. 목록 항목에 대형 스냅샷을 내려 보내지 않는다.
5. 비교 h2 아래 기준 차이 경고, 이어 표 하나. 왼쪽 항목 열 160px, 선택한 분석 2~4열은 남은 폭을 균등 분배한다. 4열일 때 1280에서도 각 열 약 200px다. `table-fixed`, 모든 셀 `min-w-0 wrap-anywhere whitespace-normal`; 긴 버전·실패 코드·공고명을 줄바꿈한다. 선택 순서를 유지하고 열별 제거 버튼을 둔다. 별도 가로 스크롤·카드별 세로 스크롤은 만들지 않는다.

### 선택과 조회 계약

`bidId/status/recommendation/runMode/cursor/limit`는 승인된 `AnalysisHistoryQuery`, 선택은 `?compare=id1,id2`로 복원한다. 중복 ID는 첫 항목만 남긴다. 5번째 선택은 미선택 체크 상자를 비활성화하고 `최대 4건까지 비교할 수 있습니다`를 연결한다. 기존 선택은 계속 해제 가능하다. URL에 4건을 초과하면 임의의 4건을 비교하지 않고 `최대 4건을 선택하세요` 안내와 선택 초기화를 제공한다. 잘못된 UUID는 유효하지 않은 비교 선택 안내로 처리한다. 필터 변경은 커서를 지우며 유효한 비교 선택은 유지한다.

비교 버튼은 선택 ID를 URL에 반영하고 비교 영역으로 이동·제목에 초점을 준다. 공유 URL로 진입하면 바로 해당 결과를 조회한다. 목록에서 체크만 바꿨을 때 비교 결과를 이미 표시 중이면 URL·열도 같은 선택으로 갱신한다. 1건이 남으면 단건 값은 볼 수 있고 `비교하려면 한 건을 더 선택하세요`를 표시한다. 0건이면 비교 영역 대신 선택 안내다.

목록은 `GET /api/v1/analyses`, 비교는 기존 `GET /api/v1/analyses/:id`를 선택당 한 번, 최대 4번 병렬 조회한다. 한 열 오류는 다른 열을 유지한다. 재시도는 그 열만 다시 읽는다. 404 문구는 `분석을 찾을 수 없거나 접근할 수 없습니다`이며 타 조직 존재를 구분하지 않는다. 다른 열 제목을 실패한 분석 제목으로 추정하지 않는다.

### 비교 행

| 행 | 표시 규칙 |

| 열 머리 | 공고 제목·DEMO·공고 상세 링크·선택 해제 |
| 상태 / SOL Score / 권고 | 기존 `StatusBadge`, 점수는 `N / 100`; null은 `—` + 상태·이유 |

## N7 — 인력 배치 시뮬레이션 `/workforce`

### 흐름과 배치

제목 `인력 배치 시뮬레이션`, 설명 `저장된 분석의 인력 가용성과 현재 배정의 기간 충돌을 확인합니다.` 아래 `조회 결과는 저장되거나 실제 인력 배정에 반영되지 않습니다.`를 항상 표시한다.

1. 공고 선택: 제목으로 고르는 `Select` + outline `추가`, 최대 3개. 기존 조직 공고 조회를 재사용한다. 선택된 공고는 제목·DEMO·제거 버튼의 세로 목록으로 표시한다. 같은 bidId 중복 추가를 막고 3개면 추가를 비활성화한다. 저장·배정·확정 버튼은 없다. 기본 버튼은 `시뮬레이션 조회` 하나. 선택은 URL `?bidIds=id1,id2,id3`로 공유·복원한다. 선택 0건에는 조회를 비활성화하고 `공고를 1~3건 선택하세요`를 연결한다.
2. 결과 상단: `분석 당시 인력 가용성` h2, 공고별 1~3열 카드(`grid-cols-N gap-4`). 1280에서도 3카드가 약 309px씩 확보된다. 카드 안은 세로로 쌓아 내용이 줄바꿈되도록 한다.
3. 각 카드: 공고명·DEMO·공고 상세 링크 → 분석 ID 짧은 표시/시각·revision → 수행 기간 → `필요 N FTE`, `가용 N FTE` → 필요 인력 근거·기간 근거·missing 사유 → 후보 목록. FTE는 사람 수와 구분하며 저장 계산값의 정밀도를 유지하고 불필요한 소수 0만 줄인다. 합산 총인원·가상 직원 200명을 가용 수로 제시하지 않는다.
4. 후보는 해당 카드 아래 세로 목록, 처음 6명 + 네이티브 `details` 나머지 N명. 이름·부서·직무·기술·분석 당시 가용 FTE·DEMO만 표시한다. 연락처·성별·고유 프로필 배경 정보를 넣지 않는다. 동일 후보가 여러 공고에 나와도 제거하지 않는다. 기술이 길면 줄바꿈하며 16px 아이콘은 의미가 있을 때만 쓴다.
5. 별도 구역 `현재 배정과 기간 충돌` h2 + `현재 배정 기준 {currentAssignmentsAsOf} KST`. 위 snapshot 카드와 선으로 분리한다. 기존 배정 과부하 표와 공고 간 공유 후보 표를 구분한다. 두 표는 이름 / 관련 공고·배정 / 겹치는 기간 / 근거 열로 960px에 맞춘다. 타임라인·드래그·간트 라이브러리를 추가하지 않는다.

### 계산 의미와 데이터 계약

`GET /api/v1/workforce/simulation?bidIds=<1~3 UUID>`만 쓴다. 응답에 공고별 제목·DEMO·analysisId·snapshotAsOf·period·requiredFte·requiredFteSource·availableFte·missingReason·후보, 별도 currentAssignmentsAsOf·충돌 구간이 필요하다. 세부 DTO 이름은 도메인 구현이 정하되 두 기준을 합치지 않는다.

- 최신 COMPLETED/PARTIAL의 **검증된 입력 스냅샷**으로 `staffAvailability`·`availableFte`를 재사용한다. team·today·기간을 현재 값으로 바꾸지 않는다. `snapshotAsOf`는 그 team 스냅샷 기준이며 분석 완료 시각을 같은 시각으로 추정하지 않는다.
- 최신 시도가 RUNNING/FAILED지만 이전 유효 완료 결과가 있으면 `최근 완료 분석 기준 · {시각}. 최신 시도: {상태}`를 해당 카드에 표시한다. 새 시도 때문에 기존 FTE를 지우지 않는다.
- `BUDGET_TIER`면 `필요 인력은 예산 구간 추정입니다`, 기본 기간이면 `수행 기간 미확인 · 분석의 기본 기간`을 표시한다. 값이 없으면 `정보 부족`/`분석 필요`와 구체 사유, FTE는 `—`; 0으로 채우지 않는다.
- 후보는 스냅샷 점수 대상 인력에 한정한다. 현행 가상 직원 체계는 200명이며 후보 개수는 실제 조회 결과다. 역할·기술 요구가 없으면 `후보 적합성 확인 필요`; 자격·채용 적합성 확정 문구를 쓰지 않는다. 스냅샷 personId에 대응하는 표시 이름이 없으면 식별 가능한 중립 표시를 쓰고 다른 사람을 추정해 붙이지 않는다.
- 현재 배정은 요청당 한 now로 읽는다. 과부하는 **기존 배정**이 가용량을 넘은 실제 구간과 근거다. `공유 후보`는 선택 공고끼리 기간이 겹치고 같은 사람이 후보라는 뜻이다. `확정 충돌`·`배정 완료`·`인력 부족 확정`으로 쓰지 않는다. 후보를 선택 공고에 자동 배정한 allocation을 만들어 계산하지 않는다.
- 기간 경계는 엔진의 `[시작, 종료)`다. 표에는 `시작 포함·종료 제외`를 caption으로 한 번 설명하고 시각이 있으면 KST까지 표시한다. 종료와 다음 시작이 같은 두 기간은 충돌로 표시하지 않는다.

| 상태 | 언제 | 보이는 것 | 사용자가 할 수 있는 것 |
|---|---|---|---|
| 초기 | 선택 없음 | `공고를 선택하면 인력 가용성과 기간 충돌을 확인할 수 있습니다` | 공고 1~3건 선택 |
| 로딩 | 조회 중 | 카드·충돌 표 skeleton, 선택 유지, `aria-busy` | 중복 조회 방지; 기존 결과와 새 선택을 혼합 표시하지 않음 |
| 분석 필요 | 유효한 완료 스냅샷 없음 | 해당 카드 `분석 필요`, FTE `—`, 공고 상세 링크 | 상세에서 분석; 다른 카드 계속 확인 |
| 정보 부족 | 필요 인력/기간/후보 근거 부족 | 사유·기본 기간/추정 여부 | 상세 근거 확인 |
| 후보 없음 | 판정 가능한 조건이나 일치 후보 0 | `조건에 맞는 후보가 없습니다`; 전체 인력 부족 확정 아님 | 공고 요구·상세 확인 |
| 요구 없음 | 기술·역할 판정 근거 없음 | `후보 적합성 확인 필요` | 제공된 인력 정보·근거 확인 |
| 충돌 없음 | 과부하·공유 후보 0 | `현재 조회 범위에서 확인된 기간 충돌이 없습니다` + 기준 시각 | 다른 공고 조회 |
| 공유 후보 | 여러 공고의 겹치는 후보 | `공유 후보`와 기간·공고, 설명 문구 | 조회·공고 상세 |
| 오류 | 읽기 실패 | 기존 `WorkError`·requestId; 이전 성공 값을 최신 결과처럼 남기지 않음 | 다시 조회 |
| 잘못된 선택 | 4개 초과/잘못된 UUID/다른 조직 | 한도 안내/400, 타 조직은 일반 404 | 선택 수정·초기화 |
| 접근 불가 | 로그인·업무 조직 문제 | 기존 업무 가드 안내 | 기존 인증 흐름 |

## N3 — 현재 사업기회 UI 적용

옛 N3 디자인의 낙관적 토글·실패 복구·해제 직후 행 유지·`aria-pressed`는 유지한다. 표·필터 구조는 현재 Opportunity UI로 대체한다.

- `/watchlist`도 현재 `OpportunityFilters`·`OpportunityTable`·더 보기·출처/기관/단계/분야를 쓴다. 서버의 `watched=me` 범위는 항상 고정하고 초기화로 지우지 않는다. 일반 목록·상세 복귀에서도 필터와 본인 범위를 보존한다.
- 관심 식별자는 **item.bidId = bid_notices UUID**다. opportunity id로 watch를 생성하거나 source 묶음 전체에 자동 등록하지 않는다. 같은 사업기회의 다른 source 공고는 별도 관심이다. source 대화상자가 이 구분을 보여 준다. 현재 DTO는 초기 단계에도 bidId가 있으므로 단계만으로 관심을 금지하지 않는다.
- 현재 표의 11열과 의도된 내부 가로 스크롤(`min-width:1184px`)을 보존한다. 관심 기능을 켠 표에서 40px 열을 더해 최소 1224px, ★ 32px·셀 `px-1 py-1.5`. 스크롤 힌트·초점 가능한 region을 유지하고 caption을 관심 목록에 맞춘다. 페이지 전체 넘침은 없어야 한다. 대시보드 간추린 목록에는 ★를 추가하지 않는다.
- 토글을 끄면 행을 즉시 없애지 않고 별 outline 상태·`관심 해제됨`을 표시한다. 필터 변경/새 조회에서 사라진다. 실패하면 원래 상태 복구·toast. 더 보기 행과 포커스를 잃는 강제 refresh는 하지 않는다.
- 전체 빈 목록 `관심 등록한 공고가 없습니다` + `/bids` 링크, 필터 0건 `조건에 맞는 관심 공고가 없습니다` + 초기화. D-3·D-1 마감 알림과 대시보드 7일 필터를 혼동하지 않는다.

## N6 — 현재 DTO·대시보드 적용

기존 N6 draft의 5열 보드·320px 상세 레일·수명 규칙·체크리스트·대화상자 흐름을 재사용한다. 초기 질문·대규모 시험 행렬은 새 범위의 필수 작업으로 복구하지 않는다.

- 보드는 `검토 대기 → 제안 준비 → 제출 완료 → 결과 확인 → 종료`, `grid-cols-5 gap-3`. 960px에서 약 182px, 1120px에서 약 214px/칸. `min-w-0`, 제목 두 줄 + `wrap-anywhere`, 세로 메타 정보, 칸별 6장 후 `details`. 보드 자체 가로 스크롤·drag 없음. 검토 대기 카드는 점선·공고 상세 링크이며 아직 프로젝트가 아니다.
- 검토 대기는 기존 review-pending 서비스 의미를 따른다. 현재 대시보드 둘째 카드는 `분석 대기`다. 옛 draft의 `검토 대기 = 둘째 카드` 가정을 복원하지 않는다. 공공조달 source·단계 확장 때문에 분석 가능한 공고·유효 결과 정의를 임의로 넓히지 않는다.
- 상세 주 영역 + 320px 레일, `gap-6`. ADMIN·SALES만 변경 컨트롤을 보이고 다른 역할에는 값과 읽기 전용 안내 한 번만 둔다. 앞으로 버튼 하나만 default; 뒤로·종료 outline. 최신 사람 결정이 BID가 아니면 경고·전진만 차단, 자동 종료하지 않는다. 정정 revision·최신 공고 링크를 표시한다.
- 체크리스트 담당자는 로그인 조직 구성원이다. 가상 직원 후보 200명을 담당자 Select에 넣지 않는다. 결과는 중립 표시하며 점수·모델 입력으로 쓰지 않는다는 안내를 둔다.
- 공고 상세 레일의 결정 패널 위 `projectEntry` 슬롯으로 만들기/보기/다시 열기를 둔다. 관심 버튼은 기존 머리 동작 자리다. 양 기능이 같은 헤더를 중복 소유하지 않는다. 프로젝트 키는 canonical bidId이며 묶인 opportunity를 프로젝트로 대체하지 않는다.
- 대시보드 첫 4카드·분석 요약·전용 수집 상태 패널은 보존한다. 다섯째를 `진행 중 입찰 프로젝트`로 교체, 링크 `/projects`, 값은 `status <> CLOSED`의 현재 origin 범위다. 긴 label은 1280에서 두 줄을 허용하고 5카드 모두 label 최소 높이를 같게 맞춰 숫자 기준선을 정렬한다. 오래된 1줄 라벨 시험을 복원하지 않는다. 수집 상태는 전용 패널에 남는다.
- DTO(`canManage`, owner, effectiveDueAt, warnings, checklist, result, history)는 현재 서버 반환값을 표시한다. UI가 새로운 기본 담당자·삭제 권한·취소 공고 생성 규칙을 만들지 않는다. 기존 오류 코드와 서버 전이를 따른다.

## 공통 접근성·토큰·확인 기준

- `AppPage`만 main을 만들고 구역 h2·카드 h3 순서를 지킨다. 표 caption·`th scope`·Select의 가시 label·체크 상자의 `공고명 revision N 비교 선택` 이름을 제공한다. 전체 행 클릭 대신 제목 링크·명시적 체크를 쓴다.
- Tab 순서는 필터 → 선택/조회 → 목록 → 더 보기 → 비교/충돌. `details/summary`는 네이티브 키보드 동작을 유지한다. 비활성 사유는 hover tooltip만으로 전달하지 않는다. 숫자·색만으로 상태를 전달하지 않는다.
- 목록/선택 개수 변화는 짧은 `aria-live="polite"`; 오류는 `role="alert"`. 여러 열 로딩을 중복 낭독하지 않는다. 제거 뒤 초점은 다음 선택 제거 버튼, 없으면 선택 컨트롤로 보낸다. 대화상자는 기존 focus trap·닫힘 후 trigger 복귀를 유지한다.
- 색: background/card/foreground/muted-foreground/border/input/ring, primary/primary-foreground, warning/destructive/success는 실제 상태에만, brand는 선택에만. DEMO는 기존 DemoBadge. `type-title/heading/body/label/caption`, Pretendard 상속, 날짜·FTE `tabular-nums`. 새 색·글꼴·임의 px 글자·그라데이션 없음.
- Button 36px(작은 아이콘 32px), Select/Input 40px, 아이콘16px, focus-visible ring. 기존 Card·Button·Select·Input·Field·Table·Skeleton·Dialog·toast·WorkError와 네이티브 체크 상자/details를 재사용한다. 값만 받는 feature 내부 표시 부품은 새 전역 UI 라이브러리로 추출하지 않는다.
- 통합 확인: 1440에서 핵심 데이터·선택·부분/실패·읽기 전용 흐름, 1280에서 긴 제목·4열 비교·3공고 카드·5열 보드·내부 스크롤·오버레이·페이지 가로 넘침을 확인한다. ADR-046에 따라 이 정적 명세 때문에 새 전수 상태/폭 시험을 만들지 않는다.

## 열린 질문

승인 계획을 넘는 제품 결정은 없다. DTO 이름은 구현 담당자가 확정하고 위 의미를 유지한다. N5/N7 범위 명세는 호출자의 실행 지시에 따라 `polaris/specs/in-progress/2026-10-22-n5-analysis-comparison.md`, `2026-10-22-n7-workforce-simulation.md`에 둔다. 승인 전 계획의 `planned/` 경로를 별도 중복 문서로 만들지 않는다.

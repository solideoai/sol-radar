## 2. 점검 결과

1차 정리 뒤 이틀 동안 커밋 146개가 들어왔다. 그 사이 다음이 다시 어긋났다.

1. **PROGRESS가 다시 작업 로그가 됐다.** 운영 상태 표 칸에 커밋 해시·시각·세션 이름·재생성 이력이 쌓였다(해시 30곳, 세션 이름 3곳). "회사 반영" 칸 하나가 약 2,000자다. ADR-057은 "현재 상태 요약 + 기능 상태 표 + 최근 작업 로그"만 허용한다.
2. **"실공고 분석 0건"이 낡았다.** 2026-10-29에 회사 AI gateway를 바꾼 뒤 실공고 3건을 분석했다(부경대 38 보류 `RULES_ONLY` 등, `evidence/company-rollout/20261029/ai-gateway-rollout.md`). 그런데 12·18·PROGRESS 요약·limitations·slides-spec은 아직 0건으로 쓴다. PROGRESS 안에서도 요약(0건)과 작업 로그(3건)가 다르다.
3. **Bosun 서빙 상태가 서로 다르다.** gateway는 회사 호스트 Bosun `127.0.0.1:8009`를 부른다. DEMO 17건 run도 `bosun-v3.1-0.6b`로 돌았다. 그런데 PROGRESS·22는 "B2(회사 서버 준비·확인) 미결정"으로 쓴다.
4. **첨부·회사 반영 상태가 낡았다.** Documents Worker는 2026-10-28부터 운영 중이다. 그런데 기능 상태 표 C3·C5와 일부 정본은 아직 "회사 반영 대기"로 쓴다.
5. **지난 날짜가 남아 있다.** `10-2[0-6]` 날짜가 16에 103곳, 22에 25곳, 03에 19곳, slides-spec에 18곳, 06에 14곳 있다. 이력 서술인지 지난 일정인지 가려야 한다.
6. **새 결정이 정본에 덜 들어갔다.** ADR-058~066이 그렇다. 058 출처 색, 059 발표 대본, 060 새 메뉴 3개, 061 화면 개편, 062 추천·보류·비추천, 063 직속 배치, 064 첨부 조립 v0.2, 065 번역 검증, 066 추천 분석(10-29 병합)이다.
7. **"미구현·구현 전" 표기를 확인해야 한다.** 03에 21곳, 05에 19곳, 15에 6곳 있다. 코드와 대조해 맞는지 본다.
8. **끝난 계획이 남아 있다.** 끝난 계획 6개는 코드도 정본도 인용하지 않는다. 끝난 계획 20개는 코드 주석이 가리켜서 남아 있다(§7 Q2).
9. **진행 중 spec이 끝난 일을 가리킨다.** `polaris/specs/in-progress/`의 `public-procurement-expansion`·`company-public-profile`은 일이 끝났다.

## 3. 공통 규칙 (모든 묶음)

1차 계획 §5(git `4ee81d08`의 `docs/plans/2026-10-27-docs-cleanup-plan.md`)를 그대로 쓰고, 아래를 더한다.

- **정본은 현재 사실만 쓴다.**
  - 지울 것: 커밋 해시 나열, 시각(분 단위), 세션 이름("45 세션이 …"), 재생성·롤백 이력.
  - 근거는 증거 링크 하나로 둔다. 운영 이미지 태그처럼 지금 값 하나가 필요한 곳만 남긴다.
- **날짜**
  - 남는 날짜는 화면 동결 11-01, 제출 11-03, 발표 11-04다. 일정은 [[12-ROADMAP]] "남은 일정 제안" 표 한 곳에만 둔다.
  - 지난 날짜는 이력 근거(ADR 날짜, "2026-10-19 C1 실응답 확인" 같은 검증 시점)일 때만 남긴다. 지난 일정·마감·"오늘/내일" 표현은 지운다.
- **숫자를 반복하지 않는다.** 운영 DB migration 수·수집 건수·첨부 처리 건수는 PROGRESS 운영 상태 표에만 적는다. 다른 문서는 링크한다.
- **현재 사실의 정본은 이 순서다.**
  1. 코드(`web/`·`services/`·`supabase/migrations/`·`infra/`)
  2. `infra/company/README.md`
  3. 최신 증거(`docs/evidence/company-rollout/20261029/`·`20261028/`)
  4. 16 ADR
  5. PROGRESS
  - 운영에서 확인하지 않은 것은 "미확인"으로 쓴다. 운영 DB·회사 서버를 조회해 확인하지 않는다.
- **결정이 필요한 것은 고치지 않는다.** 묶음 보고에 "결정 필요"로 적고 원문은 그대로 둔다.
- **Obsidian 규약**: frontmatter 5개 키를 지키고 `updated: 2026-10-29`로 바꾼다. `## 관련 문서` 절과 위키링크를 유지한다. 파일 이름은 바꾸지 않는다. 루트 `AGENTS.md`의 기술 스택 목록은 줄이지 않는다.
- **링크**
  - §5의 삭제 목록을 가리키는 링크는 각 묶음이 자기 파일 안에서 고친다. 링크를 지우거나 정본 절·git 해시로 바꾼다.
  - 다른 묶음 파일의 깨진 링크는 고치지 않고 보고한다.

## 4. 작업 공간과 순서

- worktree를 하나 쓴다. 메인 세션이 만든다.
  - 명령: `git -C /Users/leegwanghui/dev/hackathon/sol-radar worktree add /Users/leegwanghui/dev/hackathon/sol-radar-worktrees/docs-cleanup-1029 -b docs/cleanup-1029 3ae02acf`
  - 세 세션은 이 폴더에서 자기 파일만 고친다.
- **커밋**
  - 메인 세션이 묶음 보고를 받으면 diff를 확인한다. 그 묶음 파일만 지정해 `docs: …`로 커밋한다.
  - main 병합·push는 §7 Q3의 결정대로 한다.
- **main은 계속 바뀐다**(다른 세션이 PROGRESS·증거를 커밋한다).
  - PROGRESS는 C 묶음의 마지막 과제로 미룬다.
  - 병합 직전에 메인 세션이 main을 이 브랜치에 merge한다. 충돌이 나면 main 쪽 새 사실을 살리고 §3 규칙을 다시 적용한다.
- **검증**: `docs/`만 바꾸면 `pnpm verify:changed`가 돌릴 검사가 없다(`verify.config.json`의 changedPaths에 `docs/`가 없다). 그래서 검증은 아래 세 가지로 한다.
  1. 링크 검사: `node <메인 scratchpad>/check-links.mjs <worktree> --list`. 결과는 기준선 이하여야 하고, 자기 파일에 새 깨진 링크가 0건이어야 한다.
  2. 묶음별 grep 완료 기준(§6)
  3. 메인 세션의 diff 확인
  - Q2에서 코드 주석까지 고치기로 하면, 그 과제만 `pnpm verify:changed`를 슬롯 스크립트로 감싸 돌린다.

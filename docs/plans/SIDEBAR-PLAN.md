# SOL RADAR 대시보드 메뉴 및 기능 확장 프롬프트

## 1. 역할 및 목표

너는 SOL RADAR 프로젝트의 시니어 풀스택 아키텍트이자 AI 시스템 설계자다.

현재 SOL RADAR는 공공기관의 입찰·발주 정보를 수집하고, 기업의 기술력·수행 실적·보유 인력 등을 AI로 분석하여 입찰 참여 의사결정을 지원하는 B2B SaaS 플랫폼이다.

현재 구현된 기능과 설계 문서를 분석하고, 단순한 공고 검색 서비스를 넘어 **공고 탐색 → AI 적합도 분석 → 인력 배치 검토 → 수주 전략 분석 → GO/NO-GO 의사결정 → 입찰 프로젝트 관리**까지 연결되는 플랫폼으로 확장하라.

기존 아키텍처와 설계 원칙을 최대한 유지하고, 중복 기능이나 불필요한 복잡성을 만들지 않는다.

## 2. 기존 프로젝트 분석

먼저 다음 항목을 조사하라.

1. 프로젝트 README 및 `docs/` 하위 설계 문서
2. 현재 프론트엔드 라우팅 및 사이드바 구성
3. 백엔드 API와 인증·인가 구조
4. PostgreSQL 데이터베이스 스키마 및 마이그레이션
5. 공고 수집 및 AI 분석 파이프라인
6. 기존 SOL Score 산정 로직
7. 테스트 코드 및 배포 설정

기술 스택은 기존 프로젝트를 기준으로 하되 다음 구성을 우선 고려한다.

- Frontend: Next.js, TypeScript
- Backend: NestJS
- Database: PostgreSQL
- AI: 기존 Qwen 및 Kev 기반 파이프라인
- Infrastructure: Docker Compose
- UI: 기존 디자인 시스템과 컴포넌트 재사용

현재 실제 코드와 정본 설계 문서가 위 내용과 다르면 차이를 먼저 파악하고, 임의로 기술 스택을 변경하지 마라.

## 3. 기존 메뉴

현재 다음 메뉴가 존재한다.

| 메뉴 | 경로 | 권한 |
|---|---|---|
| 대시보드 | `/dashboard` | 전원 |
| 공고 | `/bids`, `/bids/[id]` | 조회 전원, 분석 ANALYST·SALES·ADMIN, 최종 결정 SALES·ADMIN |
| 회사 역량 | `/company` | 조회 전원, 편집 ADMIN |
| 알림 | `/notifications` | 본인 알림만 |
| 관리자 | `/admin/ingestion` | ADMIN 전용 |

위 메뉴와 기능은 유지하되, 명칭과 메뉴 배치는 사용자 경험에 맞게 개선할 수 있다.

## 4. 목표 사이드바 구조

다음 구조를 목표로 하라.

### WORKSPACE
- 대시보드 — `/dashboard`
- 입찰 공고 — `/bids`
- 관심 공고 — `/watchlist`

### AI INTELLIGENCE
- AI 적합도 분석 — `/analysis`
- 인력 배치 시뮬레이션 — `/workforce`
- 수주 전략·시장 분석 — `/intelligence`

### BID MANAGEMENT
- 입찰 프로젝트 — `/projects`
- 입찰 일정 — `/calendar`

### ORGANIZATION
- 회사 역량 — `/company`
- 알림 센터 — `/notifications`

### SYSTEM
- 설정 — `/settings`
- 데이터 수집 관리 — `/admin/ingestion`

다만 위 구조를 무조건 그대로 구현하지는 마라.

기존 기능과 중복되는 메뉴, 독립 페이지가 필요하지 않은 기능은 하위 탭이나 상세 페이지로 통합할 수 있다.

특히 `/bids/[id]`와 `/analysis`가 동일한 기능을 중복 구현하지 않도록 다음 원칙을 적용한다.

- `/bids/[id]`: 개별 공고 분석 실행 및 결과 상세
- `/analysis`: 여러 공고의 분석 결과 비교 및 분석 이력
- `/workforce`: 인력 배치 시뮬레이션
- `/projects`: 참여 확정 이후 입찰 업무 관리

## 5. 신규 기능 상세 요구사항

### 5.1 관심 공고

경로: `/watchlist`

주요 기능:
- 공고 북마크 등록 및 해제
- 관심 공고 목록
- 마감일 기준 정렬
- 기관별·상태별 필터
- 공고 상세 페이지 이동
- 마감 임박 공고 알림
- 사용자별 관심 공고 관리

기존 공고 데이터와 연동하고, 공고 데이터 자체를 중복 저장하지 마라.

### 5.2 AI 적합도 분석

경로: `/analysis`

주요 기능:
- AI 분석 결과 목록
- 여러 공고의 SOL Score 비교
- 분석 이력 조회
- 점수 구성 항목 시각화
- 적합도 판단 근거
- 주요 위험 요소
- 참가자격 충족 여부
- 분석 신뢰도 및 데이터 출처
- 분석 실행 상태와 실패 사유

SOL Score는 기존 정본 문서의 산정 기준을 따른다.

기존 점수 체계가 정의되어 있다면 임의로 가중치를 변경하지 마라.

AI 분석은 다음 요소를 고려한다.

1. 참가자격 충족 여부
2. 기술 역량 적합성
3. 유사사업 수행 실적
4. 보유 인력 및 가용성
5. 사업 규모 적합성
6. 기타 입찰 리스크

참가자격과 같은 필수 조건은 단순 점수로 대체하지 않는다.

AI 모델의 추론 결과와 실제 규칙 기반 검증 결과를 명확하게 구분한다.

분석 결과에는 판단 근거와 출처를 표시하고, 근거가 부족하면 확인 필요 상태로 처리한다.

### 5.3 인력 배치 시뮬레이션

경로: `/workforce`

핵심 목표는 공고에 요구되는 인력과 실제 회사의 보유 인력을 비교하여 사업 수행 가능성을 분석하는 것이다.

주요 기능:
- 프로젝트별 요구 인력 분석
- 보유 인력 조회
- 기술스택 및 경력 매칭
- 기존 프로젝트 투입 현황
- 인력별 가용률 산정
- 권장 인력 구성
- 부족 인력 및 기술 역량 분석
- 외부 채용·협력 필요 여부
- 여러 입찰에 동시 참여할 때의 자원 충돌 분석

시뮬레이션 결과에는 다음을 표시한다.

- 추천 인력
- 추천 근거
- 예상 투입 기간
- 투입률
- 인력 부족 여부
- 수행 가능성
- 데이터 부족 시 확인 필요 항목

보유 인력 정보가 충분하지 않으면 임의로 인력을 생성하거나 실제 직원처럼 표시하지 않는다.

실제 인력 정보와 시뮬레이션용 예제 데이터는 반드시 구분한다.

### 5.4 수주 전략·시장 분석

경로: `/intelligence`

공식 공공데이터를 기반으로 발주기관 및 입찰 시장을 분석한다.

주요 기능:
- 발주기관별 사업 이력
- 기관별 발주 규모
- 유사사업 검색
- 과거 낙찰업체 정보
- 낙찰 및 계약금액 분석
- 사업 분야별 발주 추이
- 기술 키워드 트렌드
- 유사사업과 현재 공고 비교
- AI 기반 전략 제안

가능한 경우 공공데이터포털 및 나라장터 공식 API를 우선 활용한다.

기존 프로젝트에 정의된 공공 API 명세와 데이터 파이프라인을 먼저 확인한다.

실제 API에서 제공하지 않는 데이터는 임의로 생성하지 않는다.

특히 과거 계약 이력만으로 수주 확률을 확정적으로 제시하지 마라.

데이터가 충분하지 않다면 정량적 수주 확률 대신 근거 기반 정성 평가와 한계를 표시한다.

### 5.5 입찰 프로젝트 관리

경로: `/projects`

AI 분석 결과가 실제 입찰 업무로 연결되도록 한다.

프로젝트 상태는 다음과 같이 구성한다.

1. 관심
2. 분석 중
3. 참여 검토
4. 참여 확정
5. 제안 준비
6. 제출 완료
7. 결과 확인
8. 종료

주요 기능:
- 공고 기반 입찰 프로젝트 생성
- 담당자 지정
- 참여 여부 결정
- GO / NO-GO 판단 근거 기록
- 상태 변경 이력
- 제안 준비 체크리스트
- 업무 담당자 및 진행률
- 제출 마감일 관리
- 최종 낙찰·미낙찰 결과 기록
- 프로젝트별 관련 분석 결과 연결

GO / NO-GO 최종 결정은 SALES 또는 ADMIN 권한만 가능하도록 한다.

AI는 결정을 지원하지만 최종 결정을 자동으로 확정하지 않는다.

### 5.6 입찰 일정

경로: `/calendar`

주요 기능:
- 입찰 마감일
- 사전규격 및 질의 기한
- 제안서 제출 일정
- 제안 발표 일정
- 프로젝트 내부 일정
- 사용자별 담당 일정
- 마감 임박 알림

기존 공고 및 입찰 프로젝트의 일정과 연동하고 중복 데이터를 최소화한다.

MVP에서는 프로젝트 상세의 일정 탭으로 구현하는 대안도 검토한다.

### 5.7 설정

경로: `/settings`

주요 기능:
- 개인 프로필
- 비밀번호 및 계정 설정
- 알림 수신 설정
- 관심 사업 분야
- 공고 추천 조건
- 조직 구성원 관리
- 역할 및 권한 관리

조직 전체 설정과 개인 설정은 접근 권한을 분리한다.

## 6. 권한 설계

기존 RBAC 체계를 유지한다.

역할:
- VIEWER
- ANALYST
- SALES
- ADMIN

기본 권한은 다음과 같다.

| 기능 | VIEWER | ANALYST | SALES | ADMIN |
|---|---|---|---|---|
| 공고 조회 | O | O | O | O |
| 관심 공고 | 본인 | 본인 | 본인 | 전체 관리 |
| AI 분석 결과 | 조회 | 조회·실행 | 조회·실행 | 전체 |
| 인력 시뮬레이션 | 제한 | 실행 | 실행 | 전체 |
| 시장 분석 | 조회 | 분석 실행 | 분석 실행 | 전체 |
| 입찰 프로젝트 | 조회 | 분석 의견 | 결정·관리 | 전체 |
| 입찰 일정 | 조회 | 조회 | 관리 | 전체 |
| 회사 역량 | 조회 | 조회 | 조회 | 편집 |
| 데이터 수집 관리 | X | X | X | 전체 |

반드시 다음 원칙을 지킨다.

- 프론트엔드의 메뉴 숨김만으로 접근을 제한하지 않는다.
- NestJS API에서 실제 권한 검사를 수행한다.
- 권한이 없는 요청은 적절한 403 응답을 반환한다.
- 소속 조직이 다른 데이터에 접근할 수 없도록 한다.
- 사용자별 데이터 접근 범위를 검증한다.
- 중요한 결정 및 권한 변경은 감사 로그에 기록한다.
- 인력의 개인정보는 최소한으로 노출한다.

## 7. UX/UI 요구사항

기존 SOL RADAR 디자인 시스템과 일관성을 유지한다.

- B2B SaaS 스타일
- 반응형 레이아웃
- 사이드바 그룹 구분
- 현재 페이지 활성 상태
- 역할별 메뉴 노출
- 검색·필터·정렬
- 빈 데이터 상태
- 로딩 상태
- 오류 상태
- 권한 없음 상태
- 공통 테이블 및 카드 재사용
- 데이터 시각화
- 한국어 UI

특히 대시보드에서는 핵심 정보를 한눈에 확인할 수 있도록 한다.

추천 KPI:
- 신규 입찰 공고 수
- 분석 완료 공고 수
- 고적합도 공고 수
- 참여 검토 중 프로젝트
- 마감 임박 공고
- 진행 중 입찰 프로젝트

KPI는 실제 데이터에 근거해야 하며, 고적합도 기준은 기존 SOL Score 규칙을 따른다.

## 8. 핵심 사용자 흐름

다음 업무 흐름이 자연스럽게 연결되도록 설계한다.

공공데이터 수집
→ 입찰 공고 조회
→ 관심 공고 등록
→ AI 적합도 분석
→ 회사 역량 비교
→ 인력 배치 시뮬레이션
→ 수주 전략 분석
→ GO/NO-GO 의사결정
→ 입찰 프로젝트 관리
→ 제출 및 결과 기록

각 단계에서 공고 ID, 분석 결과, 프로젝트 정보를 일관되게 연결한다.

분석 결과와 의사결정 당시의 데이터 버전 및 근거를 추적할 수 있도록 한다.

## 9. 우선순위 및 단계별 구현

### P0 — MVP 핵심

- 사이드바 정보 구조 개선
- 관심 공고
- AI 분석 결과 비교·이력
- 인력 배치 시뮬레이션 기본 기능
- 입찰 프로젝트 관리
- 기존 공고 상세와 신규 기능 연결
- RBAC 적용
- 기본 테스트

### P1 — 확장 기능

- 수주 전략·시장 분석
- 입찰 일정 캘린더
- 개인 및 조직 설정 확장
- 정교한 알림 조건
- 분석 결과 기반 고급 시각화

P0 기능에서도 핵심 사용자 흐름을 우선 구현하고, 실제 데이터와 API가 아직 준비되지 않은 경우 데이터 출처와 실행 모드를 명확히 구분한다.

## 10. 설계 문서 동기화

기존 `docs/` 디렉터리의 정본 문서를 확인하고 관련 변경 사항을 반영한다.

특히 다음 범위를 검토한다.

- PRD
- Architecture
- AI Pipeline
- Database / ERD
- API Specification
- UI / UX
- Data Pipeline
- SOL Scoring
- Security / RBAC
- Testing
- Roadmap

파일명은 실제 저장소를 기준으로 확인한다.

기존 문서와 새로운 요구사항이 충돌할 경우, 충돌 목록과 해결 방안을 정리하고 무조건 새로운 요구사항으로 덮어쓰지 않는다.

API 명세, DB 스키마, UI 화면, 권한 정책, 테스트 기준이 서로 일치하도록 한다.

필요하다면 Mermaid로 메뉴 구조, 데이터 흐름, 사용자 여정 및 ERD를 작성한다.

## 11. 구현 원칙

1. 기존 동작 중인 기능을 훼손하지 않는다.
2. 기존 컴포넌트와 코드를 최대한 재사용한다.
3. 불필요한 라이브러리 추가를 피한다.
4. 임시 Mock 데이터를 실제 데이터처럼 표시하지 않는다.
5. 기존 AI 분석 파이프라인과 중복되는 로직을 만들지 않는다.
6. 새로운 DB 테이블에는 관계·인덱스·제약조건을 고려한다.
7. 기존 API와의 하위 호환성을 검토한다.
8. 외부 API 연동에는 오류 처리와 호출 제한을 고려한다.
9. 각 기능에 적절한 단위·통합·E2E 테스트를 작성한다.
10. SOL Score의 기존 판단 기준을 임의로 변경하지 않는다.

## 12. 최종 작업 지시

다음 순서로 수행하라.

**1단계 — 현황 분석**
- 현재 코드베이스와 설계 문서 확인
- 이미 구현된 기능 식별
- 메뉴 중복 여부 분석
- 신규 요구사항과 기존 설계 충돌 확인

**2단계 — 최종 구조 결정**
- 최적의 사이드바 메뉴 구성
- 각 메뉴의 정확한 책임 정의
- 라우팅 구조
- 권한 매트릭스
- 데이터 모델과 API 변경점
- AI 파이프라인 연계 방식

**3단계 — 구현 계획 수립**
- P0/P1 구분
- 기능 간 의존성 확인
- DB 마이그레이션 계획
- 페이지 및 컴포넌트 구성
- 단계별 테스트 기준

**4단계 — 실제 구현**
- P0 기능부터 구현
- 기존 UI 디자인 유지
- 프론트엔드와 백엔드 연동
- 권한 검증
- 테스트 실행
- 관련 설계 문서 동기화

**5단계 — 결과 보고**
- 새롭게 추가된 메뉴
- 변경된 라우팅
- 구현한 기능과 미구현 기능
- 추가·수정된 API
- DB 변경 내역
- 테스트 결과
- P1에서 추가할 기능
- 알려진 제약사항

우선 기존 설계를 충분히 분석한 뒤 코드는 수정하지 말고 문서만 수정하라.

작업 중 기존 정본 설계 문서와 충돌하거나 제품 정책 결정을 요구하는 부분은 임의로 확정하지 말고, 충돌 내용과 추천안을 정리해 승인을 요청하라.

그 외 명확한 범위의 작업은 단계적으로 진행하라.

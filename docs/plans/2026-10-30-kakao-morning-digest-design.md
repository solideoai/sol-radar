# 디자인 스펙 — 평일 아침 추천 공고 카카오톡 묶음

> [!info] 상태
> 사용자와 정한 설계다(2026-10-30). 구현 계획은 이 문서를 근거로 따로 쓴다. ADR 번호는 정본 반영 직전에 `main`의 [[16-DECISIONS|16]]을 다시 보고 정한다.

## 1. 의도와 이유

- 지금 공고 카톡은 사람이 [분석]·[재분석]을 눌러 끝난 분석이 추천·보류일 때만 간다([[2026-10-20-kakao-memo-notify-design|카카오 알림 설계]] §5.1). 영업팀이 공고마다 버튼을 눌러야 알림을 받는 셈이라 쓰기 불편하다.
- 영업팀은 아침에 "오늘 볼 공고"를 한 번에 받고 싶다. 그래서 **평일 아침 9시에 그날의 추천 공고를 모아 카카오톡 한 통으로 보낸다.**
- 새 공고는 지금 자동 분석하지 않는다([[16-DECISIONS|ADR-069]] 5번). 묶음에 넣을 점수가 없으므로 **평일 아침 7시에 새 IT 공고를 자동 분석**하는 단계를 함께 만든다.

## 2. 사용자가 정한 것 (2026-10-30)

| 항목 | 사용자 결정 |
|---|---|
| 방향 | "매일 평일(주말 제외) 오전 9시에 그 날의 추천 공고만 모아서 카카오톡 알림으로 리스트 업해서 보내주는 방향" |
| 묶음의 근거 | 선택지 1: 07시에 새 IT 공고를 자동 분석하고 9시에 SOL Score 상위 공고를 묶는다. ADR-069 5번을 바꾸고 회사 Qwen·Bosun을 매일 쓴다 |
| 성격 | 발표 뒤 실제 영업팀 운영용으로 제대로 만든다. **단, 해커톤 발표(2026-11-04) 전에 구현을 다 끝낸다** |
| 세부 기본값 | 아래 표 7개 항목을 그대로 승인("그래 진행해") |
| 카카오 실발송 | 상시 켠다(선택지 1). 즉시 카톡도 상시 나간다. 실행서 §9.6·ADR-068 6번 "시험 뒤 끈다"를 개정 |

| # | 항목 | 정한 값 |
|---|---|---|
| 1 | 받는 사람 | 지금 즉시 카톡과 같다. 조직 구성원 ∧ 카카오 연결 CONNECTED ∧ 알림 켬 ∧ 활동 계정. 역할 제한 없음. 켜기 스위치 하나로 즉시·아침 묶음 둘 다 |
| 2 | 대상 공고 | 실공고만(DEMO 제외), IT 범위(`it_scope`), 지난 묶음 이후 새로 들어온 공고, 마감 전 |
| 3 | 고르는 기준 | 권고와 상관없이 **SOL Score 80점 이상**, 점수 높은 순. NO_BID 제외 |
| 4 | 쉬는 날 | 토·일만 뺀다. 공휴일은 보낸다 |
| 5 | [전체 보기] | 공고 목록에 "이번 묶음" 필터를 더해 점수순으로 보인다 |
| 6 | 즉시 카톡 | 사람이 누른 분석의 즉시 카톡은 그대로 둔다 |
| 7 | 자동 분석 시각 | 07:00 KST. 06시 수집분까지 들어가고 09:00 전에 끝난다 |

근거 숫자(운영 DB SELECT, 2026-10-30): 분석된 실공고 IT 371건 중 추천 2·보류 366·비추천 3. "추천(BID)만"이면 대부분 0건이라 점수 기준으로 정했다. 최근 며칠 하루 80점 이상 4~12건(75점 이상 6~23건). 분석 1건 4~13초.

## 3. 목표 · 비목표 · 안 할 것

**목표**
- 평일 09:00 KST 전후로, 받는 사람마다 카카오톡 한 통에 그날 묶음(최대 3건 미리보기 + [전체 보기])이 도착한다.
- 묶음에 든 공고는 07:00 자동 분석의 SOL Score로 고른다.
- [전체 보기]로 들어가면 그 묶음의 공고 전부를 점수순으로 본다(데스크톱·모바일 웹).
- 같은 날 같은 사람에게 묶음은 한 번만 간다(재시작·동시 처리·재시도에도).
- 운영자가 시험·녹화를 위해 시간 조건 없이 묶음을 한 번 돌릴 수 있다.

**비목표**
- 공휴일 달력, 개인별 발송 시각·기준 점수 설정, 묶음 전용 켜기 스위치(즉시와 분리).
- 인앱 알림 묶음, 이메일, 알림톡 전환(운영 전환은 알림톡이라는 ADR-038 원칙은 그대로).
- 오래된(창 밖) 미분석 공고의 자동 분석.

**안 할 것(이러면 실패)**
- 같은 날 같은 사람에게 두 통 이상 보내기, 주말에 보내기.
- DEMO 공고를 영업팀 묶음에 섞기.
- 자동 분석이 사람의 [분석]을 오래 막기(동시 진행 상한을 지킨다).
- 묶음 카톡에 AI 서술(Qwen 출력)·조직 밖 사람 정보를 싣기(지금 피드와 같은 원칙).

## 4. 제약

- **일정**: 화면 동결 2026-11-03(ADR-073), 제출 11-03, 발표 11-04. 첫 자동 발송은 **11-03(월) 09:00**이다(11-01·02 주말). 녹화는 운영자 수동 실행(§5.6)으로 한다.
- **운영 반영 승인**: 마이그레이션 `db:push`, 회사 Analysis·알림 Worker 재생성, main push(Vercel), 운영 수동 실행(실발송·Qwen 호출)은 항목마다 사용자 승인 뒤에 한다(§11).
- **카카오 규격**(2026-10-30 공식 기본 템플릿 문서 확인):
  - 리스트 템플릿 `object_type:"list"`: `header_title` 필수·최대 200자, `header_link` 필수, `contents` **최소 2개·최대 3개**(각 항목 `title`·`image_url`·`description` 중 하나 필수, `link` 필수, 제목+설명 최대 4줄 표시), `buttons` 최대 2개.
  - Link 는 `web_url`·`mobile_web_url` 등 중 하나 필수, 도메인은 앱 설정의 웹 도메인과 같아야 한다.
  - 1건이면 리스트를 못 쓰므로 지금의 피드 템플릿을 쓴다.
- **회사 GPU**: 07:00 자동 분석은 회사 Qwen·Bosun을 쓴다. 사람의 [분석]과 같은 Analysis Worker 큐(`analysis`, concurrency 1)를 쓰므로 동시 진행 run 상한을 둔다(일괄 분석 CLI와 같은 기본 2).
- **ADR-069 5번 개정**: "새 공고 자동 분석은 하지 않는다" → "평일 07:00에 묶음 창의 새 IT 실공고만 자동 분석한다". 새 ADR로 개정한다.
- 시험은 MVP 핵심만(ADR-046). 순수 규칙·DB 정책·발송 소비자 핵심만 더한다.
- **다른 작업과 겹침(2026-10-30 sol-radar-c0 알림)**: 구글 캘린더 연동(브랜치 `feat/google-calendar-sync`, worktree `sol-radar-worktrees/google-calendar`)이 마이그레이션 `20261030002000`, ADR-073, 그리고 공유 파일 `scripts/database.test.mjs`·`web/lib/database.types.ts`·`web/app/(app)/[slug]/settings/page.tsx`·`web/app/account/account-settings.tsx`·`web/app/api/v1/_lib/http.ts`·`web/server/kakao-notify/kakao-token.crypto.ts`·`oauth-state.ts`(→ `web/server/token-seal`)를 쓴다. 이 묶음의 마이그레이션은 그보다 뒤 번호를 쓰고, 공유 파일은 구글 브랜치가 main에 들어간 뒤(10-31 목표) 그 위에서 고친다. 마이그레이션·ADR 번호는 쓰기 직전에 main과 그 브랜치를 다시 본다.

## 5. 동작

### 5.1 용어

- **영업일**: 월~금(KST). 공휴일도 영업일로 본다.
- **묶음 날짜 D**: 묶음을 보내는 영업일(KST 날짜).
- **묶음 창**: `[창 시작, 창 끝)`. 창 시작은 그 조직의 **직전 묶음 행의 `window_end`**이고, 직전 묶음이 없으면 직전 영업일 07:00 KST다. 창 끝은 자동 회차면 D 07:00 KST, 수동 실행이면 실행 시각이다. 그래서 주말에 수동 실행을 한 번 해도 다음 자동 묶음과 겹치거나 비지 않는다 **(설계 판단, 검토 반영)**.
- **늦은 공고 받기**: 자동 분석과 고르기는 이번 창에 더해 **직전 창**의 공고도 본다(아직 어떤 묶음에도 없는 것만). 09:00 뒤에 분석이 끝났거나 전날 원문이 없어 건너뛴 공고가 다음 날 묶음에 들어간다. 직전 창보다 오래된 공고는 자동으로 다루지 않는다 **(설계 판단, 검토 반영)**.
- **대상 조직**: env `DIGEST_ORG_SLUGS`(쉼표 목록)에 있는 조직. 비면 기능 전체가 꺼진다(자동 분석·묶음 모두). 운영은 `solideo` 하나로 시작한다 **(설계 판단: 회사 GPU 사용을 조직 단위로 켜고 끄는 스위치)**.
- **시작일**: env `DIGEST_START_DATE`(KST 날짜). 이 날짜 전에는 자동 회차(07시·09시)가 돌지 않고 수동 실행만 된다. 평일 낮에 Worker를 반영해도 그 자리에서 자동 묶음이 나가지 않게 한다. 운영은 `2026-11-03`으로 둔다 **(설계 판단, 검토 반영)**.

### 5.2 07:00 자동 분석 (회사 Analysis Worker)

- 영업일 07:00 KST 뒤 첫 회차(주기 5분)가 대상 조직마다 그날 묶음 행을 만든다(`bid_digests`, 상태 `ANALYZING`, 창 기록). 같은 조직·날짜 행이 이미 있으면 아무것도 하지 않는다.
- 분석 대상: 그 조직의 실공고(`is_demo=false`) ∧ `it_scope` ∧ 마감 전 ∧ `first_seen_at`이 직전 창 시작 이후이고 이번 창 끝 전 ∧ 어떤 묶음에도 없음 ∧ 최신 회사 프로필로 돈 분석(COMPLETED·PARTIAL·진행 중)이 없음 ∧ 분석할 원문이 있음. 원문이 없는 공고는 건너뛰고 수만 센다.
- 첨부가 아직 파싱 대기인 공고는 이번 회차에서 넣지 않는다. 첨부 대기(ADR-056, 최대 300초)로 concurrency 1 큐를 오래 잡지 않게 한다. 다음 날 직전 창으로 다시 본다 **(설계 판단, 검토 반영)**.
- 규모: 최근 하루 새 IT 공고는 40~180건(백필 포함 값)이다. 월요일 창(3일)은 더 많을 수 있어 아래 하루 상한을 둔다.
- 넣는 방식은 일괄 분석 CLI(`web/worker/it-batch-analyze.ts`, ADR-069)와 같은 enqueue 계약이다: `score_runs` QUEUED 행 + `analysis` job, `requested_by` 없음(즉시 카톡 이벤트를 만들지 않는다), 동시 진행 상한 2, 마감 임박 순. 멱등 키는 일괄 분석과 구별되는 접두사(예: `it-daily-<D>-…`)를 쓴다.
- 하루 상한 300건(설계 판단). 넘으면 마감 임박 순으로 자르고 잘린 수를 기록한다.
- 모든 대상이 끝나면(성공·PARTIAL·FAILED 모두 끝으로 본다) 묶음 행을 `ANALYZED`로 바꾸고 건수(대상·완료·실패·원문 없음·잘림)를 적는다.
- gateway가 죽어 있으면 다음 회차에 이어서 한다. 08:55까지 끝나지 않으면 남은 것은 그대로 두고(사람이 보는 분석 큐는 계속 돈다) 행을 `ANALYZED`로 닫고 미완 수를 적는다.

### 5.3 09:00 묶음 만들기 (회사 알림 Worker)

- 영업일 09:00 KST 뒤 회차(주기 5분)가 대상 조직의 그날 묶음 행을 본다. `ANALYZED`면 바로, `ANALYZING`이면 09:30까지 기다렸다가 09:30 뒤에는 그대로 진행한다(늦음 표시). 행이 아예 없으면(07시 단계가 안 돌았다) 09:30 뒤에 창만 기록한 행을 만들고 진행한다.
- **고르기**: 그 조직의 실공고 ∧ `it_scope` ∧ 마감 전 ∧ `first_seen_at`이 직전 창 시작 이후이고 이번 창 끝 전 ∧ 화면에 보이는 최신 분석이 COMPLETED·PARTIAL ∧ SOL Score ≥ 80 ∧ 권고 ≠ NO_BID ∧ 앞선 묶음에 들어간 적 없음. 정렬은 점수 내림차순, 같으면 마감 임박 순, 그다음 id. 사업기회 목록 표(`opportunity_list_items`)의 값을 그대로 쓴다(화면 `/bids`와 같은 숫자).
- 고른 **사업기회 id**(`opportunity_list_items.id`)와 그 행의 대표 공고 id를 순서대로 묶음 행에 **얼려 둔다**(상태 `READY`). [전체 보기]는 사업기회 id로 보인다(대표 공고가 바뀌어도 빠지지 않는다). 카톡 링크는 얼린 대표 공고 id로 `/bids/<bidId>`다. "앞선 묶음에 들어간 적 없음"은 사업기회 id로 본다. 뒤에 재채점·재분석이 있어도 묶음 내용은 바뀌지 않는다 **(검토 반영)**.
- 0건이면 행을 `EMPTY`로 닫고 보내지 않는다.
- 1건 이상이면 같은 트랜잭션에서 outbox 이벤트 `BID_DIGEST` 1건을 쓴다(멱등 키 `<orgId>:<D>:BID_DIGEST`). 기존 알림 소비자가 처리한다.

### 5.4 보내기 (알림 소비자)

- `BID_DIGEST`를 받으면 받는 사람을 그때 다시 고른다(§2 표 1번 규칙, 지금 `BID_RECOMMENDED`와 같은 함수). 0명이면 이벤트를 닫는다.
- 사람마다: KAKAO 알림 행(`type` `BID_DIGEST`, 멱등 키 `<outboxEventId>:<userId>:KAKAO`)을 보장 → 영속 claim(`kakao_send_claims`, 키 `DIGEST:<userId>:<orgId>:<D>`)을 얻은 실행자만 보낸다 → 결과를 행과 연결 표의 "마지막 발송"에 적는다. claim 뒤 실패는 지금처럼 UNKNOWN으로 닫고 자동 재발송하지 않는다.
- 발송 수단·토큰 갱신·1초 간격·만료 처리·`NOTIFY_KAKAO_PROVIDER`(꺼짐·mock·memo) 규칙은 지금 sender 를 그대로 쓴다. sender 는 리스트 템플릿도 받도록 넓힌다.
- 묶음 내용은 조직마다 같다. 이미 즉시 카톡으로 받은 공고도 묶음에 다시 나온다 **(설계 판단: 사람마다 내용을 달리하지 않는다)**.
- 묶음 행은 이벤트를 다 처리하면 `SENT`(보낸 사람 수·실패 수 기록)가 된다.

### 5.5 메시지 모양

- **2건 이상: 리스트 템플릿**
  - `header_title`: `오늘의 추천 공고 {N}건 · {M/D}({요일})`. `header_link`: [전체 보기] 주소.
  - `contents`: 상위 3건(2건이면 2건). `title` = 공고명(넘치면 …), `description` = `{발주처} · {마감 D-n 또는 M/D} · {점수}점 {권고 한글}`. PARTIAL이면 "규칙만" 표시. `link` = `/bids/<bidId>`.
  - `buttons`: [전체 보기 {N}건] → `/bids?digest=<D>`, [알림 설정] → `/settings`.
- **1건: 피드 템플릿**(지금 즉시 카톡 피드를 그대로 쓰되 제목 줄에 "오늘의 추천 공고"를 붙인다).
- 모든 링크는 `SITE_URL` 기준 앱 안 경로다. AI 서술은 싣지 않는다.
- 글자 수 자르기는 지금 `feed.model`의 코드 포인트 규칙을 쓴다.

### 5.6 운영자 수동 실행

- 운영자 CLI(worker 컨테이너, service role): `digest:run --org <slug> [--skip-analyze] [--dry-run] [--resend]`.
  - 묶음 날짜는 **오늘(KST)만**이다. 주말·`DIGEST_START_DATE` 전에도 된다. 시간·요일 조건을 무시하고 §5.2 → §5.3을 그 자리에서 한 번 돈다(자동 분석이 끝날 때까지 기다린다). `--dry-run`은 대상·고른 공고 수만 출력하고 아무것도 쓰지 않는다.
  - 오늘 행이 이미 `READY`·`SENT`·`EMPTY`면 거절한다(한 날짜에 한 번). 오늘 수동으로 쓰면 그날 09:00 자동 회차는 끝난 것으로 본다.
  - `--resend`: 오늘 행의 `BID_DIGEST` 이벤트가 `DEAD`(예: 카카오가 꺼져 있었다)면 `PENDING`으로 되돌려 다시 보낸다. 이미 받은 사람은 claim으로 건너뛴다. 다른 상태면 거절한다 **(검토 반영)**.
- 출력·로그에는 건수와 id만 싣는다(공고명·점수·사람 정보 없음).

### 5.7 예외

| 상황 | 동작 |
|---|---|
| 주말 | 07시·09시 단계 모두 아무것도 하지 않는다 |
| Worker가 그날 늦게 떴다 | 07시 단계는 08:55 전이면 돈다. 09시 단계는 그날 23:59 KST 전이면 돈다(늦게라도 한 번) |
| 다음 날 | 지난 날짜 묶음은 만들지 않는다(밀린 날을 몰아 보내지 않는다) |
| 카카오 꺼짐(`NOTIFY_KAKAO_PROVIDER` 빈 값·live) | 지금처럼 claim 없이 재시도 후 DEAD. 묶음 행은 그대로 남는다 |
| 고른 공고가 그사이 마감·취소 | 얼린 목록 그대로 보낸다. [전체 보기] 화면이 상태를 보인다 |
| 대상 조직에 회사 프로필이 없다 | 07시 단계가 건너뛰고 기록한다. 09시는 0건으로 `EMPTY` |

## 6. 데이터

- **새 표 `bid_digests`**: `id`, `org_id`, `digest_date`(date, KST), `window_start`·`window_end`(timestamptz), `trigger`(`AUTO`·`MANUAL`), `status`(`ANALYZING`·`ANALYZED`·`READY`·`EMPTY`·`SENT`), `analysis_counts`(jsonb), `opportunity_ids`·`bid_ids`(uuid[], 같은 순서), `total`(int), `late`(bool), `created_at`·`updated_at`. `unique(org_id, digest_date)`.
  - RLS: 만들자마자 잠근다. `authenticated`는 자기 조직 행 SELECT만(`org_id in (select public.my_org_ids())`). 쓰기는 service role(worker·운영자 CLI)만.
- **outbox**: `outbox_events_event_type_check`에 `BID_DIGEST`, `notifications_type_check`에 `BID_DIGEST`. 부분 인덱스 `outbox_events_notify_due_idx`와 `NOTIFY_EVENT_TYPES`·`findDue` 필터를 함께 바꾼다(세 곳이 같아야 한다는 지금 규칙).
- **claim**: `claim_kakao_digest(p_notification_id)` — `claim_kakao_notification`과 같은 모양, 키 `DIGEST:<userId>:<orgId>:<D>`.
- **묶음 고르기·얼리기**는 DB 함수 하나(`freeze_bid_digest(p_org_id, p_date, p_now)`)로 원자적으로 한다(행 갱신 + outbox 이벤트). 07시 행 만들기도 함수 또는 repo 한 곳에서 한다.
- 마이그레이션은 새 파일로만 쌓는다. 번호는 쓰기 직전 `main`을 다시 본다. `web/lib/database.types.ts`를 같은 커밋에 재생성한다.

## 7. worker 배치

| 단계 | 어디서 | 주기 |
|---|---|---|
| 07:00 자동 분석 | 회사 Analysis 전용 Worker. 등록은 `startAnalysisRuntime`(`web/worker/analysis-runtime.ts`)에 넣는다. `analysis-only-main.ts`는 회사 운영 원본 대조 대상(실행서 §7.2)이라 고치지 않는다 **(검토 반영)** | 5분 |
| 09:00 묶음 만들기 | 회사 알림 전용 Worker(`notify-only-main.ts`)에 등록 하나 추가(마감 알림과 같은 모양) | 5분 |
| 발송 | 알림 Worker의 기존 outbox 회차(2초) | 2초 |

- 전체 Worker(`main.ts`)에도 같은 등록을 넣되, 지금처럼 회사에서는 띄우지 않는다.
- env: `DIGEST_ORG_SLUGS`·`DIGEST_START_DATE`(두 Worker 공통), 선택 `DIGEST_MIN_SCORE`(기본 80), `DIGEST_DAILY_ANALYZE_LIMIT`(기본 300). `.env.example`·`infra/env/*.env.example`·`pnpm check:env`에 키 이름만 더한다.

## 8. 화면

- **공고 목록 `/bids?digest=<YYYY-MM-DD>`**: 그 조직의 그 날짜 묶음 행을 읽어 얼린 사업기회 id 순서(점수순)로 보인다. 화면은 지금처럼 `loadOpportunityPage`·`opportunity_list_items`를 쓴다. 다른 필터·정렬은 이 모드에서 숨기거나 끈다. 위에 띠 하나: "{M/D}({요일}) 아침 추천 공고 {N}건 · SOL Score {기준}점 이상 · [전체 공고 보기]"(필터 해제).
  - 묶음이 없거나 남의 조직 날짜면 빈 상태 문구("이 날짜의 추천 묶음이 없습니다")를 보인다.
  - 카톡에서 열리므로 모바일 웹이 주 경로다. 360·390·768·1280·1440px를 확인한다(ADR-072).
- **개인 설정 "카카오톡 알림" 칸**: 설명 문구에 "직접 분석한 공고가 추천·보류이면 바로, 평일 오전 9시에 그날 추천 공고 묶음"을 적는다. 스위치는 그대로 하나다.
- API: `GET /api/v1/opportunities`에 `digest` 쿼리(날짜)를 더한다. `GET /api/v1/bids`(`bid_list_items`)는 바꾸지 않는다. 다른 필터와 함께 오면 400 **(검토 반영)**.

## 9. 보안

- 묶음 표는 조직 RLS로 읽는다. 웹은 service role을 쓰지 않는다.
- 카톡으로 나가는 값은 지금 피드와 같다: 공고 공개 정보 + 조직 내부 점수·권고. [[09-SECURITY|09]]의 카카오 외부 전송 항목에 "묶음"을 더한다.
- 로그는 건수·id만.

## 10. 시험과 증거 (MVP 핵심만)

- 순수 규칙(Vitest): 영업일·07/09시 시각 판정과 묶음 창 계산(월요일·KST 경계), 고르기 정렬·기준, 템플릿 선택(0·1·2·3건 이상)과 리스트 템플릿 한도.
- DB(PGlite `scripts/database.test.mjs`): `bid_digests` RLS(자기 조직만 읽기·anon 거부·authenticated 쓰기 거부), `freeze_bid_digest` 멱등(두 번 불러도 행·이벤트 1건), `claim_kakao_digest` 한 사람 하루 한 번.
- 소비자: `BID_DIGEST` 처리에서 claim 뒤에만 발송, 두 번 처리해도 한 통.
- 화면: `?digest=` 목록 브라우저 시험 1건, 5개 폭 스크린샷.
- 운영 증거: 수동 실행 dry-run 출력, 실발송 1회 결과(행 상태·claim), 카톡 수신 화면(사용자 녹화) → `docs/evidence/kakao-digest/`.

## 11. 운영 반영 순서 (항목마다 승인)

1. 마이그레이션 `db:push`(표·함수·제약) → `db-verify`.
2. 회사 Analysis·알림 Worker 이미지 재생성(env `DIGEST_ORG_SLUGS=solideo`, `DIGEST_START_DATE=2026-11-03`). 재생성 시간 창(정각 +15분 ~ 다음 정각 −30분)과 `rollback-*` 태그 규칙을 따른다. 시작일 전이라 자동 회차는 돌지 않는다.
3. main push → Vercel(목록 `?digest=` 화면).
4. 운영자 수동 실행 `--dry-run` → 실발송 1회(회사 Qwen 호출·카톡 실발송) → 녹화.
5. 11-03(월) 09:00 첫 자동 회차 확인.

Worker를 웹보다 먼저 바꾼다. 시작일 env 때문에 2번 뒤 자동 발송이 없고, 실발송(4번)은 3번 뒤에 하므로 깨진 링크가 나가지 않는다.

> [!important] 카카오 실발송 상시 켜기 — 사용자 결정(2026-10-30, 선택지 1)
> 알림 Worker의 `NOTIFY_KAKAO_PROVIDER=memo`를 **상시 켠다**. 사람이 누른 분석의 즉시 카톡(`BID_RECOMMENDED`)도 상시 나간다. 실행서 `infra/company/README.md` §9.6의 "시험이 끝나면 바로 끈다"와 ADR-068 6번을 새 ADR로 개정하고, `infra/compose.notify-only.company.yaml`의 기본값을 memo로 바꾼다(키 4개 누락이면 기동 거부는 그대로). 실제 재생성은 §11 2번의 승인을 따른다.

## 13. 빌더에게 맡기는 것

- 07시 행 만들기를 DB 함수로 할지 repo로 할지, 고르기 SQL의 세부 모양(목록 표 사용 전제).
- 리스트 템플릿 `description` 줄의 정확한 문구·자르기 길이(4줄 안).
- 수동 실행 CLI의 파일 이름과 `pnpm` 스크립트 이름.
- `?digest=` 모드에서 기존 필터 UI를 숨길지 비활성으로 둘지.

### 설계자가 정한 것 (사용자 확인 전 판단)

- 대상 조직 스위치 `DIGEST_ORG_SLUGS`(비면 꺼짐), 시작일 `DIGEST_START_DATE`(전에는 수동만).
- 묶음 창은 직전 묶음의 `window_end`부터 이어 붙임. 자동 분석·고르기는 직전 창까지 거슬러 봄(늦게 끝난 공고를 다음 날 받음).
- 첨부 파싱 대기 공고는 그날 자동 분석에서 미룸.
- 수동 실행은 오늘 날짜만, `--resend`로 DEAD 묶음 다시 보내기.
- `?digest=`는 `GET /api/v1/opportunities`에 붙이고 사업기회 id로 얼림.
- 하루 자동 분석 상한 300건·동시 진행 2.
- 09:30까지 분석 완료를 기다림, 08:55에 자동 분석 마감.
- 묶음 내용은 조직마다 같음(즉시 카톡과 겹쳐도 다시 보임).
- 늦게 뜬 Worker는 그날 안에는 한 번 보냄, 지난 날짜는 몰아 보내지 않음.
- 1건은 피드 템플릿, 0건은 보내지 않음.
- 창 밖 오래된 미분석 공고는 자동 분석하지 않음.

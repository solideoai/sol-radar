# 설계: 데모 강화 2건 (BOOST-1 실공고 선별 깔때기 · BOOST-2 가정 재계산)

사용자 승인(2026-10-20, §11). 다음은 계획(단계별 파일·완료 기준)이다. 정본(`docs/00`~`23`, `PROGRESS.md`)은 고치지 않는다. 정본에 반영할 절 목록은 §8에 두고, 반영은 정본 담당 세션이 한다. 코드는 main `554b34c` 기준으로 읽었다.

## 1. 왜 하는가

사용자 판단(2026-10-20): "해커톤이 다음 주인데 데모용으로도 기능이 약하다. 대상을 꼭 받아야 한다."

현재 5분 데모([[18-HACKATHON|18]] §6)의 약점을 코드·증거로 확인한 결과:

1. **목업처럼 보인다.** 5분 중 약 4분이 "(가상)" fixture 공고와 `mock` 응답이다. 실제 공고는 3:30 S-LIVE 1건이고, 회사 GPU 추론 엔드포인트(C1 ③)가 없으면 `PARTIAL` WATCH 73 "확인 필요"로 끝난다(`docs/evidence/demo-day/20261020-1434/run-modes.md`). 배점 실용성 30의 "실제 업무에 바로 적용 가능한가"에 약하다.
2. **기억에 남는 순간이 없다.** 대시보드는 숫자 카드 5개와 표 2개(`docs/evidence/demo-day/20261020-1009/screenshots/20261020-demo-dashboard-loaded-1440.png`), 상세는 긴 세로 스크롤, 흐름의 끝은 결정 라디오 버튼이다.
3. 경쟁 4곳이 공개 페이지에서 보여 주지 않는 축(참가자격 판정·참여 권고·근거, [[18-HACKATHON|18]] §3.2.1)을 우리는 갖고 있는데, 데모에서 그것이 "판정 결과 읽기"로만 보인다. 판정이 **업무를 바꾸는 장면**(하루치 공고를 걸러 준다, 안 되는 공고를 되게 하는 조건을 알려 준다)이 없다.

있는 자산:

- live 수집은 동작한다. 2026-10-20 24시간 창에서 나라장터 정보화 공고 86건, 그중 72건에 구조화 자격(면허제한 110행·참가지역 2·허용업종 1), 82건에 첨부가 있었다(같은 증거 폴더 `live-bids.txt`·`structured-requirements-count.txt`). 규칙만 쓴 분석은 3.4초였다.
- 규칙 엔진 `analyze()`(`web/server/scoring/analyze.ts:45`)와 자격 판정 `assessQualifications()`(`web/server/scoring/qualification.ts`)는 DB·네트워크·시각에 닿지 않는 순수 함수다. 추출(`extraction`)이 `null`이어도 API 구조화 필드(`structuredQualifications`)로 판정한 항목(`basis: "API_FIELD"`)을 낸다. 다만 추출이 없으면 필수 "참가 자격 요건" 확인 필요(`NOTICE_INFO_MISSING`, `basis: "EXTRACTION"`) 1건이 늘 붙어 종합 판정이 `SATISFIED`가 될 수 없다(`qualification.ts:266-279`, `:494-498`). 면허제한이 2행 이상이면 행마다 `AMBIGUOUS_MATCH` 확인 필요다(`:325-337`, 16 미결정 19번).
- X6a 녹음(`fixtures/recorded/train/`, gitignore, main 작업 폴더에만 있음)에 공고 144건의 면허제한 응답이 있다. 118건이 면허제한 1행 이상, `lmtGrpNo` 2그룹 이상은 6건이다(`docs/evidence/eval/recording-20261020.md` §76). 공공 API를 부르지 않고 선별 분포를 잴 수 있다.
- 분석 입력 전체가 `score_runs.input_snapshot`(jsonb, `AnalysisInput`)에 저장된다(`supabase/migrations/20261019000004_score_runs.sql:58`). 저장된 run 을 그대로 다시 계산할 수 있다.
- 가상 솔리데오 프로필(`fixtures/company/solideo-profile.json`)은 보유 5종(소프트웨어사업자·직접생산·중소기업·ISO 27001·CMMI L3)과 미보유 4종(정보통신공사업·방산업체·ISMS-P·CSAP), 최대 계약 50억 원을 갖는다. 실제 공고와 대조하면 통과·탈락이 섞여 나온다(분포는 §4.1 0단계에서 확인).

## 2. 목표·비목표·실패 조건

**목표**

- G1. 데모 첫 장면을 **실제 나라장터 공고**로 시작한다. "어제 하루 정보화 공고 N건 중 우리 회사가 자격으로 탈락하는 공고 a건(사유별), 정보가 부족해 확인이 필요한 공고 b건, 검토할 공고 c건"을 한 화면에서 보여 준다. (BOOST-1)
- G2. NO-BID·WATCH 공고에서 "무엇이 있으면 들어갈 수 있는가"를 즉시 보여 준다. 부족한 자격·기술을 "보유했다고 가정"하면 같은 입력으로 점수·권고가 다시 계산된다. (BOOST-2)
- G3. 두 기능 모두 발표 5분을 늘리지 않는다(§7 시간표).
- G4. 10-23 기능 freeze 안에 끝난다. 끝나지 않으면 데모에서 빼고 지금 시나리오로 돌아간다.

**비목표**

- 새 공고 자동 정밀 분석(Qwen·결정 모델 일괄 호출). 핵심 컷에 없고([[12-ROADMAP|12]] C3 아래 문단), GPU 하나를 concurrency 1로 쓴다(`web/worker/analysis-job.ts:359`).
- 가정 시나리오 저장·공유·결정 기록 연결.
- 공동수급 규정(분담이행·공동이행에 따른 면허 인정)의 판정. 가정은 "보유 가정"일 뿐 공동수급 적법성을 판정하지 않는다.
- `/bids` 목록에 선별 결과 필터 추가.

**실패 조건(기술적으로 돌아가도 실패)**

- F1. 이번에 새로 만드는 카드·띠에 확률·승률·"수주 가능성"처럼 읽히는 수치가 나온다(ADR-007 범위 외 "승률 예측"). 기존 결정 모델 패널의 "확률 분포(충족·수주 확률 아님)" 고지(`web/components/bids/kev-opinion.tsx`)는 그대로 둔다.
- F2. 정보 부족을 탈락으로 센다. `NEEDS_REVIEW`(확인 필요)는 탈락과 다른 칸이다([[18-HACKATHON|18]] D3 "정보 부족 ≠ 미충족").
- F3. 가정 결과가 실제 분석·결정 기록·알림·감사 로그에 섞인다. 가정은 DB에 아무것도 쓰지 않는다.
- F4. 실제 공고와 가상 회사 프로필의 조합을 숨긴다. 선별 화면에도 "실제 공고 × 가상 회사 프로필" 표시가 있어야 한다.
- F5. 핵심 컷(C1~C9)의 일정·작업자를 빼앗거나 핵심 컷 코드 경로(수집 저장 RPC, analysis job, `analyze()` 계산식, 골든 94/72/68)를 바꾼다.

## 3. 제약

- 기술 스택·구조는 [[16-DECISIONS|ADR-017]] 그대로다. 서버 코드는 `web/server/<도메인>/`, Route Handler 는 `/api/v1`, 데이터 접근은 anon 키 + RLS. service role 키는 쓰지 않는다.
- 마이그레이션은 되도록 만들지 않는다. 필요하면 새 파일로만 쌓고, 생성 타입(`pnpm db:types`)을 같은 커밋에 넣는다.
- 화면은 1440·1280 두 폭만 확인한다(모바일 없음). 색·글꼴은 `design/tokens.json`에서만 온다.
- 기능 freeze 10-23, 최종 리허설 10-24, 제출 10-27([[12-ROADMAP|12]] freeze ~ D-day).
- 작업은 `sol-radar-worktrees/<이름>` worktree 에서 하고, main 병합은 병합 게이트 세션을 거친다. 무거운 검증(`pnpm verify`·e2e·build)은 공용 슬롯 스크립트로 감싼다.
- live 수집은 공공 API 개발계정 한도(서비스당 1,000건/일)를 쓴다. 24h 창 1회에 약 266회다(`run-modes.md` "live 수집 1회"). ADR-034 B1 검증 전에는 `live`·`fixture` 모드 기동을 하지 않는다.
- 결정 모델(Bosun) 의견은 가정 재계산에서 다시 부르지 않는다. 저장된 `input.kev`를 그대로 둔다.

## 4. BOOST-1 실공고 선별 깔때기

### 4.1 무엇을 하는가

대시보드 맨 위에 "오늘 아침 선별" 카드 하나를 더한다. 대상은 **마감 전 실제 공고 전체**(`is_demo=false`, 최신 revision, `deadline_at > now`)다. 각 공고를 지금 조직의 회사 프로필로 **공고 API 자격 필드만** 판정해 칸을 나눈다. 첨부(제안요청서)의 자격은 이 단계에서 보지 않으며, 카드가 그렇게 말한다.

선별이 보는 판정: `assessQualifications()` 결과 가운데 `basis: "API_FIELD"`인 필수 항목만(면허제한·허용업종·참가지역·보조 조회 실패). 추출이 없어서 붙는 "참가 자격 요건"(`basis: "EXTRACTION"`)은 "첨부 자격 미확인"으로 따로 표시하고 칸 판정에서는 뺀다.

| 칸 | 조건 | 화면 이름(초안) |
|---|---|---|
| 제외 | API 근거 필수 항목에 `NOT_SATISFIED` 가 하나 이상 | 공고 자격으로 제외 |
| 확인 필요 | 제외가 아니고 API 근거 필수 항목에 `NEEDS_REVIEW` 가 하나 이상(면허제한 여러 행 `AMBIGUOUS_MATCH`, 사전에 없는 면허, 보조 조회 실패), 또는 보조 조회 전에 수집된 live revision(`auxLookup` 없음) | 정보 부족 · 확인 필요 |
| 통과 | 나머지 | 공고 자격 통과 · 첨부 자격 미확인 |
| 정밀 분석 | 제외가 아닌 공고 가운데 최신 `score_runs`(COMPLETED·PARTIAL)가 있는 공고. 권고 BID·WATCH·NO-BID 수 | 분석 완료 |

- 제외·확인 필요 칸은 사유별 건수를 붙인다(예: "정보통신공사업 등록 미보유 4", "면허제한 여러 행 12"). 사유 이름은 판정 결과의 요건 이름과 사유 코드에서 온다.
- 규모 한도 초과(`SCALE_LIMIT_EXCEEDED`)는 칸이 아니라 공고 행의 경고 배지다. [[08-SCORING|08]] §3.4(권고를 바꾸지 않고 경고로만)와 같게 한다.
- 통과 칸은 공고 목록(제목·발주기관·예산·마감)으로 펼쳐 상세(`/bids/[id]`)로 간다.
- 칸은 늘 선별 결과로 정한다. 정밀 분석 run 이 있는 공고도 칸은 바뀌지 않는다. run 의 결과(첨부 자격 포함)는 상세 화면이 정본이다(구현자 판단 아님, 메인 세션 결정).

카드에 늘 보이는 것: 수집 시각(최근 `ingest_runs`), 대상 공고 수, "실제 공고 × 가상 회사 프로필", "공고 API 자격만 판정 · 첨부 자격은 상세 분석에서 · 저장하지 않음 · 알고리즘 sol-v0.1.0".

**0단계(게이트, 1~2시간):** 구현 전에 X6a 녹음(`fixtures/recorded/train/`, 공고 144건 면허제한 응답)을 정규화해 선별 함수를 돌리고 칸 분포를 잰다. 공공 API 를 부르지 않고 B1 검증과 무관하다. 결과를 사용자에게 보고하고 진행 여부를 받는다(§11 열린 질문 1).

### 4.2 어떻게 (정해진 것)

- **저장하지 않는다.** 선별은 읽을 때마다 계산하는 보기다. `score_runs`를 만들지 않고, worker·큐·gateway 를 부르지 않는다. 공고 수십~수백 건에 순수 함수라 요청 안에서 끝난다.
- 판정 로직은 새로 만들지 않는다. 규칙 엔진의 자격 판정(`assessQualifications`)과 규모 한도 검사(`scaleFit`)를 `extraction=null`로 재사용하고 `basis`로 거르는 순수 함수 `triage(bid, profile, today)`를 점수 도메인(`web/server/scoring`)에 두고 배럴로 내보낸다. 새 규칙은 하나뿐이다: live 공고인데 `auxLookup`이 없으면(보조 조회 전 수집) 확인 필요로 센다. 이 규칙이 없으면 판정 항목이 0개라 통과로 잘못 센다(`qualification.ts:452-454`). `analyze()`와 계산식은 바꾸지 않는다.
- 공고·구조화 자격·보조 조회 상태·회사 프로필은 사용자 세션(anon 키 + RLS)으로 읽는다. 읽기 경로가 RLS 로 막혀 있으면 정책을 넓히지 말고 사용자에게 보고한다.
- 대상이 0건이면(live 수집 전) 카드는 "실제 공고가 아직 없습니다. 수집 관리에서 수집을 실행하세요" 상태를 보여 주고 숨지 않는다.

### 4.3 데모 데이터

- 발표 당일 S0 에서 live 수집 1회를 돌린다(약 266회 호출). 이미 S-LIVE 사전 run 을 위해 하는 단계와 같다([[19-DEMO-SCENARIO|19]] §3). `pnpm demo:reset`은 live 공고를 보존한다.
- 리허설에서는 수집 시각이 그대로 보이므로 "어제 하루"라고 말할지 "10-22 수집"이라고 말할지는 화면 값을 읽고 정한다. 녹화·이전 수집을 오늘 것이라고 말하지 않는다.
- live 수집을 못 하면 그때 DB에 있는 실제 공고로 보여 주고 수집 시각을 그대로 말한다. 실제 공고가 0건이면 이 장면을 빼고 지금 대시보드 장면으로 간다.

## 5. BOOST-2 가정 재계산

### 5.1 무엇을 하는가

공고 상세(`/bids/[id]`)에서 최신 분석 run 이 있을 때, 부족한 항목 옆에 "보유 가정" 스위치를 둔다.

| 가정 종류 | 스위치가 붙는 곳 | 입력에 하는 일 |
|---|---|---|
| 면허·등록 보유 가정 | 필수 자격 중 회사 미보유로 `NOT_SATISFIED`·`NEEDS_REVIEW`인 항목 | `profile.licenses`(또는 `industryCodes`)의 해당 코드를 `HELD`로 바꾸거나 더한다 |
| 기술 보유 가정 | 점수 분해 "기술 스택 적합"에서 회사에 없는 필수·우대 기술 | `profile.technologies`에 그 기술을 더한다 |

스위치를 켜면 화면 위쪽에 "가정 시나리오" 띠가 나타난다: 켠 가정 목록, **원래 → 가정** 권고와 SOL Score, 바뀐 요소별 점수, 자격 판정 변화. 띠에는 늘 "가정 결과입니다. 저장되지 않고 결정 기록에 쓰이지 않습니다." 와 "결정 모델 의견은 가정에 포함하지 않았습니다."가 붙는다. "가정 지우기"로 원래 화면으로 돌아간다.

데모 예: FX-03(NO-BID 68, 정보통신공사업 등록 미충족)에서 "정보통신공사업 등록 보유 가정"을 켜면 자격 판정이 충족으로 바뀌고 권고가 NO-BID → WATCH 가 된다. 자격 판정은 점수에 들어가지 않으므로 점수는 68 그대로다. BID 까지 가려면 부족 기술 가정을 더 켜야 한다(검토자 추산: 기술 2개를 더하면 78, 구현 뒤 골든으로 확인). 바뀐 숫자는 구현 뒤 골든 시험으로 고정하고, 그 전에는 발표 원고에 숫자를 쓰지 않는다.

### 5.2 어떻게 (정해진 것)

- 서버에서 계산한다. 저장된 run 의 `input_snapshot`을 사용자 세션(RLS)으로 읽고 `analysisInputSchema`로 검증한 뒤, 가정을 적용하는 순수 함수(`applyAssumptions(input, assumptions)`, 점수 도메인)를 거쳐 `analyze()`를 부른다. 원래 결과와 가정 결과를 함께 돌려준다.
- `config.today`·`config.thresholds`·`bid`·`extraction`·`team`은 스냅샷 그대로 둔다. 바뀌는 것은 가정이 건드린 `profile` 필드뿐이다.
- 가정 계산에서는 `kev`를 `null`로 둔다. 띠의 "원래" 값도 같은 스냅샷을 `kev=null`로 다시 계산한 것이다. 점수·권고·자격 판정은 결정 모델 영향을 받지 않으므로 저장값과 같다(`web/server/scoring/kev-no-override.test.ts`). 저장된 결정 모델 응답은 원래 프로필을 보고 낸 것이라, 그대로 두면 가정 결과에 `KEV_MANDATORY_RISK`·`MODEL_RULE_DISAGREEMENT` 같은 낡은 플래그가 붙는다(`web/server/scoring/decision.ts:104-108`). 띠는 "결정 모델 의견은 가정에 포함하지 않았습니다"라고 말한다. 원래 결과와 가정 결과의 차이를 비교할 때 결정 모델 플래그는 빼고 본다(메인 세션 결정).
- DB에 아무것도 쓰지 않는다. `score_runs`·`bid_reviews`·`audit_logs`·알림·outbox 모두 그대로다.
- 진입점은 Route Handler `POST /api/v1/analyses/{id}/what-if` 하나(본문: 가정 목록, zod 검증)로 한다. 다른 조직의 run 이면 지금 분석 API 와 같이 404다. 가정 목록은 그 run 의 입력에서 실제로 부족했던 항목만 받는다(임의 코드·임의 기술 문자열을 받지 않는다).
- 화면은 클라이언트 상태(스위치)만 갖고, 스위치가 바뀔 때마다 위 API 를 부른다.
- 결정 패널은 가정과 무관하다. 가정 값을 결정 사유에 자동으로 넣지 않는다.

### 5.3 시험 기준

- 가정 0개면 가정 결과가 원래 결과와 같다(같은 `inputSnapshotHash`가 아니라 같은 점수·권고·자격 판정. 스냅샷을 다시 계산하면 저장값과 같아야 한다).
- 가정 하나가 그 항목 외의 입력을 바꾸지 않는다.
- FX-03 정보통신공사업 가정, FX-02 기술 가정의 결과를 골든으로 고정한다.
- 다른 조직 run → 404, 미분석 공고 → 상세에 스위치가 없다.
- 호출 전후로 관련 표의 행 수가 같다(쓰기 없음).
- 새 카드·띠에 확률·승률 문구가 없다(F1).

## 6. 화면 배치 (초안, 디자인 스펙은 구현 전에 web-designer 가 낸다)

## 11. 사용자 결정 (2026-10-20)

1. BOOST-1은 0단계 게이트(X6a 녹음 144건 분포)를 먼저 잰다. 결과를 보고 ① 그대로 진행 ② 미결정 19번(면허제한 여러 행 AND/OR) 해석을 근거와 함께 확정해 규칙을 고친다(핵심 엔진 변경, ADR) ③ BOOST-1을 뺀다 중에서 사용자가 고른다. 게이트 전에는 BOOST-1 화면을 만들지 않는다.
2. FX-03 가정 장면은 스위치 1개(정보통신공사업 등록 보유 가정, NO-BID → WATCH, 점수 그대로)로 끝낸다. "부족 항목 모두 가정" 버튼은 만들지 않는다.
3. 이 문서 승인을 §8 ADR 제안 승인으로 본다. 정본 반영은 정본 담당 세션이 하고, 구현은 worktree 에서 나란히 시작한다. main 병합은 정본 반영 뒤 병합 게이트를 거친다.

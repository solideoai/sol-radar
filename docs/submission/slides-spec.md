# 발표 덱 제작 명세 (pptx 스킬용)

이 문서 하나로 pptx 스킬을 가진 AI 가 발표 덱을 만든다. 사람이 읽는 대본이 아니라 **슬라이드 제작 명세**다. 2026-10-21 사용자와 합의한 구성(18장 · 20분 · 영상 클립 5개)을 담고, `slides-outline.md`(12장 구성안)를 대체한다. 캡처 매핑은 `slides-outline.md` 의 "캡처 매핑" 절을 그대로 쓴다. 수치는 정본([[18-HACKATHON|18 해커톤]] · [[19-DEMO-SCENARIO|19 데모 시나리오]] · [[08-SCORING|08 점수]] · `limitations.md`)과 이 문서 부록 C 출처표에 있는 것만 쓴다.

**발표 조건(2026-10-21 사용자 입력)**: 사내 해커톤. 심사위원은 사장 · 부사장 · CFO 와 AI 심사위원(Claude Fable 5.1). 30분 중 발표 20분, Q&A 10분. 시연은 라이브가 아니라 **녹화 영상을 덱 안에 삽입**한다. AI 심사위원은 덱(또는 서비스)을 **마크다운으로 변환한 파일**로 채점한다. 평가 배점은 실용성 30 · 사업적 창의성 25 · 완성도 25 · 확장 가능성 20([[18-HACKATHON|18]] §4).

> [!warning] 18 §1 과 다른 점
> [[18-HACKATHON|18]] §1 은 심사자를 "사람 5인 + Fable 5.1" 로 적었다. 이 문서는 사용자 입력(사장 · 부사장 · CFO + AI)을 따른다. 정본 갱신은 부록 D.

### 0.2 AI 심사위원(md 변환) 대응 규칙

md 변환본에는 글만 남는다. 그림 · 영상 · 도형 안 글자는 사라질 수 있다. 그래서:

1. **모든 그림 · 영상 자리에 캡션 글 상자**를 둔다. 캡션은 `[그림]` 또는 `[영상 클립 n · 길이 · 실행 모드]` 로 시작하고, 화면에 보이는 핵심 값(공고 ID · 점수 · 판정 · 배지 문구)을 글로 적는다. 아래 장별 명세의 "캡션" 문구를 그대로 쓴다.
2. 표는 **실제 표 개체**로 만든다. 표를 그림으로 넣지 않는다.
3. 숫자 · 판정 · 모델명은 도형 안이 아니라 **글 상자**에 넣는다. 흐름 띠(도형)에도 같은 내용을 글 한 줄로 아래에 반복한다.
4. 모든 장에 **발표자 노트**를 넣는다. 노트에는 말할 내용 전문, 근거 문서 경로, 출처 URL 을 적는다. md 변환에 노트가 포함되는지는 변환 도구에 따라 다르므로, 채점에 꼭 필요한 근거는 슬라이드 본문의 출처 줄에도 적는다.
5. 금지 표현(0.4)은 노트에도 쓰지 않는다.

### 0.3 상태 값

장별 명세의 "상태" 열은 다음 중 하나다.

- **확정**: 정본에 있고 바뀌지 않는다. 그대로 만든다.
- **재확인**: 발표 전 정본 · 증거에서 값을 다시 확인한다. 값이 바뀌면 바꾼다.
- **측정 뒤 채움**: 실험 · 조사 결과를 기다린다. 값이 없으면 "측정 전" 글자를 남기고 추정값을 넣지 않는다.
- **green 조건**: 10-24(토) 22:00 기능 freeze([[16-DECISIONS|ADR-042]])까지 해당 기능이 main 에서 green 이면 넣고, 아니면 명세에 적힌 **대체 문장**으로 바꾼다.

### 0.4 금지 표현 (18 §5 · §7 · §8, `limitations.md`)

| 쓰지 않는 것 | 대신 쓰는 것 |
|---|---|
| "충족 확률" · "수주 확률" · "낙찰 확률" · "승률" | "SOL Score 는 내부 적합도이며 낙찰 확률이 아니다" |
| "30분 → 10분 단축했다" | "30분 → 10분 은 가설이다. 예비 검증(n=3)은 하지 않았다" |
| "HWP · PDF 첨부를 파싱한다" | "첨부는 목록만 저장한다. 파싱은 미구현이다" |
| "AI 가 설명을 생성한다" · "의미 검색" | 설명은 템플릿 문장이고 Qdrant 검색은 미구현이다 |
| 녹화를 "실시간" 이라 말하기, mock 결과를 실모델 결과라 말하기 | 모든 클립 자막에 "녹화 · 실행 모드 mock" |
| "경쟁사는 이 기능이 없다" | "공개 페이지에서 미확인" |
| 모델 성능 수치, 한국어 성능 | 평가 리포트(`docs/evidence/eval/`)가 나오기 전에는 말하지 않는다 |
| "파인튜닝했다" | 결과를 받았으면 Δ 와 95% CI, 못 받았으면 "회사 측 미실행 · 결과 없음" |
| "매일 수백 건" 같은 근거 없는 규모 | 부록 C 의 공식 통계만 |
| 결제 · 구독 · 모바일 · 자동 투찰 · 승률 예측 | 범위 외. 언급하지 않는다([[16-DECISIONS|ADR-007]]) |

## 2. 장별 명세

각 장은 제목 · 레이아웃 · 화면 글(그대로 넣는다) · 그림/영상 · 캡션 · 발표자 노트 · 근거 · 상태로 적는다. "화면 글" 의 `{…}` 는 발표자가 채우는 자리다.

### 슬라이드 1 — 표지 (0:20)

- 레이아웃: 가운데 정렬. 워드마크(너비 4 in) → 한 줄 정의 → 행사 · 발표자.
- 화면 글:
  - SOL RADAR
  - 우리 회사 기준으로 "이 입찰에 들어가야 하는가"를 근거와 함께 10분 안에.
  - 솔리데오 사내 해커톤 2026 · 발표 20분 + Q&A 10분
  - 발표자 `{이름 · 부서}`
- 발표자 노트: "SOL RADAR 는 공공 SI 영업팀이 '이 입찰에 들어가야 하는가' 를 근거와 함께 판단하도록 돕는 의사결정 지원 플랫폼입니다. 낙찰 확률을 지어내지 않고, 자격 판정 · 점수 · 근거를 보여 주며, 최종 결정은 사람이 내리고 기록합니다." (근거 [[18-HACKATHON|18]] §1)
- 상태: 확정.

### 슬라이드 2 — 아이디어의 출발: 입찰 전에 있었으면 했던 네 순간 (0:50)

- 레이아웃: 제목 + 2×2 칸. 칸마다 번호와 한 문장. 아래 한 줄.
- 화면 글:
  1. 입찰 전에 영업팀 · 경영진 · 사업 참여자가 **우리에게 맞는 공고를 미리 추천**받는다.
  2. **우리 직원들의 역량**을 기준으로 수행 가능 · 불가능을 판정받는다.
  3. 그 공고에서 우리 회사가 **어디에 강하고 어디가 약한지** 본다.
  4. 공고를 **카카오톡으로** 받아본다.
  - 공고를 찾아주는 도구는 이미 있다. 우리 회사 기준으로 AI 가 판단해 주는 사내 서비스는 없다.
- 발표자 노트: 네 순간은 발표자(사용자)가 2026-10-21 에 적은 원문이다. 제품 용어로 1 은 추천 공고(`BID_RECOMMENDED`, [[16-DECISIONS|ADR-038]]), 2 는 필수 자격 판정 + 인력 가용성 점수([[08-SCORING|08]] §2 · §5), 3 은 5요소 점수 분해 · 미충족 사유 · 가정 재계산([[16-DECISIONS|ADR-037]]), 4 는 카카오톡 "나에게 보내기"(ADR-038)다. 슬라이드 12 의 카카오 10초가 실제 나라장터 공고 추천의 휴대폰 수신 녹화다〔10-25 결과 대기〕. 마지막 줄의 "찾아주는 도구" 는 사용자 진술이고 도구 이름은 확인하지 않았다. 이름을 말하지 않는다.
- 상태: 확정(원문, 문구 유지). 4번은 슬라이드 12 의 카카오 10초와 연동한다. 녹화를 못 하면 4번 원문은 두고, 발표에서 "카카오톡으로 받는 장면을 보였다"고 말하지 않는다(2026-10-24 사용자 재결정(실제 나라장터 공고 추천의 카카오 실수신을 녹화, [[16-DECISIONS|ADR-038]] 재개정)).

### 슬라이드 3 — 공공 AI 예산은 늘고, 공공 SW 사업은 해마다 1만 6천 건 (0:50)

- 레이아웃: 제목 + 숫자 카드 4개(2×2). 카드는 큰 숫자(44pt, `#1B64DA`) + 설명 2줄. 아래 보조 한 줄 + 출처 줄.

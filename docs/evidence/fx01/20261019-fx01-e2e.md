## 두 seed의 공존 검사

데모 계정은 `scripts/demo/plan.mjs`의 `admin/sales/analyst/viewer@soltech.invalid`, `viewer@other.invalid`다. 기존 인증 시험의 `seed-*@example.test` 5명과 이메일이 다르며 비밀번호도 별도다. 새 시험은 `demo:reset`에 사용한 `DEMO_SEED_PASSWORD` 환경변수만 사용한다. service role로 시험을 실행하지 않는다.

| 검사 | 실제 결과 |
| --- | --- |
| `db-seed` 실행 | 조직 생성 INSERT에서 RLS 403. 현재 ADR-026 운영자 전용 조직 생성 정책과 템플릿 seed의 일반 owner 생성이 충돌한다. |
| 기존 `demo:reset` 구현 실행 | 성공. `orgs=2 users=5 profileRevisions=2 people=200 portraits=200 bids=19 quarantined=1 reviews=2 isDemo=true`. |
| 데모 seed 후 `db-seed` 재실행 | 같은 RLS 403. 기존 데모 계정·조직 자료는 남아 있다. |
| 양쪽 계정 | Auth 총 10명: `seed-*` 5명 + 데모 5명. 명부 200명·scoring 27명·공고 19건·리뷰 2건 유지. |
| 사전 분석 | score_runs 0건. seed 자체는 점수 결과를 만들지 않는다. 상위 담당 구현으로 사전 분석이 필요하다. |

계정과 자료는 함께 존재하지만, **현재 `test:e2e:auth` 실행 경로는 호환되지 않는다**. 실제 `pnpm -C web test:e2e:auth fx01-flow.spec.ts --project=chromium`은 선행 `db-seed.mjs`에서 종료 코드 1로 끝나 Playwright에 도달하지 않는다. 패키지 스크립트나 seed를 임의로 바꾸지 않았다.

검사 driver 첫 시도에는 DB용 `MOCK` 대신 `mock`을 직접 전달한 호출 실수가 있었다. 기존 `toRunMode("mock")` 변환을 사용하도록 외부 driver만 정정해 데모 seed 정상 완료를 확인했다. 이 실수를 앱 결함으로 분류하지 않는다.

새 시험의 직접 실행 명령:

```sh
pnpm -C web exec playwright test -c playwright.auth.config.ts \
  fx01-flow.spec.ts --project=chromium --no-deps --workers=1 --trace=off
```

기존 setup은 `seed-*` 계정의 템플릿 팀 세션을 준비한다. 이 진단 실행은 해당 의존성 5건을 실행하지 않고, 자체 데모 로그인과 빈 storageState를 가진 새 시험 2건을 **모두 실행**했다. 표준 전체 인증 E2E 실행과 구분한다. 비밀 비밀번호가 trace에 남지 않도록 이 실행의 trace만 끈 것이며 단언·시간 제한·앱 코드는 바꾸지 않았다.

실제 RED 지점:

1. SALES 로그인·`/dashboard` 진입·대시보드 제목 확인 뒤, `BID 권고` 표의 FX-01 행이 0개여서 기대 1개 단언 실패. 상세·근거·결정·이력 단언은 이 실행에서 미도달이다.
2. 같은 조직 SALES 토큰으로 `/api/v1/bids?origin=demo&q=…` 호출 시 기대 200 대신 404. 이후 자격 200 대조군·다른 조직 자격 404·공용 공고 200 단언은 미도달이다. 이를 조직 격리 통과로 보고하지 않는다.

Playwright 프로덕션 서버는 실행 후 자동 종료되었다. `NO_COLOR`와 `FORCE_COLOR` 동시 설정에 따른 Node 경고가 있었으며 실패 원인은 위 단언 두 건이다. 전체 verify의 Python 시험에는 기존 Starlette/httpx 폐기 예정 경고 1건이 있었다. 패키지 변경은 이번 범위에 포함하지 않았다. raw 로그는 외부 전용 폴더의 `e2e-fx01-red.log`, `e2e-normal-entry.log`, `e2e-build.log`, `e2e-final-verify.log`에 보존했다.

현재 API·화면과 분석 결과를 시험에서 흉내 내지 않는다. fixture 입력을 실제 모델 추론으로 표현하지 않는다. `test.skip`, `.only`, 응답 가로채기, 조건부 단언 우회는 없다.

## 통합 뒤 실행

1. 사용자 지정 순서 Gateway → 수집 → 분석 클라이언트 → C6 화면 병합 후 최신 main을 기준으로 이 시험 브랜치를 통합한다. 현재 기준에는 Gateway만 반영되어 있다.
2. 전용 로컬 DB에 당시 main 마이그레이션을 적용하고 기존 데모 seed와 담당 worker로 mock 사전 분석을 실제 저장한다. 시험에서 score_runs를 만들지 않는다.
3. 템플릿 `db-seed`의 현재 RLS 차단을 담당 범위에서 정합화한 뒤 표준 `test:e2e:auth`로 재검증한다. 패키지 스크립트 변경은 사용자 확인이 필요하다.
4. `DEMO_SEED_PASSWORD`, 격리 대상 `SOL_RADAR_TEST_SUPABASE_WORKDIR`와 `SOL_RADAR_TEST_SUPABASE_API_URL`, `E2E_PORT=3301`을 설정하고 빌드 뒤 아래를 실행한다.

```sh
pnpm -C web test:e2e:auth fx01-flow.spec.ts --project=chromium
```

테스트가 실제 통과하기 전에는 S2~S7 전체·G1~G10·실모델 E2E를 완료로 표시하지 않는다. main 병합·push·배포는 수행하지 않는다.

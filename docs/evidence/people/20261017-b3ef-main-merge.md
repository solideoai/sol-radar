# b3ef → main 병합·검증 기록 (2026-10-17)

사용자의 코드 병합 승인에 따라 b3ef만 main에 병합했다. 공유 DB 적용·배포·push·9663 병합은 승인 범위에 포함되지 않으며 수행하지 않았다. 추가 기능 구현은 하지 않았다.

## 병합 범위와 충돌 해결

- 병합 직전 main `114a10aa245b76909c4952c3c82a473337ba0cbd`, b3ef `df51f2f560f60eb210a34a318b88a5cdb7743f26`, 9663 `694b6fac5caaaf02681a1af70a4e1d928c8a7cca`가 승인 기준과 일치했고 모두 clean이었다. 초기 검사에서 이번 작업이 만든 임시 파일 3개를 발견해 저장소 밖으로 옮긴 뒤 다시 확인했다. 다른 세션의 변경은 없었다.
- 실제 merge commit: `42a4eaddf4b21256b0a69a816371815ea2a8f779`. 부모는 main `114a10a`와 b3ef `df51f2f`다. b3ef 고유 커밋 41개를 가져왔고, main 기준 변경은 467개 파일 항목(이름 변경 3건 포함; 이전·새 경로를 별도로 세면 470개)이다. 별도의 검증 보고 커밋은 문서·증거만 추가한다.
- 예상한 `docs/11-TESTING.md`, `docs/PROGRESS.md`만 충돌했다. 준비된 해결 patch를 hunk별로 적용했으며 어느 한쪽 전체 파일을 선택하지 않았다.
- TESTING: 최신 PPL-06·07과 `team_member_scoring`, 전체 골든 94/72/68 및 운영 편집 후 기존 `score_runs` 불변 수용 조건을 모두 보존했다. 순수 계산 회귀의 통과와 전체 파이프라인 미검증을 구분했다. main §9를 유지하고 중복된 가입 QA 번호만 §9.1로 정리했다.
- PROGRESS: 양쪽의 기존 날짜 있는 작업 로그 22행을 모두 유지했다. 같은 날짜는 기존 순서를 유지하고 10월 16일 기록 뒤에 17일 QA 기록을 보존했다. 동기화 당시의 미구현 안내는 원문을 인용한 과거 기록으로 남겼다.
- main 정본 00~21 중 TESTING을 제외한 문서와 CLAUDE 22개는 기존 main과 바이트 단위로 동일하다. ADR-020·021 내용과 기존 랜딩 작업을 보존했다. b3ef의 migration 12개·생성 타입·명부·점수 입력도 보존했다.

공개·브라우저 첫 실행은 공개138 통과 뒤 Vite가 `next/image`·`nodemailer`를 추가 최적화하면서 chunk 이름이 바뀌어 브라우저 import가 실패하고 진행이 멈췄다. 새 생성 파일과 기존 요청 경로를 비교해 원인을 확인했다. 해당 작업이 시작한 프로세스만 종료(exit130)하고 로그를 보존했다. 캐시 삭제나 테스트/설정/소스 수정 없이 최적화가 끝난 같은 환경에서 정상 결합 명령을 한 번 재실행해 공개138/브라우저108을 통과했다. 첫 실행을 PASS로 표시하지 않으며 초기 의존성 최적화의 불안정성은 기록으로 남긴다.

사진 HTTP/해시와 decode는 최초 별도 probe에서 200건씩 통과한 JSON을 보존했다. 같은 probe의 후속 화면 캡처 대기에서 선택창 닫힘 전환의 두 DOM 요소를 단일 locator로 찾는 검수 스크립트 오류가 발생했다. 외부 UI probe의 대기/선택자만 고쳐 별도로 검사했고 200개 사진 검사는 반복하지 않았다. 제품 소스는 수정하지 않았다.

실제 DB는 새로 만든 전용 로컬 Supabase 프로젝트만 사용했다(API 58621/DB 58622). 기존 공유 543xx와 다른 세션의 DB는 검증 대상이 아니다. 과거 b3ef `a05217a`의 Auth95/Next200, `ca719cf`의 verify350/879 및 기존00002→00003/4 populated-upgrade 증거는 원래 SHA로 유지한다. 이번 새 검증과 혼합하지 않는다.

## 미검증·미구현 범위

- 상위 부모 TEAM 25개·GROUP 4개(총 29개)는 근거가 없어 null과 사유를 보존했다. 노드 수·종류·참조/순환 제약 통과가 완전히 연결된 본부→그룹→팀 조직도 검증을 의미하지 않는다.
- 제품 조직도·직원 목록·상세(`/people`)는 미구현/미검증이다. 공통 사진 경로 `/demo/people/<personId>.png`와 PersonAvatar fallback은 준비됐다.
- 전체 G1~G10, SOL Score 전체 파이프라인 94/72/68, 운영 정보 편집 후 실제 기존 `score_runs` 불변은 미검증이다. 순수 worked-example 회귀와 일반 인증/RLS 회귀를 전체 골든으로 승격하지 않는다.
- 전체 ADR-021 N1/N2·`sol_role=ADMIN` 정책 전환·`/ops`·신규 메뉴, 실제 외부 OAuth 제공자 연결은 완료로 표시하지 않는다.
- 운영/공유 DB의 실제 이력·데이터에서 migration을 실행한 결과, 배포 환경 검증은 없다.

## 9663 잔여 차이와 보존

9663은 `694b6fa` 그대로 유지한다. 전용 커밋 `2d416f7`(사진 생성), `8ba2810`(승인), `694b6fa`(문서 정정) 3개는 main의 조상이 아니다. b3ef에 이미 통합된 승인 PNG 200장과 manifest만 원본 바이트로 유지했다. 9663 전용 문서 설명·사진 계획 기록을 이번에 추가 병합하지 않았다.

제품 코드 병합 커밋 기준 main↔9663 차이는 311개 파일 항목이다. main의 최신 설계·가입/DB/인력 코드·랜딩과 증거, 9663의 이전 코드 및 사진 전용 문서 차이가 포함된다. 사진 200장과 manifest는 동일하다. 문서·검증 자료만 기록하는 후속 커밋은 56개 파일(신규55 + 기존PROGRESS)을 포함한다. 이를 포함한 최종 main↔9663 차이는 366개 항목이며 추가된55개 차이는 검증 보고 자료다.

## 공유 DB 적용 전 필요한 작업

1. 별도 적용 승인을 받고 대상 DB와 migration 이력을 확인한다. 현재 데이터 백업·복원 확인 및 복제본을 준비한다.
2. 복제본에서 append-only 00001~00004 적용 경로를 실제 기존 이력에 맞게 리허설한다. 특히 00003의 평가 27명 role/grade/skills/availability/created_at backfill 동일성과 기존 직원·조직·계정 ID, 과거 개인 조직 보존을 확인한다.
3. 00004의 profile-only 신규 가입과 무조직 계정 라우팅을 함께 배포할 순서를 확정한다. 현재 조직 결정·프로필 보완·가입 실패 복구와 RLS를 실제 대상 복제본에서 검증한다.
4. 일반 개발용 `db:seed`를 공유 DB에 실행하지 않는다. 이 스크립트는 시험 데이터 초기화용이며 비시드 회원이 섞인 팀을 거절하는 보존 장치가 있다. 대상 데이터를 보존할 별도의 적재 계획·검증·복구 절차를 확정한다.
5. 부모 미확정 29건의 회사 조직 근거를 확보한다. 전체 조직도 완료, 전체 SOL 기능 완료, 배포 승인을 이번 코드 병합 승인으로 간주하지 않는다.

# 16. 아키텍처 결정 기록 (ADR)

상태 값: `제안` → `채택` → `검증됨`(근거 URL·날짜 필수). 외부 사실 확인 전이면 `미검증`, 철회는 `폐기`, 해커톤에서 뺀 결정은 `해커톤 제외`다. 검증 결과는 날짜·근거 URL·결정자와 함께 이 문서에 갱신한다. 폐기한 결정도 색인 행을 지우지 않는다.

- **대체 표시**: 뒤 ADR이 앞 ADR의 조항을 바꾸면 양쪽(색인 상태 칸과 본문)에 "ADR-NNN로 대체·개정"을 단다.
- **구현·운영 상태**: 이 문서가 판정하지 않는다. [[PROGRESS]]에 있다.
- **줄인 기록**: ADR-027(폐기)·ADR-029~033·035·036(정본 반영 기록)과 ADR-042 일정 표·담당 배정은 ADR-057에 따라 한 줄로 줄였다. 원문은 git `5261730f` 의 이 파일에 있다. 색인 ADR-019 이후 행의 근거 칸은 "본문"으로 줄였고, 색인 근거 원문도 git `5261730f` 의 docs/16-DECISIONS.md에 있다.
- **순서**: 아래 색인은 번호순이고, 본문은 최신이 위다.

## ADR-068 10-29 결정 대기 9건 정리(추천안대로)

## ADR-066 버튼으로 부르는 추천 분석(Qwen 설명)·Bosun 인력 입력·연 1회 재학습 구조

**채택 (2026-10-29 사용자: "다 추천대로 하자").** 스펙은 `polaris/specs/in-progress/2026-10-29-recommendation-insight.md`, 계획은 [[2026-10-29-recommendation-insight|단계 계획]]이다.

- **계기**: 사용자 원래 계획은 회사 자료(가상 인력 200명·솔리데오 기술·과거 수행 사업)로 Bosun 을 파인튜닝해 공고 적합도를 보고, Qwen 이 "왜 추천하는지·강점·보완할 점"을 설명하는 것이었다. 하지만 지금 설명은 `/explain` 템플릿 문장뿐이다. 회사 자료는 규칙 엔진 입력에는 있지만 설명에는 쓰이지 않는다.
- **결정**:
  1. **판정은 규칙 엔진이 한다.** Bosun 은 참고 의견(검토 플래그)으로만 보인다(ADR-034 2번 유지). Qwen 설명은 판정 이름(추천·보류·비추천·`BID`·`WATCH`·`NO_BID`)을 다시 쓰지 않는다.
  2. **Qwen 은 버튼을 눌렀을 때만 부른다.** 분석된 모든 공고(추천·보류·비추천)의 상세 화면에 [추천 분석]을 둔다. 결과는 분석 run 마다 `recommendation_insights` 에 저장한다. 분석 job 의 `/explain`·`score_runs.explanation` 은 그대로다.
  3. **흐름은 분석과 같은 비동기다.** Vercel relay 는 15초 안에 끝나야 하고 202 만 성공으로 받기 때문이다. 화면 POST → redis-api 가 PENDING 행과 BullMQ `insight` job → Analysis Worker 가 gateway `POST /insight` → DONE(MODEL·TEMPLATE)·FAILED. 화면 GET 은 RLS 로 직접 읽는다.
  4. **모델 출력은 검증한다.** 모양·글자 수·숨은 문자, 없는 근거 번호, 금지어, 다른 판정 이름·참여를 권하거나 말리는 표현, 입력에 없는 숫자 중 하나라도 걸리면 규칙 결과로 만든 문장(TEMPLATE)으로 대체하고 화면에 표시한다. 분석 run 이 인젝션 의심이거나 gateway guard 가 모델 입력에서 지시문을 찾으면 모델을 부르지 않고 TEMPLATE(`INJECTION_SUSPECTED`)로 답한다. 이때 공고 인용은 보내지 않는다. 로그에 프롬프트·모델 출력을 남기지 않는다.
  5. **인력은 학습하지 않고 입력으로 넣는다.** 인력은 자주 바뀌기 때문이다. Bosun 요청의 `profileSummary.staffAvailability` 를 규칙 엔진 인력 요소(K6)와 같은 기간·가용 FTE 로 채운다. 추천 분석 요청의 `company.staff` 도 같은 값이다.
  6. **과거 수행 사업은 연 1회 재학습한다.** 최종 결정 기록이 200건 쌓이면 수동으로도 돌린다. 구조는 [[21-MODEL-TRAINING|21]] §5.7 이고 구현은 발표 뒤다. 해커톤 전에는 Bosun 을 재학습하거나 교체하지 않는다.
  7. **PaddleOCR 공유 전제를 지운다(ADR-034 10번 개정).** SOL RADAR 는 회사 PaddleOCR 을 쓰지 않는다(사용자). 회사 컨테이너는 우리 것이 아니므로 멈추거나 옮기지 않는다. GPU 1 학습·서빙 전에 메모리를 확인하는 것만 남긴다.
- **선택지(1·2·5)**: Bosun 파인튜닝을 지금 하는 안은 해커톤 일정·GPU 승인·라벨 수 때문에 로드맵으로 미뤘다. 분석마다 Qwen 을 부르는 안은 회사 GPU 를 계속 쓰고 분석이 느려져 버렸다. 판정을 Bosun 에 맡기는 안은 ADR-034 2번과 맞지 않아 버렸다.
- **바뀌지 않는 것**: 점수·권고·필수 자격 계산, 골든 시험, `/explain`·`/health` 응답 모양, 추출 `promptHash`(`fa2ff603…`), 유료 hosted 모델 금지, service role 은 worker 만.
- **영향**: Bosun 의 실제 state·출력은 STAFF 줄이 생겨 바뀔 수 있다(골든 점수는 그대로). 추천 분석의 `promptHash` 는 `insight/v0.1`(`f623bb44…`)로 추출과 따로다.
- **운영 반영**: 2026-10-29 끝났다(운영 DB migration 2개, 회사 gateway·Analysis Worker·redis-api 교체, 운영 화면 실공고·DEMO 각 1건 확인). [기록](evidence/company-rollout/20261029/rec-insight-rollout.md).
- **반영**: 표 `supabase/migrations/20261029000100_recommendation_insights.sql`·보안 보강 `20261029000200_recommendation_insights_guard.sql`([[04-DATABASE|04]]), 경로 `/api/v1/bids/{bidId}/analyses/{runId}/insight`([[05-API-SPEC|05]]), gateway `/insight`([[03-AI-PIPELINE|03]]·[[15-DATA-CONTRACTS|15]]), 화면 패널([[06-UI-UX|06]]).

## ADR-065 번역 검증의 비교 표현 넓히기와 누락 사유 로그

**채택 (2026-10-29 사용자: 선택지 1번).** 고른 안은 번역 검증기와 번역 프롬프트를 넓히는 것이다. 회사 AI gateway 교체는 응답 인용 길이 수정([[15-DATA-CONTRACTS|15]] §5.3)과 묶어 한 번에 한다. 95c8abdc는 추출 행 하나만 지우고 재분석한다.

- **계기**: 2026-10-29 운영 실공고(부경대, run 95c8abdc)는 추출 10개 필드가 `KNOWN`인데 규칙만으로 판정됐다(38 보류). `restrictions[2]`("공동수급체 구성원 2개사 이하")·`[3]`("공동수급체 구성원별 최소 지분율 10% 이상")이 `TRANSLATION_MISSING`이라 `/kev`가 Bosun을 부르지 않았다.
- **원인**:
  - 번역 대상 13개 중 2개만 빠졌고, 요청 상한(64개·32KiB)보다 작았다(운영 SELECT). 남은 원인은 Qwen 생략 또는 검증기 거부다. Qwen의 원래 출력은 남지 않아 둘을 가릴 수 없다.
  - 검증기는 `이하`에 at most 류만, `N% 이상`에는 비교어가 숫자 바로 앞에 붙은 형태만 인정했다. "Up to 2 companies", "2 or fewer", "minimum share of 10% or more" 같은 표현을 거부한다(로컬 검사, 모델 호출 없음).
  - 번역 프롬프트에는 `이상` 예시만 있었다.
- **선택지**: 1 검증기·프롬프트 넓히기(채택). 2 빠진 항목을 `(untranslated)`로 두고 Bosun 진행(ADR-034 완전한 영어 state 원칙 약화). 3 빠진 경로만 다시 번역(Qwen 1회 추가). 4 번역 응답의 모든 경로를 필수로(억지 번역이 같은 이유로 거부된다). 5 현행 유지.
- **결정**: [[03-AI-PIPELINE|03]] §5.11 비교 표현.
  1. `이하`에 up to와 숫자 뒤 or fewer·or less를, `이상`에 숫자 뒤 or more·or higher·or greater를 더한다.
  2. 비교어와 숫자 사이에 영어 단어 4개까지 둔다. 숫자·부정어(not·no·never·without)·다른 비교어(less·more·than·up·within·maximum·minimum 등)는 끼지 못한다.
  3. 번역 프롬프트에 `5명 이하 -> at most 5 people (or 5 or fewer people)` 예시를 더한다.
  4. 빠진 경로는 `ABSENT`(응답에 없음)·`REJECTED`(검증 거부)만 로그에 남긴다.
- **바뀌지 않는 것**:
  - 숫자 다중집합·단위·부정·식별자·인젝션 검사.
  - "Bosun에는 검증한 영어만"(ADR-034)과 번역이 하나라도 빠지면 Bosun을 부르지 않는 규칙.
  - `AI_PROMPT_VERSION`과 `promptHash`(`fa2ff603…`). 번역 프롬프트와 검증기는 해시에 들어가지 않는다.
- **영향**: 넓히기만 했다. 전에 통과한 번역은 그대로 통과하고, 자격 사전 영어 라벨 32개의 판정도 같다. 그래서 저장된 추출(DEMO 포함)의 번역 판정은 바뀌지 않는다. 비교어와 숫자 사이의 수식어 허용은 `초과`·`미만`·`이내`에도 같이 적용된다(within the last 3 years).
- **남는 것**:
  - 저장된 추출의 빠진 번역은 다시 채워지지 않는다. 추출 행을 지우고 재분석해야 한다.
  - Qwen 생략이 원인이었다면 이 수정으로 고쳐지지 않는다. 그때는 로그 `reason=ABSENT`로 알 수 있다.
  - 부정 검사는 여전히 비교 표현 바로 앞 단어만 본다.
- **반영**: `services/ai`의 `translation_validation.py`·`translation.py`·`prompts/state-translate.v0.1.md`, 시험 `tests/test_translation.py` 18건(통과해야 할 표현 7건과 로그 1건은 고치기 전 코드에서 실패. 반대 사례 10건은 계속 거부). 회사 AI gateway 재생성은 사용자 승인 뒤다.

## ADR-064 추출 입력 첨부 조립 v0.2: 조각 나누기·문서마다 돌아가며 채우기·같은 문서 한 벌

**채택 (2026-10-28 사용자: 추천 1).** 사용자 원문: "추천1번". 고른 안은 gateway 코드 수정과 `AI_PROMPT_VERSION` 올림이다. 회사 반영은 승인 뒤다.

- **계기**: 2026-10-28 운영에서 실공고 첫 분석(나라장터 R26BK01791420, 사용자 승인)을 돌렸다. 첨부는 공고서 PDF·같은 공고서 HWPX·제안요청서 HWPX였고, 셋 다 파싱이 끝난 상태였다. run은 `COMPLETED` 54 보류(`WATCH`)였다. 그런데 추출은 전 항목 `UNKNOWN`, 근거 0건, `TRUNCATED_INPUT`이었다.
- **원인(코드)**:
  - 나라장터 공고는 본문이 빈 문자열이라(`web/server/ingestion/normalize-g2b.ts`) 추출 입력은 첨부뿐이다.
  - Worker는 첨부를 문서당 200,000자·전체 600,000자까지 보낸다(`web/server/documents/document-text.repo.ts`).
  - HWP·HWPX 파서는 쪽(`pages`)을 비운다. 그래서 gateway v0.1 `build_user_message`(`services/ai/src/sol_ai/adapters/qwen.py`)에서 문서 전체가 chunk 하나였다. v0.1은 예산 `QWEN_CONTEXT_BUDGET_TOKENS`(12,000자)를 넘는 첫 chunk에서 멈췄다. 첫 첨부가 12,000자를 넘는 HWPX면 첨부가 0자 들어간다.
  - 회사 이미지 `9bb24b002f9b`(`05f9572` 기반)와 main이 이 경로에서 같다. 재배포만으로는 고쳐지지 않는다.
- **결정**: [[03-AI-PIPELINE|03]] §4.3 v0.2 규칙.
  1. 쪽이 없는 문서와 긴 쪽을 2,500자 안의 조각으로 나눈다. 자르는 자리는 문장 끝이나 공백이고, 조각마다 원문 기준 절대 `charOffset`을 붙인다.
  2. 문서마다 앞 조각부터 한 조각씩 돌아가며 넣는다. 남은 예산보다 긴 조각은 남은 만큼 앞부분을 넣고 멈춘다.
  3. 같은 문서의 다른 형식은 하나만 넣는다. gateway는 첨부 이름을 받지 않아 내용 지문(문자·숫자 앞 4,000자의 8글자 조각, Jaccard 0.6 이상)으로 알아본다. 쪽 번호가 근거에 남는 PDF를 남긴다.
  4. `AI_PROMPT_VERSION`을 `req-extract/v0.2`로 올린다. system prompt 파일은 v0.1 그대로다.
- **바뀌지 않는 것**:
  - 예산 기본값 12,000. 회사 vLLM의 길이 한도를 확인하지 못했다.
  - system prompt·스키마·인용 검증.
  - web·Worker 코드. Worker는 분석 job마다 gateway `/health`의 `promptHash`로 캐시 키를 만든다.
  - mock. 추출 fixture의 `promptVersion` v0.1을 그대로 쓴다.
  - 본문만 있는 요청의 user message. 운영 DEMO 공고는 첨부 텍스트가 없어(DEMO 시드는 `text_object_key`를 쓰지 않는다) v0.1과 글자 하나까지 같다. FX-01~20으로 확인했다.
- **영향**: 버전이 `promptHash`에 들어가 v0.1로 만든 추출 행을 다시 쓰지 않는다. 그래서 gateway 반영 뒤 [재분석]하면 DEMO 공고도 Qwen을 새로 부른다. DEMO의 Qwen 입력은 같고 설정도 같다(`temperature` 0·`seed` 42). 같은 추출을 기대하지만 보장하지는 않는다. ADR-059 발표 숫자(FX-02 43 보류)는 운영 재분석 뒤 다시 확인한다.
- **남는 것**:
  - 이 버전 올림은 이번 한 번의 캐시 무효화다. 첨부 일부만 파싱된 때 만든 추출을 다시 쓰는 문제(ADR-056)는 그대로다.
  - 12,000자 예산이면 문서 둘에 각각 6,000자 안팎만 들어간다. 제안요청서의 뒤쪽(기술 요건 등)은 여전히 빠질 수 있다.
- **반영**: `services/ai`의 `adapters/qwen.py`·`settings.py`, 시험 `tests/test_local_qwen.py` 4건(고치기 전 코드에서 4건 모두 실패), [[03-AI-PIPELINE|03]] §3·§4.3. 회사 AI gateway 재생성은 사용자 승인 뒤다.

## ADR-063 본부·그룹 직속 직원 허용과 운영 조직도 인원 재배치(ADR-021 개정)

**채택 (2026-10-28 사용자).** 사용자 원문: "대시보드에 조직도 확인해보니까 0명인 팀들이 6개나 있는데 0명이 있으면 안돼. 팀 적절하게 분배 다시 해봐. 지금 팀에 있는 사람들 다 완전 옮기지말고 적절하게 많은 부서에서 옮겨서 0명인 팀 없게 해." 이어서 "공공영업그룹은 팀이 아니지만 3명 정도 사람들어가고, 사업혁신그룹도 팀이 아니지만 그룹장 1명 넣고, 품질&정보보호그룹도 팀이 아니지만 3명 정도 넣고, 크리에이티브그룹도 팀이 아니지만 3명 넣고, P&A컨설팅본부도 팀이 아니지만 2명 넣어. DB 규칙을 그냥 수정하자."

- **결정**: 직원(`team_members.department_id`)은 팀뿐 아니라 본부·그룹에도 직접 소속할 수 있다. ADR-021의 "직원은 팀에만" 조항(트리거 `team_members_check_department`, 종류 변경 때 `employee_requires_team`, 추가·이동 RPC의 `DEPARTMENT_NOT_TEAM`)을 마이그레이션 `20261028000100`이 없앤다.
- **바뀌지 않는 것**: 계층 규칙(본부 > 그룹 > 팀, 팀 아래 부서 없음), 본부·그룹의 `target_count`·`source_count` null, 가입 선택 목록(`GET /signup-options`, 팀만, [[05-API-SPEC|05]]), 명부 화면 `/people`의 부서 필터와 `GET /team-members`의 `departmentId`(팀만). 승인 fixture와 `pnpm people:check`의 배분 규칙(원본 명부 200명은 팀에만)은 그대로라 로컬 seed는 지금 운영 배치와 다르다.
- **화면**: 조직도는 직속 직원이 있는 본부·그룹을 고를 수 있게 한다. 하위 부서가 없으면 팀처럼 한 줄, 있으면 펼친 목록 맨 위 `<이름> 직속` 줄이다. 직원 추가·이동 대화상자는 본부·그룹도 고른다([[06-UI-UX|06]] §5.9.1).
- **운영 org-01 배치(2026-10-28)**: 0명이던 6곳을 채웠다. 공공영업그룹 직속 3명, 사업혁신그룹 직속 그룹장 1명(수석에서 그룹장으로), 품질&정보보호그룹 직속 3명, 크리에이티브그룹 직속 3명, P&AX컨설팅본부 직속 수석 2명(같은 본부로 연결한 "P&AX컨설팅본부 전략컨설팅팀"에서), 정보기술연구소 4명. 인원이 많은 팀에서 한두 명씩 옮겼고 팀장·본부장은 옮기지 않았다. 팀의 `target_count`는 새 인원과 맞췄다. 이동마다 `audit_logs`(`TEAM_MEMBER_UPDATE`, `request_id` `ops-20261028-org-rebalance`)를 남겼다. 같은 날 먼저 만든 그룹 아래 새 팀 4개(SOL-D050~053)는 이 결정으로 지웠다.

## ADR-062 권고 화면 표기 한글화: 추천·보류·비추천

**채택 (2026-10-28 사용자).** 사용자 원문: "BID WATCH, NO-BID 이 부분을 한글로 고치고 싶어. 영상 뿐만 아니라 프로젝트에 적용된 대시보드에도 한글로 나오게 해." 이어서 "참여 권고 기니까 '추천'으로 바꾸고 WATCH는 사람 검토가 아니라 '보류' 그리고 참여 비권고는 '비추천' 이렇게 가자. 문서도 다 수정해."

- **결정**: 사람이 보는 권고 표기를 `BID` → **추천**, `WATCH` → **보류**, `NO_BID`(화면 "NO-BID") → **비추천**으로 바꾼다. 업무 화면(목록·상세·필터·대시보드·분석 비교·관심 공고·담당자 결정), 랜딩(분석 예시·업무 데모), 앱 안 알림·카카오·메일 문구에 같이 쓴다. 담당자 최종 결정의 선택지도 같은 세 낱말이다.
- **바뀌지 않는 것**: DB·API·쿼리 문자열·스키마·결정 모델(Bosun) 입출력의 값 `BID`·`WATCH`·`NO_BID`, 점수 계산과 권고 규칙([[08-SCORING|08]]), 상태색(추천 `success`·보류 `warning`·비추천 `destructive`)과 아이콘, 금지어, "SOL Score는 수주 확률이 아닙니다" 고지. 결정 모델 입력은 영어 state 그대로다(ADR-034).
- **이전 표기**: 서버 템플릿 설명은 "BID(참여 권고)·WATCH(사람 검토)·NO-BID(참여 비권고)"였다. 새 분석은 새 표기로 저장한다. 이미 저장된 분석 설명 문장(운영 DEMO 17건 등)은 DB를 고치지 않고, 화면에 그릴 때 우리 템플릿이 만들던 옛 문구만 정확히 맞춰 새 표기로 바꿔 보인다(2026-10-28 사용자 선택 "화면에서 옛 표기만 바꿔 보이기". 다시 분석하면 점수가 달라져 ADR-059 대본 숫자가 흔들릴 수 있어 고르지 않았다). 사람이 쓴 결정 사유(`bid_reviews.reason`)와 이미 보낸 카카오 문구는 바꾸지 않는다.
- **알림 이름**: 카카오 알림 "추천 공고"는 권고가 추천·보류일 때 보내는 그대로 이름을 유지하고, 설정 설명 "추천 공고(추천·보류 권고)"로 범위를 알린다(2026-10-28 사용자 선택 "'추천 공고' 그대로").
- **AI gateway 템플릿**: `services/ai`의 `/explain` 템플릿 문장은 웹이 저장하지 않고 버리므로(웹 `chooseExplanation`은 모델 문장만 쓴다) 이번에 고치지 않았다. 다음 회사 gateway 배포 때 라벨과 조사를 함께 맞춘다.
- **문서**: 설계 문서의 화면 표기와 설명은 추천·보류·비추천으로 쓴다. 값을 가리킬 때는 `BID`처럼 코드 글꼴로 쓴다(예: 추천(`BID`)). ADR 본문의 지난 결정 원문·사용자 원문 인용과 `docs/evidence/`의 지난 기록은 고치지 않는다.
- **반영**: [[06-UI-UX|06]] 표기 표, [[08-SCORING|08]], [[19-DEMO-SCENARIO|19]] 등 설계 문서, design-system 스킬, 화면 코드와 시험.

## ADR-061 화면 UI 개편: 파스텔 선택색·묶음 머리 아이콘 사이드바·업무 화면 공통 틀·랜딩 흐르는 줄과 업무 데모(ADR-021 개정)

**채택 (2026-10-28 사용자).** 사용자가 브라우저 시안으로 범위·사이드바·영상·로고 줄을 고르고(스펙 §2 U1~U8) 스펙을 승인했다("승인할게. 진행해."). 사이드바는 첫 결과 스크린샷을 보고 확정했다("이대로 확정"). 근거는 [스펙](../polaris/specs/done/2026-10-28-ui-refresh.md)과 [단계 계획](plans/2026-10-28-ui-refresh.md)이고, 사용자 원문 전체와 랜딩 영상·위치·속도 조정 경위는 git `3ae02acf` 의 docs/16-DECISIONS.md "ADR-061"에 있다.

- **맥락**: 사용자는 대시보드 레퍼런스(`web/public/reference/ui.png`)의 "사이드바를 눌렀을 때 파스텔톤이고, 아이콘이 심플하고 깔끔함"을 원했고, 랜딩은 granter.biz처럼 데모 화면과 회사 수행 서비스·데이터 출처 로고가 옆으로 흐르기를 원했다.
- **결정 — 색**: 선택·켜짐 바탕 `selected`(#EAF2FE)와 글자 `selected-foreground`(#1B64DA, 대비 4.8:1)를 더하고 `sidebar-accent`도 같은 값으로 둔다. "강조색 하나"(`brand`)의 연한 색이라 새 hue는 없다. hover는 회색(`accent`). `brand`·`primary`·상태색·`source-*`(ADR-058)·`demo`는 그대로다([[06-UI-UX|06]] §3.1).
- **결정 — 사이드바(ADR-021 4차 개정)**: 묶음 줄은 회색 아이콘(업무 서류가방·분석 막대 차트·회사 건물) + 굵은 이름 + 늘 보이는 접기 화살표, 묶음 안 메뉴는 글자만 들여 쓰기, 활성은 연한 파랑 바탕 + 파란 글자 + 굵기 600이다. 접기·글자 +3px(ADR-030 B26)·묶음 3개와 순서·맨 아래 고정 칸·64px 아이콘 줄·줄 높이 32px는 그대로다([[06-UI-UX|06]] §4.1).
- **결정 — 업무 화면 공통 틀**(U1): 머리 경로 → 제목 → 설명 → 1px 구분선, 표 머리 연한 회색·둥근 1px 테두리, 회색 칩·파란 테두리 배지(`Chip`), 카드 그림자 없음, 선택 표시 3종(탭·하나 고르기 전환·거르기 칩)([[06-UI-UX|06]] §3.5). 로그인·가입은 색 토큰만 따른다.
- **결정 — 랜딩**: 히어로 아래에 "솔리데오가 수행한 공공 서비스"(govSM.do 17개)와 "SOL RADAR 가 공고를 가져오는 곳"(9곳: 나라장터·LH·K-water·한국전력공사·기업마당·중소벤처기업부·한국도로공사·국방전자조달·한국철도공사) 줄을 CSS만으로 흘린다. 로고만, 가운데 정렬, 늘 원래 색이다. 그 아래 HTML로 그린 업무 데모(가짜 커서, 수집 → 관련 공고 → 분석 상세 → 관심 공고, 약 25초, 가상 공고)와 자동 재생 분석 예시 판(세 공고 약 24초, 누르거나 초점이 들어오면 멈춤)을 둔다. 녹화 영상 파일은 저장소에 넣지 않는다([[06-UI-UX|06]] §3.4).
- **결정 — 출처 로고(U8)**: "연결 예정" 꼬리표 없이 9곳 로고만 둔다. 사용자 원문 "SOL RADAR가 공고를 가져오는곳은 연결 예정 빼고 다 해커톤 전에 연결할 거니까 연결 안 된 것들만 문서로 남겨. 로고만 나오게 깔끔하게 수정해". 조건: 공식 제출 전 운영 읽기로 9곳 수집을 확인하고, 연결되지 않은 기관의 로고를 뺄지는 사용자가 정한다([랜딩 출처 연결 목록](plans/2026-10-28-landing-sources-to-connect.md)). 공식 CI 파일을 고치지 않고, 줄 아래 "기관 로고는 공고 데이터 출처 표시이며 제휴·인증을 뜻하지 않습니다."를 둔다.
- **정한 것**(메인 세션 판단, 사용자에게 알림): 위 막대에서 화면 이름을 뺀다. 공공데이터포털은 출처 줄에 넣지 않는다(같은 출처를 두 번 센다). 서비스 줄 제목은 "수행한"이다. 랜딩 시험은 "분석 예시 보기를 누르면 점수와 고지가 함께 화면 안에 보인다"로 바꾸고, 점수가 고지 없이 보이지 않는다는 단언은 지킨다.
- **바뀌지 않는 것**: 서버·DB·API·계산·권한, 문구의 뜻과 고지("수주 확률이 아닙니다", 담당자 결정, 예시 데이터 표시), 상태색·`DEMO`·출처 배지, 금지어(승률·확률·가능성·수주 금액·점유율·경쟁사·%), 데스크톱 1280px 이상(ADR-007). 새 차트·애니메이션 라이브러리 없음.
- **바뀌는 것**: ADR-021 3차 개정의 묶음 줄·펼친 메뉴 아이콘·활성 굵기 500. design-system 스킬의 "가운데 정렬은 히어로 하나다"는 "히어로와 흐르는 줄 둘"로 바뀐다.

## ADR-058 공고 출처 배지에 기관 로고 상징 색

**채택 (2026-10-27 사용자 결정, 질문 답).** 운영에서 수집한 공고의 출처 배지가 모두 흰 칸이라 구분이 안 된다는 사용자 지적에서 나왔다. 수집 서비스 10개(`web/app/_lib/opportunity-sources.ts` `SERVICE_IDS`)는 네 기관(나라장터·K-water·LH·KEPCO)에 속하고 배지는 기관 단위(`SourceFamily`)다.

## ADR-056 추출 캐시 키에 입력 문서 집합이 없다 (첨부 일부만 파싱된 추출의 재사용)

**채택: 대안 A (2026-10-29 사용자 결정, ADR-068 9번). 구현 전.** 2026-10-27 문서 반영 중 발견해 제안으로 올렸다. 구현은 브랜치 `feat/analysis-wait-documents`에서 한다. 2026-10-27 첨부 처리 구현(main `8cfaac31`, [[07-DATA-PIPELINE|07]] "documents 큐 소비자 계약")으로 분석이 첨부 텍스트를 읽게 됐다. 그런데 추출 캐시 키는 그대로 `(revision_id, model_name, prompt_hash)`다(`requirement_extractions` UNIQUE, `web/server/analysis/analysis.repo.ts`). 분석은 이 키로 성공 추출이 있으면 `/extract`를 다시 부르지 않는다(`analysis.service.ts` `prepareExtraction`). 재분석 `force=true`는 score run 중복 판정에만 쓰이고 이 캐시를 건너뛰지 않는다.

- **문제**: 공고 하나의 첨부(기본 3건)는 documents job이 차례로 처리한다. 본문이 비어도 `PARSED`·`PARTIAL` 첨부가 하나라도 있으면 분석 요청을 받는다(202). 그래서 첨부 일부만 파싱된 순간에 분석하면, 그 일부로 만든 추출이 캐시에 남는다. 아직 `PENDING`인 첨부는 문제 문서로 치지 않아 `attachmentsIncomplete`도 붙지 않는다. 나머지 첨부가 뒤에 파싱돼도 같은 revision·모델·프롬프트의 다음 분석은 그 추출을 다시 쓴다. 첨부에만 있는 자격 조건이 계속 빠질 수 있다. 같은 추출 행은 여러 조직의 분석이 함께 쓴다.
- **확인한 것**: 코드 읽기로 확인했다. 실제로 재현한 기록은 없다. 운영 실공고 분석은 2026-10-29부터 있다([기록](evidence/company-rollout/20261029/ai-gateway-rollout.md)). 그 분석에 이 문제가 있었는지는 확인하지 않았다(미확인).
- **대안 A — 처리 중 문서가 있으면 분석이 기다린다**: [[2026-10-21-redis-gateway-supabase-storage-migration|10-21 Redis·Storage 계획]] 297행 근처의 bounded dependency 안이다. 분석 job이 그 revision의 문서 처리를 최대 300초 기다리고(RUNNING 전, BullMQ 지연 재확인), 시간이 지나면 사유를 붙여 부분 입력으로 분석한다. 캐시 키는 그대로라, 대기 뒤에도 늦게 끝난 문서는 반영되지 않는다.
- **대안 B — 캐시 키에 입력 문서 집합을 넣는다**: 같은 계획 §8.4 안이다. 본문·구조화 요구조건·문서 id·원본 sha256·파싱 상태·parser id·텍스트 sha의 manifest로 `source_hash`를 만들고, 키를 `(revision_id, model_name, prompt_hash, source_hash)`로 넓힌다. 새 마이그레이션과 `analysis_input_version` 기록이 필요하다. 문서가 늘면 추출을 다시 하므로 모델 호출이 늘어난다.
- **A와 B는 함께 쓸 수 있다.** 지금은 A만 한다(B는 하지 않는다). A가 회사 Analysis Worker에 반영되기 전까지는 분석 결과를 볼 때 "첨부 일부만 반영됐을 수 있다"고 밝힌다. A 뒤에도 300초 안에 끝나지 않은 문서와 범위 밖 첨부(ADR-055)는 그 추출에 들어가지 않는다.
- **관련**: [[07-DATA-PIPELINE|07]] "documents 큐 소비자 계약"의 분석 연결, [[03-AI-PIPELINE|03]] §2.1 재사용 키, [[04-DATABASE|04]] `requirement_extractions`.

## ADR-055 documents 소비자 계약 변경: 범위 밖 첨부는 PENDING, 우리 쪽 장애는 미룬다 (07 개정)

**채택: ① 구현대로 (2026-10-29 사용자 결정, ADR-068 9번).** 2026-10-27 구현이 먼저 바꿔 제안으로 올렸다. 2026-10-27 documents 소비자 구현(`web/worker/documents-job.ts`, main `8cfaac31`, [구현 기록](evidence/attachment-pipeline/20261027-implementation.md))이 [[07-DATA-PIPELINE|07]]의 옛 계약 두 줄(ADR-033 E1, 채택)과 다르게 동작한다. 회사 Documents Worker는 2026-10-28부터 돈다(`infra/company/README.md` §8). 07은 구현대로 고쳐 적고 "(바뀜)"으로 표시했다. 이 기록은 그 변경을 받아들일지 사람이 정하도록 올린다.

1. **끝내기 전 상태.**
   - 옛 계약: job을 끝내기 전에 그 revision의 첨부 행을 **모두** `PENDING` 밖으로 옮긴다.
   - 구현: 처리 범위 안의 첨부만 옮긴다. 범위 밖 첨부는 받지 않고 `download_status=PENDING`으로 남는다. 범위 밖은 이름이 `.pdf`·`.hwp`·`.hwpx`가 아닌 것, 공고당 상한(`DOCUMENTS_MAX_PER_BID` 기본 3) 밖, 최신 revision이 아니거나 `OPEN`·`AMENDED`가 아니거나 마감이 지난 공고다.
   - 이유: 나라장터 요청과 파싱 비용을 공고당 몇 건으로 묶는다. Qwen 입력 예산(약 12,000자)에서 뒤 문서는 거의 쓰이지 않는다.
   - 영향: `PENDING`이 "아직 안 했다"와 "하지 않기로 했다"를 함께 뜻한다. 화면은 그 첨부를 미처리로 보인다. 분석은 `PENDING`을 문제 문서로 보지 않으므로(`analysis-store.model.ts` `toDocumentIssues`) `attachmentsIncomplete`를 붙이지 않는다. 그래서 범위 밖 첨부에만 있는 조건은 표시 없이 분석에서 빠진다. 복구 회차는 `document_processing_candidates`로 상한을 채운 revision을 다시 넣지 않는다.
2. **장애 시 미루기.**
   - 옛 계약: 처리 실패는 재시도(attempts 3) 뒤 마지막 시도에 `FAILED`로 남긴다.
   - 구현: 우리 쪽이 준비되지 않은 경우는 기록하지 않고 10분씩 최대 12번(약 2시간) 미룬다. Storage·DB 오류, gateway 접속 실패·timeout·5xx·breaker, `PARSER_NOT_CONFIGURED`가 여기 든다. 그 뒤에는 `PENDING`으로 두고 job을 끝낸다. jobId 보존(1일)이 끝나면 복구 회차가 다시 넣는다.
   - 이유: 우리 쪽 장애를 문서의 영구 실패(`FAILED`)로 남기면, 장애가 풀린 뒤에도 그 첨부를 다시 처리하지 않는다.
   - 영향: 장애가 길면 첨부가 하루 넘게 `PENDING`에 머물 수 있다. 미루는 동안 실패 기록이 남지 않으므로 운영자는 로그(`documents.job`)로 본다.
3. **함께 옮긴 것**: 복구 회차(문서 큐 등록 복구)는 ingest 쪽이 아니라 documents 등록이 갖는다. live는 `document_processing_candidates`(회차당 revision 10개)를 쓰고, mock·fixture는 소비자 없이 옛 복구(100행 keyset)만 돈다.

- **고를 것**: ① 구현대로 채택(추천: 비용 상한과 장애 복구가 분명하다. 범위 밖 첨부를 따로 표시하는 값은 후속으로 검토) ② 범위 밖 첨부를 새 상태(예: `SKIPPED` 사유)로 닫도록 구현을 바꾼다(새 마이그레이션 필요, 04 §4 값 집합 변경) ③ 옛 계약으로 되돌린다.
- **바뀌지 않는 것**: 다운로드·파싱 사유 코드, 영구 사유는 바로 기록, 문서 하나의 실패는 그 문서에만 남는다, 실행 모드 범위(live만).

## ADR-052 회사 공개 프로필과 EXECUTIVE 역할(ADR-020·019 개정)

**채택 (2026-10-27 사용자 결정 D1~D13).** 사용자가 운영 서버(`https://www.solideos-radar.com`)에서 시연하므로, 회사 역량을 인터넷에서 찾을 수 있는 정보로 채우자고 했다. 질문과 답은 [스펙](../polaris/specs/done/2026-10-27-company-public-profile.md) §2 표에 있다. 운영 반영 절차·결과 원문은 git `3ae02acf` 의 docs/16-DECISIONS.md "ADR-052"에 있다. 상태는 [[PROGRESS]]다.

> [!note] 이어진 결정 (2026-10-27 사용자)
> - D6 개정: "운영 반영 전에 DEMO 공고 19건 삭제"는 ADR-054와 부딪혀 추천안 1번으로 바꿨다. DEMO를 남기고, 공개 프로필 반영 뒤 발표에 쓸 DEMO 공고를 새 프로필로 다시 분석한다.
> - D9 자격: 공개 조회로 등록이 보이는 정보통신공사업(`ICT_CONSTRUCTION`)만 `HELD`다. 나머지는 기록이 없어 공고가 요구하면 `NEEDS_REVIEW`이고 권고는 WATCH를 넘지 않는다([[08-SCORING|08]]). D10 기술: 회사가 공개적으로 쓴다고 밝힌 기술만. D11 금액: 솔리데오 몫이 단독으로 보이는 금액만(2026-10-27 기준 0건). D12: DART 감사보고서와 자격 공식 공개 조회도 출처. D13: 사용자가 고른 선호 분야(민원·데이터 플랫폼·AX·스마트시티)를 넣는다.

### 결정

1. **회사 프로필은 환경에 따라 가상이거나 공개 자료다(ADR-020 개정).** 로컬·시험·`demo:reset`은 가상 프로필(`is_demo=true`, `fixtures/company/solideo-profile.json`)이다. 운영 DB는 공개 자료 프로필(`is_demo=false`)을 새 revision으로 쌓는다(D5). 지난 `score_runs`는 그때 revision에 고정된다. 가상 fixture·골든 94/72/68·08 §6.1은 바뀌지 않는다.
2. **값마다 출처를 저장하고 공개되지 않은 칸은 비운다**(D3·D4). 자료는 회사 홈페이지·기사·채용공고·나라장터 계약 기록까지이고, 로그인이 필요하거나 자동 수집을 막는 곳은 쓰지 않는다. `company_profiles.sources`·`public_history`(점수에 쓰지 않는 연혁) JSONB 열과 항목의 `sourceIds`로 잇는다([[04-DATABASE|04]] §3.2).
3. **지금 유효한지 모르는 자격은 `HELD`로 적지 않는다**(D7). 취득 연도만 공개된 것은 `publicHistory`에 둔다. 회사가 보유를 확인한 자격만 `COMPANY_CONFIRMED`(확인자·확인일) 출처로 `HELD`에 넣는다. 운영자 CLI가 `HELD` 항목이 quote 있는 `PUBLIC` 출처나 `confirmedBy` 있는 `COMPANY_CONFIRMED` 출처를 가리키는지 확인한다.
4. **점수는 모르는 값을 중립으로 둔다**([[08-SCORING|08]] §3.2·§3.4·§4). 실적 `amountKrw`·`completedAt`은 `null`일 수 있고, `null` 금액은 금액비 0.5, `null` 완료일은 최근성 0.2이며 최대 과거 실적에서는 뺀다. AI gateway(`ProfileProject.amountKrw` nullable, `kev_state.py`)도 맞췄다.
5. **`EXECUTIVE` 업무 역할을 둔다**(D1·D2·D8). 화면 이름 "임원", 권한은 VIEWER + 회사 역량 열람이다. 쓰기 역할 목록에는 넣지 않는다. ADMIN이 초대·가입 승인·역할 변경에서 부여한다. sol_role CHECK 3곳은 마이그레이션 `20261027000700`이 바꾼다.
6. **`/company`는 ADMIN·EXECUTIVE만 본다**(D1). 메뉴, 페이지 가드(권한 없음 안내, HTTP 200), `GET /api/v1/company-profile`·`/revisions`(`403 FORBIDDEN`)가 `COMPANY_PROFILE_READ_ROLES`를 함께 쓴다.
7. **`company_profiles` RLS는 조직 전원 읽기 그대로다.** 프로필 전체가 `score_runs.input_snapshot.profile`에 복사되고 `score_runs`는 조직 누구나 읽으므로, 표만 잠가도 막히지 않고 사본까지 잠그면 일이 너무 크다. 넣는 값은 공개 자료이거나 회사가 확인한 보유 자격이다. **비공개 자료를 넣게 되면 그 전에 DB 수준 잠금을 다시 정한다**([[09-SECURITY|09]]).
8. **넣는 길은 운영자 CLI 하나다.** 편집 화면·`PUT`은 만들지 않는다. `pnpm ops:company-profile`(`scripts/ops/company-profile.mjs`)을 사람이 로컬에서 돌린다. `--env-file <path> --file <json> --created-by <email> [--apply]`, 기본은 dry-run이다. `created-by`가 org-01 ADMIN인지, `isDemo=false`·`note`·출처 규칙을 확인하고 revision 중복(23505)이면 끝낸다. `--apply` 전에 `pnpm -C web exec vitest run server/company-profile/public-profile-file.test.ts`를 돌린다. 실제 프로필 JSON은 `fixtures/`에 두지 않는다.
9. **실제 직원 수와 가상 명부 200명이 어긋나는 것을 받아들인다**(D5). 인력 가용성 점수는 바뀌지 않는다.

### 반영

- 운영 반영은 마이그레이션 → Vercel 배포 → 회사 Worker·AI gateway 갱신 → CLI dry-run → `--apply` → 재분석 순서였고, 단계마다 실행 직전에 사용자 확인을 받았다. DEMO 공고는 지우지 않았다. 기록은 [운영 반영](evidence/company-public-profile/20261027/prod-rollout.md).
- 공고 상세 배지는 분석에 쓴 프로필의 `is_demo`로 "가상 회사 프로필로 분석"·"공개 자료 회사 프로필로 분석"을 고른다.

## ADR-051 프로필 사진과 명부 연결(ADR-019 개정, Storage 예외)

**채택 (2026-10-24 사용자 설계 승인).** 사용자가 회원가입·간편 로그인·설정에 프로필 사진 등록이 없다고 지적하고, 사진은 연결된 Supabase 클라우드에 저장하며 본인과 다른 사람이 조직도에서 보게 해 달라고 했다. 신규 입사자와 가상 직원 200명의 사진 변경, 가입 때 명부 연결 + 관리자 승인도 요구했다. [설계](../polaris/specs/done/2026-10-24-profile-photo-member-link.md)를 사용자가 "응 진행해"로 승인했다. 설계 C15에 따라 이 승인을 ADR 채택으로 본다(ADR-037 선례). 구현 계획(원문: git `5261730f` 의 `docs/plans/2026-10-24-profile-photo-member-link-plan.md`)은 실행 방식을 사용자의 상시 위임("추천안대로 진행해")에 따라 정했다.

- **ADR-019 개정 — 명부와 계정은 관리자 승인으로만 잇는다.** 명부(`team_members`)와 Auth 계정은 여전히 다른 행이다. 가입만으로 멤버십이 생기지 않는다. 조직이 없는 계정은 가입 신청(`member_join_requests`, 신규 입사자·기존 직원)을 낸다. org-01 ADMIN이 `/settings/organization`에서 승인·거절한다. 승인은 한 트랜잭션이다: 멤버십(업무 역할 기본 VIEWER)을 만들고, 신규 입사자는 `team_members`에 비데모 행(`SOL-N0001` 대역)을 만들며, 기존 직원은 그 행의 `user_id`에 계정을 잇는다. 한 직원에게는 계정 하나만 이어진다. 쓰기는 security definer RPC(`submit_join_request`·`decide_join_request`·`find_unlinked_member`)로만 한다. "이름이 같아도 자동 연결하지 않는다"(ADR-019)는 그대로다.
- **Storage 예외 — 비공개 버킷 `profile-photos`.** ADR-019의 "공개 자산은 가상 정장 사진뿐"은 유지한다. 올린 사진은 공개하지 않는다. 버킷은 private이고 2MB, `image/jpeg`·`image/png`·`image/webp`만 받는다. 경로는 본인 `users/{uid}/`, 관리자 `members/{team_member_id}/`다. 읽기·쓰기는 사용자 JWT와 `storage.objects` 정책이 정한다. 웹은 사용자 JWT로 1시간짜리 signed URL을 만든다. 웹 서버·클라이언트는 service role을 쓰지 않는다(ADR-017·048). 버킷 생성은 사람이 `node scripts/ops/ensure-storage-buckets.mjs --apply`로 한다.
- **사진 표시 순서(설계 C10).** 올린 사진 → 가상 직원의 정장 사진 → 간편 로그인 제공자 사진 → 머리글자다. 본인은 설정에서, 관리자는 조직도 상세에서 바꾼다. 연결된 사람은 계정 사진과 조직도 사진이 같다.
- **시연 초기화(설계 C12).** `pnpm demo:reset`이 신규 입사자 행·연결·신청·사진 포인터를 처음 상태로 돌린다. Storage 파일은 지우지 않는다.

마이그레이션은 `20261024000200`·`000210`·`000300` 세 개다. 운영 적용 상태는 [[PROGRESS]]에 있고, 검증은 [증거](evidence/profile-photo/)에 있다.

## ADR-050 카카오 전송 의도 선점과 불확실 결과 처리

**채택 (2026-10-29 사용자 결정, ADR-068 9번).** 2026-10-22에는 상태를 적지 않았다. 코드는 그때부터 이 방식이다(`supabase/migrations/20261023000704_kakao_send_claims.sql`).

2026-10-22 커밋 통합 중 독립 리뷰에서 외부 송신 성공 뒤 DB 상태 저장 실패 시 같은 메시지를 다시 보내는 결함을 재현했다. ADR-038의 사용자·공고별 최대 1회 정책을 유지하기 위해, Worker 전용 DB 함수가 추천은 사용자·공고, 시험은 outbox 이벤트의 고유 전송 의도를 먼저 선점한다. 선점과 추천 알림의 결과 불명 표시를 같은 트랜잭션에 기록하고 선점 성공자만 외부 전송한다. 화면 역할에는 claim 표/함수 권한을 주지 않는다. 원본 브랜치의 선송신·후저장 순서를 대체하며 기존 migration은 보존하고 `20261023000704`를 추가한다.

## ADR-049 Vercel web 단독·회사 분석 런타임

2026-10-22 사용자의 배포 책임 확정과 남은 구현 지시를 반영한다. Vercel은 web만, 회사는 기존 Redis·Next redis-api·AI gateway·Worker를 맡는다. ADR-044의 내부 ai 서비스/binding 배치 조항을 대체한다. 회사 API의 allowlist에 정확한 관리자 AI 상태 GET만 추가하고 서비스 token·사용자 JWT·ADMIN 재검증·응답 schema 검증을 유지한다. 실패 readiness의 원인은 비밀·URL·원문 없이 분류/상태/소요시간/요청ID만 기록한다.

새 Redis·Qdrant·Nginx·DB를 추가하지 않는다. 기존 회사 모델 프로세스와 Redis를 재시작/수정하지 않으며 실제 network·포트 확인 전 기동하지 않는다. 학습본 미반입 상태이므로 mock을 유지한다. [회사 실행서](../infra/company/README.md)의 코드/이미지 검증과 회사 운영 배포를 구분한다. 검증: [로컬 구현 기록](evidence/deployment/20261022-company-runtime-implementation.md).

## ADR-048 MinIO를 private Supabase Storage로 교체

2026-10-21 사용자 지시 “전환 계획에 따라서 전환하자”에 따라 전환 계획 Task 3·4를 구현한다.
원본 `bid-documents`, 결과 `bid-parsed`는 private다. Worker/운영 CLI만 service role로 쓰고 웹은 사용자 JWT와 RLS로 60초 signed URL을 발급한다.
물리 object 원장·lease/CAS·checksum 검증으로 immutable upload/DB 확정/24시간 고아 정리를 직렬화한다. 같은 원본을 참조하는 논리 문서는 보존한다.
첫 통합 리뷰의 삭제 경합 보강: `(bucket, logical_path)`로 중복을 판정하고 실제 경로에는 원장 UUID 디렉터리를 넣는다. 삭제 lease가 만료된 작업이 뒤늦게 재개되어도 다시 업로드한 파일을 지울 수 없다. Worker는 claim이 반환한 실제 경로를 사용하고 문서 FK는 그 경로를 참조한다. main에 먼저 커밋된 00700/00701은 보존하고 후속 00702에서 논리 경로를 채운다. 기존 파일 경로와 문서 참조를 유지하며 새 물리 파일만 UUID 경로를 사용한다.
Worker Storage 실검사 보고는 30초 주기·Redis TTL 120초다. 웹에 Storage 비밀키를 추가하지 않는다. 보고가 없거나 만료되면 503이다.

ADR-003(Compose의 `minio`)·005·017·028의 파일 저장소 조항을 대체한다. Redis/BullMQ·Qdrant·점수/큐/RPC 계약은 유지한다.
기존 ADR 문장은 당시 이력이며 현행 파일 저장은 이 결정을 따른다. Gateway Phase 1은 ADR-045의 기존 구현을 재사용한다.
**코드 전환과 운영 전환은 별개다. 클라우드 migration·bucket 준비·기존 파일 inventory/이전·실연결 검증 전에는 운영 완료로 표시하지 않는다. 기존 MinIO 컨테이너·볼륨·파일을 자동 삭제하지 않는다.**

## ADR-047 공공 입찰 확장·사업기회·업무 UI

**채택 (2026-10-21 사용자 "승인할게 시작해.", 2026-10-22 추가 승인으로 main 병합·운영 DB 적용·배포).** 사용자는 공공 SI·AI·AX 입찰을 폭넓게 수집해 기업 역량과 비교하도록 요청했다(조달청 4서비스 유지·신규 6서비스·KEPCO 회사 구분·중복/출처 추적·대시보드/목록/운영 화면). 설계는 [스펙](../polaris/specs/in-progress/2026-10-21-public-procurement-expansion.md), 운영 적용은 [기록](evidence/procurement-expansion/20261022-release.md)이다. 배경·대안 표·기존 정책과의 차이 표·검증 서술의 원문은 git `3ae02acf` 의 docs/16-DECISIONS.md "ADR-047"에 있다.

- **고른 안**: 출처 공고·revision을 그대로 두고 사업기회(opportunity)·확정 연결(link)·새 읽기 계약을 더한다. 대표 1건으로 합치는 안(출처별 정정·사람 결정·과거 분석의 뜻이 깨진다)과 기관별 별도 DB·수집 엔진 안(기존 Postgres·Worker·AI 재사용과 충돌)은 고르지 않았다.

### 채택한 결정

1. Source family4개(G2B/KWATER/LH/KEPCO), API서비스10개, 발주기관/KEPCOcompanyId, 기술분야, 사업단계를 각각 저장한다. 기존4서비스·env이름·공고ID를 유지한다. P0신규3종 다음 P1신규3종을 검증해 활성화한다.
2. 기존 공고/revision을 지우지 않고 고유사업기회와 확정link를 추가한다. 확정중복/후보/별도공고를 구분하고 정정/취소/재공고/단계연결을 보존한다. 후보는 아직 별개로 집계하고 잠재중복 수를 표시한다.
3. 넓은 수집 후 근거/버전이 있는 관련성분류를 수행한다. 저관련/미분류도 보존한다. 기본 SI·AI우선은 숨김 없는 정렬, early는OFF다. 관련성0~100은 신호량이며 SOL Score/확률이 아니다.
4. JSON/XML 정제 원문구조를 private저장하고 비밀/담당자제거를 유지한다. byte원본전체보관·HTTP첨부예외는 별도승인이다. serviceKey뿐 아니라 apiKey 마스킹·기관별HTTPSallowlist·실패/정상0건/완전성 구분을 활성화 조건으로 둔다.
5. 기존AI/규칙/점수30/25/20/15/10·75/50·사람결정·RLS를 유지한다. source대표revision변경 시 과거점수를 현재로 복사하지 않는다. 신규관련성 DTO와 기회읽기계약을 별도로 둔다.
6. 대시보드KPI5개·검토입찰/소스/early/권고포트폴리오, 입찰11열·필터·중앙정렬Source배지, ADMIN서비스현황/실행이력을 설계한다. 1280px 표내부가로스크롤과 대시보드세로배치는 명시적정책예외안이다.

- **기존 정책과 달라진 것**: live Worker만 G2B 사전 정보화 필터를 풀고 수집 뒤 관련성으로 우선 노출한다(Connector 기본·quota 유지, 전수 AI 실행 없음). 1280px 표는 표 안에서만 가로 스크롤을 허용한다. 가공 전 byte 원본은 보존·접근 정책 승인 없이 보관하지 않는다. 신규 서비스는 registry에 `disabled`로 넣고 서비스별 검증 뒤 켠다(지금 켠 출처는 [[07-DATA-PIPELINE|07]]·`infra/sources/registry.yaml`).
- **포함하지 않는 것**: 넓은 자동 AI 분석·운영 전수 재수집·모델 교체.

## ADR-046 해커톤 검증 실행 범위·시점 분리

**개정(2026-10-21 사용자 추가 지시)**: "아니 웹 테스트 6830개 너무 많잖아. 그런 거도 다 최대한 없애자고"에 따라 시험 자체도 실제 삭제했다. 웹 6,830 → 286, AI 1,511 → 101, 결정 서버 152 → 57, DB는 핵심 21개를 남겼다. 중복 계층·상수/목업 고정·전수 오류 조합·템플릿 CRUD·확장 회귀는 제거하고, 핵심 점수·정보 부족·권한·조직 격리·수집·사람 결정·모델 장애를 남긴다. 전체 테스트 명령·게이트·CI·린트는 유지한다. `skip`·탐색 제외로 기존 시험을 숨기지 않는다. 현재 목록은 [[11-TESTING|11 테스트]] "현재 MVP 자동 시험"과 `docs/evidence/verification/20261021-pruned-tests.json`이고, 축소 전 시험 목록을 일률적으로 복구하지 않는다.

- **결정자·날짜**: 사용자, 2026-10-21. 기존 분석의 우선순위대로 검증 부담을 줄이도록 승인했다.
- **개발 중**: `pnpm verify:changed`로 HEAD 대비 staged·unstaged·untracked를 수집한다. 커밋된 브랜치 변경은 `--base <기준 커밋>`으로 포함한다. 실행할 명령은 `verify.config.json`의 `changedPaths`로 선택하고 `--dry-run`으로 확인한다. 웹 변경은 웹 quick, Python 변경은 해당 서비스 검사, DB·루트 도구·공유 fixture는 관련 공통 검사와 의존 프로젝트를 실행한다. 문서만 바뀌면 코드 검사는 없다. 미분류 코드·검증 설정 변경은 전체 quick으로 넓히고, 잘못된 Git 기준이나 설정을 성공으로 처리하지 않는다.
- **통합·제출 전**: 기존 전체 `pnpm verify`와 변경 사용자 흐름 E2E를 한 번 실행한다. 제출 전에는 핵심 데모 리허설도 확인한다. 같은 코드·테스트·설정·fixture·환경의 성공 결과는 실행 커밋과 범위를 밝혀 재사용한다. 변경된 입력에 의존하는 검사는 다시 실행한다. 전체 verify에 포함된 DB·pytest, `test:e2e`에 포함된 브라우저 시험은 중복 실행하지 않는다.
- **Compose·QA**: 기동 절차 1~7은 Compose·Dockerfile·환경변수 계약·의존성·컨테이너 진입점 변경과 데모 스택 통합 때 실행한다. 일반 화면·문구 변경마다, 또는 입력이 그대로인 날마다 전체 스택을 재기동하지 않는다. 작은 작업은 구현자가 검증하고 독립 리뷰는 통합 단위로 한 번 모은다. E2E는 변경 spec·흐름을 선택하고, 기능은 1440 중심·변경 화면의 1280 배치 확인·제출 전 대표 흐름 양폭 확인으로 실행한다.
- **보존**: 기존 커밋 게이트·CI·린트 필수 검사, RLS·조직 격리·골든 94/72/68·정보 부족·모델 장애·DEMO 표시·사람 결정 저장. 편집 금지 파일이나 게이트 자기 보호 시험을 수정해 검사를 끄지 않는다. 새 테스트는 계산·권한·저장·외부 입력 계약·실제 결함 회귀에 집중한다.
- **우선순위**: [[17-CLAUDE-IMPLEMENTATION|17 구현 규칙]] "해커톤 검증 정책"이 템플릿·스킬의 매 단계 전체 검증·다중 리뷰 지시보다 우선한다. [[11-TESTING|11 테스트]]의 전체 수용 조건은 제출 전 최종 검증 기준으로 유지한다. 미실행 검사는 통과로 표시하지 않는다.

## ADR-045 Redis HTTPS 접수에 기존 Next.js API 재사용

2026-10-21 사용자 승인 범위는 [[2026-10-21-redis-gateway-supabase-storage-migration|전환 계획]]의 **Phase 1 Gateway 로컬 구현·테스트**다. 운영 컨테이너·Nginx·DB·배포 변경과 Storage/parser 다음 단계는 별도 승인 대상이다. 검증: [[20261021-phase1-redis-gateway|로컬 검증 기록]](2026-10-21).

2026-10-21 추가 결정: **Gateway·Vercel은 해커톤 안에 완료한다.** 당시 붙인 freeze·리허설 날짜 조건은 지난 일정이다(ADR-054·057). 결과: 2026-10-26 운영 전환으로 이 경로가 운영 기본이 됐다([[PROGRESS]]). 당시 기본 데모는 Compose Redis/BullMQ·MinIO였고 새 경로는 env로 선택했다(MinIO는 ADR-048로 제거). ADR-037·039·042 조건②의 예외는 frontend HTTPS → 회사의 기존 접수 API로 나누는 전송/배포 경로에 한정한다. analysis job payload·처리 의미와 수집 저장 RPC `ingest_save_revision` signature·원자성, 규칙 엔진·골든 94/72/68은 유지한다. 기존 함수 모양 변경이 필요하면 먼저 사용자에게 알린다. durable dispatch·quota 예약·Storage 신규 구현은 이 예외로 자동 승인되지 않는다. 병합 조건·지침 문안·요금제(원문: git `5261730f` 의 `docs/plans/2026-10-21-redis-vercel-merge-conditions.md`)를 함께 검토했고, 지침 문안과 유료 Pro 전환은 사용자 승인 전 적용하지 않는다.

- 같은 Next.js 코드를 `frontend`와 `redis-api` 역할로 실행한다. Vercel frontend는 분석·수집 POST를 인증된 HTTPS로 전달하고 DB 조회/WHAT-IF는 기존 RLS 경로를 유지한다. 별도 Redis 명령 Gateway를 만들지 않는다.
- 회사 Redis는 기존 `127.0.0.1:6379`, HTTP host publish는 `127.0.0.1:6380`, 기존 Nginx `/redis/` 접두어 제거 프록시를 유지한다. 회사 Redis를 추가 생성하거나 포트를 공개하지 않는다.
- redis-api는 `/health`·분석 접수/조회·수집 접수/조회만 허용하고 서비스 토큰을 검증한다. 업무 요청에는 사용자 Bearer도 필요하며 기존 Auth/RBAC/RLS를 다시 검사한다. 웹 런타임에 service role을 주지 않는다.
- 기존 limiter·멱등·BullMQ·Worker·quota 로직을 재사용한다. durable dispatch·동시 예산 예약 보강은 후속 단계이며 이번 완료 범위로 주장하지 않는다.
- 그때 남긴 ADR-044의 Vercel ai/binding과 MinIO는 뒤에 ADR-048·049로 뺐다.
- 운영 배포는 역할 명시·서버 전용 API token·HTTPS 설정을 필수로 하고, Gateway 서비스 전체를 loopback에만 게시한다. 로컬 개발/시험은 `standalone` 호환 역할을 사용한다.

## ADR-043 가상 직원 200명 전체 계산 속성과 점수 검증 확대

2026-10-21 사용자 요청으로 채택했다. “200명 전부한테 임의적으로 자격증이나 기술, 실적, 가용성 넣어. DB 테이블에 없으면 테이블 고치고 db:push 해”에 이어 “기존 점수 검증도200명 전부 하자”를 반영한다. 이 결정이 ADR-019·021·042의 계산 대상 27명 제한을 대체한다.

- 정본 명부의 200명 전원을 scoringEligible로 만들고 기존 신원·사진·27명 계산 속성·배정 7건을 보존한다. 재현 가능한 ID 기반 생성기는 실제 이름·성별·직위를 능력 근거로 사용하지 않는다.
- team_member_scoring에 certifications·past_projects·capability_source·capability_version을 추가한다. 자격증과 개인 실적은 가상 표시·synthetic 증거 참조를 가지며 실제 회사 자격·실적으로 합치지 않는다.
- 원래 조직 RLS와 쓰기 제한을 유지하고, 추가 마이그레이션은 고정 org-01의 기존 가상 직원만 보강한다. Auth·타 조직·기존 score_runs를 바꾸지 않는다. 로컬 seed도 같은 200명 데이터를 사용한다.
- 점수 산식은 유지하고 입력·검증을 200명으로 확장한다. 고정 기간 가용 95.5 FTE, FX-01/02/03은 94/72/68 유지, FX-15는 58→68이다. 기간·가용성 변경에 따른 비포화 점수 회귀도 유지한다.
- 클라우드 db:push는 이번 요청에서 승인됐다. 적용 전 전체 검증과 적용 후 200행 속성·격리·마이그레이션 상태를 확인한다. 과거 ADR 본문의 27명은 당시 기록이다.

## ADR-040 부처 지원사업 공고 수집·목록 (확장 컷 추가)

2026-10-21 사용자 결정. 정부 부처 공고를 "API로 가져와서 공고 목록에" 보이고, 소스는 기업마당 지원사업 API와 중기부 사업공고 RSS로 정했다(토스·네이버 블로그는 뺐다). 설계가 정한 화면 배치·표시 범위·녹음 응답 데모는 "설계에서 정한 것대로"로 승인했고, "위임 판단"은 사용자 위임("결정이 필요한 것들은 다 추천안대로 진행해")으로 정했다. 스펙은 [부처 지원사업 공고](../polaris/specs/done/2026-10-21-agency-program-notices.md)다.

- **결정(사용자)**: 두 소스를 수집해 공고 목록에 보인다. 웹훅·기술 블로그는 넣지 않는다.
  - 기업마당: `GET https://www.bizinfo.go.kr/uss/rss/bizinfoApi.do`, 인증 `crtfcKey`, JSON.
  - 중기부 RSS: `GET https://mss.go.kr/rss/smba/board/310.do`, 인증 없음, RSS 2.0(최신 20건).
  - 화면은 `/bids` 안 "나라장터 공고 | 부처 지원사업" 전환이다. 점수·권고 없이 목록과 원문 링크만, 정렬은 신청 마감순·등록일순이다. 데모는 녹음 응답으로도 돈다.
- **조건**: ADR-039와 같은 4개다. 핵심 컷 경로·계약(`ingest_save_revision`, analysis job, `/api/v1/bids`, `analyze()`, 골든)과 `infra/sources/registry.yaml`은 바꾸지 않는다.
- **위임 판단(스펙)**:
  - AI 추출·점수·권고·알림을 붙이지 않는다(추정금액·참가자격이 없어 규칙 엔진을 쓸 수 없다).
  - 저장은 새 표다. 공개 공고라 조직 데이터가 아니고, 읽기는 `bids`와 같은 대상, 쓰기는 worker(service role)만, 표는 만들자마자 RLS로 잠근다.
  - 소스 설정은 `infra/sources/` 새 파일로 따로 검사하고, 틀려도 나라장터 수집과 worker 기동을 막지 않는다.
  - 기업마당은 분야 "기술"(`searchLclasId=02`)만 받는다. 마감 지난 공고는 기본으로 숨긴다.
  - 보안: 호출 호스트는 `www.bizinfo.go.kr`·`mss.go.kr`만(다른 호스트 리다이렉트는 따르지 않는다), XML 외부 엔티티 끔, `crtfcKey`가 든 URL은 로그·오류·증거에서 가림, 본문 속 전화·이메일은 가려 저장([[09-SECURITY|09]]).
  - env는 `BIZINFO_API_KEY`(worker 전용)다. 없으면 기업마당만 건너뛴다. `NEXT_PUBLIC_`·웹 번들·로그에 넣지 않는다.
  - 녹음 응답은 `fixtures/recorded/`에 개인정보를 가려 두고 mock·fixture 모드에서 쓴다.
- 운영 기업마당 정기 수집은 전용 Worker가 맡는다(`infra/company/README.md` §10). 상태는 [[PROGRESS]]다.

## ADR-038 카카오톡 추천 공고 알림(나에게 보내기)

> [!warning] 2026-10-24 재개정 — 실제 공고로 실수신을 녹화한다 (ADR-050·054 반영)
> - **현재 결정(사용자 원문, 2026-10-24)**: "공고를 해커톤 시연때 mock이 아니라 실제 공고를 받아야 해. 시연 영상도 찍어야 하니까 내 의견 반영해". 실제 공고를 분석해 BID·WATCH 추천이 나오면 "나에게 보내기"로 실발송하고(`NOTIFY_KAKAO_PROVIDER=memo`) 휴대폰 수신을 녹화한다. 녹화 뒤 `mock`으로 되돌린다.
> - **녹화 시점(ADR-054 §3)**: 실공고 분석 경로는 운영에 들어갔다([2026-10-29 기록](evidence/company-rollout/20261029/ai-gateway-rollout.md)). 알림 전용 Worker는 회사에서 기동하지 않았고(`infra/company/README.md` §9) 카카오 운영 연결은 0건이다. 실발송·휴대폰 수신은 아직 없다. 녹화 뒤에만 "확인"으로 적는다.
> - **송신 순서(ADR-050)**: 송신 전에 Worker 전용 DB 함수가 전송 의도를 선점한다.
> - 카카오 migration 5개(`20261023000700`~`000704`)는 운영 DB에 적용했다. 아래는 2026-10-20~21 결정 기록이다.

**채택 (2026-10-21 사용자 결정).** 사용자 위임("결정이 필요한 것들은 다 추천안대로 진행해")으로 채택하고 ADR-018 예외를 승인했다.

- **왜**: 영업팀은 자리에 없거나 출장 중이라 공고를 휴대폰으로 본다.
- **사용자 결정 (2026-10-20)**: 본인 카톡으로 받는다 · 개인 설정 ON/OFF · BID·WATCH 권고 공고만 · 사업자 없이 "나에게 보내기" · 피드형(권고·제목·사유 한 줄·항목 표·버튼 2개) · 여러 건이면 건마다 따로 · 데모는 녹화.
- **추천안으로 확정한 것**: 사람이 요청한 분석만 보낸다(데모 사전 분석 제외) · 결과가 불분명한 실패는 다시 보내지 않는다(최대 한 번).
- **바뀌는 조항**: ADR-006 해커톤 조항 → `NOTIFY_KAKAO_PROVIDER=memo` 실발송(기본 `mock`) · ADR-018 예외 → 카카오 비밀값(`KAKAO_REST_API_KEY`·`KAKAO_CLIENT_SECRET`·`KAKAO_TOKEN_ENC_KEY`)을 웹 서버·worker env에 두고 서버에서만 읽는다 · 미결정 5번은 운영 전환 때.

## ADR-037 데모 강화 컷 (BOOST-2 가정 재계산, ADR-023 개정)

2026-10-20 사용자 승인(데모 강화 설계 승인을 설계 §8 ADR 제안 승인으로 본다). 근거: 데모 강화 설계·BOOST-2 계획(원문: git `5261730f` 의 `docs/plans/2026-10-20-demo-boost-design.md`·`2026-10-20-boost2-what-if-plan.md`), [화면 디자인 스펙](plans/2026-10-20-boost2-what-if-ui.md). 맥락·BOOST-1 게이트 서술 원문은 git `3ae02acf` 의 docs/16-DECISIONS.md "ADR-037"에 있다.

- **결정**: "데모 강화 컷"을 핵심 컷과 나란히 둔다. 대상은 **BOOST-2 가정 재계산 하나**다. 조건 4개:
  1. 작업자가 겹치면 핵심 컷이 먼저다.
  2. 추가형이다. 수집 저장 RPC·analysis job·`analyze()` 계산식·골든 94/72/68을 바꾸지 않는다.
  3. 기능 freeze까지 green이 아니면 데모에서 뺀다.
  4. 새 띠·스위치에 확률·승률·"수주 가능성"처럼 읽히는 수치·문구를 두지 않는다(ADR-007).
- **BOOST-2가 하는 일**: 공고 상세에서 최신 점수 run의 필수 자격 가운데 서버가 가정 가능하다고 준 행에 "보유 가정" 스위치를 둔다. 켜면 서버가 그 run의 `input_snapshot`에서 `profile.licenses`만 바꿔 규칙 엔진을 다시 돌리고, 점선 "가정 시나리오" 띠에 원래 → 가정(권고·SOL Score·필수자격·요소별 점수)을 보인다. 고정 문구는 "가정 결과입니다. 저장되지 않고 결정 기록에 쓰이지 않습니다."와 "결정 모델 의견은 가정에 포함하지 않았습니다."다. 계약 [[05-API-SPEC|05]] §4.5, 계산 [[08-SCORING|08]] §5.6, 화면 [[06-UI-UX|06]] §6.1, 시험 [[11-TESTING|11]].
- **정한 것**(메인 세션 결정):
  - DB에 아무것도 쓰지 않는다(`score_runs`·`bid_reviews`·`audit_logs`·알림·outbox).
  - 원래와 가정 모두 `kev=null`로 계산한다. 저장된 결정 모델 응답은 원래 프로필 기준이라 낡은 플래그가 붙기 때문이다. 점수·권고·자격 판정은 결정 모델 영향을 받지 않는다.
  - 가정 가능한 항목은 자격 코드 사전에 있는 필수 항목 가운데 `NOT_SATISFIED`이거나 `NEEDS_REVIEW`(`COMPANY_EVIDENCE_MISSING`)인 것뿐이다. 그 밖의 코드는 400으로 거절한다.
  - 결정 패널의 권고·점수는 원래 값이다. 가정은 저장·공유하지 않고 결정 기록과 잇지 않는다.
  - 면허·등록 보유 가정뿐이다. 공동수급에 따른 면허 인정의 적법성은 판정하지 않는다.
  - 응답은 규칙 엔진 이름(`score`·`factors`·`qualificationStatus`·`checks`)을 쓴다. ADR-028 때 맞춘다.
- **데모**: D1 장면은 ADR-059로 S4 `FX-02` 재분석 뒤 두 자격 가정 → 비추천이다. 로컬 `mock` 장면은 `FX-03`(68, 정보통신공사업 등록 `NOT_SATISFIED`)에서 가정 스위치를 켜면 권고가 NO-BID → WATCH, 점수는 68 그대로다(`web/server/scoring/what-if.test.ts`).
- **BOOST-1 제외**: 대시보드 "실공고 선별 깔때기"는 "제외" 칸을 채우려면 미결정 19번 해석을 핵심 엔진에 넣어야 해서 뺐다([게이트 결과](evidence/boost1/boost1-gate-20261020.md)). 19번이 공식 근거로 확인되면 다시 검토한다.
- **바뀌지 않는 것**: 확장 컷·P1 착수 규칙, 핵심 컷 C0~C9. 핵심 컷 green 판정은 데모 강화 컷을 기다리지 않는다. 구현 상태는 [[PROGRESS]]다.

## ADR-028 해커톤 뒤 API·worker NestJS 전환

상태는 **채택**이다(사용자 결정 2026-10-19, 원문: "서버는 Nest.js인데 Next.js로 되어 있어"). 사용자는 범위를 API·worker만으로, 시점을 해커톤 뒤로 골랐다. 당시 마감이 가까웠고 C3·C5 서버 작업이 Next.js 구조 위에 있어 지금 옮기면 핵심 컷 일정이 깨진다. 착수는 해커톤 제출 뒤다(제출일은 ADR-054). 그 전까지는 ADR-017과 그 구현 결과 절이 현재 구조의 정본이다.

- **바뀌는 것**: `/api/v1/**` Route Handler와 헬스체크, 서버 도메인의 repo·service, worker(`web/worker`, BullMQ 소비자)를 NestJS 앱으로 옮긴다. Next.js(`web/`)는 화면만 맡는다. ADR-017의 "NestJS는 쓰지 않는다"는 이 범위에서만 바뀐다.
- **바뀌지 않는 것**: Supabase(Postgres·RLS·Auth), 조직 격리(`org_id` + RLS), `memberships.sol_role`, append-only 마이그레이션·정책 시험(`pnpm test:db`)·타입 생성, service role은 worker·seed만(운영자 CLI 예외는 미결정 25번), 파일 저장 Supabase Storage(ADR-048로 MinIO 대체)·Qdrant·Redis/BullMQ·Python AI gateway·Docker Compose, `/api/v1` 경로와 DTO 계약([[05-API-SPEC|05 API]]). Prisma·자체 JWT 인증은 쓰지 않는다(ADR-002 폐기 그대로).
- **인증·권한(목표)**: NestJS는 요청의 Supabase access token(`Authorization: Bearer`)을 검증하고, 요청마다 그 토큰으로 Supabase 클라이언트를 만들어 RLS가 권한을 정하게 한다. 요청 처리 경로의 기본 통로는 anon 키 + 사용자 토큰이고, service role 키는 쓰지 않는다.
- **해커톤 동안**: NestJS 코드·의존성을 만들지 않는다. 현재 구조를 설명하는 문서(02·04·05·07·10·11·17·20, `.claude` 에이전트·스킬, `docs/boilerplate/`)는 Next.js 기준 그대로 둔다.
- **착수 때 할 일**: 목표 구조 스펙(앱 위치 초안은 루트 `api/`로 `web/`처럼 독립 설치, 모듈 구조, 화면이 데이터를 NestJS로 읽을지 Supabase를 직접 부를지) → 사용자 승인 → `verify.config.json`에 새 프로젝트와 계층 규칙 등록 → Compose `api` 서비스 → 도메인별 이전(시험 먼저) → 문서 갱신(ADR-017 구현 결과 절, 위 문서들, `CLAUDE.md`·`AGENTS.md`·`docs/CLAUDE.md`) → CI(`.github/` 편집 금지는 2026-10-21 사용자 지시로 해제됐다. CI 필수 검사와 훅은 유지).
- **남은 결정**: NestJS 버전과 모듈 구조, worker를 NestJS 앱의 별도 진입점으로 둘지 별도 앱으로 둘지, 화면의 데이터 경로. 착수 스펙에서 정한다.
- **되돌리기**: 착수 전이면 이 ADR을 폐기하면 된다.

## ADR-026 팀 만들기는 서비스 운영자만

- **결정**(사용자 2026-10-19, 추천안 채택): `organizations` insert 정책 "팀 만들기"를 `with check (personal_owner_id is null and public.is_admin())`로 바꾼다(`supabase/migrations/20261019000008_team_creation_operator_only.sql`). 정지된 운영자는 `is_admin()`이 false라 만들지 못한다. 열 권한(`slug`·`name`), `add_team_owner`(만든 사람 owner+ADMIN, ADR-021), 개인 조직 금지 검사는 그대로다.
- **이유**: 04 §3.6의 운영 표(`ingest_runs`·`ingest_errors`·`eval_runs`)는 조직 데이터가 아니라 "어느 조직에서든 ADMIN"이 읽는다. 템플릿처럼 누구나 팀을 만들면 가입만 한 사람이 자기 팀의 ADMIN이 되어 운영 표를 읽는다. 업무 조직 합류는 초대로만 하므로(ADR-018·021) 일반 회원이 팀을 만들 이유가 없다. 대안(운영 표 읽기를 `is_demo` 조직 ADMIN으로 좁히기, 위험 수용)보다 단순하고 되돌리기 쉽다.
- **영향**: 템플릿 "팀 만들기" 화면(`/teams/new`)은 운영자가 아니면 RLS 거절을 받는다. 해커톤 화면 범위에 없으니 메뉴에서 빼거나 안내만 한다(C6에서 정한다). 템플릿 로컬 seed(`scripts/db-seed.mjs`)처럼 사용자 토큰으로 팀을 만드는 경로는 막히므로 `pnpm demo:reset`은 service role로 조직을 만들고, `pnpm db:seed`도 시드 팀을 관리 키로 만든 뒤 소유자 멤버십(owner+ADMIN)을 직접 넣는다(빈 DB에서 RLS 403이 나던 결함을 2026-10-19에 고침, 회귀 시험 `scripts/db-seed.test.mjs`). 로그인 뒤 E2E(`web/e2e-auth`)의 팀 만들기 시나리오는 운영자 계정으로 바꾼다(확장 컷·P1).
- **되돌리기**: 새 마이그레이션으로 정책을 템플릿 본문(`with check (personal_owner_id is null)`)으로 다시 만든다.
- **검증**: C2 2단계 정책 시험 — 일반 회원 팀 insert 거절, 운영자 통과(owner+ADMIN), 정지된 운영자 거절, 마이그레이션 재실행 스냅샷 유지([[11-TESTING|11 테스트]] §4 Phase 1).

## ADR-025 회사 GPU 추론 엔드포인트

**채택 (2026-10-19 사용자 결정. 모델·런타임은 ADR-034로 개정).** 1~8번·모델 라우터(2-1~2-3)·미검증 가정의 원문은 git `3ae02acf` 의 docs/16-DECISIONS.md "ADR-025"에 있다. 아래는 지금 유효한 조항이다. 아키텍처(Worker → gateway → 모델)·실행 모드·장애 처리·데이터 경계는 ADR-020 그대로다.

1. **연결 방식**: 회사 GPU 서버는 밖에서 SSH·VPN으로 들어갈 수 없다. 모델은 회사가 HTTPS로 제공하거나 회사 호스트 안에서 gateway가 붙는다. 처음 정한 터널·노트북 `host.docker.internal` 전제는 폐기했다.
2. **지금 경로**: 추출·설명 Qwen은 회사가 운영하는 vLLM API `https://acropolissg.com/vllm/v1`(served id `Qwen3.8-Flash-Next-AWQ-INT4`, ADR-034)이다. 결정 모델은 우리 `sol_decision` 서버(Bosun v3.1 0.6B)이고, 운영 회사 Compose gateway(`network_mode: host`)가 같은 호스트의 `KEV_BASE_URL=http://127.0.0.1:8009`로 붙는다(2026-10-27 확인, [기록](evidence/company-public-profile/20261027/prod-rollout.md)). 회사 nginx에 `/sol-radar` location은 등록되지 않았다(2026-10-27 사용자 확인). 그래서 설계한 `/sol-radar/qwen`·`/sol-radar/kev` 경로와 모델 라우터(`infra/compose.gpu.yaml`·`infra/gpu/model-router.conf`)는 등록 전 참고 구성으로만 남는다.
3. **env 이름**: `QWEN_BASE_URL`·`KEV_BASE_URL`·`QWEN_API_KEY`·`KEV_API_KEY`는 그대로다.
4. **운영 책임**: 모델 런타임 기동·GPU 메모리 배분·가중치 대조·`nvidia-smi` 실측은 회사 몫이다. 우리는 gateway 기동 때 `GET /v1/models` 응답을 레지스트리(`services/ai/models/registry.yaml`)와 대조하고([[03-AI-PIPELINE|03]] §11) 지연을 잰다.
5. **장애 처리**: 엔드포인트에 닿지 않으면 gateway가 `QWEN_UNAVAILABLE`·`KEV_UNAVAILABLE`을 따로 기록하고 `PARTIAL`·`RULES_ONLY`로 끝낸다. 자동 mock 대체는 없다. 필요하면 사람이 `mock`으로 바꾼다.
6. **보안**: 공개 인터넷 엔드포인트는 TLS 필수(인증서 검증을 끄지 않는다)이고, 같은 호스트 루프백(`127.0.0.1:8009`)만 예외다. API 키는 필수이고 서버 env 파일에만 둔다. 회사로 가는 데이터는 개인정보를 가린 공고와 회사 프로필뿐이다(Supabase 키·사용자 정보 없음, [[09-SECURITY|09 보안]]).
7. **C1 ③ 확인 절차**: G1 HTTPS 접속 → G2 Qwen·Bosun `GET /v1/models`·레지스트리 대조 → G3 지연 실측 → G4 guided JSON → G5 회사 제공 GPU 정보 기록 → G6 차단 때 `PARTIAL`. 정본은 [[03-AI-PIPELINE|03]] §5.9다. 외부 의존성 컷 규칙(ADR-023)의 "GPU 정상" = G2·G3 통과.
8. **미결정**: 17번(회사 엔드포인트 경로·인증·`/v1/models`·지연). GPU 메모리 배분(3번)은 회사 결정으로 넘겼다.

- **연결**: registry 항목의 `serviceKeyEnv`가 env **이름**을 가리킨다. 값은 `infra/.env`(깃 제외)에만 둔다 ([[15-DATA-CONTRACTS|15 데이터 계약]] §8, [[10-DEPLOYMENT|10 배포]]).
- **읽는 쪽**: worker의 `OfficialApiConnector`만 읽는다. web·gateway·`NEXT_PUBLIC_` 변수·`web/.env.local`·루트 `.env.local`에는 두지 않는다.
- **빠졌을 때**: `live`에서 4개 모두 필수다. `pnpm check:env`는 빠진 키마다 그 이름으로 `MISSING_KEY`를 낸다. worker는 기동할 때 빠진 env 이름을 알리고 멈춘다. 다른 서비스의 키로 대신 부르지 않는다. `fixture`·`mock`에는 필요 없다.
- **호출 예산**: 서비스마다 따로 센다. 에러코드 22를 받으면 그 서비스의 그날 호출만 멈추고, 다른 서비스의 수집은 계속한다 ([[07-DATA-PIPELINE|07 수집]] §2.2).
- **값 형식**: 포털이 Encoding 키(URL 인코딩된 값)만 제공하므로(2026-10-19 사용자 확인) env에는 Encoding 키를 그대로 넣는다. worker의 `readG2bServiceKey`(`web/worker/env.ts`)가 `decodeURIComponent`로 한 번 디코딩해 Decoding 키로 만들고, Connector가 그 값을 URL 인코딩 한 번만 한다. Decoding 키를 넣어도 결과는 같다. Encoding 키 경로는 C1 실제 호출(2026-10-19)에서 확인했다([API 호출 증거](evidence/phase-0/external-deps-api-20261019.md) §1). 2026-10-18 채택 당시의 "Decoding 키를 넣는다"를 대체한다.
- **비밀 보호**: 네 값을 모두 로그·오류 메시지·`ingest_errors`·응답 본문·증거에서 가린다(V2-11, [[11-TESTING|11 테스트]]). 네 값이 같아도 env는 나눈다.
- 승인 설계 실데이터 AI 파이프라인 v0.2(원문: git `5261730f` 의 `docs/plans/2026-10-16-ai-pipeline-finetune-design.md`)의 단일 `G2B_SERVICE_KEY` 표기는 이 ADR이 대체한다. 서비스 확장(4+6 서비스)은 ADR-047이다.

## ADR-020 실데이터 MVP와 AI 파이프라인 v0.2

> [!note] 바뀐 것

2026-10-16 사용자 대화로 정했다. 사용자 원문: "해커톤 시연용 가짜 AI가 아니라, 실제 공공입찰 데이터를 대상으로 끝까지 동작하는 SOL RADAR MVP". 승인 설계는 git `5261730f` 의 `docs/plans/2026-10-16-ai-pipeline-finetune-design.md`, 모델 역할·실추론 위치·해커톤 순서를 포함한 원문은 git `3ae02acf` 의 docs/16-DECISIONS.md "ADR-020"에 있다.

- **실행 모드**: `SOL_RUN_MODE=live|fixture|mock`(기본 `mock`). `live` = 나라장터 Open API + 실제 AI, `fixture` = fixture 20건 + 실제 AI, `mock` = fixture 20건 + mock AI. 모드와 모순된 env는 기동 거부. 데이터 출처(`source`·`is_demo`)와 분석 모드(`score_runs.run_mode`·`ai_provider`·모델 이름)를 기록하고 표시한다. 골든은 `mock`에서만 단언한다([[03-AI-PIPELINE|03]], [[10-DEPLOYMENT|10]]).
- **회사 프로필**: 가상 솔리데오 프로필(`is_demo=true`)이고 live 분석은 "실제 공고 × 가상 회사 프로필" 배지를 붙인다(ADR-019, 운영은 ADR-052).
- **수집**: 입찰공고(용역)·면허제한·참가가능지역·e발주 첨부, 사전규격, 발주계획, 업종 코드. 첨부는 `www.g2b.go.kr` allowlist, 형식별 `DocumentParser`. 같은 조건이면 API 구조화 필드가 Qwen 추출보다 우선이고, 다르면 `CONFLICTED`다([[07-DATA-PIPELINE|07]], [[15-DATA-CONTRACTS|15]]).

- **모델 역할**: Qwen = 구조화 추출·영어 표기·근거 설명. 결정 모델 = 요구사항별 충족/미충족/확인 필요, 기술 적합성, 실적 연관성, 수행 리스크(`kev-qs/v0.2`). 규칙 엔진 = 명시 조건. SOL Score = `sol-v0.1.0`. **결정 모델 확률은 점수 입력이 아니며** 참고 지표와 `reviewFlags`로만 표시한다. 점수 반영은 평가셋 검증 뒤 새 ADR로 정한다([[08-SCORING|08]]).
- **근거 추적**: 공고 `EvidenceRef`에 회사 `CompanyEvidenceRef`를 더하고 state 줄마다 `KevStateTrace`를 저장한다([[15-DATA-CONTRACTS|15]]).
- **라벨**: `SATISFIED`·`NOT_SATISFIED`·`NEEDS_REVIEW` + 사유 코드. 미충족에는 공고·회사 양쪽 근거가 필요하고 정보 부족은 미충족이 아니다.
- **평가·파인튜닝**: 평가셋은 실제 공고 × 가상 기업 원형 6개, test 20·dev 10 사업, 사업 단위 분할([[21-MODEL-TRAINING|21]]). 목표에 미달해도 자동으로 파인튜닝하지 않고, 모델 판단 오류가 주원인일 때 사람이 결정한다. 실제 낙찰 결과는 학습 목표로 쓰지 않는다.
- **모델 버전**: `services/ai/models/registry.yaml` + sha256 + 기동 시 `/v1/models` 대조. 불일치면 gateway 기동 거부.

## ADR-018 구현 결과

- **코드**: 템플릿 그대로다. 버튼은 `web/app/auth/social-sign-in.tsx`(로그인·가입 화면의 가는 선 아래), 켤 제공자 판단은 `web/lib/auth-providers.ts`, 콜백은 `web/app/auth/callback/route.ts`(받은 코드를 세션으로 바꾼다). 마이페이지의 로그인 수단 연결(템플릿 `/api/auth/*`)을 남길지는 Phase 3 N1 템플릿 정리(ADR-024 D15)에서 정한다([[05-API-SPEC|05 API]]).
- **버튼 켜기**: `web/.env.local`의 `NEXT_PUBLIC_AUTH_GOOGLE`·`NEXT_PUBLIC_AUTH_KAKAO`·`NEXT_PUBLIC_AUTH_NAVER`가 `true`인 제공자만 보인다(빌드 때 코드에 박힌다). Supabase에 제공자를 설정하기 전에 켜면 누를 때 Supabase가 `provider is not enabled`를 보이고 사이트로 돌아오지 않는다. 데모·배포 환경에서는 설정을 마친 제공자만 켠다.
- **제공자 설정(후순위)**: 구글·카카오는 Supabase 기본 제공자, 네이버는 사용자 정의 OIDC 제공자 `custom:naver`다. Client ID·Secret은 Supabase 쪽(클라우드는 대시보드, 로컬은 `supabase/config.toml` + 깃 제외 `supabase/.env`)에만 두고 웹 env에는 넣지 않는다. 절차는 `docs/boilerplate/OAUTH-PROVIDERS.md`.
- **가입이 여는 범위**: 가입하면 계정과 `profiles` 행이 생긴다(템플릿 가입 트리거는 개인 조직도 만들었지만 ADR-021로 새 마이그레이션에서 중단했다. 이미 있는 개인 조직은 지우지 않는다). 업무 조직(예: 솔리데오) 데이터는 멤버십이 있어야 RLS(`my_org_ids()`)가 보여 주므로 가입만으로는 보이지 않는다. 공용 표(`bid_notices` 등)는 `authenticated` 읽기라 가입한 사용자도 읽는다.
- **데모**: 로그인은 seed 계정의 이메일 + 비밀번호다([[19-DEMO-SCENARIO|19 데모 시나리오]] S0). 간편 로그인은 데모 장면에 쓰지 않는다.

## ADR-017 구현 결과

- **코드 위치**: 화면·Route Handler·서버 도메인은 `web/` 하나다. 서버 도메인은 `web/server/<도메인>/`(model·repo·service·index 배럴, `import "server-only"`), 외부 계약은 `web/app/api/v1/**/route.ts`, 헬스체크는 `web/app/health/{live,ready}/route.ts`. pnpm workspace·공유 계약 패키지는 만들지 않고 `web/`은 독립 설치한다. 계약 단일 원천은 zod(ADR-016).
- **DB**: Supabase Postgres + RLS. `supabase/migrations/*.sql`에 새 파일로만 쌓는다. 타입 생성물 `web/lib/database.types.ts`(`pnpm db:types`), 클라우드 적용 `pnpm db:push`(사용자 확인 뒤), 정책 시험 `pnpm test:db`(PGlite).
- **조직·권한**: 조직 소유 열은 `org_id`, RLS `org_id in (select public.my_org_ids())`. 템플릿 표 `profiles`·`organizations`·`memberships`·`invitations`·`activities`를 재사용하고 `tasks`는 입찰 프로젝트 체크리스트로 쓴다(ADR-021). 업무 역할은 `memberships.sol_role`(`ADMIN`·`SALES`·`ANALYST`·`VIEWER`, ADR-052로 `EXECUTIVE` 추가)이다. 구성원 관리도 `sol_role=ADMIN` 기준이고 `org_role`은 템플릿 호환용이다. 운영자 `profiles.is_admin`도 남의 조직은 못 읽는다. 다른 조직 자원은 `404`다.
- **공용 데이터**: `bid_notices`·`bid_revisions`·`bid_documents`·`requirement_extractions` 등은 `authenticated` 읽기만, 쓰기는 worker(service role)만.
- **Auth**: Supabase Auth(이메일·간편 로그인, 공개 가입 + 초대, ADR-018). 템플릿 `/auth/*`와 `web/server/auth`가 맡고 자체 토큰 엔드포인트는 없다. 세션 쿠키는 `@supabase/ssr`(SameSite=Lax, 운영 Secure), XSS 방어는 CSP nonce(`web/proxy.ts`·`web/server/csp`). Route Handler는 세션 쿠키나 `Authorization: Bearer`를 받고, 쿠키 인증 상태 변경에는 `X-Requested-With: sol-radar`를 요구한다. 세부 설정은 미결정 10번.
- **service role**: worker·seed 스크립트와 사람이 로컬에서 돌리는 운영자 CLI(`scripts/ops/`, 닫힌 미결정 25번)만 쓴다. 웹 요청 경로는 anon 키 + 로그인 쿠키다. worker는 쓸 때 `org_id`를 직접 지정한다. 이 키는 `NEXT_PUBLIC_`·브라우저 번들·로그에 넣지 않는다.
- **Worker**: `web/worker/`가 BullMQ 소비자 진입점이다. `node --conditions=react-server --import tsx worker/main.ts`로 띄운다(닫힌 미결정 9번). 모델 호출은 AI gateway만 한다.
- **Compose**: `infra/compose.yaml`(로컬 데모·대체 경로)은 `redis`·`qdrant`·`ai-gateway`·`worker`다. 운영 web은 Vercel(ADR-049). 데모 seed는 `pnpm demo:reset`. 파일 저장은 private Supabase Storage(`bid-documents`·`bid-parsed`, ADR-048). pgvector·Supabase Queues는 쓰지 않는다([[10-DEPLOYMENT|10]]).
- **시험**: Vitest(웹·도메인·Route Handler·골든·worker), `node --test` + PGlite(DB 정책), Playwright(`web/e2e/`·`web/e2e-auth/`), pytest(AI gateway), `infra/smoke.sh`. G5(조직 격리)는 RLS 시험 + Route Handler 시험 + E2E([[11-TESTING|11]]).
- **데모 네트워크**: DB·Auth가 Supabase 클라우드라 인터넷이 필요하다. 대체 경로는 [[19-DEMO-SCENARIO|19]]다(닫힌 미결정 8번).

## ADR-007 ~ 014 구현 결과

- **ADR-007**: `web/`에 1280px 미만 breakpoint·결제 모듈·요금 화면 없음. UI 토큰·그리드는 1280~1920만 ([[06-UI-UX|06 UI]]). 17 절대 규칙으로 강제.
- **ADR-008**: `infra/env/demo.env.example` 기본값 `SOL_RUN_MODE=mock`(→ `AI_PROVIDER=mock`, `KEV_ENABLED=true`로 mock adapter가 응답, `DEMO_MODE=true`, ADR-020). `KEV_ENABLED`는 기본값이 `true`일 뿐이고 세 모드 모두 `false`를 허용한다(ADR-029 A5). mock adapter는 `services/ai/src/sol_ai/adapters/mock.py`, fixture ID별 고정 응답. 프로필 전환에 코드 변경 없음.
- **ADR-009**: 모든 md에 frontmatter. 파일 이름 변경 금지(링크가 파일명 기준). 00이 MOC. 저장소의 `docs/` 폴더가 이 vault.
- **ADR-010**: `AI_PROVIDER=hosted`인데 `AI_HOSTED_APPROVED=false`면 gateway가 기동을 거부한다(조용히 mock으로 바꾸지 않는다). Route Handler `GET /api/v1/admin/ai/status`는 `422 HOSTED_NOT_APPROVED`. 호출 시 provider·모델·토큰 수를 로그에 기록(키는 기록 금지). 승인 기록은 [[PROGRESS]] 작업 로그에 남긴다.
- **ADR-011**: extract job(`web/worker`, ADR-020 이후 ingest → documents → extract 순서)이 `/extract`를 호출하고 `requirement_extractions`에 UNIQUE(`revision_id`, `model_name`, `prompt_hash`)로 저장. analysis job은 이것을 읽어 `/kev`와 규칙 엔진을 돈다 ([[02-ARCHITECTURE|02 아키텍처]] 흐름).
- **ADR-012**: state 빌더는 `services/ai/src/sol_ai/adapters/kev.py`, 템플릿은 `services/ai/kev/state-templates/{en,ko}.v0.2.txt`에만 둔다(ADR-020). 한국어/영어 비교는 평가셋 E1·E2([[21-MODEL-TRAINING|21 모델 학습]]), `permute` 순서 민감도는 03 §5.9. 발표의 고정 장면은 mock 결정 모델, `live`·`fixture` 모드는 결정 모델 Bosun v3.1 0.6B 실추론(참고 지표, ADR-034).
- **ADR-013**: 11의 골든 시나리오 표, 07의 fixture 표, 19의 장면 표가 `G`·`S`·`FX` ID로 서로 가리킨다. 시험 이름(`describe`)에 ID를 넣는다(예: `describe("G3 필수 자격 미충족 → NO-BID")`). 시험 파일은 [[11-TESTING|11 테스트]] §3 표가 ID 행으로 가리킨다(예: G3 → `web/server/scoring/decision-policy.golden.test.ts`).
- **ADR-014**: `fixtures/*.json`의 날짜 필드는 `+Nd` 문자열. seed 스크립트(`pnpm demo:reset`)가 실행 시각의 KST 18:00을 기준으로 절대 ISO8601로 바꿔 적재한다. 테스트는 기준 시각을 고정해 결정적으로 돈다.

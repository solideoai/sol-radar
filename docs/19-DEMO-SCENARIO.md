# 19. 데모 시나리오

> [!note] 발표 형식과 촬영 경로 ([[16-DECISIONS|ADR-054]])
> 본편은 "덱 20분 + 녹화 클립"이다. 클립의 길이·자막·캡션은 [[slides-spec|덱 제작 명세]] 부록 A가 정본이고, 이 문서는 클립을 찍는 클릭 경로와 장면별 촬영 경로를 정한다. D1 운영 사이트(`https://www.solideos-radar.com`, 시작 URL에 `?origin=demo`)는 S0~S4·S-LIVE·S7의 촬영 경로이자 질의응답 때의 라이브다. S5(변경 감지)·S6(AI 장애 대체)는 로컬 Compose에서 녹화한 클립으로 보인다. S5는 30초 클립 6으로 S4 뒤·장애 대체(클립 4) 앞에 넣는다([[18-HACKATHON|18]] §6). 운영 회사 gateway를 멈추는 장면은 만들지 않는다. 운영에 `pnpm demo:reset`은 돌리지 않는다. 남은 날의 일정은 [[12-ROADMAP|12 로드맵]] "남은 일정 제안" 표다.

이 문서는 조작자가 따라가는 **클릭 경로**, 데모에 쓰는 **가상 기업과 fixture**, 각 장면에서 **화면에 보여야 하는 것**을 정의한다. fixture 20건의 전체 명세는 [[07-DATA-PIPELINE|07 수집]] §6.2의 fixture 표(`FX-01`~`FX-20`)가 단일 원천이고, 데모 기업 프로필과 점수 계산 예시는 [[08-SCORING|08 SOL Score]]가 단일 원천이다. 이 문서와 충돌하면 07·08을 따르고 이 문서를 고친다.

> [!warning] 가상 데이터
> 회사명 "솔리데오"와 부서·직급 명칭은 사용자 회사 기준이다(ADR-019). 가상 직원 200명·사용자·사진·공고·실적·자격·재무·가용성은 데모 설정이며 실제 회사 현황/공고를 뜻하지 않는다. 모든 데모 fixture는 `isDemo=true`이며, 공고 fixture의 `sourceUrl`은 `https://demo.sol-radar.invalid/notices/FX-xx`다. 화면에 `DEMO` 배지가 붙는다. 발주기관 이름은 실제 기관명을 쓰지만 공고 내용은 지어낸 것이다. `live` 모드의 공고는 실제 나라장터 공고(`isDemo=false`)다. 회사 프로필은 로컬·시험·`demo:reset`에서 가상 솔리데오이고, 운영(D1)에서는 공개 자료로 만든 솔리데오 프로필에 회사가 확인한 자격 3건을 더한 revision 6이다([[16-DECISIONS|ADR-052]], [[16-DECISIONS|ADR-059]] 2차 개정). 분석 화면 배지는 그 분석에 쓴 프로필에 따라 "가상 회사 프로필로 분석" 또는 "공개 자료 회사 프로필로 분석"이다.

위 5계정은 가상 직원 명부 200명과 별개이며 명부에서 Auth 계정을 자동 생성하지 않는다. `.invalid`의 `soltech`는 기존 데모 계정 별칭으로 실제 회사 이메일이 아니다. 사용 회사 선택 UI는 솔리데오 하나만 표시하고 비교 조직은 격리 시험에서만 쓴다.

계정은 Supabase Auth 사용자이고, 역할 열은 조직 구성원 표의 업무 역할 `memberships.sol_role` 값이다. admin@solideos.com는 조직 관리 권한도 가진다(`org_role=owner` + `sol_role=ADMIN`). 계정·조직·구성원은 `pnpm demo:reset`이 service role 키로 Supabase 프로젝트에 만든다([[16-DECISIONS|16 ADR]] ADR-017). 운영(D1)에 어느 계정이 있는지는 §3.1에서 확인한다.

관리자 한 계정만 준비할 때는 `node scripts/ops/demo-admin.mjs --env-file .env.local`로 대상을 먼저 확인하고 `--apply`를 붙인다. 비밀번호는 실행 환경의 `DEMO_ADMIN_PASSWORD` 또는 해당 파일의 `DEMO_ADMIN_PASSWORD`·`DEMO_SEED_PASSWORD`로 전달하며 명부·공고·분석은 초기화하지 않는다. 이 작업의 부서·직급 카탈로그는 가상 직원 200명의 생성 원본과 분리한다. `관리자` 직급 표시는 권한을 부여하지 않으며 실제 권한은 `memberships`에 별도로 적용한다.

관리자를 제외한 4계정의 이메일 도메인은 예약 TLD `.invalid`(RFC 2606)라 실제로 전달되지 않는다. seed 합계: 조직 2, 사용자 5, 프로필 revision 2, 공고 19건 적재 + 1건 격리(FX-12), 사전 리뷰 2건(FX-01 추천, FX-03 비추천). seed 로그 마지막 줄 `seed: orgs=2 users=5 profileRevisions=2 people=200 portraits=200 bids=19 quarantined=1 reviews=2 isDemo=true` ([[10-DEPLOYMENT|10]]).

비밀번호는 `.env.example`의 `DEMO_SEED_PASSWORD` placeholder로 두고 실제 값은 seed 시 입력한다. 문서와 저장소에 실제 값을 쓰지 않는다.

### 3.2 대체 경로: 로컬 Compose

S5·S6 촬영, 운영에 `org-02` 계정이 없을 때의 S7 촬영, 회선·Supabase 장애(§5 대체 경로 ①)에 쓴다. 모드는 `mock`이고 골든 94·72·68이 나온다.

> [!warning] 운영 Supabase를 가리키지 않는다


   access token에는 만료 시간이 있다(값은 Supabase Auth 설정, 미검증). 찍기 직전에 받는다.
2. 그 토큰으로 FX-01 자격 판정을 조회한다. `$BASE`는 D1이면 `https://www.solideos-radar.com`, 로컬이면 `http://localhost:3000`이다.

   ```bash
   curl -s -i -H "Authorization: Bearer $ORG02_TOKEN" \
     "$BASE/api/v1/bids/{FX-01 id}/qualification-checks"
   ```

3. 보여야 하는 것: `404 NOT_FOUND`, 본문 `{error:{code,message,details,requestId}}`. 서버가 토큰을 Supabase로 검증한 뒤 그 사용자 권한으로 조회하므로, RLS가 `org-01`의 자격 판정 행을 숨겨 404가 된다.
4. 대조: 같은 토큰으로 `GET $BASE/api/v1/bids/{FX-01 id}` → `200`. 공고는 공용 데이터이고, 회사 점수·판정·검토·인력은 조직 밖에서 보이지 않는다.
5. 마무리 슬라이드: 정직성 표([[18-HACKATHON|18]] §7)와 범위 외 항목.

### 녹화 전용: 카카오톡 추천 공고 수신 ([[16-DECISIONS|ADR-038]])

슬라이드 12의 카카오 10초다([[slides-spec|덱 제작 명세]] 부록 A). 실공고 추천은 실공고 분석이 있어야 나온다. 2026-10-30 운영에서 연결(14:13, admin@solideos.com, `CONNECTED`)·S0 수신 시험(`KAKAO_TEST` 2통)·추천 카톡 23통 실발송을 했고, 15:47 알림 Worker 카카오를 다시 껐다. 연결 행은 15:31부터 `enabled=false`다([실발송 기록](evidence/kakao-notify/20261030-prod-live-send.md)). 실수신 화면 녹화는 아직 없다. 녹화 파일·발송 결과는 `docs/evidence/kakao-notify/`에 남기고, 실수신은 녹화 뒤에만 "확인"으로 적는다.

> [!warning] 카톡이 다시 가지 않는 공고
> `BID_RECOMMENDED`는 조직·공고마다 한 번만 생긴다(키 `<orgId>:<bidId>:BID_RECOMMENDED`, [[13-NOTIFICATIONS|13]]). 2026-10-30에 보낸 22개 공고(FX-01·FX-02를 포함한 DEMO 19·실공고 3)와 15:12 1건은 다시 분석해도 카톡이 가지 않는다. 알림 Worker 카카오가 꺼진 동안 사람이 요청한 분석은 이벤트가 `DEAD`가 되고, 연결이 꺼져(`enabled=false`) 받는 사람이 0명이면 이벤트가 `PROCESSED`로 닫힌다. 어느 쪽이든 그 공고는 나중에 켜도 다시 보내지 않는다. 그래서 Worker `memo`와 연결 `enabled`를 둘 다 켠 뒤에 녹화할 공고를 분석한다.

1. 준비: 운영 연결은 admin@solideos.com 1건이다(`CONNECTED`, 2026-10-30). 연결 주인이 개인 설정 "카카오톡 알림"을 다시 켜고(`enabled`, [[06-UI-UX|06]] §5.10.1), 알림 전용 Worker(`infra/compose.notify-only.company.yaml`)를 `NOTIFY_KAKAO_PROVIDER=memo`로 다시 만든다(`infra/company/README.md` §9.6, [[16-DECISIONS|ADR-068]]). 두 가지는 각각 사용자 승인을 받는다. 카카오 키는 Vercel과 회사 Worker env에 있고 값은 문서·로그에 적지 않는다([[10-DEPLOYMENT|10 배포]] "카카오 앱 설정"). 받는 사람은 연결을 켠 구성원 전원이라 분석은 어느 계정으로 요청해도 된다([[13-NOTIFICATIONS|13]]). 2026-10-30 기동과 실발송 순서는 [기동 기록](evidence/company-rollout/20261030/notify-worker-rollout.md)과 [실발송 기록](evidence/kakao-notify/20261030-prod-live-send.md)이다.
2. 카톡을 받은 적 없는 실제 나라장터 공고 1건(`BID_RECOMMENDED` 이벤트·`kakao_send_claims` 0건, 첨부 텍스트 있음)의 상세에서 [분석 실행] 또는 [재분석]을 누른다(회사 Qwen·Bosun 호출, 사용자 승인). 2026-11-01 `sol-v0.2.1` 재채점 뒤 실공고 추천 7건(85점)은 모두 이벤트·claim이 0건이다(운영 DB 읽기). 공고는 촬영 때 정한다. 추천 알림은 사람이 요청한 분석에서 추천·보류 권고가 처음 나온 공고에만 간다([[13-NOTIFICATIONS|13]]). 비추천이면 다른 실공고로 한다.
3. 휴대폰 카카오톡 "나와의 채팅"에 피드 한 통(제목 공고명, 설명 `<권고> 권고 · <사유 한 줄>`, 발주처·마감·추정금액·점수, 버튼 [분석 보기]·[공고 원문])이 오는 장면을 녹화한다. [분석 보기]는 운영 도메인을 가리킨다. 휴대폰에서 버튼이 열리는지는 녹화 때 확인하고, 안 열리면 수신까지만 보여 준다.
4. 말할 것: "실제 나라장터 공고를 우리 회사 기준으로 분석해 추천이 나오면, 알림을 켠 사람의 카카오톡으로 간다. 회사 프로필은 공개 자료로 만든 것이다. 해커톤에서는 카카오 '나에게 보내기'로 보내고, 운영에서는 알림톡으로 바꾼다."
5. 같은 공고는 조직마다 처음 한 번만 보낸다. 실발송은 녹화에 필요한 만큼만 한다. 녹화가 끝나면 알림 Worker 카카오를 끈다(`NOTIFY_KAKAO_PROVIDER` 빈 값, 2026-10-30 15:47과 같다). `mock`은 외부 호출 없이 성공으로 처리하므로([[13-NOTIFICATIONS|13]] 발송 수단) 그 뒤 분석한 공고가 받은 것으로 남는다. 평일 아침 묶음 카톡 ADR이 들어오면(설계안은 `memo` 상시) 이 값은 그 ADR을 따른다. 녹화 파일·발송 결과(받은 시각, 공고번호)는 `docs/evidence/`에 두고, 토큰·카카오 사용자 ID는 적지 않는다.

## 1. 한 줄 요약

> **SOL RADAR는 공공 SI·AX 기업의 영업팀이 "이 입찰에 들어가야 하는가"를 근거와 함께 10분 안에 판단하도록 돕는 의사결정 지원 플랫폼이다. 낙찰 확률을 지어내지 않고, 자격 판정·점수·근거를 보여 주며, 최종 결정은 사람이 내리고 기록한다.**

심사 기준: 사람 5인 + Claude Fable 5.1(AI 심사). 두 심사자가 모두 확인할 수 있도록 **모든 주장에 근거 위치**를 붙인다 (§5, [[00-README|00 인덱스]]의 주장·근거 표).

## 2. 문제

### 2.1 시장 배경

> [!success] 검증됨 (2026-10-16, 웹 검색 결과 기준)
> 조달청 「2025 공공조달통계연보」(2026년 6월 발간) 기준 2025년 공공조달 규모는 계약 기준 238.5조원, 명목 GDP의 8.9%다. 2024년은 225.1조원이었다. 출처: [조달청 조달사업통계 게시판](https://www.pps.go.kr/kor/bbs/list.do?key=00664), [2024년 규모 보도](https://m.boannews.com/html/detail.html?idx=137866). 발표 전 연보 원문에서 수치를 다시 확인한다.

> [!warning] 미검증 가정
> 연간 입찰공고 건수, SI 분야 공고 비중, 평균 제안 비용은 공식 통계를 찾지 못했다. 발표에서는 수치 없이 "매일 수백 건" 같은 표현을 쓰지 않고, 데모 기업 기준 체감 수치(§2.2)만 가설로 말한다.

### 2.2 현장의 고통 (데모 기업 가설)

| 단계 | 지금 하는 방식 | 문제 |
|---|---|---|
| 공고 발견 | 나라장터·알림 서비스에서 키워드 알림 수신 | 키워드 매칭이라 노이즈가 많고, 발주계획 → 사전규격 → 공고로 이어지는 흐름을 사람이 다시 이어 붙인다 |
| 자격 확인 | 담당자가 공고문·첨부(HWP/PDF)를 열어 참가자격·실적 요건을 눈으로 확인 | 필수 자격 하나를 놓치면 제안서 작업 전체가 무효. 확인 결과가 기록되지 않아 재검토가 반복된다 |
| 참여 판단 | 영업 책임자의 경험과 감 | 근거가 남지 않고, 인력·일정 충돌을 늦게 발견한다 |
| 변경 추적 | 정정공고를 사람이 다시 확인 | 마감·예산·자격 변경을 놓친다 |

> [!warning] 미검증 가정
> 위 표는 공공 SI 영업 프로세스에 대한 일반적 관찰이다. 데모 기업 인터뷰나 설문 결과가 있으면 수치와 함께 교체한다.

## 3. 해결과 차별점

### 3.1 핵심 흐름

실제 나라장터 공고 수집(정보화사업) → 변경 감지(revision) → 첨부 다운로드·파싱 → 요구조건 추출(Qwen3.8-Flash-Next, 근거 인용 필수) → 명시 조건 규칙 판정(API 구조화 필드 우선) → SOL Score(결정론적, 분해 가능) → 결정 모델(Bosun v3.1 0.6B) 참고 지표(점수 미반영) → 근거 설명 → 추천(`BID`)·보류(`WATCH`)·비추천(`NO_BID`) **권고** → 사람 최종 결정 기록 → 인앱 알림. 세 실행 모드(`live` 실제 공고 + 실추론, `fixture` 가상 공고 + 실추론, `mock` 가상 공고 + 고정 AI 응답)가 같은 흐름을 탄다([[16-DECISIONS|ADR-020]]). 상세는 [[02-ARCHITECTURE|02 아키텍처]], [[03-AI-PIPELINE|03 AI 파이프라인]], [[08-SCORING|08 SOL Score]], [[21-MODEL-TRAINING|21 모델 학습]].

### 3.2 차별점 다섯 가지

| # | 차별점 | 흔한 접근 | SOL RADAR | 근거 위치 |
|---|---|---|---|---|
| D1 | **우리 회사 기준 자격 판정** | 공고 수집·키워드 알림까지 | 회사 프로필(기술·자격·실적·인력)과 공고 요구조건을 대조해 `SATISFIED / NOT_SATISFIED / NEEDS_REVIEW` 판정, 항목마다 원문 인용. 부족한 자격을 "보유 가정"으로 켜면 저장하지 않고 권고·점수를 다시 계산해 무엇이 있으면 들어갈 수 있는지 보여 준다(가정 재계산, 결정 모델 재호출 없음, [[16-DECISIONS]] ADR-037). 공고 하나의 판정을 실공고 전체로 넓힌 자격 갭 레이더(`/gaps`)는 마감 전 실공고를 공고 API 구조화 필드(면허제한·참가가능지역)만으로 1차 선별해 "어떤 자격이 몇 건·얼마의 공고를 막는가"를 보이고, 자격 하나를 보유로 가정하면 새로 열리는 공고와 배정 예산 합을 저장 없이 다시 센다(첨부·AI 미사용, 예산 합은 수주 금액이 아님, [[16-DECISIONS]] ADR-060) | [[08-SCORING]], [[15-DATA-CONTRACTS]], [[06-UI-UX]] §5.13 |
| D2 | **설명 가능한 점수** | 블랙박스 "적합도 87%" | 5개 요소·가중치·입력 스냅샷·알고리즘 버전을 저장하는 결정론적 점수. 같은 입력이면 같은 점수 | [[08-SCORING]], [[04-DATABASE]] |
| D3 | **정직한 AI** | "낙찰 확률 73%" 같은 근거 없는 수치 | 수주확률을 표시하지 않는다. 결정 모델 분포는 "모델 선택지 신뢰 분포 (충족·수주 확률 아님)"로만, 점수에 넣지 않는 참고 지표로 표시. 근거 부족은 `INSUFFICIENT_DATA`/`NEEDS_REVIEW`이고 정보 부족을 미충족으로 판정하지 않는다. 실행 모드와 데이터 출처를 화면에 표시하고 mock으로 몰래 대체하지 않는다 | [[03-AI-PIPELINE]], [[06-UI-UX]], [[08-SCORING]] |
| D4 | **사람이 최종 결정, 기록이 남는다** | AI가 결정을 대신하거나 결정이 메신저에 흩어짐 | 권고와 결정을 분리. `bid_reviews`에 결정자·사유·시각 저장, 규칙과 모델이 충돌하면 `MODEL_RULE_DISAGREEMENT`로 사람 검토 강제 | [[08-SCORING]], [[09-SECURITY]] |
| D5 | **작은 결정 모델 + 규칙 엔진 조합** | 대형 LLM에 전부 맡김 | 추출은 Qwen3.8-Flash-Next(회사 vLLM API, 운영 실추론 1건은 §7), 설명은 현재 템플릿(Qwen 설명 생성 없음), 요구사항·기술 적합성·수행 리스크 분류는 Bosun v3.1 0.6B(Qwen3-0.6B 기반 소형 결정 모델, 텍스트 생성 없이 decision token 분포로 질문별 확률 반환, 우리 도메인 보정 전이며 보정 상태는 화면에 나오지 않는다(§7), [[16-DECISIONS]] ADR-034), 명시 조건과 최종 판정은 규칙. 모델이 꺼져도 규칙만으로 완결(`PARTIAL`). 모델이 쓸모 있는지는 실제 공고 평가셋에서 규칙만 쓴 경우(E0)와 비교해 잰다 | [[03-AI-PIPELINE]], [[11-TESTING]] G6, [[21-MODEL-TRAINING]] |

### 3.3 왜 지금인가

- 공공조달 규모가 매년 커지고(§2.1) 디지털 전환·AX 사업 공고가 늘어 SI 기업의 검토 부담이 커진다.
- 소형 오픈 가중치 결정 모델(Bosun, Apache-2.0)과 오픈 LLM(Qwen)으로 **회사 GPU 서버에서** 회사 기밀을 외부 모델 API에 보내지 않고 돌릴 수 있게 되었다. 운영 실추론은 회사 Compose의 AI gateway가 회사 vLLM(Qwen)과 결정 서버(Bosun)를 부른다([[16-DECISIONS|ADR-025]]·[[16-DECISIONS|ADR-049]]). DB는 Supabase 클라우드다(§7).
- 공공데이터포털의 나라장터 Open API(무료, 자동승인)로 공고를 수집할 수 있다. 서비스 ID·오퍼레이션·필드 이름은 공식 명세로 확인했고([[16-DECISIONS|16 ADR]] 미결정 1), 서비스키로 받은 실제 응답도 2026-10-19 P0-0에서 4개 서비스 모두 확인했다(설계와 다른 점 포함, `docs/evidence/phase-0/external-deps.md` ①, [[07-DATA-PIPELINE|07 수집]]). 첨부 원문(공고문·제안요청서)의 저작권·재배포 조건은 미확인이다.

## 5. AI 심사(Fable 5.1) 대비

AI 심사자는 저장소 전체를 읽고 **내부 일관성, 주장과 근거의 연결, 지어낸 사실, 테스트 증거, 보안**을 빠르게 검사한다. 대응:

1. **주장 → 근거 위치 표**를 [[00-README|00 인덱스]]에 둔다. 각 주장은 문서 절 또는 테스트 파일로 연결된다.
2. **검증 상태를 명시**한다. 외부 사실은 `> [!success] 검증됨 (날짜, URL)` 또는 `> [!warning] 미검증 가정` 콜아웃으로 구분한다. 미검증을 사실처럼 쓰지 않는다.
3. **실제 vs mock 표**(§7)를 세 실행 모드 기준으로 유지한다. 데모에서 mock인 부분을 숨기지 않는다.
4. **문서 간 용어·필드 이름 일치**. [[20-GLOSSARY|20 용어집]]과 [[15-DATA-CONTRACTS|15 데이터 계약]]을 단일 원천으로 쓴다.
5. **증거 산출물**을 `docs/evidence/`에 둔다: 테스트 리포트, E2E 스크린샷, `docker compose ps` 로그, 장애 대체 결과. 형식은 [[11-TESTING|11 테스트]], [[17-CLAUDE-IMPLEMENTATION|17 구현 규칙]].
6. **범위 정직성**: 결제·모바일·자동 투찰·승률 예측은 범위 외라고 문서와 발표에서 같은 말로 밝힌다 ([[16-DECISIONS|16 ADR]] ADR-007).

## 8. 예상 질문과 답

1. **"낙찰 확률은 안 보여 주나?"** 보여 주지 않는다. 낙찰 라벨과 시점 정합성이 검증된 데이터가 없는 상태에서 확률을 표시하는 것은 과장이다. 대신 자격 판정·적합도 점수·근거를 보여 준다. 승률 모델은 P2로, 백테스트 통과 후에만 노출한다 ([[01-PRD]] FR-12).
2. **"결정 모델(Bosun)이 무엇인가? 한국어는 되나?"** Hanno Labs가 공개한 Apache-2.0 소형 결정 모델 Bosun v3.1 0.6B(백본 Qwen3-0.6B, LoRA + decision token 256개). 2026-10-20 ADR-034로 Kev(퇴역)를 대체했다(`KEV_*` 이름은 호환 유지). 문서와 타입이 정해진 질문(yes/no·선택·점수)을 받아 텍스트 생성 없이 질문별 확률을 돌려준다. 학습 데이터(DecisionBench)가 영어라 운영에서는 규칙·Qwen이 정형화한 상태를 **영어 템플릿**으로 넣는다. 한국어가 되는지는 주장하지 않고 잰다: 같은 구조의 영어·한국어 state로 E1'(영어)과 E2(한국어)를 같은 평가셋에서 돌려 Macro-F1·Brier·ECE 차이와 95% 신뢰구간으로 보고한다([[21-MODEL-TRAINING]] §4). 리포트가 나오기 전에는 수치를 말하지 않는다. 한국어 state는 평가 전용(`KEV_ALLOW_KO_STATE=true`)이고, 운영 사용은 평가 결과를 보고 다시 정한다. 결정 모델 결과는 참고 지표이며 점수·자격·권고를 바꾸지 못한다. `mock` 모드에서는 고정 응답이고 `live`·`fixture` 모드에서 실추론한다 ([[03-AI-PIPELINE]] §5).
3. **"왜 Qwen과 Bosun을 둘 다 쓰나?"** 역할이 다르다. Qwen은 비정형 공고문에서 구조화된 요구조건과 근거 span을 뽑는 역할이다. 한국어 설명은 현재 템플릿이고 Qwen 설명 생성은 없다. Bosun은 정형화된 상태를 읽고 질문별 선택지 분포를 낸다. 도메인 품질·지연은 아직 측정 전이다. 둘 다 없어도 규칙 엔진만으로 결과가 나온다.
4. **"실제 데이터인가?"** `live` 모드는 나라장터 Open API로 실제 입찰공고(용역 중 정보화사업)를 3시간마다 수집한다. 나라장터 목록에는 본문이 없어(`web/server/ingestion/normalize-g2b.ts:146`) 실공고 분석은 첨부(공고서·제안요청서) 파싱 텍스트와 API 구조화 필드로 한다. 첨부 처리가 회사에 반영되기 전인 지금 운영 실공고 분석은 0건이다(본문·첨부 텍스트가 없으면 분석을 막는다). 공고마다 출처와 `DEMO` 배지로 실제·가상을 구분하고, 분석마다 실행 모드와 모델이 분석 요약 띠에 남는다. 운영 회사 프로필은 공개 자료로 만든 솔리데오 프로필이라 운영 live 분석은 "실제 공고 × 공개 자료 회사 프로필"이다([[16-DECISIONS]] ADR-052). 로컬은 가상 프로필이다. 본편 장면은 운영 사이트의 가상 fixture(`?origin=demo`)로 찍는다(D1, [[16-DECISIONS]] ADR-054, [[19-DEMO-SCENARIO]] §2.1). 실제 응답·첨부 다운로드 확인 결과는 `docs/evidence/phase-0/external-deps.md`에 있다. 엔드포인트는 공식 명세로 확인해 `registry.yaml`에 등록한 것만 부르고 지어내지 않는다.
5. **"HWP 첨부는 어떻게 하나?"** 형식별 파서(`DocumentParser`)로 PDF(텍스트 레이어)·HWPX·HWP를 읽는다(pdfplumber·sol-hwpx·sol-hwp5, `services/ai/src/sol_ai/parsers/`). 코드는 main에 있고 회사 반영 전이라 운영에서는 아직 파싱하지 않는다. 반영과 실공고 증거가 나오기 전에는 파싱했다고 말하지 않는다. 스캔 PDF·zip·암호 문서처럼 처리할 수 없는 첨부는 `PARSE_UNSUPPORTED`와 "첨부 원문 확인"으로 표시하고, 읽지 못한 내용을 AI가 추측해 채우지 않는다. xlsx·zip·docx는 내려받지 않고 `PENDING`으로 둔다([[16-DECISIONS]] ADR-055 제안). 파서 "지원" 판정 규칙과 실공고 형식별 파싱 성공률(P0-3)은 아직 없다([[03-AI-PIPELINE]] §10.3).
6. **"GPU 없으면 못 쓰나?"** `mock` 모드는 GPU 없이 고정 AI 응답으로 전 기능이 돈다. `live`·`fixture` 모드의 실추론은 회사 GPU 서버(Qwen3.8-Flash-Next는 회사가 이미 운영하는 vLLM API `https://acropolissg.com/vllm/v1`, Bosun은 우리 `sol_decision` 서버)에서 돈다. 운영에서는 회사 Compose의 AI gateway가 API 키로 붙는다([[16-DECISIONS|ADR-049]]). Qwen은 회사 vLLM API `https://acropolissg.com/vllm/v1`, 결정 모델은 같은 호스트의 `sol_decision`(`http://127.0.0.1:8009`)이다. 로컬 대체 경로의 노트북 gateway(`ai-local`)는 Qwen API에는 붙는다. 결정 모델용 공개 경로(`https://acropolissg.com/sol-radar/kev`)는 회사 nginx에 등록되지 않아(2026-10-27) 노트북에서는 결정 모델에 닿지 않는다. GPU 서버 자체는 외부에서 접근할 수 없고 모델 런타임 기동·GPU 배분은 회사가 운영한다 ([[10-DEPLOYMENT]], [[16-DECISIONS|ADR-025]]).
7. **"기존 입찰 정보 서비스와 뭐가 다른가?"** 수집·알림은 기존 서비스도 한다. 우리는 **우리 회사 프로필 기준 자격 판정과 설명 가능한 점수, 사람 결정 기록**까지 간다 (§3.2 D1·D2·D4).
8. **"AI가 틀리면?"** 근거 없는 인용은 무효 처리하고, 저신뢰·모순은 `NEEDS_REVIEW`로 사람에게 넘긴다. 사람 판정과 AI 차이를 지표로 추적한다 ([[14-OBSERVABILITY]]). 얼마나 틀리는지는 실제 공고 평가셋으로 잰다. 특히 정보 부족을 미충족으로 잘못 판정하는 비율을 따로 보고, 오답은 원인 단계(파싱·추출·번역·state·규칙·라벨·모델)로 나눠 고친다 ([[21-MODEL-TRAINING]]).
9. **"보안은?"** 테넌트 격리는 Supabase RLS(`org_id`, 다른 조직 자원은 `404`)와 정책 시험으로 강제한다. 인증은 Supabase Auth이고, 토큰 만료·refresh 회전·로그인 시도 제한·비밀번호 정책은 Supabase Auth 설정으로 다룬다(구체 값은 대시보드에서 정하고 확인할 항목, 미검증). 쿠키 인증의 상태 변경 요청은 `X-Requested-With` 헤더 검사(CSRF), XSS는 CSP nonce, RLS를 무시하는 service role 키는 worker·seed·사람이 로컬에서 직접 실행하는 운영자 CLI만 사용하고 브라우저·`NEXT_PUBLIC_` 변수·로그에 넣지 않는다. 그 밖에 SSRF allowlist, 외부 문서는 불신 데이터로 처리, 로그 마스킹 ([[09-SECURITY]]).
10. **"왜 Supabase인가?"** 출발 템플릿(agentic-boilerplate)이 이미 Next.js + Supabase로 조직·역할·초대·RLS·인증 견본과 정책 시험(PGlite)·타입 생성(`pnpm db:types`) 게이트를 갖추고 있다. 그대로 쓰면 인증과 조직 격리를 새로 만들지 않고, 해커톤 시간을 자격 판정·점수·근거에 쓴다. Supabase가 맡는 것은 DB·인증·private Storage(첨부 원본·파싱 결과, ADR-048)이고 임베딩 검색(Qdrant)·작업 큐(Redis + BullMQ)·AI gateway(Qwen·Bosun)는 따로다 ([[16-DECISIONS]] ADR-017).
11. **"데모 중 네트워크가 끊기면?"** 본편은 덱과 녹화 클립이라 회선과 무관하다. 질의응답의 라이브(D1)는 운영 DB와 인증이 Supabase 클라우드라 인터넷이 끊기면 로그인과 조회가 멈춘다. 오프라인 시연은 약속하지 않는다. 끊기면 로컬 Supabase CLI(`pnpm db:start` → `pnpm demo:reset` → 모드 확인(mock) → `pnpm demo:preanalyze` → web 재시작)로 전환하고 전환했다고 말한다. 로컬 DB에는 S-LIVE run이 없으므로 그 장면은 녹화로 보여 준다([[19-DEMO-SCENARIO]] §5 대체 경로 ①, [[16-DECISIONS]] ADR-023). AI 장애는 별개로, AI gateway를 꺼도 규칙만으로 `PARTIAL` 결과가 나오는 것을 시연한다(§6 4:15). `live`·`fixture` 모드는 회사 GPU 추론 엔드포인트(HTTPS) 접속도 필요하다. 엔드포인트에 닿지 않으면 규칙만으로 `PARTIAL`·`RULES_ONLY` 결과가 나오고 이를 숨기지 않으며, 필요하면 `mock` 모드로 바꿔 이어 간다.
12. **"해커톤 이후 계획은?"** 평가셋 확대(test 40 사업 이상) → 해커톤 E4 결과와 오류 분석으로 Bosun LoRA 운영 반영 판단 → 결정 모델의 점수 반영은 평가 기준 통과 뒤 새 알고리즘 버전(`sol-v0.2.x`)과 ADR로 → 데모 기업 파일럿 → 경쟁사 통계·인력 배치 저장/배정 확정 순서(조회 전용 인력 배치 시뮬레이션은 이번 해커톤 P1, ADR-042) ([[12-ROADMAP]], [[21-MODEL-TRAINING]]).
13. **"파인튜닝했나?"** 회사 GPU 학습(X6) 실행 여부는 **사용자 미결정**이고 회사 서버에서 돈 기록은 없다([[16-DECISIONS]] ADR-054). 그 상태로 발표하면 "학습셋과 절차는 준비했고, 학습 결과는 아직 없다"고 답한다. 아래는 학습을 실행해 결과가 나왔을 때의 답안이다. Bosun v3.1 0.6B의 공개 LoRA를 이어 학습해 E4로 공개 Bosun(E1')과 같은 test 분할에서 비교했다([[16-DECISIONS]] ADR-034). 학습·보정은 회사가 회사 GPU에서 돌렸고, 우리는 평가셋·학습셋·학습 요청서·평가를 맡았다. 결과는 Δ와 95% 신뢰구간으로만 말하고, 구간이 0을 포함하면 "차이 없음"이라고 한다. 데모는 공개 Bosun을 쓴다. 운영 모델 교체는 오류 분석과 ADR을 거친 뒤다. Qwen 파인튜닝은 하지 않았다(2026-10-20 사용자 결정). 회사 측 학습이 마감 안에 끝나지 않았으면 "학습셋과 절차를 넘겼고 결과는 아직 없다"고 답한다 ([[21-MODEL-TRAINING]] §4.4·§5, [[22-FINETUNE-RUNBOOK]]).
14. **"예산 합계는 수주 금액인가?"** 아니다. 자격 갭 레이더의 예산 합계는 공고 API 기준으로 참가 자격이 열리는 공고의 배정 예산(`budget_krw`) 합이다. 입찰은 가격·평가·경쟁을 거치므로 이 합은 수주 금액이나 확률과 관계없다. 화면에 "예산 합계는 참가 자격이 열리는 공고의 배정 예산 합이며 수주 금액이나 확률이 아닙니다."가 늘 보인다. 낙찰·계약 데이터는 수집하지 않는다([[01-PRD]] FR-10, [[16-DECISIONS]] ADR-060).
15. **"면허제한이 없는 공고는 누구나 들어가나?"** 그렇게 단정하지 않는다. 보조 조회(면허제한·참가가능지역)를 다 받았고(`auxLookup.status=OK`) 행이 없을 때만 "참가 가능(API 기준)"으로 센다. 이것은 공고 API 구조화 필드 기준이다. 첨부(제안요청서)에만 적힌 자격 요건은 반영하지 않았고, 화면 맨 위에 그렇게 적혀 있다. 보조 조회가 실패했거나 일일 한도로 건너뛰었거나 결과가 없으면 행이 없어도 "제한 없음"이 아니라 "사람 확인 필요"다(정보 부족 ≠ 미충족·충족). 한도로 건너뛴 비율은 운영 읽기 확인([기록](evidence/gaps/20261028/prod-readonly-check.md))에 있다. "기타자유업종/9999"처럼 뜻을 확인하지 못한 업종 코드는 사전 밖으로 두고 사람 확인 필요로 센다([[16-DECISIONS]] ADR-060 남은 확인).
16. **"면허제한이 여러 행이면 AND인가 OR인가?"** 확인하지 못했다([[16-DECISIONS]] 미결정 19). 공식 근거가 없어 해석을 규칙 엔진에 넣지 않았다. 2행 이상인 공고는 모두 "사람 확인 필요"(면허제한 여러 행, AND/OR 미확인)로 센다. 2026-10-28 운영 실측에서 면허제한이 있는 공고 410건 중 209건(2행 154·3행 이상 55)이 여기에 든다. 그래서 "참가 가능" 수는 적게 잡히고, 이런 공고는 보유 가정으로도 열리지 않는다. 막는 자격 표의 "조건 묶음 포함"이 그 규모다. 같은 이유로 ADR-037에서 대시보드 실공고 선별 깔때기(BOOST-1)를 뺐다.
17. **"실공고 AI 분석이 0건인데 이 숫자는 무엇으로 냈나?"** 첨부·AI 없이 공고 API 구조화 필드와 기존 규칙 엔진으로 냈다. 공고 상세 분석의 구조화 필드 판정과 같은 함수다(`assessStructuredQualifications`). 점수·권고는 내지 않는다.

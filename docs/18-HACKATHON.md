# 18. 해커톤 출품 전략

> [!todo] 해커톤 공식 정보 입력
> 해커톤 이름, 주최, 제출 마감일, 발표 시간, 공식 심사 기준과 배점을 확인하는 즉시 이 문서 §4와 [[12-ROADMAP|12 로드맵]]의 해커톤 컷을 갱신한다. 확인 전까지 §4는 일반적인 해커톤 기준으로 작성한 가설이다.

## 1. 한 줄 요약

> **SOL RADAR는 공공 SI·AX 기업의 영업팀이 "이 입찰에 들어가야 하는가"를 근거와 함께 10분 안에 판단하도록 돕는 의사결정 지원 플랫폼이다. 낙찰 확률을 지어내지 않고, 자격 판정·점수·근거를 보여 주며, 최종 결정은 사람이 내리고 기록한다.**

심사 기준: 사람 5인 + Claude Fable 5.1(AI 심사). 두 심사자가 모두 확인할 수 있도록 **모든 주장에 근거 위치**를 붙인다 (§5, [[00-README|00 인덱스]]의 주장·근거 표).

## 2. 문제

### 2.1 시장 배경

> [!success] 검증됨 (2026-10-16, 웹 검색 결과 기준)
> 조달청 「2025 공공조달통계연보」(2026년 6월 발간) 기준 2025년 공공조달 규모는 계약 기준 238.5조원, 명목 GDP의 8.9%다. 2024년은 225.1조원이었다. 출처: [조달청 조달사업통계 게시판](https://www.pps.go.kr/kor/bbs/list.do?key=00664), [2024년 규모 보도](https://m.boannews.com/html/detail.html?idx=137866). 발표 전 연보 원문에서 수치를 다시 확인한다.

> [!warning] 미검증 가정
> 연간 입찰공고 건수, SI 분야 공고 비중, 평균 제안 비용은 공식 통계를 찾지 못했다. 발표에서는 수치 없이 "매일 수백 건" 같은 표현을 쓰지 않고, 데모 기업 기준 체감 수치(§2.2)만 가설로 말한다.

### 2.2 현장의 고통 (데모 기업 가설)

| 단계 | 지금 하는 방식 | 문제 |
|---|---|---|
| 공고 발견 | 나라장터·알림 서비스에서 키워드 알림 수신 | 키워드 매칭이라 노이즈가 많고, 발주계획 → 사전규격 → 공고로 이어지는 흐름을 사람이 다시 이어 붙인다 |
| 자격 확인 | 담당자가 공고문·첨부(HWP/PDF)를 열어 참가자격·실적 요건을 눈으로 확인 | 필수 자격 하나를 놓치면 제안서 작업 전체가 무효. 확인 결과가 기록되지 않아 재검토가 반복된다 |
| 참여 판단 | 영업 책임자의 경험과 감 | 근거가 남지 않고, 인력·일정 충돌을 늦게 발견한다 |
| 변경 추적 | 정정공고를 사람이 다시 확인 | 마감·예산·자격 변경을 놓친다 |

> [!warning] 미검증 가정
> 위 표는 공공 SI 영업 프로세스에 대한 일반적 관찰이다. 데모 기업 인터뷰나 설문 결과가 있으면 수치와 함께 교체한다.

## 3. 해결과 차별점

### 3.1 핵심 흐름

실제 나라장터 공고 수집(정보화사업) → 변경 감지(revision) → 첨부 다운로드·파싱 → 요구조건 추출(Qwen3.5-9B, 근거 인용 필수) → 명시 조건 규칙 판정(API 구조화 필드 우선) → SOL Score(결정론적, 분해 가능) → Kev-9B 참고 지표(점수 미반영) → 근거 설명 → BID / WATCH / NO-BID **권고** → 사람 최종 결정 기록 → 인앱 알림. 세 실행 모드(`live` 실제 공고 + 실추론, `fixture` 가상 공고 + 실추론, `mock` 가상 공고 + 고정 AI 응답)가 같은 흐름을 탄다([[16-DECISIONS|ADR-020]]). 상세는 [[02-ARCHITECTURE|02 아키텍처]], [[03-AI-PIPELINE|03 AI 파이프라인]], [[08-SCORING|08 SOL Score]], [[21-MODEL-TRAINING|21 모델 학습]].

### 3.2 차별점 다섯 가지

| # | 차별점 | 흔한 접근 | SOL RADAR | 근거 위치 |
|---|---|---|---|---|
| D1 | **우리 회사 기준 자격 판정** | 공고 수집·키워드 알림까지 | 회사 프로필(기술·자격·실적·인력)과 공고 요구조건을 대조해 `SATISFIED / NOT_SATISFIED / NEEDS_REVIEW` 판정, 항목마다 원문 인용 | [[08-SCORING]], [[15-DATA-CONTRACTS]] |
| D2 | **설명 가능한 점수** | 블랙박스 "적합도 87%" | 5개 요소·가중치·입력 스냅샷·알고리즘 버전을 저장하는 결정론적 점수. 같은 입력이면 같은 점수 | [[08-SCORING]], [[04-DATABASE]] |
| D3 | **정직한 AI** | "낙찰 확률 73%" 같은 근거 없는 수치 | 수주확률을 표시하지 않는다. Kev 분포는 "모델 선택지 신뢰 분포 (충족·수주 확률 아님)"로만, 점수에 넣지 않는 참고 지표로 표시. 근거 부족은 `INSUFFICIENT_DATA`/`NEEDS_REVIEW`이고 정보 부족을 미충족으로 판정하지 않는다. 실행 모드와 데이터 출처를 화면에 표시하고 mock으로 몰래 대체하지 않는다 | [[03-AI-PIPELINE]], [[06-UI-UX]], [[08-SCORING]] |
| D4 | **사람이 최종 결정, 기록이 남는다** | AI가 결정을 대신하거나 결정이 메신저에 흩어짐 | 권고와 결정을 분리. `bid_reviews`에 결정자·사유·시각 저장, 규칙과 모델이 충돌하면 `MODEL_RULE_DISAGREEMENT`로 사람 검토 강제 | [[08-SCORING]], [[09-SECURITY]] |
| D5 | **작은 결정 모델 + 규칙 엔진 조합** | 대형 LLM에 전부 맡김 | 추출·설명은 Qwen3.5-9B, 요구사항·기술 적합성·수행 리스크 분류는 Kev-9B(Qwen3.5 기반 소형 결정 모델, 텍스트 생성 없이 질문별 확률 반환, 우리 도메인 보정 전에는 `UNCALIBRATED` 표시), 명시 조건과 최종 판정은 규칙. 모델이 꺼져도 규칙만으로 완결(`PARTIAL`). 모델이 쓸모 있는지는 실제 공고 평가셋에서 규칙만 쓴 경우(E0)와 비교해 잰다 | [[03-AI-PIPELINE]], [[11-TESTING]] G6, [[21-MODEL-TRAINING]] |

### 3.3 왜 지금인가

- 공공조달 규모가 매년 커지고(§2.1) 디지털 전환·AX 사업 공고가 늘어 SI 기업의 검토 부담이 커진다.
- 소형 오픈 가중치 결정 모델(Kev, Apache-2.0)과 오픈 LLM(Qwen)으로 **회사 GPU 서버에서** 회사 기밀을 외부 모델 API에 보내지 않고 돌릴 수 있게 되었다. 해커톤 실추론은 데모 노트북의 gateway가 터널로 회사 GPU 서버에 붙는다(모델 추론 기준. 개발 DB는 Supabase 클라우드다, §7).
- 공공데이터포털의 나라장터 Open API(무료, 자동승인)로 공고를 수집할 수 있다. 서비스 ID·오퍼레이션·필드 이름은 공식 명세로 확인했고([[16-DECISIONS|16 ADR]] 미결정 1), 서비스키로 받은 실제 응답은 P0-0에서 확인한다([[07-DATA-PIPELINE|07 수집]]). 첨부 원문(공고문·제안요청서)의 저작권·재배포 조건은 미확인이다.

## 5. AI 심사(Fable 5.1) 대비

AI 심사자는 저장소 전체를 읽고 **내부 일관성, 주장과 근거의 연결, 지어낸 사실, 테스트 증거, 보안**을 빠르게 검사한다. 대응:

1. **주장 → 근거 위치 표**를 [[00-README|00 인덱스]]에 둔다. 각 주장은 문서 절 또는 테스트 파일로 연결된다.
2. **검증 상태를 명시**한다. 외부 사실은 `> [!success] 검증됨 (날짜, URL)` 또는 `> [!warning] 미검증 가정` 콜아웃으로 구분한다. 미검증을 사실처럼 쓰지 않는다.
3. **실제 vs mock 표**(§7)를 세 실행 모드 기준으로 유지한다. 데모에서 mock인 부분을 숨기지 않는다.
4. **문서 간 용어·필드 이름 일치**. [[20-GLOSSARY|20 용어집]]과 [[15-DATA-CONTRACTS|15 데이터 계약]]을 단일 원천으로 쓴다.
5. **증거 산출물**을 `docs/evidence/`에 둔다: 테스트 리포트, E2E 스크린샷, `docker compose ps` 로그, 장애 대체 결과. 형식은 [[11-TESTING|11 테스트]], [[17-CLAUDE-IMPLEMENTATION|17 구현 규칙]].
6. **범위 정직성**: 결제·모바일·자동 투찰·승률 예측은 범위 외라고 문서와 발표에서 같은 말로 밝힌다 ([[16-DECISIONS|16 ADR]] ADR-007).

## 6. 5분 데모 스크립트

상세 클릭 경로와 fixture는 [[19-DEMO-SCENARIO|19 데모 시나리오]]에 있다. 발표자는 §6 시간표를, 조작자는 19의 단계를 따른다.

| 시각 | 장면 | 말할 것 | 보여 줄 것 |
|---|---|---|---|
| 0:00 | 문제 | "영업팀은 매일 공고를 눈으로 거르고, 자격 하나를 놓치면 제안서 작업이 무효가 된다" | 슬라이드 1장 |
| 0:30 | 대시보드 | "수집 최신화 시각, 검토 대기, 마감 임박. 지금 실행 모드는 mock이고, 데이터는 DEMO 배지가 붙은 가상 공고, 회사는 가상 솔리데오 프로필이다" | `/dashboard`, 머리말 "실행 모드: mock", `DEMO` 배지, 신선도 표시 |
| 1:00 | 공고 탐색·자격 근거 | "단계·점수로 거른다. 필수 자격마다 원문 인용이 붙고, 대조에 실패한 인용은 무효다" | `/bids` 필터 → FX-01(BID 94) 상세 → 자격 3건 `SATISFIED` → 근거 서랍 |
| 1:30 | 규칙 우선 | "모델이 BID라고 해도 필수 자격 미충족은 규칙이 이긴다. Kev 분포는 수주확률이 아니다" | FX-03(NO-BID) 상세 → `NOT_SATISFIED` → Kev BID 0.55 → `MODEL_RULE_DISAGREEMENT` 배지 |
| 2:15 | 라이브 분석·점수 | "점수는 5개 요소로 분해되고 버전이 남는다. 50~75 구간은 사람 검토" | FX-02 분석 요청 → `QUEUED → COMPLETED` → 72점 분해, Kev WATCH 0.52 |
| 3:00 | 사람 결정 | "권고는 WATCH, 결정은 사람이 사유와 함께 기록한다" | 결정 패널 → `bid_reviews` 기록 → `REVIEW_ASSIGNED` 알림 1건 |
| 3:30 | 변경 감지 | "정정공고가 들어오면 revision이 쌓이고 알림은 한 번만 간다. 중복 전송은 0건" | 관리자 수동 수집(live) → FX-07 revision diff(예산·기술) → WATCH→BID, FX-09 중복 0건 |
| 4:15 | 장애 대체 | "AI를 끄면 규칙만으로 PARTIAL 결과를 내고 상태를 숨기지 않는다" | `docker compose stop ai-gateway` → `AI: unavailable` → FX-01 재분석 → `PARTIAL` 배너, 이전 run 보존 |
| 4:45 | 격리와 마무리 | "다른 조직 토큰으로는 404. 결제·모바일·자동 투찰은 범위 밖" | API 호출 404 응답(RLS가 다른 조직 행을 숨김) → 마무리 슬라이드 |

시간이 밀리면 3:30 변경 감지 장면을 건너뛰고 4:15 장애 대체로 간다. 장애 대체와 격리는 D3·D4의 증거라 생략하지 않는다.

- 기본 시연 모드는 `mock`이고 위 수치(94·72·68, Kev 분포)는 mock 기준이다([[19-DEMO-SCENARIO|19 데모 시나리오]] §2.1). 2:15 라이브 분석을 `live` 모드의 실제 공고로 바꾸는 선택안은 19 §4에 있고, 구현 때 정한다.
- `live`·`fixture` 장면을 쓰다가 장애가 나면 `live` → `fixture` → `mock` 순서로 바꾸고(env 변경 + worker·ai-gateway 재시작) 바꿨다고 말한다. 자동으로 바뀌지 않는다.
- 회사 GPU 서버 터널이 끊기면 `PARTIAL`·`RULES_ONLY` 화면을 그대로 보여 주고 4:15 장애 대체 설명으로 잇는다.

## 7. 정직성 표: 데모에서 실제인 것과 mock인 것

실행 모드는 세 가지다([[16-DECISIONS|ADR-020]]): `live`(실제 나라장터 공고 + 실추론), `fixture`(가상 공고 20건 + 실추론), `mock`(가상 공고 20건 + 고정 AI 응답). 화면 머리말에 지금 모드가, 분석마다 그때의 모드가 보인다. 발표 본편의 기본 모드는 `mock`이다([[19-DEMO-SCENARIO|19 데모 시나리오]] §2.1).

## 8. 예상 질문과 답

1. **"낙찰 확률은 안 보여 주나?"** 보여 주지 않는다. 낙찰 라벨과 시점 정합성이 검증된 데이터가 없는 상태에서 확률을 표시하는 것은 과장이다. 대신 자격 판정·적합도 점수·근거를 보여 준다. 승률 모델은 P2로, 백테스트 통과 후에만 노출한다 ([[01-PRD]] FR-12).
2. **"Kev가 무엇인가? 한국어는 되나?"** Jared Palmer가 공개한 Apache-2.0 소형 결정 모델. Qwen3.5 기반(0.8B/4B/9B, 27B는 Qwen3.8). 우리는 Kev-9B@v1.0을 쓴다. 문서와 타입이 정해진 질문(yes/no·선택·점수)을 받아 텍스트 생성 없이 질문별 확률을 돌려준다. 모델 카드는 영어 전용이라고 명시하므로 운영에서는 규칙·Qwen이 정형화한 상태를 **영어 템플릿**으로 넣는다. 한국어가 되는지는 주장하지 않고 잰다: 같은 구조의 영어·한국어 state로 E1(영어)과 E2(한국어)를 같은 평가셋에서 돌려 Macro-F1·Brier·ECE 차이와 95% 신뢰구간으로 보고한다([[21-MODEL-TRAINING]] §4). 리포트가 나오기 전에는 수치를 말하지 않는다. 한국어 state는 평가 전용(`KEV_ALLOW_KO_STATE=true`)이고, 운영 사용은 평가 결과를 보고 다시 정한다. Kev 결과는 참고 지표이며 점수·자격·권고를 바꾸지 못한다. `mock` 모드에서는 고정 응답이고 `live`·`fixture` 모드에서 실추론한다 ([[03-AI-PIPELINE]] §5).
3. **"왜 Qwen과 Kev를 둘 다 쓰나?"** 역할이 다르다. Qwen은 비정형 공고문에서 구조화된 요구조건과 근거 span을 뽑고 한국어 설명을 만든다. Kev는 정형화된 상태를 읽고 빠르고 일관된 보조 판단을 준다. 둘 다 없어도 규칙 엔진만으로 결과가 나온다.
4. **"실제 데이터인가?"** `live` 모드는 나라장터 Open API로 실제 입찰공고(용역 중 정보화사업)와 첨부를 수집해 분석한다. 화면 머리말에 실행 모드가 보이고, 공고마다 출처와 `DEMO` 배지로 실제·가상을 구분한다. 회사 프로필은 모든 모드에서 가상 솔리데오라 live 분석은 "실제 공고 × 가상 회사 프로필"이다. 발표 본편 장면은 같은 수치를 재현하려고 `mock` 모드의 가상 fixture로 진행한다(§7, [[19-DEMO-SCENARIO]] §2.1). 실제 응답·첨부 다운로드 확인 결과는 `docs/evidence/phase-0/external-deps.md`에 있다. 그 파일이 없거나 막힌 항목이 있으면 그대로 말한다. 엔드포인트는 공식 명세로 확인해 `registry.yaml`에 등록한 것만 부르고 지어내지 않는다.
5. **"HWP 첨부는 어떻게 하나?"** 형식별 파서(`DocumentParser`)로 PDF(텍스트 레이어)·HWPX·HWP를 파싱한다. HWP 파서는 오픈소스 후보의 라이선스와 추출 품질(본문·표·금액·자격 조건·요구사항 누락)을 실제 RFP 샘플로 비교한 뒤 정한다([[16-DECISIONS]] 미결정 4). 스캔 PDF·zip·암호 문서처럼 처리할 수 없는 첨부는 `PARSE_UNSUPPORTED`와 "첨부 원문 확인"으로 표시하고, 읽지 못한 내용을 AI가 추측해 채우지 않는다. 원문 다운로드는 유지하고 AI 추출은 `PENDING_REVIEW`로 표시한다. 실공고 형식별 파싱 성공률을 증거로 낸다(P0-3).
6. **"GPU 없으면 못 쓰나?"** `mock` 모드는 GPU 없이 고정 AI 응답으로 전 기능이 돈다. `live`·`fixture` 모드의 실추론은 회사 GPU 서버(`ai-local`: Qwen3.5-9B는 vLLM, Kev-9B는 `kev.serve`)에서 돌고, 데모 노트북의 gateway가 터널로 붙는다. 모델 런타임은 GPU 서버의 `127.0.0.1`에만 바인딩해 외부 포트를 열지 않는다 ([[10-DEPLOYMENT]]).
7. **"기존 입찰 정보 서비스와 뭐가 다른가?"** 수집·알림은 기존 서비스도 한다. 우리는 **우리 회사 프로필 기준 자격 판정과 설명 가능한 점수, 사람 결정 기록**까지 간다 (§3.2 D1·D2·D4).
8. **"AI가 틀리면?"** 근거 없는 인용은 무효 처리하고, 저신뢰·모순은 `NEEDS_REVIEW`로 사람에게 넘긴다. 사람 판정과 AI 차이를 지표로 추적한다 ([[14-OBSERVABILITY]]). 얼마나 틀리는지는 실제 공고 평가셋으로 잰다. 특히 정보 부족을 미충족으로 잘못 판정하는 비율을 따로 보고, 오답은 원인 단계(파싱·추출·번역·state·규칙·라벨·모델)로 나눠 고친다 ([[21-MODEL-TRAINING]]).
9. **"보안은?"** 테넌트 격리는 Supabase RLS(`org_id`, 다른 조직 자원은 `404`)와 정책 시험으로 강제한다. 인증은 Supabase Auth이고, 토큰 만료·refresh 회전·로그인 시도 제한·비밀번호 정책은 Supabase Auth 설정으로 다룬다(구체 값은 대시보드에서 정하고 확인할 항목, 미검증). 쿠키 인증의 상태 변경 요청은 `X-Requested-With` 헤더 검사(CSRF), XSS는 CSP nonce, RLS를 무시하는 service role 키는 worker·seed 전용이고 브라우저·`NEXT_PUBLIC_` 변수·로그에 넣지 않는다. 그 밖에 SSRF allowlist, 외부 문서는 불신 데이터로 처리, 로그 마스킹 ([[09-SECURITY]]).
10. **"왜 Supabase인가?"** 출발 템플릿(agentic-boilerplate)이 이미 Next.js + Supabase로 조직·역할·초대·RLS·인증 견본과 정책 시험(PGlite)·타입 생성(`pnpm db:types`) 게이트를 갖추고 있다. 그대로 쓰면 인증과 조직 격리를 새로 만들지 않고, 해커톤 시간을 자격 판정·점수·근거에 쓴다. Supabase가 맡는 것은 DB와 인증뿐이고 첨부 원본(MinIO), 임베딩 검색(Qdrant), 작업 큐(Redis + BullMQ), AI gateway(Qwen·Kev)는 그대로다 ([[16-DECISIONS]] ADR-017).
11. **"데모 중 네트워크가 끊기면?"** 개발 DB와 인증이 Supabase 클라우드라 인터넷이 끊기면 로그인과 조회가 멈춘다. 오프라인 시연은 약속하지 않는다. 대체 경로(로컬 Supabase CLI `pnpm db:start`로 전환, 사전 녹화 영상)는 아직 정하지 않았다([[16-DECISIONS]] 미결정 표). AI 장애는 별개로, AI gateway를 꺼도 규칙만으로 `PARTIAL` 결과가 나오는 것을 시연한다(§6 4:15). `live`·`fixture` 모드는 회사 GPU 서버 터널도 필요하다. 터널이 끊기면 규칙만으로 `PARTIAL`·`RULES_ONLY` 결과가 나오고 이를 숨기지 않으며, 필요하면 `mock` 모드로 바꿔 이어 간다.
12. **"해커톤 이후 계획은?"** 평가셋 확대(test 40 사업 이상) → 오류 분석에서 모델 판단 오류가 주된 원인이면 회사 GPU에서 Kev-9B LoRA → Kev의 점수 반영은 평가 기준 통과 뒤 새 알고리즘 버전(`sol-v0.2.x`)과 ADR로 → 데모 기업 파일럿 → P1(경쟁사 통계·인력 배치) 순서 ([[12-ROADMAP]], [[21-MODEL-TRAINING]]).
13. **"파인튜닝했나?"** 하지 않았다. 해커톤 범위는 Kev-9B 베이스라인 추론, 한국어/영어 비교, 평가셋·평가 하네스, 회사 GPU용 학습셋 내보내기까지다. 초기 목표(Macro-F1 0.80, 정보부족→미충족 혼동률 5%, 보정 후 ECE 0.08)에 못 미쳐도 그것만으로 학습을 시작하지 않는다. 오류 분석에서 모델 자체의 판단 오류가 주된 원인일 때 사람이 정한다 ([[21-MODEL-TRAINING]] §4.4).

| 회장 네트워크 불안 | `mock` 모드의 AI는 외부 호출이 없다. `live`·`fixture` 모드는 회사 GPU 서버 터널이 필요하다(아래 행). DB·Auth는 Supabase 클라우드라 인터넷이 필요하다. 발표 전 회선과 Supabase 프로젝트 접속(`/health/ready`의 `checks.db`)을 확인한다. 끊겼을 때 대체 경로(로컬 Supabase CLI `pnpm db:start`, 사전 녹화 영상)는 미결정 ([[16-DECISIONS]] 미결정 표) | 조작자 |
| 분석 지연 | 데모 공고 3건은 분석 결과를 미리 생성해 둔다. 라이브 분석은 1건만. 실추론(`live`·`fixture`) 지연은 실측 전이라 mock보다 길 수 있다고 보고 리허설에서 잰다 | 조작자 |
| 회사 GPU 서버 터널 단절 | `live`·`fixture` 실추론이 멈춘다. gateway가 `QWEN_UNAVAILABLE`·`KEV_UNAVAILABLE`을 기록하고 `PARTIAL`·`RULES_ONLY` 결과를 내므로 그 화면을 그대로 보여 준다. 재연결을 한 번 시도하고, 안 되면 `mock` 모드로 전환(env 변경 + worker·ai-gateway 재시작)하고 바꿨다고 말한다. D-1에 재연결을 리허설한다([[12-ROADMAP]]) | 조작자 |
| 공공 API 일일 한도·장애 | 개발계정은 서비스당 1,000건/일이다. 한도의 90%에서 보조 조회를 멈추고, 에러코드 22를 받으면 그날 수집을 멈춘다. 리허설·시연 호출 수를 미리 계산하고, 막히면 `fixture` 모드로 전환한다 | 조작자 |
| 첨부 다운로드 불가 | g2b 첨부 자동 다운로드 가능 여부는 미검증(P0-0). 안 되면 공고 본문·API 필드만으로 분석하고 `DOCUMENT_DOWNLOAD_FAILED`와 관련 자격 `확인 필요`를 그대로 보여 준다 | 조작자 |
| 모드 표시 혼동 | 모드를 바꿀 때마다 머리말 "실행 모드"와 분석 패널의 AI 표시를 확인한다. mock 결과를 실모델 결과처럼 말하지 않는다 | 발표자 |
| DB 상태 오염 | `pnpm demo:reset`으로 seed 재적용(service role로 Supabase 프로젝트에 적용, 멱등) | 조작자 |
| 프로젝터 해상도 | 1440px 기준 레이아웃, 브라우저 확대 110% 사전 점검 | 발표자 |
| 시간 초과 | §6 시간표 체크포인트. 3:30 장면 생략 가능 | 발표자 |
| 질문이 길어짐 | §8 답을 한 문장으로 먼저 말하고 문서 위치를 안내 | 발표자 |
| 노트북 고장 | 데모 영상(3분) 백업, 두 번째 노트북에 동일 이미지 | 전원 |

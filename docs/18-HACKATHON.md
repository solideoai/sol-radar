## 1. 한 줄 요약

> **SOL RADAR는 공공 SI·AX 기업의 영업팀이 "이 입찰에 들어가야 하는가"를 근거와 함께 10분 안에 판단하도록 돕는 의사결정 지원 플랫폼이다. 낙찰 확률을 지어내지 않고, 자격 판정·점수·근거를 보여 주며, 최종 결정은 사람이 내리고 기록한다.**

심사 기준: 사람 심사위원(사장·부사장·CFO, 2026-10-21 사용자 입력. 그 전 문서의 "5인"은 가정이었다) + Claude Fable 5.1(AI 심사). 두 심사자가 모두 확인할 수 있도록 **모든 주장에 근거 위치**를 붙인다 (§5, [[00-README|00 인덱스]]의 주장·근거 표).

### 2.2 현장의 고통 (데모 기업 가설)

| 단계 | 지금 하는 방식 | 문제 |

## 3. 해결과 차별점

### 3.1 핵심 흐름

실제 나라장터 공고 수집(정보화사업) → 변경 감지(revision) → 첨부 다운로드·파싱 → 요구조건 추출(Qwen3.8-Flash-Next, 근거 인용 필수) → 명시 조건 규칙 판정(API 구조화 필드 우선) → SOL Score(결정론적, 분해 가능) → 결정 모델(Bosun v3.1 0.6B) 참고 지표(점수 미반영) → 근거 설명 → 추천(`BID`)·보류(`WATCH`)·비추천(`NO_BID`) **권고** → 사람 최종 결정 기록 → 인앱 알림. 세 실행 모드(`live` 실제 공고 + 실추론, `fixture` 가상 공고 + 실추론, `mock` 가상 공고 + 고정 AI 응답)가 같은 흐름을 탄다([[16-DECISIONS|ADR-020]]). 상세는 [[02-ARCHITECTURE|02 아키텍처]], [[03-AI-PIPELINE|03 AI 파이프라인]], [[08-SCORING|08 SOL Score]], [[21-MODEL-TRAINING|21 모델 학습]].

### 3.2 차별점 다섯 가지

| # | 차별점 | 흔한 접근 | SOL RADAR | 근거 위치 |
|---|---|---|---|---|
| D1 | **우리 회사 기준 자격 판정** | 공고 수집·키워드 알림까지 | 회사 프로필(기술·자격·실적·인력)과 공고 요구조건을 대조해 `SATISFIED / NOT_SATISFIED / NEEDS_REVIEW` 판정, 항목마다 원문 인용. 부족한 자격을 "보유 가정"으로 켜면 저장하지 않고 권고·점수를 다시 계산해 무엇이 있으면 들어갈 수 있는지 보여 준다(가정 재계산, 결정 모델 재호출 없음, [[16-DECISIONS]] ADR-037). 공고 하나의 판정을 실공고 전체로 넓힌 자격 갭 레이더(`/gaps`)는 마감 전 실공고를 공고 API 구조화 필드(면허제한·참가가능지역)만으로 1차 선별해 "어떤 자격이 몇 건·얼마의 공고를 막는가"를 보이고, 자격 하나를 보유로 가정하면 새로 열리는 공고와 배정 예산 합을 저장 없이 다시 센다(첨부·AI 미사용, 예산 합은 수주 금액이 아님, [[16-DECISIONS]] ADR-060) | [[08-SCORING]], [[15-DATA-CONTRACTS]], [[06-UI-UX]] §5.13 |
| D2 | **설명 가능한 점수** | 블랙박스 "적합도 87%" | 5개 요소·가중치·입력 스냅샷·알고리즘 버전을 저장하는 결정론적 점수. 같은 입력이면 같은 점수 | [[08-SCORING]], [[04-DATABASE]] |
| D3 | **정직한 AI** | "낙찰 확률 73%" 같은 근거 없는 수치 | 수주확률을 표시하지 않는다. 결정 모델 분포는 "모델 선택지 신뢰 분포 (충족·수주 확률 아님)"로만, 점수에 넣지 않는 참고 지표로 표시. 근거 부족은 `INSUFFICIENT_DATA`/`NEEDS_REVIEW`이고 정보 부족을 미충족으로 판정하지 않는다. 실행 모드와 데이터 출처를 화면에 표시하고 mock으로 몰래 대체하지 않는다 | [[03-AI-PIPELINE]], [[06-UI-UX]], [[08-SCORING]] |
| D4 | **사람이 최종 결정, 기록이 남는다** | AI가 결정을 대신하거나 결정이 메신저에 흩어짐 | 권고와 결정을 분리. `bid_reviews`에 결정자·사유·시각 저장, 규칙과 모델이 충돌하면 `MODEL_RULE_DISAGREEMENT`로 사람 검토 강제 | [[08-SCORING]], [[09-SECURITY]] |
| D5 | **작은 결정 모델 + 규칙 엔진 조합** | 대형 LLM에 전부 맡김 | 추출은 Qwen3.8-Flash-Next(회사 vLLM API, 운영 실추론은 §7), 분석 설명은 템플릿이고 Qwen 설명은 [추천 분석] 버튼을 눌렀을 때만 만든다([[16-DECISIONS]] ADR-066), 요구사항·기술 적합성·수행 리스크 분류는 Bosun v3.1 0.6B(Qwen3-0.6B 기반 소형 결정 모델, 텍스트 생성 없이 decision token 분포로 질문별 확률 반환, 우리 도메인 보정 전이며 보정 상태는 화면에 나오지 않는다(§7), [[16-DECISIONS]] ADR-034), 명시 조건과 최종 판정은 규칙. 모델이 꺼져도 규칙만으로 완결(`PARTIAL`). 모델이 쓸모 있는지는 실제 공고 평가셋에서 규칙만 쓴 경우(E0)와 비교해 잰다(발표 뒤 진행 예정, [[16-DECISIONS]] ADR-067) | [[03-AI-PIPELINE]], [[11-TESTING]] G6, [[21-MODEL-TRAINING]] |

### 3.2.1 경쟁 서비스 비교 (2026-10-29 재조사, 공개 페이지 기준)

> [!success] 검증됨 (2026-10-29, 공식 사이트 공개 페이지 재조사. URL·근거 문장·가림 이름 대응은 [경쟁 서비스 재조사](evidence/competitors/2026-10-29-competitors.md) §4)
> 조사 범위는 비로그인 공개 페이지뿐이다. "—"는 공개 페이지에서 찾지 못했다는 뜻이고 "제공하지 않는다"가 아니다. 로그인 뒤 화면·영업 자료에 있을 수 있다. 비교 대상은 SOL RADAR처럼 공고를 모아 주는 서비스 네 곳이고, 랜딩·덱에는 첫 글자 + XX로만 쓴다. 10-19 조사(3곳 + 나라장터 기준선)는 이 표로 바뀌었다. 랜딩 "서비스 소개" 표와 같은 값이다.

|---|---|---|---|---|---|---|
| 공고 찾기·읽기 | 공고 수집·조건 검색 | ✓ | ✓ | ✓ | ✓ | 제공(나라장터·LH·KEPCO·K-water 입찰공고) |

| 〃 | 우리 회사 기준 참가자격 판정 | — | △ | — | ✓ | 규칙 3값 + 사유 코드 + 양쪽 근거 |
| 〃 | 판단 근거 원문 인용 | — | — | — | ✓ | 원문 대조 인용·`EvidenceRef` |
| 참여 판단 | 보유 인력 반영 | — | — | — | △ | 200명·고정 기간 가용 95.5 FTE 입력(가상) |

| 가격 | 투찰 가격 분석 | ✓ | ✓ | ✓ | △ | 참고 낙찰가 범위: 실제 나라장터 공고 상세에 같은 분류·비슷한 금액대 지난 낙찰률 사분위를 이번 공고 금액으로 보인다(협상 계약 포함). 사정율·낙찰예측가·확률은 내지 않는다([[16-DECISIONS\|ADR-077]]). 운영 화면 확인 2026-11-03(사용자) |

기호: ✓ 공개 페이지에서 확인, △ 일부만 확인(사람 검수·일부 업종, 등록만 가능 등), — 공개 페이지에서 확인되지 않음. 알림 행은 표를 만들 때(2026-10-29) 운영 알림 Worker가 없어 뺐고(알림 전용 Worker는 2026-10-30 기동, 카카오 발송 꺼짐), 발주계획·사전규격 연결 행은 운영 수집 전이라 뺐다([랜딩 비교 표 스펙](../polaris/specs/done/2026-10-29-landing-competitor-table.md) D6·D8·D9). 가격 줄 항목(⑬) 정의는 2026-11-02에 "지난 낙찰가·사정율·낙찰예측가·투찰 성향 가운데 하나 이상을 계산해 보여 줌"으로 넓혔고, 타사 칸은 그대로다([경쟁 서비스 재조사](evidence/competitors/2026-10-29-competitors.md) §4).

관찰: 네 곳 모두 공고 수집·조건 검색을 하고, 세 곳(인XX·비XX·모XX)이 앞세우는 분석은 투찰가·낙찰예측가로 **"얼마에 쓸까"** 축이다. 클XX는 2026-10-19에 AI 요약·자격 판정·원문 근거를 공개 페이지에 내걸어 이 세 칸은 더 이상 차별점이 아니다. 보유 인력 반영·참여 권고·결정 기록은 네 곳 모두 공개 페이지에서 확인되지 않았다. SOL RADAR는 **"우리가 들어가야 하는가, 들어가지 말아야 하는 이유는 무엇인가"** 를 다룬다. 가격은 사정율·낙찰예측가를 맞히지 않고, 같은 분류·비슷한 금액대 지난 낙찰값으로 참고 낙찰가 범위만 보인다(협상 계약 포함, 최종 투찰가는 담당자, [[16-DECISIONS|ADR-077]]).

핵심 메시지: **"공고를 찾아주는 서비스를 넘어, 우리 회사가 이 사업에 참여해야 하는 이유와 참여하지 말아야 하는 이유를 설명합니다."**

### 3.3 왜 지금인가

- 공공조달 규모가 매년 커지고(§2.1) 디지털 전환·AX 사업 공고가 늘어 SI 기업의 검토 부담이 커진다.
- 소형 오픈 가중치 결정 모델(Bosun, Apache-2.0)과 오픈 LLM(Qwen)으로 **회사 GPU 서버에서** 회사 기밀을 외부 모델 API에 보내지 않고 돌릴 수 있게 되었다. 운영 실추론은 회사 Compose의 AI gateway가 회사 vLLM(Qwen)과 결정 서버(Bosun)를 부른다([[16-DECISIONS|ADR-025]]·[[16-DECISIONS|ADR-049]]). DB는 Supabase 클라우드다(§7).
- 공공데이터포털의 나라장터 Open API(무료, 자동승인)로 공고를 수집할 수 있다. 서비스 ID·오퍼레이션·필드 이름은 공식 명세로 확인했고([[16-DECISIONS|16 ADR]] 미결정 1), 서비스키로 받은 실제 응답도 2026-10-19 P0-0에서 4개 서비스 모두 확인했다(설계와 다른 점 포함, `docs/evidence/phase-0/external-deps.md` ①, [[07-DATA-PIPELINE|07 수집]]). 첨부 원문(공고문·제안요청서)의 저작권·재배포 조건은 미확인이다.

## 5. AI 심사(Fable 5.1) 대비

AI 심사자는 저장소 전체를 읽고 **내부 일관성, 주장과 근거의 연결, 지어낸 사실, 테스트 증거, 보안**을 빠르게 검사한다. 대응:

1. **주장 → 근거 위치 표**를 [[00-README|00 인덱스]]에 둔다. 각 주장은 문서 절 또는 테스트 파일로 연결된다.
2. **검증 상태를 명시**한다. 외부 사실은 `> [!success] 검증됨 (날짜, URL)` 또는 `> [!warning] 미검증 가정` 콜아웃으로 구분한다. 미검증을 사실처럼 쓰지 않는다.
3. **실제 vs mock 표**(§7)를 세 실행 모드 기준으로 유지한다. 데모에서 mock인 부분을 숨기지 않는다.
4. **문서 간 용어·필드 이름 일치**. [[20-GLOSSARY|20 용어집]]과 [[15-DATA-CONTRACTS|15 데이터 계약]]을 단일 원천으로 쓴다.
5. **증거 산출물**을 `docs/evidence/`에 둔다: 테스트 리포트, E2E 스크린샷, `docker compose ps` 로그, 장애 대체 결과. 형식은 [[11-TESTING|11 테스트]], [[17-CLAUDE-IMPLEMENTATION|17 구현 규칙]].
6. **범위 정직성**: 결제·네이티브 모바일 앱·자동 투찰·승률 예측은 범위 외라고 문서와 발표에서 같은 말로 밝힌다 ([[16-DECISIONS|16 ADR]] ADR-007). 모바일 웹(반응형)은 2026-10-30부터 범위 안이다(ADR-072).

## 8. 예상 질문과 답

1. **"낙찰 확률은 안 보여 주나?"** 보여 주지 않는다. 낙찰 라벨과 시점 정합성이 검증된 데이터가 없는 상태에서 확률을 표시하는 것은 과장이다. 대신 자격 판정·적합도 점수·근거를 보여 준다. 승률 모델은 P2로, 백테스트 통과 후에만 노출한다 ([[01-PRD]] FR-12). 공고 상세의 참고 낙찰가 범위는 같은 분류·비슷한 금액대 지난 낙찰값의 사분위를 이 공고 금액으로 바꾼 참고 값이고 확률이 아니다. 그 값에 낙찰된다는 뜻도 아니다([[16-DECISIONS]] ADR-077).
2. **"결정 모델(Bosun)이 무엇인가? 한국어는 되나?"** Hanno Labs가 공개한 Apache-2.0 소형 결정 모델 Bosun v3.1 0.6B(백본 Qwen3-0.6B, LoRA + decision token 256개). 2026-10-20 ADR-034로 Kev(퇴역)를 대체했다(`KEV_*` 이름은 호환 유지). 문서와 타입이 정해진 질문(yes/no·선택·점수)을 받아 텍스트 생성 없이 질문별 확률을 돌려준다. 학습 데이터(DecisionBench)가 영어라 운영에서는 규칙·Qwen이 정형화한 상태를 **영어 템플릿**으로 넣는다. 한국어가 되는지는 주장하지 않고 잰다: 같은 구조의 영어·한국어 state로 E1'(영어)과 E2(한국어)를 같은 평가셋에서 돌려 Macro-F1·Brier·ECE 차이와 95% 신뢰구간으로 보고한다([[21-MODEL-TRAINING]] §4). 이 평가는 발표 뒤 진행 예정이다([[16-DECISIONS]] ADR-067). 리포트가 나오기 전에는 수치를 말하지 않는다. 한국어 state는 평가 전용(`KEV_ALLOW_KO_STATE=true`)이고, 운영 사용은 평가 결과를 보고 다시 정한다. 결정 모델 결과는 참고 지표이며 점수·자격·권고를 바꾸지 못한다. `mock` 모드에서는 고정 응답이고 `live`·`fixture` 모드에서 실추론한다 ([[03-AI-PIPELINE]] §5).
3. **"왜 Qwen과 Bosun을 둘 다 쓰나?"** 역할이 다르다. Qwen은 비정형 공고문에서 구조화된 요구조건과 근거 span을 뽑는 역할이다. 분석 설명(`/explain`)은 템플릿이고, Qwen 설명은 상세 화면 [추천 분석] 버튼을 눌렀을 때만 만든다([[16-DECISIONS]] ADR-066). Bosun은 정형화된 상태를 읽고 질문별 선택지 분포를 낸다. 도메인 품질·지연은 아직 측정 전이다. 둘 다 없어도 규칙 엔진만으로 결과가 나온다.
4. **"실제 데이터인가?"** `live` 모드는 나라장터 Open API로 실제 입찰공고(용역 중 정보화사업)를 3시간마다 수집한다. LH·KEPCO·K-water 입찰공고도 같은 주기로 받는다(`infra/sources/registry.yaml`). 나라장터 목록에는 본문이 없어(`web/server/ingestion/normalize-g2b.ts:146`) 실공고 분석은 첨부(공고서·제안요청서) 파싱 텍스트와 API 구조화 필드로 한다. 첨부는 회사 Documents Worker가 내려받아 파싱하고, 2026-10-29에 실공고 개별 3건과 IT 실공고 371건 일괄 분석을 했다(§7 S-LIVE 행, [[16-DECISIONS]] ADR-069). 2026-11-03 `sol-v0.2.2` 재채점 뒤 화면에 보이는 실공고 run은 364건(추천 9·보류 344·비추천 11)이다. 본문·첨부 텍스트가 없는 공고는 분석을 막는다(`409 ANALYSIS_SOURCE_MISSING`). 공고마다 출처와 `DEMO` 배지로 실제·가상을 구분하고, 분석마다 실행 모드와 모델이 분석 요약 띠에 남는다. 운영 회사 프로필은 공개 자료로 만든 솔리데오 프로필(revision 6부터 회사가 확인한 자격 3건 포함)이라 운영 live 분석은 "실제 공고 × 공개 자료 회사 프로필"이다([[16-DECISIONS]] ADR-052·059). 로컬은 가상 프로필이다. 본편 장면은 운영 사이트의 가상 fixture(`?origin=demo`)로 찍는다(D1, [[16-DECISIONS]] ADR-054, [[19-DEMO-SCENARIO]] §2.1). 실제 응답·첨부 다운로드 확인 결과는 `docs/evidence/phase-0/external-deps.md`에 있다. 엔드포인트는 공식 명세로 확인해 `registry.yaml`에 등록한 것만 부르고 지어내지 않는다.
5. **"HWP 첨부는 어떻게 하나?"** 형식별 파서(`DocumentParser`)로 PDF(텍스트 레이어)·HWPX·HWP를 읽는다(pdfplumber·sol-hwpx·sol-hwp5, `services/ai/src/sol_ai/parsers/`). 운영에서는 회사 Documents Worker가 2026-10-28부터 파싱한다([기록](evidence/company-rollout/20261028/sources-rollout.md)). 처리 건수는 [[PROGRESS]]다. 스캔 PDF·zip·암호 문서처럼 처리할 수 없는 첨부는 `PARSE_UNSUPPORTED`와 "첨부 원문 확인"으로 표시하고, 읽지 못한 내용을 AI가 추측해 채우지 않는다. xlsx·zip·docx는 내려받지 않고 `PENDING`으로 둔다([[16-DECISIONS]] ADR-055 채택). 파서 "지원" 판정 규칙과 실공고 형식별 파싱 성공률 표(P0-3)는 아직 없다([[03-AI-PIPELINE]] §10.3).
6. **"GPU 없으면 못 쓰나?"** `mock` 모드는 GPU 없이 고정 AI 응답으로 전 기능이 돈다. `live`·`fixture` 모드의 실추론은 회사 GPU 서버(Qwen3.8-Flash-Next는 회사가 이미 운영하는 vLLM API `https://acropolissg.com/vllm/v1`, Bosun은 우리 `sol_decision` 서버)에서 돈다. 운영에서는 회사 Compose의 AI gateway가 API 키로 붙는다([[16-DECISIONS|ADR-049]]). Qwen은 회사 vLLM API `https://acropolissg.com/vllm/v1`, 결정 모델은 같은 호스트의 `sol_decision`(`http://127.0.0.1:8009`)이다. 로컬 대체 경로의 노트북 gateway(`ai-local`)는 Qwen API에는 붙는다. 결정 모델용 공개 경로(`https://acropolissg.com/sol-radar/kev`)는 회사 nginx에 등록되지 않아(2026-10-27) 노트북에서는 결정 모델에 닿지 않는다. GPU 서버 자체는 외부에서 접근할 수 없고 모델 런타임 기동·GPU 배분은 회사가 운영한다 ([[10-DEPLOYMENT]], [[16-DECISIONS|ADR-025]]).
7. **"기존 입찰 정보 서비스와 뭐가 다른가?"** 수집·알림은 기존 서비스도 한다. 우리는 **우리 회사 프로필 기준 자격 판정과 설명 가능한 점수, 사람 결정 기록**까지 간다 (§3.2 D1·D2·D4).
8. **"AI가 틀리면?"** 근거 없는 인용은 무효 처리하고, 저신뢰·모순은 `NEEDS_REVIEW`로 사람에게 넘긴다. 사람 판정과 AI 차이를 지표로 추적한다 ([[14-OBSERVABILITY]]). 얼마나 틀리는지는 실제 공고 평가셋으로 잰다. 특히 정보 부족을 미충족으로 잘못 판정하는 비율을 따로 보고, 오답은 원인 단계(파싱·추출·번역·state·규칙·라벨·모델)로 나눠 고친다 ([[21-MODEL-TRAINING]]).
9. **"보안은?"** 테넌트 격리는 Supabase RLS(`org_id`, 다른 조직 자원은 `404`)와 정책 시험으로 강제한다. 인증은 Supabase Auth이고, 토큰 만료·refresh 회전·로그인 시도 제한·비밀번호 정책은 Supabase Auth 설정으로 다룬다(구체 값은 대시보드에서 정하고 확인할 항목, 미검증). 쿠키 인증의 상태 변경 요청은 `X-Requested-With` 헤더 검사(CSRF), XSS는 CSP nonce, RLS를 무시하는 service role 키는 worker·seed·사람이 로컬에서 직접 실행하는 운영자 CLI만 사용하고 브라우저·`NEXT_PUBLIC_` 변수·로그에 넣지 않는다. 그 밖에 SSRF allowlist, 외부 문서는 불신 데이터로 처리, 로그 마스킹 ([[09-SECURITY]]).
10. **"왜 Supabase인가?"** 출발 템플릿(agentic-boilerplate)이 이미 Next.js + Supabase로 조직·역할·초대·RLS·인증 견본과 정책 시험(PGlite)·타입 생성(`pnpm db:types`) 게이트를 갖추고 있다. 그대로 쓰면 인증과 조직 격리를 새로 만들지 않고, 해커톤 시간을 자격 판정·점수·근거에 쓴다. Supabase가 맡는 것은 DB·인증·private Storage(첨부 원본·파싱 결과, ADR-048)이고 임베딩 검색(Qdrant)·작업 큐(Redis + BullMQ)·AI gateway(Qwen·Bosun)는 따로다 ([[16-DECISIONS]] ADR-017).
11. **"데모 중 네트워크가 끊기면?"** 본편은 덱과 녹화 클립이라 회선과 무관하다. 질의응답의 라이브(D1)는 운영 DB와 인증이 Supabase 클라우드라 인터넷이 끊기면 로그인과 조회가 멈춘다. 오프라인 시연은 약속하지 않는다. 끊기면 로컬 Supabase CLI(`pnpm db:start` → `pnpm demo:reset` → 모드 확인(mock) → `pnpm demo:preanalyze` → web 재시작)로 전환하고 전환했다고 말한다. 로컬 DB에는 S-LIVE run이 없으므로 그 장면은 녹화로 보여 준다([[19-DEMO-SCENARIO]] §5 대체 경로 ①, [[16-DECISIONS]] ADR-023). AI 장애는 별개로, AI gateway를 꺼도 규칙만으로 `PARTIAL` 결과가 나오는 것을 시연한다(§6 클립 4). `live`·`fixture` 모드는 회사 GPU 추론 엔드포인트(HTTPS) 접속도 필요하다. 엔드포인트에 닿지 않으면 규칙만으로 `PARTIAL`·`RULES_ONLY` 결과가 나오고 이를 숨기지 않으며, 필요하면 `mock` 모드로 바꿔 이어 간다.
12. **"해커톤 이후 계획은?"** 발표 뒤 X6·E0~E3 실행([[16-DECISIONS]] ADR-067) → 평가셋 확대(test 40 사업 이상) → E4 결과와 오류 분석으로 Bosun LoRA 운영 반영 판단 → 결정 모델의 점수 반영은 평가 기준 통과 뒤 새 알고리즘 버전(`sol-v0.3.0` 이후)과 ADR로 → 데모 기업 파일럿 → 경쟁사 통계·인력 배치 저장/배정 확정 순서(조회 전용 인력 배치 시뮬레이션은 이번 해커톤 P1, ADR-042) ([[12-ROADMAP]], [[21-MODEL-TRAINING]]).
13. **"파인튜닝했나?"** 하지 않았다. 회사 GPU 학습(X6)과 평가 실험(E0~E3)은 **발표 뒤 진행 예정**이다([[16-DECISIONS]] ADR-067). 해커톤 안에는 Bosun을 재학습하거나 바꾸지 않는다(ADR-066 6번). 회사 서버에서 학습·채점을 돌린 기록과 평가 리포트는 없다. 발표에서는 "학습셋과 절차는 준비했고, 학습은 발표 뒤에 하며 결과는 아직 없다"고 답한다. 데모·운영 모델은 공개 Bosun v3.1 0.6B다. 아래는 발표 뒤 학습을 실행해 결과가 나왔을 때의 답안이다. Bosun v3.1 0.6B의 공개 LoRA를 이어 학습해 E4로 공개 Bosun(E1')과 같은 test 분할에서 비교했다([[16-DECISIONS]] ADR-034). 학습·보정은 회사가 회사 GPU에서 돌렸고, 우리는 평가셋·학습셋·학습 요청서·평가를 맡았다. 결과는 Δ와 95% 신뢰구간으로만 말하고, 구간이 0을 포함하면 "차이 없음"이라고 한다. 데모는 공개 Bosun을 쓴다. 운영 모델 교체는 오류 분석과 ADR을 거친 뒤다. Qwen 파인튜닝은 하지 않았다(2026-10-20 사용자 결정) ([[21-MODEL-TRAINING]] §4.4·§5, [[22-FINETUNE-RUNBOOK]]).
14. **"예산 합계는 수주 금액인가?"** 아니다. 자격 갭 레이더의 예산 합계는 공고 API 기준으로 참가 자격이 열리는 공고의 배정 예산(`budget_krw`) 합이다. 입찰은 가격·평가·경쟁을 거치므로 이 합은 수주 금액이나 확률과 관계없다. 화면에 "예산 합계는 참가 자격이 열리는 공고의 배정 예산 합이며 수주 금액이나 확률이 아닙니다."가 늘 보인다. 이 화면은 낙찰·계약 데이터를 쓰지 않는다([[01-PRD]] FR-10, [[16-DECISIONS]] ADR-060). 낙찰 이력은 공고 상세의 참고 낙찰가 범위에만 쓴다(ADR-077).
15. **"면허제한이 없는 공고는 누구나 들어가나?"** 그렇게 단정하지 않는다. 보조 조회(면허제한·참가가능지역)를 다 받았고(`auxLookup.status=OK`) 행이 없을 때만 "참가 가능(API 기준)"으로 센다. 이것은 공고 API 구조화 필드 기준이다. 첨부(제안요청서)에만 적힌 자격 요건은 반영하지 않았고, 화면 맨 위에 그렇게 적혀 있다. 보조 조회가 실패했거나 일일 한도로 건너뛰었거나 결과가 없으면 행이 없어도 "제한 없음"이 아니라 "사람 확인 필요"다(정보 부족 ≠ 미충족·충족). 한도로 건너뛴 비율은 운영 읽기 확인([기록](evidence/gaps/20261028/prod-readonly-check.md))에 있다. "기타자유업종/9999"처럼 뜻을 확인하지 못한 업종 코드는 사전 밖으로 두고 사람 확인 필요로 센다([[16-DECISIONS]] ADR-060 남은 확인).
16. **"면허제한이 여러 행이면 AND인가 OR인가?"** 확인하지 못했다([[16-DECISIONS]] 미결정 19). 공식 근거가 없어 해석을 규칙 엔진에 넣지 않았다. 2행 이상인 공고는 "사람 확인 필요"(면허제한 여러 행, AND/OR 미확인)로 센다. 단 회사가 행을 모두 보유하면 AND로 읽든 OR로 읽든 충족이라 참가 가능으로 센다(2026-10-30 `sol-v0.2.1`, [[16-DECISIONS]] ADR-071). 2026-10-28 운영 실측에서 면허제한이 있는 공고 410건 중 209건(2행 154·3행 이상 55)이 여기에 든다. 그래서 "참가 가능" 수는 적게 잡힌다. 보유 가정은 묶인 업종을 모두 보유하게 될 때만 이런 공고를 연다. 막는 자격 표의 "조건 묶음 포함"이 그 규모다. 같은 이유로 ADR-037에서 대시보드 실공고 선별 깔때기(BOOST-1)를 뺐다.
17. **"자격 갭 레이더 숫자는 AI 분석 결과인가?"** 아니다. 첨부·AI 없이 공고 API 구조화 필드와 기존 규칙 엔진으로 냈다. 공고 상세 분석의 구조화 필드 판정과 같은 함수다(`assessStructuredQualifications`). 점수·권고는 내지 않는다.

| 분석 지연 | D1 운영에는 DEMO 19건 중 18건에 회사 프로필 revision 6 분석(2026-10-30 재채점, FX-01은 revision 6 재분석)이 있고, FX-02는 옛 run(revision 2, 66 보류)뿐이라 목록에 "미분석"으로 보인다([[19-DEMO-SCENARIO]] §2.2). 라이브 장면은 FX-02 재분석 1건이다. 로컬 대체 경로에서만 S0 사전 분석을 한다([[19-DEMO-SCENARIO]]). 실추론(`live`·`fixture`) 지연은 실측 전이라 mock보다 길 수 있다고 보고 리허설에서 잰다 | 조작자 |
| 회사 GPU 추론 엔드포인트 미접속 | `live`·`fixture` 실추론이 멈춘다. gateway가 `QWEN_UNAVAILABLE`·`KEV_UNAVAILABLE`을 기록하고 `PARTIAL`·`RULES_ONLY` 결과를 내므로 그 화면을 그대로 보여 준다. 재접속 확인(`GET /v1/models`)을 한 번 시도하고, 안 되면 `mock` 모드로 전환(env 변경 + worker·ai-gateway 재시작)하고 바꿨다고 말한다. 리허설에서 재접속 확인을 리허설한다(리허설 날짜는 [[12-ROADMAP]] 남은 일정 제안 표) | 조작자 |
| 공공 API 일일 한도·장애 | 개발계정 한도는 기능(오퍼레이션)마다 1,000건/일이다. 보조 조회는 그 오퍼레이션 예산의 90%에서 멈춘다. 결과코드 22는 목록에서 받으면 그 run의 남은 호출을 멈추고, 보조 조회에서 받으면 그 오퍼레이션만 막는다([기록](evidence/ingestion/20261029-g2b-aux-budget.md)). 리허설·시연 호출 수를 미리 계산하고, 막히면 `fixture` 모드로 전환한다 | 조작자 |
| 첨부 다운로드 불가 | P0-0에서 공고 3건의 첨부는 로그인·세션 없이 받았다(② B1~B4, 2026-10-19). 운영은 회사 Documents Worker가 받는다(`infra/company/README.md` §8). 다운로드 실패는 `DOCUMENT_DOWNLOAD_FAILED`로 따로 보이고, 첨부 텍스트가 없는 실공고는 분석 요청이 `409 ANALYSIS_SOURCE_MISSING`이다 | 조작자 |
| 모드 표시 혼동 | 상단바에는 실행 모드·AI 표시가 없다. 분석 결과를 말하기 전에 공고 상세 분석 요약 띠의 "분석 실행 모드"와 "AI" 표시를 확인한다. mock 결과를 실모델 결과처럼 말하지 않는다(FX-02 `mock` 골든 72 / 운영 이전 run 66은 가상 프로필 revision 2 기준 / 재분석은 화면 값) | 발표자 |
| DB 상태 오염 | D1 발표(운영 사이트)에서는 `pnpm demo:reset`을 하지 않는다([[16-DECISIONS]] ADR-054). 운영 DEMO 정리(삭제)는 발표 뒤로 미뤘다. DEMO 공고 마감은 +15일 옮겼다(되돌리기 `docs/evidence/demo-deadline/20261027/04-rollback.sql`). 리허설 중 FX-02 재분석은 하지 않는다(촬영 때 이전 분석 66 → 새 분석 59가 보여야 한다). 아래는 로컬·격리 스택 기준이다. `pnpm demo:reset`으로 seed 재적용(service role로 Supabase 프로젝트에 적용, 멱등). reset 하면 S-LIVE run도 지워진다(데모 조직의 `score_runs`를 모두 지운다, [[04-DATABASE]] §6). S-LIVE는 리허설 뒤 reset 하지 말고, 지웠으면 다시 돌린다([[19-DEMO-SCENARIO]] §3) | 조작자 |
| 프로젝터 해상도 | 1440px 기준 레이아웃, 브라우저 확대 110% 사전 점검 | 발표자 |
| 시간 초과 | [[slides-spec\|덱 제작 명세]] §1 누적 시각이 체크포인트다. 줄일 때는 S5와 S2 조직·인력 화면(선택 15초, [[19-DEMO-SCENARIO]] §4)부터 뺀다. S6·S7은 빼지 않는다. S-LIVE는 클립 5(green 조건)이고, 없으면 슬라이드 14 그림으로 대신한다 | 발표자 |
| 질문이 길어짐 | §8 답을 한 문장으로 먼저 말하고 문서 위치를 안내 | 발표자 |
